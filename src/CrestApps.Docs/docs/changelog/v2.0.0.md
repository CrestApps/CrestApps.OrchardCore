# Version 2.0.0 Release Notes

Version `2.0.0` is the major upgrade from the `v1.x` line to the current `v2` platform. It moves CrestApps.OrchardCore to Orchard Core 3 on .NET 10, expands the solution into a broader modular platform, and reshapes how AI deployments, chat experiences, retrieval, external integrations, and omnichannel communication are modeled.

This page is organized by module and feature so related changes stay together. Breaking changes, migration notes, and follow-up fixes are listed under the module or platform area they affect.

## Highlights in 2.0.0

- **Platform upgrade** to `.NET 10` and the Orchard Core `3.0.0` line used by this repository
- **Expanded AI platform** with deployments, provider connections, orchestrators, tools, AI Documents, AI Memory, MCP, A2A, Claude, and Copilot integrations
- **Broader Orchard module surface** including Content Access Control, Content Transfer, phone-number support, DNC Registry, Omnichannel Management, Recipes, SignalR, Roles, and Time Zones
- **Provider-agnostic telephony** with a soft phone widget, a SignalR hub, and DialPad plus Asterisk provider integrations
- **Provider-agnostic retrieval architecture** built around AI Data Sources, AI Documents, and AI Memory instead of provider-bound BYOD flows
- **Canonical Docusaurus documentation** under `src\CrestApps.Docs`

## Recommended migration path

Use this order when moving a tenant or solution from `v1.x` to `v2.0.0`:

1. Back up every tenant database and export any important recipes or deployment plans.
2. Install the `.NET 10` SDK and move application projects to `net10.0`.
3. Update package feeds and package references to the `v2.0.0` line.
4. Review custom code for moved namespaces, shared `CrestApps.Core` packages, and updated async interface signatures.
5. Start the application once and allow the data migrations to complete.
6. Review AI provider connections, AI deployments, default deployment settings, AI profiles, and chat data in the admin UI.
7. Rebuild and validate tenant features such as AI chat, data sources, documents, MCP, Omnichannel imports, and custom modules.

## Before you upgrade

Before upgrading from `v1.x` to `v2.0.0`, back up every tenant database and review your custom code, package references, enabled features, and configuration.

At a high level, the platform changes are:

| Area | v1.x | v2.0.0 |
| --- | --- | --- |
| .NET SDK | `8.0.100` | `10.0.100` |
| Target frameworks | `net8.0;net9.0` | `net10.0` |
| Orchard Core | `2.1.x` line | `3.0.0-preview` line |

## Module and feature changes

### Contact Center

- Turned the read-only Workflows bridge into a two-way integration, so a no-code author can now *act* on the contact center in response to a domain event rather than only observe one. The **Contact Center Event** activity previously took the event type as a free-text field, so a typo silently produced an activity that matched nothing and there was no way to discover the valid names; it is now a grouped, localized picker of every canonical event, kept from drifting by a test that binds the picker's values one-for-one to the `ContactCenterConstants.Events` constants. Alongside it, five task activities let a workflow drive the contact center: **Set Agent Presence**, **Enqueue Activity**, **Schedule Callback**, **Start Call Recording**, and **Stop Call Recording**. Each resolves its identifiers through Liquid so they bind to the triggering event (for example `{{ Workflow.Input.InteractionId }}`), and each is gated with `[Feature(Workflows)]` + `[RequireFeatures(capability)]` so it appears only when the capability that owns its service is enabled and the service is guaranteed resolvable — an availability task cannot surface on a tenant without the Availability feature. The recording tasks expose a third **Indeterminate** outcome that mirrors the recording service's own indeterminate result, so a workflow can branch into reconciliation when the provider may have acted but its outcome could not be observed, instead of assuming success or failure. Transferring a live call and assigning work to a specific agent are deliberately **not** shipped as tasks: a transfer is authorized against the initiating agent's `ClaimsPrincipal` for destination access control, which a background workflow does not have, and agent-targeted assignment is owned by the routing engine that honors presence, skills, and reservations — both would require bypassing a guarantee, so they remain code-driven actions and **Enqueue Activity** is the supported way to hand work to routing. See [Workflows automation](../contact-center/workflows.md).
- Brought the Contact Center browser assets onto the same Gulp build pipeline every other module uses, instead of shipping hand-authored scripts and a stylesheet straight out of `wwwroot`. The four agent-desktop, supervisor-dashboard, real-time, and soft-phone scripts now live under `Assets/js`, the workspace stylesheet moved to `Assets/scss` as SCSS, and an `Assets.json` mirroring the Telephony module drives `npm run rebuild` so each source is transpiled and minified into `wwwroot/scripts` and `wwwroot/styles` with a `.min` sibling. The two resource manifests now register each script and style with the two-argument `SetUrl(min, debug)` overload, so a production tenant downloads the minified variant and a debug build serves the readable one — previously every tenant downloaded the unminified, source-map-free files for the two highest-traffic authenticated pages, and the documented pre-commit asset check silently skipped them because `npm run rebuild` never touched them. See [Contact Center](../contact-center/index.md).
- Took the screens out of the capabilities, so a deployment that serves no user interface can enable the whole contact center without activating one. Every capability feature registered its own admin menus and display drivers, which meant a headless tenant that wanted agent state, queues, the dialer, recording, or entry points got their dashboard pages whether or not it had any use for them — and, because the base feature depended on the Omnichannel management module, it got the CRM administration experience as well. Each capability now registers services only, and the screens it used to register are folded into a single `CrestApps.OrchardCore.ContactCenter.Admin` feature, each capability's screens gated on that capability being enabled with `[RequireFeatures]`, so enabling a capability can never pull a user interface in and one administration feature — not six — carries the whole dashboard. The split crosses module boundaries for the same reason: `CrestApps.OrchardCore.Omnichannel.Managements` is now the administration experience layered over a new headless `CrestApps.OrchardCore.Omnichannel.Activities` feature that owns the activity model itself, and the Telephony provider settings screen moved to `CrestApps.OrchardCore.Telephony.Admin` — a capability that transitively drags an administration module in is no more headless than one that registers the screens itself. `CrestApps.OrchardCore.ContactCenter.Admin` carries the settings screens, the administration menu, and the screens for `Agents`, `Queues`, `Dialer`, `Recording`, and `EntryPoints`, each appearing only when both that feature and the capability are enabled; the agent desktop, soft phone, supervision, analytics, and maintenance features are user experiences in their own right and were not folded, because nothing would be left behind if they were. Controllers moved with the screens they serve, because a route left on a capability whose drivers have gone is worse than one that never moved: it stays registered and authorized while the display pipeline that binds and validates its form no longer resolves, so a create post persists whatever the empty editor produced — each admin controller is now gated on `[Feature(Admin)]` + `[RequireFeatures(capability)]` and returns 404 until both are on. The guarantee is proved structurally rather than by a list of feature names: a tenant boots the entire headless closure and every navigation provider, display driver, and routed administration controller it can resolve is enumerated by reflection, so a screen added to a capability feature later fails the build without anyone remembering to extend the test, while enabling administration with a capability must register strictly more Contact Center admin surface than administration alone and a capability without administration must stay headless — neither list can be padded to weaken the closure. **Upgrading tenants must enable Contact Center Administration to get their screens back**: enable `CrestApps.OrchardCore.ContactCenter.Admin` and the screens for every enabled capability appear automatically, plus `CrestApps.OrchardCore.Telephony.Admin` where telephony is configured from the dashboard. See [Contact Center](../contact-center/index.md).
- Gave every table that grows with traffic a retention policy, instead of purging one and letting twelve others grow forever. Only the interaction event log was aged out; interactions, call sessions, queue items, activity reservations, outbox and webhook inbox messages, provider commands, agent sessions, daily metrics, processed-event markers and callback requests had no policy at all, which is a gap that stays invisible until a disk fills. Each entity now declares a policy that says which timestamp it is aged from, what makes one of its records finished, and which governance floors hold it beyond its configured window. Records are aged from the moment they settled — a queue item from when it was dequeued, a provider command from when it completed, a callback from when it was last modified — never from when they arrived, when they were last retried, or when they were scheduled, because ageing from arrival deletes exactly the work that waited longest and ageing from a scheduled time deletes work that has not happened yet. A record that is still live survives regardless of age. Legal hold applies to communication history, the projection replay horizon to the event log alone, and a new redelivery envelope to deduplication markers, whose premature deletion would let a redelivered event run its side effect a second time; every floor can only extend a window, never shorten one. Purging now drains each entity in batches until its table is empty rather than deleting a fixed slice, commits between batches so a large drain never accumulates one unbounded transaction, isolates a failing entity so one unhealthy table cannot keep every other table growing, and logs a warning naming the entities that still have work when its per-cycle budget runs out instead of finishing quietly. Adding a table now fails the build until it is either given a policy or exempted with a written reason. Seven indexes gained the settlement timestamp their policy needs, backfilled in a single set-based statement so an upgraded tenant does not present every existing row as infinitely old and delete its own history on the first cycle. A settlement column is only useful if something writes it, so every settlement stamp is now written on the transition that settles the record — reservations on release and cancellation, callbacks on promotion, webhook deliveries on completion and on dead-lettering — and a gate asserts each of those statements still exists. Completed webhook inbox rows are the tombstones that make a repeated provider delivery a duplicate, so they are aged from settlement rather than receipt and carry the redelivery floor, and every purge predicate is backed by an index leading with the timestamp it selects on so draining a large table does not scan it end to end. A backfill only helps if it can execute meaningfully on the database it runs against, so every migration that writes raw SQL takes its identifiers from the database dialect rather than quoting them itself: an engine that reads a hardcoded double quote as a string literal turns the statement into a comparison between a constant and a set of numbers, which matches no rows and reports success, leaving the whole pre-upgrade backlog permanently unpurged. Completed webhook inbox rows are floored by the seven-day duplicate-detection horizon the inbox already enforces, so retention can never shorten the window in which a repeated provider delivery is still recognized as a duplicate; and because that inbox already sweeps its own settled rows at that horizon, the sweep now also honors a longer configured retention window instead of silently overruling it. A purge batch that fails partway through commits and attributes the deletes it had already staged, so partial work is never committed under the next entity's transaction and left uncounted. See [Production support](../contact-center/production-support.md).
- Made recording/media erasure a first-class durable operation, because until now recorded audio was never deleted by any path: the erasure command had no caller, the media store's delete was never invoked, a second recording pointer lived on `CallSession` and was never cleared, the interaction retention path deleted the row that carried the reference on age alone without deleting the media, and the durable Asterisk ingest could write media after an erasure request, so deletion was both unimplementable and racy. An authorized, antiforgery-validated endpoint (`POST {admin}/contact-center/recordings/erase`, permission `ManageInteractions`) now takes an interaction id and a required non-empty reason and, in one YesSql unit of work, clears both the `Interaction` and mirrored `CallSession` recording references, stamps the `RecordingErasedUtc` tombstone, and enqueues durable media deletion on the existing Contact Center outbox — pointer clears, tombstone, and enqueue commit together or not at all. The outbox handler performs the media-store delete in a fresh scope; delivery is at-least-once so an already-absent recording counts as erased, an unconfirmed delete throws so the outbox retries instead of reporting false success, and a confirmed delete publishes a `RecordingMediaDeleted` receipt keyed deterministically off the erasure event. The interaction retention path now enqueues media deletion and clears the mirrored pointer before it deletes the row, and honors the per-record `RecordingLegalHold` flag — previously only the policy-level legal-hold floor widened the time window, so a held recording was both orphaned and deleted on age. The Asterisk recording ingest job consults the tombstone before download and again after storing media, deleting any media it wrote and cancelling the job if the recording was erased in the window, so a late ingest can never resurrect deleted media. Tenant removal now fails closed: a media store that does not implement tenant-wide purge, or a purge that returns unsuccessfully or throws, blocks decommissioning with an operator-visible error rather than silently orphaning media. When Orchard's Audit Trail feature is enabled, confirmed deletion — not merely request acceptance — is recorded under the **Contact Center** category as **Recording media deleted**, though the durable outbox completion plus tombstone remain authoritative if the audit category is disabled or trimmed. This delivers recording/media erasure as a component of a GDPR Art. 17 / CCPA response; it is not a general cross-entity subject-erasure feature. See [Production support](../contact-center/production-support.md).
- Widened the call-session provider-call identifier and the claim key composed from it, because a provider call identifier arrives verbatim from an external switch and can be long — a SIP Call-ID is bounded by nothing Contact Center controls — while the column declared it at a length too short for it. An engine that enforces a declared length rejects an over-length write outright (PostgreSQL `22001`, SQL Server `8152`, MySQL `1406` under the default strict mode), so the call session is never persisted and a reconciliation lookup can never find it; only non-strict MySQL truncates, and a truncated identifier — once the claim key composed from it outgrew its own column — forged a collision between two distinct calls, the opposite of the uniqueness the claim exists to guarantee. The widening is forward-only: it lets the full identifier be stored going forward and repairs no row already rejected or truncated under the narrow length. The identifier is now stored at 256 — a deliberate ceiling, comfortably longer than any real provider call identifier — and the claim key at a length derived from the parts it concatenates — the provider technical name plus a separator plus the widened identifier — so the composed key can never truncate a value its source columns can hold, and it stays within the 900-byte unique-index key limit SQL Server imposes. Because SQLite has no `ALTER COLUMN`, the widening is a rebuild rather than an alter: a replacement column is added at the wider length, the values are copied across, the original is dropped, and the replacement is renamed into its place, with the unique claim index and the covering index that name a rebuilt column dropped first and recreated afterwards, and the rebuild resumes rather than restarts so an engine that commits each schema change on its own cannot strand a tenant mid-upgrade. SQLite stores every text column as unbounded `TEXT`, so it never rejected or truncated and the rebuild is a value-preserving no-op there; the widening exists for SQL Server, PostgreSQL, and MySQL, and each destructive step of the rebuild is authorized as a machine-checked in-place rebuild in the additive-migration register. Executing the upgrade against a real PostgreSQL instance in the distributed CI gate proves both columns reach the wider length, that a seeded value survives, and that the claim-key unique index still rejects a duplicate; SQL Server and MySQL enforce the same length but are not exercised in the Postgres-only gate, so their behaviour is correct by construction rather than by test. Before it recreates the unique claim index, the widening re-checks that no two rows share a claim key and aborts with actionable repair guidance, so a duplicate written into the brief window while the index is absent — possible only on an engine that autocommits each schema change — surfaces as a clear message rather than an opaque index-creation failure. See [Production support](../contact-center/production-support.md).
- Gave the Asterisk real-time listener genuine backpressure in place of a silent drop. The bound on the in-memory buffer between the WebSocket receive loop and the dispatcher was a hard-coded `1000`, and although the buffer was declared to wait when full it was written with a non-blocking try-write, so the first time it filled the listener abandoned the connection and reconnected — the exact moment of peak load was met by dropping events. The bound is now the validated `CrestApps:Asterisk:Coordination:RealtimeEventBufferCapacity` (default 1000, capped at 100000 so a saturated buffer cannot exhaust process memory), and a full buffer applies real backpressure: the receive loop stops reading the socket and awaits a bounded window for space rather than dropping the event or the connection. That backpressure only reaches the provider as genuine flow control while the provider tolerates a stalled reader — Asterisk closes the ARI WebSocket and discards its queued events once its own `websocket_write_timeout` (100 ms by default) elapses, so the bundled `ari.conf` raises that timeout above the backpressure window; with a stock timeout the provider tears the socket down first and the listener degrades to the reconnect-and-reconcile path. The first wait of each saturation episode increments the `asterisk.realtime.ingestion.saturated` counter on the `CrestApps.OrchardCore.Asterisk` meter, tagged by provider, so sustained pressure is visible as it happens and not only through its aftermath; the episode ends only once the buffer has fully drained, so a buffer oscillating near full counts as one episode. Only if the buffer stays full for the whole validated `RealtimeEventBackpressureTimeout` (default 5 seconds) does the listener give up, reconnect, and reconcile, and repeated saturation timeouts back off exponentially instead of hot-looping. That reconciliation is pointer-driven and best-effort by design — it reconciles at most 200 known calls per invocation and no-ops behind a distributed lock when a sweep is already running — so it restores each known call's current state but does not replay every intermediate hold or resume transition, and a call whose opening event was the one dropped is not recovered; sizing the buffer higher buys time before backpressure, but no configuration makes the stream lossless. See [Production support](../contact-center/production-support.md).
- Added the minimum operational signals an operator needs to run a handover safely, and the runbook that uses them. Two gaps remained after backpressure telemetry landed: the Asterisk listener had no connectivity signal, so churn on the ARI event stream was visible only in logs, and there was no store-backed count of live calls or waiting interactions, so a node drain could not be sized before it was started. The `CrestApps.OrchardCore.Asterisk` meter now emits `asterisk.realtime.connected` (successful connects, first plus every reconnect — the connectivity signal) and `asterisk.realtime.reconnect_attempted` (reconnection attempts — a sustained rate is churn and an early warning that events may be missed between reconciliation sweeps), both tagged by provider. The live counts are surfaced as health-check gauges rather than observable-gauge metrics on purpose: an observable-gauge callback is synchronous and runs with no ambient tenant scope, so it cannot issue the per-tenant store query these counts require, and a process-global count would be wrong across tenants and nodes, whereas a health check already runs inside the tenant scope with an async body. `contactcenter-active-calls` (owned by the base feature, which owns the call session store) reports `active_calls`, and `contactcenter-queue-backlog` (owned by the Queues feature, which owns the queue item store) reports `queued_interactions`; each stays healthy at any count and carries the count in its `Data`, because the acceptable ceiling is deployment specific and a backlog verdict already belongs to the outbox check. The ownership split is deliberate — a health check registered by a feature that does not own its dependency throws on any tenant that enables the registering feature without the owning one. The [voice listener handover and rollback runbook](../contact-center/runbooks.md#voice-listener-handover-and-rollback) uses these signals: it does not claim zero downtime for a Voice tenant, because the single-active-process listener cannot be swapped side by side; it is a bounded interruption of call control sized against `active_calls` first, performed as a non-overlapping cutover, and rolled back the same way in reverse. It states plainly what happens to live calls during the gap — already-bridged media keeps flowing while control (holds, transfers, disposition) pauses; a channel parked in `Stasis()` with no dialplan continuation is stranded until a listener returns; and new inbound calls entering during the gap should rely on the upstream PBX or carrier's own retry rather than on Contact Center holding them. See [Failure runbooks](../contact-center/runbooks.md#voice-listener-handover-and-rollback).
- Gave a live call a topology instead of a handful of scalars that could not describe it. `CallSession` carried `MediaTopologyId`, `ConferenceId`, `SupervisorAgentId`, `SupervisorLegId`, a `ParticipantCount`, and an `IsConference` flag; four of those six were never written by any code path and only the store's validation read them, so supervisor monitoring had no durable state at all — an engagement fired a provider command, published an event, and left nothing behind, which meant nothing could tell that a supervisor was listening, refuse a second engagement by the same supervisor, or release the right leg when one of two engagements stopped. The session now carries `Legs` with a role and a normalized `CallLegStatus` per party, a `Bridge` whose participant entries record a join time and a leave time rather than being removed, `Consults`, `MonitorSessions`, and typed `Relationships` to other calls, with `IsConference`, `ParticipantCount`, and `ActiveMonitorSessions` computed from them. Because bridge membership is append-only, `Bridge.ParticipantsAt` reconstructs who was on a call at any past instant, which is what makes conference reporting and after-the-fact review of a disputed call possible. A provider-reported participant count is carried separately from observed membership, because a provider that publishes only a count cannot say who those parties are and fabricating members to match it would make the history a fiction. `CallTopologyProjector` is the only writer of any of it, enforced by a build gate that scans every Contact Center, Telephony, and provider source. Consultative transfers now record a `ConsultCall` and a typed relationship, supervisor monitor, whisper, and barge each have a live representation with barge alone joining the supervisor to the bridge, a duplicate engagement by the same supervisor is refused, and the Asterisk provider reports the leg it created through the neutral `ContactCenterVoiceProviderResult.ProviderLegId` so the agent becomes a real party on the bridge. `InteractionCallLeg.Status` is now the `CallLegStatus` enum rather than a free string. `CallConferenceChanged` is now raised only for calls that are, or have just stopped being, a conference, because ordinary two-party setup now changes the participant count. When a call reaches a terminal state every leg still open is ended and the bridge destroyed, not only the leg the provider named on the hangup: a terminal session accepts no further deliveries, so any other leg — the agent's, on the ordinary inbound path — would have stayed open forever and the bridge would have gone on reporting an agent who had already hung up. A leg's end time is clamped so it can never precede its start, because a hangup can carry a timestamp behind the state change before it and a leg started from the application clock can be ended from the provider's; an inverted leg was rejected by the store, which failed the whole delivery and left the call stuck mid-teardown with its agent occupied. A media move to a new provider bridge identifier now retains the previous bridge in `CallSession.PriorBridges` and creates a fresh one, and `CallSession.ParticipantsAt` searches all of them, so membership before the move is still reconstructible. A monitor session records `SupervisorUserId` and `SupervisorAgentId` separately, because a supervisor is always a user but not always an agent and the two identifiers were previously mixed in one field, which made the "a supervisor cannot monitor their own agent leg" rule compare two different identity spaces and therefore never fire. `ProviderVoiceEvent` copies also carry the provider's `HangupCause`, which the copy silently dropped, so a cause the provider actually reported was replaced by one inferred from the call state. A call that ends also closes any supervisor engagement still open on it, because stopping an engagement is refused once the call is terminal and one left open could never be closed by anyone — the call would go on reporting a supervisor as listening while their leg was already ended. Work still in flight when a call ends no longer tries to join the closed bridge: connecting an agent completes after a provider round-trip, so a caller hanging up during it would otherwise have added a live participant to a destroyed bridge and failed the whole accept. See [Live Call Topology](../contact-center/live-call-topology.md).
- Started reading the schema version stored on every contact center event, which until now was written by the publisher and read by nothing. That matters because a handler never sees the object that was published: post-commit dispatch, outbox redelivery, the provider-voice reader, and projection maintenance all reload the event from storage by identifier, so every handler deserializes JSON written by whichever release wrote it into the type the running release declares. A renamed, split, or re-united payload property does not fail that deserialization — it succeeds and substitutes a default, so an event redelivered from last month is acted on with an absent reason, a zero duration, or an empty identifier, and nothing reports a problem. Stored payloads are now converted one version step at a time up to the version the running release understands, and the conversion is applied at the event store rather than at each reader, because a reader that forgot to call it would not fail, it would return stale data as though it were current. Three situations are refused instead of absorbed: a version step with no conversion registered fails the read naming the step; an event written at a version above the one this release understands fails the read, because a node cannot convert forwards and during a rolling upgrade the newer node is already writing that version; and an event with no recorded version is treated as the first version rather than as already current. The conversion serves the reader and never rewrites the stored row, so the record of what was actually published survives a rollback. Raising the schema version without registering the conversion for the step it introduces now fails the build, which is the only moment the omission is visible, and a second gate seeds an unreadable event and requires every read path on the event store, discovered by reflection rather than listed by hand, to refuse it. Workforce reporting, which had been querying the event log straight off the session and deserializing what it got back, now reads it through the store, and a build gate refuses any code outside the store that queries the event log directly, because a reader that bypasses the store bypasses the conversion and is invisible to the coverage gate. `InteractionEventStore` takes an additional constructor argument and a new list method; code that constructs it directly must supply the upcast service. See [Production support](../contact-center/production-support.md).
- Made `ProviderVoiceEvent` immutable. It is simultaneously a public provider contract and something ingestion adjusts — the provider identity is canonicalized and the idempotency key is scoped by it — and while it was mutable those adjustments were applied to the caller's own instance, so ingestion defended itself with a hand-written copy. That copy was one more thing to keep complete, and it was not: it dropped the provider's hangup cause, and because a session infers a cause when none is supplied, every call reported the inferred cause instead of the one the provider gave, with nothing anywhere to say the real one had been lost. The type is now a record whose properties are all init-only; ingestion derives its adjusted event with a `with` expression, which copies every member by construction, and the hand-written copy is gone. `Metadata` is exposed as a read-only dictionary and snapshotted on assignment, so a caller that keeps its own reference to the dictionary cannot change an event it has already handed over. The snapshot keeps the comparer the supplied dictionary was built with, and keeps it through derivation, so a provider's case-insensitive metadata stays case-insensitive however many times the event is derived rather than quietly becoming case-sensitive and changing what consumers can find. Custom providers that assigned to a `ProviderVoiceEvent` after constructing it must use an object initializer or a `with` expression. See [Building a Custom Telephony Provider](../telephony/custom-providers.md).
- Gave contact center routing its own state document so it no longer competes with the CRM for the same activity. Assignment status, reservation identity and expiry, reserving and assigned agent, and the dialer attempt count moved to a new `ContactCenterWorkState` document keyed one-to-one to the activity by a unique index on `ActivityItemId`, mutated through `IContactCenterWorkStateService`. The reservation loop previously wrote those fields directly onto `OmnichannelActivity`, which is the same optimistic-concurrency document a person edits in the admin UI, so a reservation and a CRM edit raced: one of the two writes was lost, or the routing commit failed with a concurrency exception and stranded live work with a caller on the line. `OmnichannelActivity` keeps the same fields as an eventually-consistent read model — `OmnichannelActivityAuthorizationHandler` decides activity ownership from `AssignedToId`, and the CRM activity list, bulk-manage filters, and enterprise reports query them through `OmnichannelActivityIndex` — reconciled by `ContactCenterWorkStateActivityProjection` after the routing transaction has committed. Contact center writes to CRM-owned activity fields now go through `IContactCenterActivityWriter`, which also defers the write out of the routing transaction and retries it in a fresh scope on conflict. No backfill is required: the first read or mutation of work that predates the new document adopts the projected fields the activity already carries, so an upgrade cannot re-offer work an agent already holds or reset the dialer attempt cap. Routing decisions — dialer eligibility and disposition assignment among them — now read the authoritative work state rather than the projection. `ActivityStatus` remains CRM-owned and is not extracted. The build gate that enforces the ownership boundary now compiles the sources it scans and classifies each write's receiver by the type the compiler resolves, and reports a receiver it cannot resolve as a violation: the previous version recognized receivers by the shape of the identifier naming them, so aliasing an activity through a single local passed silently. It also covers every form that stores into a field — assignment, compound assignment, increment and decrement, and object initializers including target-typed ones — where it previously saw only plain assignments and explicitly named creations. See [Routing Work State and the CRM Activity](../contact-center/routing-work-state.md).
- Made one provider call stream feed every projection instead of the first consumer that claimed it. The Asterisk realtime dispatcher walked a first-wins bridge chain, so on a tenant with Contact Center voice enabled the telephony call-history projection never ran: `TelephonyInteraction` stayed `InProgress` forever for every call Contact Center owned and the soft phone never received the hangup, while on a tenant without Contact Center the surviving projection ran with no lock, no ordering, and no de-duplication. A new provider-neutral `CrestApps.OrchardCore.Telephony.Core` ingress now owns that seam: `INormalizedVoiceEventIngestor` canonicalizes the provider identity, takes the ingestion lease exactly once through `IVoiceIngressGate`, and fans the delivery out to every registered `INormalizedVoiceEventHandler`. `TelephonyCallHistoryVoiceEventHandler` (call history and soft-phone push) and `ContactCenterVoiceProjection` (durable `CallSession`/`Interaction`) are now peers on that stream, so telephony call history is hardened whether or not Contact Center is installed. The gate is the single lock authority: `ProviderVoiceEventService` no longer opens its own distributed lock, and a consumer that re-enters ingestion — including from the fresh scope opened by the concurrency retry — is satisfied re-entrantly rather than taking a second lock on the same call, so exactly one lease and one durable de-duplication record exist per delivery. The Asterisk bridge chain survives only for internal call-control orchestration that must absorb an event before it reaches the stream, such as parking a first-seen inbound channel or releasing a module-originated agent leg.

- Put the Contact Center reservation path under an enforced query-plan budget. Retention bounds how large a table becomes but not how much of it a query reads, and the two failures are not alike: an unbounded table eventually fills a disk and announces itself, while a query that reads a whole table returns exactly the right answer and merely gets slower in proportion to how much history a tenant has accumulated, so no functional test can see it. The statement routing runs before every offer — the per-agent count of live work — was answered by loading one row per interaction and grouping them in memory, over a predicate expressed as a chain of "not this status and not that status" that no index can satisfy, against a table whose only composite index leads with the YesSql join key and answers nothing about an agent. Executing the upgrade against a real PostgreSQL instance then found two defects SQLite could not surface, because the same type affinity that hid the divergence also makes the correcting statement run: the historical version the correction starts from is reachable in two shapes, one whose enum columns are already correct, so the rebuild now probes the column's declared type and leaves a correct column alone rather than raising an undefined-operator error; and PostgreSQL and SQLite name only the index in a drop, so on a tenant whose tables live in a named schema the drop silently matched nothing and the recreation then reported the index already existed, which the step now avoids by issuing a schema-qualified drop first on exactly those engines. A third defect followed from the second: the qualified drop must name the index the way the data layer named it, since index names are prefixed on the engines that share one index namespace across tables and shortened where the engine has a name length limit, so a tenant that also sets a table prefix reproduced the same silent miss. All three are gated by executing the upgrade against PostgreSQL, with a schema and a table prefix both configured, from both reachable shapes. The reconciliation is also resumable, because MySQL commits each schema change on its own and an interrupted attempt would otherwise leave a tenant that can never activate: the replacement column is added only when absent, an attempt that stopped after the original column was dropped finishes with the rename instead of starting over, and the index drops are tolerant while the recreations are not. Authorizing that raw drop also made the register stricter: a removal written as SQL is reported by its leading verb rather than by an object name, so such an entry must now name every object it takes away and each is checked for a matching recreation in the same step. - **Provider webhook bodies are now bounded by what arrives rather than by what the caller claims.** The voice webhook endpoints checked their 1 MiB ceiling against the request's declared content length, which a caller that wants to send more simply omits, and then read the whole body into a string in one go, so a chunked body was bounded only by whatever the web server happened to allow. The permit that limits how many deliveries a tenant processes at once is still taken before the body is buffered, because that permit is what bounds how much memory concurrent deliveries can occupy; a caller that sends slowly is stopped by the web server's minimum request body data rate. - Agent presence sign-out and soft-phone credential revocation now run whenever an agent's authentication cookie session ends, instead of only when two hardcoded account URLs (`/Users/Account/LogOff` and `/Users/Account/Logout`) were POSTed. The previous tenant-wide middleware evaluated those two string comparisons on every request and silently missed every other way a session ends — programmatic or external front-channel sign-out and security-stamp rejection (for example after a password change or an administrator disabling the account). Agent sign-out is now chained onto the application cookie scheme's `OnSigningOut` and `OnValidatePrincipal` events through an `IPostConfigureOptions<CookieAuthenticationOptions>`, so those cases correctly set the agent to signed-out and revoke their browser SIP credentials, and the change also stops relying on route names that Orchard could rename. `OnValidatePrincipal` is hooked because the security-stamp validator rejects and signs out the principal inside cookie authentication before `HttpContext.User` is populated, so the triggered `OnSigningOut` cannot see the user; the handler captures the user id before the rejection and synchronizes only when the principal was actually rejected, keeping the normal validation path free of extra work. The synchronization is isolated from the sign-out flow — the cookie handler raises these events before it deletes the auth cookie, so failures are caught and swallowed and the work runs under a bounded, request-independent timeout, ensuring a slow or failing cleanup can never abort the logout and leave a live auth cookie. The agent-session cleanup background task remains the durable backstop for pure cookie-expiry cases that never call sign-out, and it now revokes browser SIP credentials too so an agent whose cookie merely expires does not leave live credentials behind.

### Telephony

- Serialized concurrent OAuth token refreshes so a provider that rotates its refresh token on first use can no longer lose the only valid replacement. When several requests for the same user found the access token expiring at once, each read the same refresh token, called the provider, and overwrote the stored credentials, so all but one refresh raced against an already-rotated token and the surviving write was whichever landed last. A per-user, per-provider distributed lock now guards the refresh: the first caller refreshes once, persists, and commits durably before releasing the lock, and a peer that was waiting reloads the user (bypassing the persistence identity map so the just-committed tokens are visible) and reuses them inside the lock instead of refreshing again, while a caller that cannot take the lock within its wait window reuses the stored tokens if they are already valid rather than starting a competing refresh. The lock wait and lease are deployment-tunable through `TokenRefreshLockTimeout` and `TokenRefreshLockExpiration` on the Telephony coordination options, and are validated at startup so the lease always outlasts the wait window.
- Stopped provider HTTP clients from automatically replaying non-idempotent requests. Both the Asterisk and DialPad resilience pipelines retried on the standard handler regardless of HTTP method, so a lost response to a call-origination POST could place a second outbound call, and a retried OAuth authorization-code or refresh-token POST could fail with `invalid_grant` after the first request had already succeeded. The retry strategy now disables replay for unsafe methods (POST, PATCH, PUT, DELETE, CONNECT) while still retrying idempotent safe methods such as status GETs, because neither provider exposes a deterministic idempotency key. The same fail-closed disable was also applied to the phone-number-verification lookup clients (AbstractAPI, Veriphone, and Twilio Lookup) so a future non-GET request cannot silently gain unsafe-retry behavior. A build-time architecture guard dynamically scans every source file that installs the standard resilience handler and fails if any does not also disable unsafe-method retries.
- Closed a false-success gap in OAuth token persistence. The user accessor discarded the `IdentityResult` returned by `UserManager.UpdateAsync`, so a validation, concurrency, or storage failure that does not throw let an OAuth connect or token refresh report success while the replacement tokens were never saved — which, under providers that rotate refresh tokens on first use, silently breaks the connection on the next request. The accessor now inspects the result and, on failure, logs only the identity error codes (descriptions can carry a username or email address and are never logged) and raises a persistence fault that carries the codes alone. The token store no longer treats a missing persistable user as a successful save. The connect flow now reports success only after the tokens are actually persisted, the connection-status probe degrades to "not connected" rather than faulting when a refresh cannot be saved, and disconnect and refresh surface the failure instead of hiding it.
- Provider technical names registered with `TelephonyProviderOptions` are now matched case-insensitively and trimmed, so casing differences no longer split one backend into two providers. Registering a different provider type under a name another module already claimed now fails fast at startup instead of being silently dropped, while re-registering the same type stays an idempotent no-op and `ReplaceProvider` remains the intentional override path.
- Soft Phone settings now include a configurable **Recent calls count** from `1` through `200`; the widget loads `30` recent calls by default.
- The Asterisk and DialPad provider settings drivers are now registered only when the **Telephony Administration** (`CrestApps.OrchardCore.Telephony.Admin`) feature is enabled, moving each `AddSiteDisplayDriver` call out of the provider's base `Startup` into a dedicated `[RequireFeatures]`-gated administration startup. A headless deployment that enables only Asterisk or DialPad no longer receives the settings editor, and a deployment that does enable the administration feature always gets both the settings tab and its `telephony` group navigation entry together instead of an editor reachable only by guessing the `groupId` URL.
- Added an architecture test that asserts no MVC controller action in the Contact Center, Telephony, Asterisk, or DialPad modules opts out of antiforgery protection on an unsafe HTTP verb. The admin catalog and entitlement POST actions rely on Orchard Core's global `AutoValidateAntiforgeryToken` filter rather than an explicit attribute; the test proves that reliance is sound by confirming none of these controllers declares `[IgnoreAntiforgeryToken]`, so a cross-site POST cannot bypass the global filter.
- The Telephony site settings tabs now use clean provider tab keys for Asterisk and DialPad, which fixes the Orchard Core settings screen when those provider features are enabled.
- Disconnecting a per-user OAuth telephony provider (DialPad) no longer discards the remote-revocation outcome. `ITelephonyAuthenticationProvider.RevokeTokensAsync` now returns a typed `TelephonyResult` — a confirmed success (2xx or nothing to revoke), a definitive failure (the provider returned a non-ambiguous rejection such as `400`/`401`/`404`), or an indeterminate outcome (`OutcomeUnknown`, when a timeout, throttling `429`, `5xx`, or transport error prevented confirming whether the unsafe deauthorize `POST` committed) — and never throws for non-cancellation failures. Revocation is attempted whenever a stored access token exists, even if the tenant has since switched to API-key authentication, so a leftover OAuth grant is never silently abandoned. `DisconnectAsync` always removes the local tokens first — durably committing that deletion before contacting the provider so a concurrent request cannot observe stale credentials — so the interactive credentials are cleared immediately even if the remote call is canceled or throws, then, when revocation was not confirmed, logs a durable warning naming the provider and the reason and returns the non-successful result. If a stored token exists but no per-user authentication provider is available to revoke it, the disconnect reports an indeterminate (`OutcomeUnknown`) outcome rather than a false success. The OAuth disconnect endpoint relays this as `remoteRevocationConfirmed: false` with the reason, so operators are told the local connection was cleared while the grant may still be active at the provider instead of the previous silent assumption that revocation always succeeded.

#### Inbound entry points (Phase 8)

- Adds a reusable **inbound entry point** catalog under **Interaction Center → Inbound entry points** (Voice feature). #### Voice foundation hardening: media delivery, call sessions, and normalized provider events

- Voice providers now declare a **delivery model** (`VoiceProviderDeliveryModel`): `AgentDeviceNative` (the provider rings the agent's own device, like DialPad's WebRTC soft phone) or `ServerSideAcd` (the provider parks the call and the Contact Center bridges it to the agent). `IContactCenterVoiceProvider` gains a `DeliveryModel` property and a `ConnectToAgentAsync` operation, plus an `AgentConnect` capability flag.
- Adds `IContactCenterCallCommandService`, a single authoritative server-side command for the agent offer lifecycle. Accepting an offer now accepts the reservation, connects the media to the agent for server-side ACD providers, and advances the interaction and call session together, so the orchestration state and the provider media state can no longer diverge. The result reports whether the agent's device must still answer the media (`RequiresDeviceAnswer`). The Contact Center `VoiceController` accept/decline actions delegate to this command.
- Adds the `CallSession` aggregate: the Contact Center's business-oriented projection of a voice call, mapping a provider call to an interaction, agent, and queue and tracking the normalized call lifecycle and talk/hold durations without owning media execution.
- Adds normalized provider voice events: `ProviderVoiceEvent` and `IProviderVoiceEventService` ingest provider/PBX call-state changes, match them to the interaction and call session by provider call id, advance state and timestamps, bridge the agent for answered outbound calls on server-side ACD providers, and publish Contact Center domain events. Events carrying an already-seen idempotency key are ignored, so duplicate or out-of-order webhook deliveries are safe.

#### Assignment safety: capacity enforcement and concurrency-safe assignment

- Agent capacity is now enforced during routing. A capacity routing strategy counts each candidate agent's active (not ended and not failed) interactions and rejects agents that have reached their configured `MaxConcurrentInteractions`, so an agent is never offered more concurrent interactions than they can handle.
- Assignment for a queue now runs under a per-queue distributed lock. Two nodes — or the reservation-expiry background task running alongside an inbound call — can no longer double-assign the same queue item or reserve the same agent twice.
- Adds a transfer/conference taxonomy. `IContactCenterTransferService` records blind or consultative transfers to an agent, queue, external destination, or entry point on the interaction's transfer history, publishes `InteractionTransferred`, and re-enqueues the activity for queue transfers; `ContactCenterVoiceProviderCapabilities` gains `CallTransfer` and `Conference` flags so provider modules can advertise media handoff support.
- See [Queues, reservations, and assignment](../contact-center/agents-queues-dialer.md#queues-reservations-and-assignment).

#### Routing depth: routing policy, sticky agent, SLA aging, business hours, and overflow

- Each queue now selects a primary **routing strategy**: *Longest idle* (default), *Round robin* (offers to the agent who least recently received an assignment, tracked on `AgentProfile.LastAssignedUtc`), or *Least busy* (offers to the agent handling the fewest active interactions). Only the selected strategy scores candidates; skill and capacity filtering still run first, and assignment still publishes an auditable routing-decision event.
- Queues can **prefer the sticky agent**. The activity's assigned user is captured on the queue item when it is enqueued, and routing boosts that agent when they are eligible and available, so returning work prefers the agent the customer already worked with. The preference is additive and never overrides eligibility.
- Queues can enable **SLA aging**, which raises a waiting item's effective priority by one step for every SLA-threshold interval it waits past the threshold, so aging work is routed ahead of newer higher-priority work instead of starving.
- Adds a reusable **business-hours calendar** catalog under **Interaction Center → Management → Business hours** (Queues feature). A calendar defines a time zone, a weekly open window per day, and all-day holiday dates. A queue can reference a calendar; while it reports the queue closed, assignment pauses, and the queue's **after-hours action** either holds items or overflows them.
- Adds queue **overflow**: a queue can set an overflow queue and an overflow-after threshold so items waiting too long (or all items while the queue is closed and set to overflow) move to a broader team's queue. Overflow runs each minute alongside reservation expiry and assignment.
- See [Routing policy](../contact-center/agents-queues-dialer.md#routing-policy) and [Business hours and overflow](../contact-center/agents-queues-dialer.md#business-hours-and-overflow).

#### Subject configuration moved to content-type part settings

The dedicated **Configure** screen, the `SubjectFlowSettings` catalog, its handlers, recipe step, and deployment step were removed; subject configuration now travels with the content type definition through the standard **Content Definition** deployment step.

The interaction type is derived from the load source (**Automatic** creates **Automated** activities; other sources create **Manual** activities).

Changing the direction, interaction type, or channel immediately shows or hides the settings that apply, so an outbound subject no longer displays inbound-only fields and an inbound manual subject no longer displays the AI section at all.

Outbound subjects no longer display the card because outbound AI configuration is part of the inventory-load process controlled by the **Automatic** source; inbound manual subjects hide it because they are always handled by an agent.

Hidden fields retain their stored values, so switching direction, interaction type, or channel never discards configuration.
- The **Subject Flows** list badges now use the standard `badge ta-badge` styling for consistency with the rest of the admin. Each subject shows its direction, and automated subjects additionally show an **Automated** badge and the channel in use; the disposition-required tag was removed from the list.

- Removed the orphaned `SubjectFlowSettings.Edit.cshtml` view left behind by the removal of the **Configure** screen.

#### Subject Flow required-disposition policy

- A subject can now be marked as **requiring a disposition** (`SubjectFlowSettings.RequireDisposition`, edited on the `OmnichannelSubjectPart` settings). When set, an activity using that subject cannot be completed until a disposition is selected.
- **Breaking change:** requiring a disposition is now **enabled by default**, because the disposition is what triggers the subject flow actions. Subjects that should complete without an outcome — fire-and-forget notification subjects such as a one-way SMS alert — must now clear the option explicitly.
- The rule is enforced centrally in `IActivityDispositionService`, so it holds for every completion path — the CRM completion screen, dialer, and automation — and for both inbound and outbound work. Completion now also skips Subject Actions when no disposition is selected instead of failing.
- Automated SMS conversations now honor this policy. When the AI reports a conversation concluded but returns no disposition and the subject flow requires one, the SMS handler no longer completes the activity directly; it leaves the activity open so the required-disposition rule is not bypassed, and the activity closes through the existing no-response timeout or opt-out paths.
- This keeps the Subject Flow as the single decision controller for inbound and outbound work; a separate contact-center wrap-up concept is not needed.
- See [Subject Flow is the single decision controller](../contact-center/index.md#subject-flow-is-the-single-decision-controller).

#### Dialer safety: per-mode strategies and an outbound compliance gate

- Each automated dialing mode is now a dedicated `IDialerStrategy` resolved by mode, so unsupported modes are withheld instead of falling through to an unsafe default. **Predictive dialing is disabled**: the editor hides it, saving a Predictive profile is rejected, and the dialer refuses to run it until answer-rate forecasting and abandonment controls exist. **Power dialing is hard-capped** at a safe number of calls per agent (`PowerDialerStrategy.MaxCallsPerAgent`).
- Adds `IDialerEligibilityService`, an outbound compliance gate that runs before every attempt and records an auditable `DialSuppressed` event when an attempt is blocked. It enforces a present destination, the attempt limit, the `RetryDelayMinutes` retry cool-down, the contact's do-not-call communication preference, a configurable calling window evaluated in the contact's local time zone, and any registered national do-not-call registry (for example USA FTC or Canada DNCL).
- Dialer profiles gain calling-window settings (*Enforce a calling window*, start/end local hour, and a default time zone). Do-not-call and registry suppressions cancel the activity, while calling-window and cool-down suppressions release the reservation and leave the activity available for a later cycle.
- The single-attempt logic moved into `IDialerAttemptService`, and `DialerService` now validates the profile and delegates pacing to the resolved strategy.
- Successful outbound dial attempts now accept the reservation before returning, so the reservation-expiry task cannot later release the agent or queue item while the provider call is still active.
- See [Dialer](../contact-center/agents-queues-dialer.md#dialer).

#### Real-time agent and supervisor layer

#### Reliable event dispatch (outbox)

- Contact Center domain-event dispatch is now **at-least-once**. `IContactCenterEventPublisher` records the immutable `InteractionEvent` and hands it to the new `IContactCenterOutbox`, which runs handlers inline for low latency and, when a handler fails, persists a durable `ContactCenterOutboxMessage` instead of silently dropping the event.
- A per-minute `OutboxDispatchBackgroundTask` retries failed dispatches with exponential back-off (30s, 60s, 120s, … capped at 30 minutes) and **dead-letters** a message after ten failed attempts for inspection.
- Handler dispatch and the per-handler failure isolation moved out of the publisher into the outbox, so a transient failure in a downstream projection (SignalR, indexing, or an external service) no longer loses work.
- Closed the poison-message and replay-safety gaps for the domain-event outbox and provider webhook inbox. Each due message runs in its own fresh Orchard child scope so a failure cannot block later work, and each event handler runs in a nested isolated scope so its effect and replay marker commit or roll back together. Every event and inbox handler must declare `ContactCenterHandlerReplaySafety` (`NaturallyIdempotent`, `DeduplicatedByEventId`, or `GuardedByDurableStore`); construction rejects `Unspecified`, blank routing identities, and duplicate identities. `IContactCenterEventDeduplicationService` persists a unique `(HandlerId, EventId)` marker for non-idempotent effects.
- See [Domain events and reliable dispatch](../contact-center/index.md#domain-events-and-reliable-dispatch).

### Phone Number Verifications

#### Provider-agnostic verification framework

- `v2.0.0` introduces the **Phone Number Verifications** module (`CrestApps.OrchardCore.PhoneNumbers.Verifications`), a provider-agnostic framework for verifying contact phone numbers. The core feature is enabled on demand and does not depend on any external verification provider.
- The core feature now declares a dependency on `OrchardCore.Contents`, since it defines the `PhoneNumberVerificationPart` content part and a migration that requires `IContentDefinitionManager`. Enabling the feature on a tenant without content management previously failed to activate the shell.
- Shared phone-number services, constants, and verification index types now live in `CrestApps.OrchardCore.PhoneNumbers.Core`, so the Phone Numbers and Phone Number Verifications modules use the same core infrastructure.
- Verification providers are pluggable: they implement `IPhoneNumberVerificationProvider` from `CrestApps.OrchardCore.PhoneNumbers.Abstractions`, are registered against a unique provider key through `AddPhoneNumberVerificationProvider`, and configure localized display names and descriptions through the registration action. Providers are discovered dynamically so adding a provider never requires changes to the core feature.
- Provider HTTP payload parsing now uses shared snake-case JSON serializer options instead of per-property DTO attributes, keeping provider response models simpler and easier to maintain.
- The **Default provider** selector lists only providers that have been explicitly enabled (see the per-provider enable toggle below), is rendered before the revalidation interval, and the framework resolves providers by key through a lean `IPhoneNumberVerificationManager` without a provider ever selecting itself. When the selected provider is disabled or unset, the first enabled provider is used.
- Each provider settings tab now includes an **Enable this provider** switch, mirroring the Orchard Core SMS settings UX. A provider is only available for verification and only listed in the **Default provider** selector when its switch is on; the switch reveals the connection/authentication fields and gates their validation. Disabling the provider that is currently the default clears the default selection.
- Providers map their native responses into a shared `PhoneNumberVerificationResult` model that includes validity, reachability, line type, country, location, carrier, time zone, line status, risk details, the raw provider response, and an extensible metadata bag.
- Verification providers treat a supplied line status as part of the verification decision: numbers must be valid and have an `active` line status to be verified; providers that do not return line status continue to use the validity flag alone. AbstractAPI also maps `phone_validation.minimum_age` into the normalized result and queue display.
- Built-in provider HTTP clients are registered through `IHttpClientFactory` with the standard .NET HTTP resilience handler so AbstractAPI, Twilio, and Veriphone calls share consistent transient-failure handling.
- The Phone Verifications Queue now renders record metadata tags beside the display text with the standard `badge ta-badge font-weight-normal` admin badge styling, keeping row actions isolated on the right and readable in dark mode.

#### Contact storage, indexing, and reporting

- Verification data is stored directly on content items through the new `PhoneNumberVerificationPart`, which retains the submitted and normalized phone number, full normalized provider response, last verification, verifying user id, attempt count, and next due date. User identifiers are stored instead of usernames because usernames can change over time.
- Omnichannel contacts now trigger phone-number verification automatically after create or update when their preferred phone number is new or changed. The handler first stores the changed number as `Unverified` during the current content save, then uses deferred work to call the provider only after the pending status is persisted. If no provider is currently available, the record remains pending for later revalidation.
- A `PhoneNumberVerificationPartIndex` SQL index exposes the commonly queried fields for reporting, dashboard widgets, revalidation jobs, and administrative searches, while provider-specific metadata stays in the stored JSON payload.
- The operational phone-number verification report now registers automatically from **Phone Number Verifications** whenever `CrestApps.OrchardCore.Reports` is enabled, contributing the report through the shared admin **Reports** area. It surfaces verified, unverified, invalid, mobile, landline, and VoIP counts, numbers pending verification or requiring revalidation, the verification success rate, failures, and provider usage. Access to the report is controlled by the dedicated `RunPhoneNumberVerificationsReport` permission.

#### Revalidation and cost optimization

- A throttled queue processor verifies pending records sequentially and applies the configured delay between provider calls, including across batches. The scheduled background task runs every five minutes to revalidate content items that already carry a stored phone number and whose verification has expired or remains pending, processing work in bounded resilient batches with distributed locking so long backlogs do not overlap provider calls. A new **Request delay (milliseconds)** setting (default `1000`) spaces out consecutive provider calls to respect provider rate limits (HTTP 429).
- Verification data on `PhoneNumberVerificationPart` acts as the authoritative cache: numbers are only (re)verified when expired or explicitly requested, which minimizes calls to paid provider APIs.

#### Resilient verification and records queue

- Verification now distinguishes a completed provider answer (`Verified`/`Invalid`) from a failed verification request (rate limits, HTTP errors, transport failures, or unparseable responses). A failed request never marks a number `Invalid`, and a previously verified number is never downgraded by a transient provider outage.
- `PhoneNumberVerificationPart` and its SQL index gained `FailedAttemptCount`, `LastError`, and `LastAttemptUtc`, so failed requests record the provider error and the consecutive-failure count on the content item. Existing tenants are upgraded by a data migration that adds the new columns and a retry index.
- A new **Maximum verification attempts** setting (default `3`) caps automatic retries. Failed records are retried by the background task until the cap is reached, after which they are flagged as **Needs attention** and excluded from the automatic retry query.
- A **Phone Verifications Queue** dashboard under **Tools** lets administrators monitor the verification queue: clickable status tiles show per-status counts and filter the list, a wide search box finds records by phone number, and records can be sorted by most/least recently attempted or newest/oldest created. The status tiles are now a mutually-exclusive partition that always sums to the total — **Pending** counts unverified records (including freshly re-queued ones), **Failed** counts records that can still be retried automatically, and **Needs attention** counts records that hit the attempt cap — fixing an earlier bug where the same record could be counted under multiple tiles. Each record shows the phone number, provider, result, attempt counts, last attempt, and any provider error. The list is paged and supports bulk actions: **Retry now** re-queues a single record, **Retry selected** (with a select-all checkbox) re-queues the records selected on the current page, and **Retry all failed** re-queues every failed or needs-attention record across all pages matching the current search. All retries are queued — they reset the failure counters, mark the records **Pending** immediately, and schedule deferred verification after the pending state is saved, which keeps the page responsive and avoids racing provider results against the request that queued them. The dashboard is gated by `RunPhoneNumberVerificationsReport`, and retries require `VerifyPhoneNumbers`.

### Platform and tooling

#### Build, packaging, and shared runtime

- Test suites that create temporary SQLite databases now release the connection pool before deleting the file and retry the delete, so Windows test runs no longer fail with file-in-use errors. The vendored telephony contract cassettes are also pinned to their recorded bytes through `.gitattributes`, keeping their provenance hashes stable on Windows checkouts.

- `v2.0.0` requires `.NET 10` and the Orchard Core `3.0.0-preview` package line used by this repository.
- Large parts of the reusable runtime moved out of Orchard-only projects and into shared `CrestApps.Core.*` packages. Custom modules that depended on older repo-local implementation assemblies should be rebuilt against the new package layout.
- Public async interfaces that can perform cancellable or longer-running work now accept an optional `CancellationToken cancellationToken = default` parameter. Custom implementations must update their signatures to match.
- The checked-in `NuGet.config` now restores Orchard Core packages from the Orchard Core preview feed and `CrestApps.Core*` packages from the CrestApps Core preview feed.
- Package tags are now computed centrally during packing so NuGet metadata is more consistent across the solution.
- The local Aspire app host no longer terminates on startup. Aspire `13.4.6` resolves each dashboard URL to a single DCP endpoint, and the Coturn container publishes the same port over both TCP and UDP, which matched more than one endpoint and threw. When it triggered, the exception killed the DCP resource watchers, so no container and no project started. The Coturn registration now clears its generated dashboard URLs, which skips that lookup while still publishing every TURN endpoint.
- The local Asterisk image no longer bakes a private key into an image layer. The self-signed WebRTC certificate is generated by the container entrypoint on first start, so each container gets its own key and no private key is present in any image layer. The image also applies the available Debian security patches with `apt-get upgrade` at build time, because its base is pinned by digest and would otherwise ship OS packages frozen at the moment the base was built - a fixable `HIGH` in `libexpat1` had already accumulated that way and failed the container scan until this was added.
- The container image scan now blocks only on images this repository builds. Pulled upstream images are still scanned and still reported to code scanning, but a CVE that only its upstream maintainer can fix no longer fails the build.
- Three workflows contained a whitespace-only line inside a folded `run: >-` block. YAML folds that into a newline rather than a space, which split a `dotnet build` command from its project path and made the shell try to execute the path. The blank lines were removed.

#### DialPad provider

- `v2.0.0` adds the `CrestApps.OrchardCore.DialPad` module, which integrates the DialPad platform as a telephony provider through its REST API and contributes a **DialPad** tab to the telephony settings.
- DialPad supports an explicit **Authentication type** setting with **Select authentication type**, **API key**, and **OAuth 2.0** options. API key authentication uses the DialPad account that owns the key for simple integrations, while OAuth 2.0 lets each user connect their own DialPad account and is recommended for production multiuser integrations. The settings UI only shows the fields relevant to the selected mode, uses DialPad's fixed `https://dialpad.com/api/v2/` REST endpoint without an API base URL field, and links administrators to `developers.dialpad.com` for OAuth 2.0 access instructions. Secrets are stored encrypted through the data protection provider, and enabling or disabling DialPad updates the default telephony provider the same way the Orchard Core SMS Twilio provider manages the default SMS provider.
- The DialPad OAuth 2.0 integration is hardened to match DialPad's documented authorization code flow requirements: **PKCE** (RFC 7636) is always used (an `S256` challenge is sent during authorization and the verifier is supplied during the code exchange), the **`offline_access`** scope is always requested so refresh tokens are issued, and disconnecting a user calls DialPad's `deauthorize` endpoint to revoke the tokens issued on their behalf before the local tokens are removed.
- A new DialPad **Environment** setting selects between the **Production** (`dialpad.com`) and **Sandbox** (`sandbox.dialpad.com`) DialPad environments for both the REST API and the OAuth 2.0 authorize, token, and deauthorize endpoints, so an integration can be validated against the sandbox before going live.
- The telephony abstractions gained PKCE support (`TelephonyAuthorizationContext.CodeChallenge`/`CodeChallengeMethod`, `TelephonyCodeExchangeContext.CodeVerifier`, and `TelephonyAuthorizationRequest`) and token revocation (`ITelephonyAuthenticationProvider.SupportsProofKeyForCodeExchange` and `RevokeTokensAsync`), so any OAuth-based telephony provider can opt in to PKCE and provider-side token revocation on disconnect. OAuth completion now returns a `TelephonyResult`, so callers can inspect the failure reason instead of receiving only a boolean.
- The DialPad provider now resolves a named HTTP client configured by startup with standard ASP.NET Core HTTP resiliency policies for DialPad REST API and OAuth token requests.
- The **DialPad Contact Center Voice** feature now handles inbound calls end to end. A new `DialPadWebhookController` at `POST /api/dialpad/webhook/call` receives DialPad call-event webhooks, validated by a configurable **Webhook signing secret** (DialPad signs the payload as an HS256 JWT; validated without any external JWT dependency, with unsigned JSON accepted only when no secret is set). New inbound DialPad calls are normalized into an `InboundVoiceEvent` and routed through the Voice Contact Center Call Router — creating a CRM activity and voice interaction, resolving the entry point/queue, and offering the call to an available agent — while subsequent state events (ringing, connected, held, ended) are normalized into `ProviderVoiceEvent`s that update the interaction and call session. Together with the existing outbound dialing, DialPad can now serve as the complete phone provider for the Contact Center. The DialPad voice provider also advertises the `CallTransfer` capability.

## Contact Center production readiness

- Added R0 characterization coverage proving that the last browser disconnect currently leaves an `Available` agent profile routable and that after-call state has no persisted server-swept deadline. These tests preserve the known failure until the R3 canonical availability and deadline-recovery implementation replaces them.
- Added a deterministic shared-SQLite reproduction in which two independent Contact Center service providers read the same waiting work before either commits and then persist two pending reservations. The test pins the missing database CAS/unique-active invariant for R3.
- Added Contact Center provider-command characterizations proving that failed reservation acceptance can discard the identity of an already-created provider call and that a lost provider response is currently treated as a definitive failure instead of a durable `OutcomeUnknown` state. These tests pin the command-intent, reconciliation, and compensation work required in R3.
- Added Contact Center provider-event characterizations proving that concurrent duplicate checks can persist and enqueue the same logical event, equal-timestamp delivery can regress a connected call to ringing, and provider aliases currently mutate stored identity. These tests pin the inbox uniqueness, sequence/high-water, and canonical-provider work required in R3.
- Inverted the Contact Center outbox characterizations: rolling-version handler reordering no longer replays an already completed handler, and a poison due message no longer blocks later work in the batch.
- Added centralized Contact Center operational-log characterizations across Telephony, SMS, and agent-presence paths. They prove the current sanitization helper removes control characters but preserves E.164 addresses, stable agent ids, and token-shaped values, pinning the classification/redaction and negative-snapshot work required in R1.
- Made the default build hermetic. The GitHub Copilot SDK downloads a platform-specific CLI from `registry.npmjs.org` during `BeforeBuild` for every project in the graph, which made the whole solution unbuildable without public npm egress. The download is now opt-in through `CopilotSkipCliDownload=false`, or a vendored binary can be supplied with `CopilotCliBinaryPath`.
- The Copilot orchestrator now reports itself unavailable when its CLI runtime is not present in the deployment instead of appearing available and failing when a chat starts. This also covers builds that target a different runtime identifier than the host and publishes that trim native assets.
- Inbound voice ingress no longer binds durable call routing to the caller's connection, so a caller who hangs up mid-request can no longer abandon the operation and strand the call. Ingress is bounded by admission control instead of a deadline: the endpoint takes a feature-work lease (returning 503 while the feature is quiescing) and a concurrency lease (returning 429 with `Retry-After` when capacity is exhausted), then runs the routing sequence to completion. Because routing performs several non-atomic durable writes, cancelling it partway would strand the call, so bounding admission rather than the mutation is what keeps resource use capped without tearing state.
- Twilio webhook validation now uses the shared Twilio request validator instead of a divergent inline implementation. The signed payload includes the query string, comparison is constant-time, the port variation is handled, and the signed URL is rebuilt from the configured site base URL so deliveries validate correctly behind a TLS-terminating proxy.
- Agent work-state healing no longer throws on a tenant that enables Queues without Voice. When no provider-state synchronization service is registered the interaction is preserved under the existing provider-backed guards, and the diagnostic identifier is pseudonymized.
- Contact Center now separates process liveness from tenant readiness. Liveness is answered by host middleware at `/health/process` (`UseContactCenterProcessLiveness`, registered before `UseOrchardCore`) because a tenant-scoped liveness route returns 404 whenever the tenant is disabled, renamed, or given a different request URL prefix — and an orchestrator reads 404 as a probe failure, restarting a healthy process forever for a tenant-level problem. It consults nothing, answers only `GET` and `HEAD`, and passes every other request through. The path is deliberately not `/health/live`: that is the default route of the `OrchardCore.HealthChecks` module, and because host middleware short-circuits before routing, taking it would silently shadow that module's endpoint for every tenant in the process — including tenants that never enable Contact Center — replacing it with an unconditional `200 Healthy`. `AddContactCenterProcessLiveness` registers a startup validator that reads every configured tenant's health-check route — tenant configuration is not host configuration, so a host-level check alone could not see a route claimed inside a shell — and fails the host with an error naming the offending tenant. Calling `UseContactCenterProcessLiveness` without the matching `Add` call also fails fast rather than running unvalidated. Readiness stays tenant-scoped at `/api/contact-center/health/ready` and selects only node-local checks. Both allow anonymous requests and return only the aggregate status word. The tenant probes inherit the tenant's request URL prefix, which is documented as part of the probe contract and covered by real HTTP tests against a live Orchard host.

- Contact Center readiness no longer aggregates shared dependency checks. A dependency shared by every node — the database, Redis, the provider, the outbox backlog — is observed identically by every node, so a readiness probe that consulted one would fail on every node at the same instant, leave the load balancer with no healthy target, and turn a *degraded* dependency into a *total* outage that cannot self-heal. Readiness now reflects only conditions that genuinely differ between nodes, and dependency health is reported on its own probe for alerting. The readiness tag is namespaced `contactcenter-ready` rather than the conventional `ready` so a check contributed by another module cannot silently join the routing verdict.

- Added an opt-in node serving gate for Contact Center readiness (`CrestApps_ContactCenter:HealthChecks:EnableNodeServingGate`, disabled by default). "Shared dependency" does not mean "fails identically on every node": a node with an exhausted connection pool, a stale DNS entry, or an expired TLS trust store fails every store call while its peers stay healthy, and purely lifetime-based readiness would never notice. When enabled, the gate drains the node after `ConsecutiveFailuresBeforeUnready` consecutive store-probe failures and returns it after `ConsecutiveSuccessesBeforeReady` consecutive successes, so a transient failure never costs capacity and a broken node cannot flap back into rotation. It is off by default because a genuine store outage is observed by every node; enable it only where the load balancer fails open once too few targets remain healthy. When disabled the check performs no I/O.
- **Readiness no longer consults any dependency.** A dependency shared by every node — the database, Redis, the provider, the outbox backlog — is observed identically by every node, so a readiness probe that consulted one would fail on every node at the same instant, leave the load balancer with no healthy target, and turn a degraded dependency into a total outage. Readiness now selects only a new node-local `contactcenter-node` check, which reports whether this process finished starting and whether it is shutting down. Reporting unready during shutdown is also what lets a load balancer drain a node before it stops accepting connections, so rolling deployments no longer drop in-flight calls.
- Added the `/api/contact-center/health/dependencies` probe. It reports per-check status for `contactcenter-storage`, `contactcenter-outbox`, and `contactcenter-provider-ingress`, and it is the probe to read during an incident. Because it discloses which dependency degraded it requires the `MonitorContactCenter` permission, and it never writes exception detail, which can carry a connection string. It must never be wired to an orchestrator probe or a load balancer.

Registering it in the base feature made the probe throw on tenants that enable Contact Center without Voice; it is now simply absent from the dependency report there.
- Enabling `OrchardCore.HealthChecks` alongside Contact Center reports a degraded `contactcenter-shared-endpoint` health check (and a `Critical` log entry on tenant activation) while that module's shared endpoint still claims a liveness route, instead of failing tenant startup. Refusing the route by throwing during shell construction bricked the tenant with no diagnostic surface — `/admin`, the one place to correct it, became unreachable — and the module's shipped-default `/health/live` route was enough to trigger it. The shared endpoint maps a single unfiltered endpoint that aggregates every module's checks regardless of tag, so despite that default route it is neither a liveness nor a readiness signal — it is an unfiltered aggregate diagnostic endpoint and must never drive routing or restarts. Wiring a liveness probe to it restarts healthy nodes whenever any shared dependency degrades. The hazard check is alerting-only and never gates readiness. - Agent-initiated soft-phone dials are now screened for compliance instead of reaching the provider ungated. Do-not-call, national-registry, and calling-window enforcement previously lived only on the campaign dialer path, so a call placed directly through the telephony hub bypassed every one of them — a compliance gap on the one origination path an agent drives by hand. Telephony now exposes a provider-agnostic `IOutboundCallScreener` extension point that `DefaultTelephonyService` runs before dispatching any origination, failing the dial closed on the first denial; standalone Telephony with no screener registered is unchanged. The **Contact Center Outbound Compliance** feature registers a manual-call screener that applies contact opt-out, national do-not-call registries, and — when `CrestApps_ContactCenter:Compliance:ManualDialing:EnforceCallingWindow` is set — calling-window enforcement to soft-phone dials, resolving the destination to E.164 and failing closed on an unparseable number while do-not-call enforcement is on. Every suppression publishes a `ManualDialSuppressed` audit event so manual originations carry the same suppression trail as campaign attempts. The behavior is configured under `CrestApps_ContactCenter:Compliance:ManualDialing` (`RespectDoNotCall`, `EnforceCallingWindow`, `CallingCalendarId`, `DefaultRegionCode`).
- Contact Center authorization boundaries are now mandatory rather than optional, closing a fail-open class in which the security decision silently disappeared when its owning feature was off. `ICallControlAuthorizationService`, `ISupervisorQueueAuthorizationService`, and `ITransferDestinationResolver` were registered in the base feature but depend on services owned by Agents and Queues, so every consumer injected them as optional constructor parameters and then branched on `null`. Those branches did not degrade — they *allowed*: call-control dispatch returned "authorized" outright, monitoring skipped its queue-scope check, transfer fell back to the caller-supplied destination without resolving it, and `ProviderCallActionCommandTypeExecutor` kept the **caller-supplied** provider call id instead of the server-resolved one, which is an insecure direct object reference against a live call. Outbound dial likewise skipped first-dial ownership verification when the session manager was absent, a toll-fraud path. Each service is now registered in the feature that owns its real dependency closure — `ICallControlAuthorizationService` and `ITransferDestinationResolver` in Voice, `ISupervisorQueueAuthorizationService` in Queues (the only feature in all three of its consumers' closures) — every consumer requires them, and all fail-open branches are deleted. Production behavior is unchanged, because the underlying dependencies were always registered in every tenant that could reach these paths; only the untested fail-open branch is gone.
- Added a fresh-tenant feature dependency audit that proves every Contact Center and Telephony feature can construct every service its own declared dependency closure registers. Each feature is booted alone in an isolated Orchard tenant and every interface in both module assemblies is resolved, individually and as a collection. A service that is not registered resolves to `null` and is correct — its owning feature is simply off — while a service that *is* registered but throws is always a manifest defect, so the gate has no false positives by construction. This replaced an earlier attempt built on `ITypeFeatureProvider`, which is not a sound oracle for "what did this feature register": Orchard also harvests a module's assembly types into the module-named feature, so a tenant with only the base feature enabled attributed 147 types to it, including types whose `[Feature]` startup never ran. The audit is what surfaced the three misplaced authorization registrations above. Its converse — proving a *declared* dependency is actually used — is not dynamically enforceable, because Orchard always enables a feature together with its full declared closure, so no tenant can be booted with a dependency removed.
- Fixed inbound calls that arrive at a closed entry point or an unroutable queue never being hung up at the telephony provider. Those terminal `Reject` and `SendToVoicemail` commands are issued by the platform with no requesting agent, so their durable payload carries no agent user — and the call-control boundary, which authorizes by agent ownership, denied them. The result was a caller left connected to nothing after hours. Call control now models *who* initiated an operation: `CallControlInitiator.System` authorizes an operation that has no principal, and because a closed-entry-point call is terminated before any provider event has been ingested there is no call session yet, the boundary resolves the provider call identifier from the server-owned interaction instead. The system initiator is deliberately narrow — it is restricted to the `Decline` and `Voicemail` verbs the platform actually issues, may never claim supervisor privilege, and still fails closed on a terminal interaction, a mismatched provider, or a request naming a different call. `Agent` is the default value of the enum, so a payload that never declares an initiator is authorized as an agent request and fails closed rather than being treated as a platform action.
- Added a declarative gate rejecting any optional injected collaborator in Contact Center constructors. An interface parameter with a default value makes a type's behavior depend on which features are enabled, silently and without a compile error, and every instance found in this module was a fail-open security boundary. The gate is a single reflection test over both module assemblies rather than per-class constructor guards, which the repository conventions forbid, so it closes the entire class rather than the four known instances.
- Search independence is now enforced instead of merely documented, against all three mechanisms that can introduce a search dependency. The support matrix declares Elasticsearch unsupported in routing, assignment, provider ingest, or any other correctness path, and the supported single-node topology deploys no search cluster, but nothing prevented a routing or ingest service from acquiring a search dependency and quietly making that claim false. A build gate now reads the PE metadata of every shipped Contact Center, Telephony, Asterisk, and DialPad assembly and walks the transitive reference closure, failing if it reaches an Elasticsearch or OpenSearch client, so no supported deployment can be made to require a search cluster. A second gate rejects any search or indexing API referenced directly by those assemblies, so a correctness path cannot be written against search at all. Because an Orchard feature dependency is a string in a manifest and creates a runtime dependency with no assembly reference whatsoever, a third gate rejects any Contact Center feature that declares a dependency on a search-backed feature, and a fourth starts each supported profile in a real tenant and fails if the enabled-feature set contains a search engine. A fifth gate executes the correctness paths themselves — routing selection, assignment through a real reservation, outbox dispatch, and provider ingest through the normalized voice-event seam every PBX adapter funnels into, including its replay suppression — against persisted state inside a real supported-profile tenant, and fails if any outbound HTTP request is issued, because a regression that reached a cluster through an ordinary HTTP client would reference no search assembly and enable no search feature, so only execution can catch it. The direct gate is deliberately not transitive: the closure legitimately reaches an embedded Lucene index through shared libraries used for unrelated reasons, and an in-process index needs no cluster and no operator action, so treating it as a violation would report a dependency the module does not have.
- Fixed a defect that made every successful Contact Center outbox dispatch throw. Completing a message marked it completed, saved, and only then deleted it, but the intermediate save detaches the message from the session identity map, so the delete failed with `Could not delete object as it doesn't have an Id property` and the message survived as a completed row nothing ever reaps. Completion is now a single unit of work that deletes the message and saves once. Nothing consumed the completed status as domain state; the only readers count it as a store-reachability probe. If the transaction fails the message stays claimed and claim expiry redelivers it; that redelivery replays every handler, because the per-handler checkpoint is not persisted on the success path, and is safe only because handlers are required to be idempotent. The defect was invisible to the existing outbox tests because they settle claims against a mocked session, which cannot reproduce identity-map detachment; it is now pinned by a test that runs against a real store, by a second real-store test proving a lapsed claim is handed back out for redelivery, and by the search-independence gate that executes dispatch end to end.
- The expand → migrate → contract upgrade policy is now enforced by a build gate rather than documented and audited by hand. A migration that drops or renames a column, index, or table breaks the still-running old node during a rolling upgrade, turning the upgrade into an outage, and nothing prevented one from being added. Every Orchard data migration is now parsed and checked by three oracles: schema-builder operations, raw SQL passed as an argument to any synchronous or asynchronous execution method, and raw SQL assigned to a command's text — the last being the dominant shape in this repository and one an argument-only check would miss entirely. The raw-SQL oracles do not scan string literals, because ordinary C# defeats that: `"drop " + "table " + name` and `$"drop {kind} {name}"` are both destructive and neither contains a matching literal. The statement is instead reconstructed from the syntax tree across concatenation, interpolation, single-assignment locals, and read-only query-builder composition, and then classified, so it is judged on what it does rather than on how it was spelled. Classification does not stop at the leading verb, because a destructive statement need not lead: `with doomed as (...) delete from t` leads with `with`, and a batch can hide a second statement after a semicolon, so a destructive verb anywhere in the statement is a finding. Quoted values are removed before that scan so a literal that merely reads like a verb is not a false positive, and a statement that can execute another statement — `EXEC`, `sp_executesql`, or a procedural `DO`/`BEGIN` block, wherever it appears — is treated as unreadable rather than as safe, since stripping quoted values would otherwise clear `DO $$ BEGIN EXECUTE 'DROP TABLE t'; END $$;`. A statement the gate cannot read is itself a finding and must be recorded per call site with what it does and why it cannot be destructive; that approval is pinned to a fingerprint of the declaring type, so changing what the statement builds — including through a helper the approved expression calls — invalidates the approval and forces a fresh review rather than silently inheriting it. The reconstruction's one special case, treating a read-only query-builder chain as a `SELECT`, is only sound while the single `SqlBuilder` in scope is the data layer's, so a separate gate fails if the repository ever declares *or aliases* a type by that name — a `using SqlBuilder = Something;` directive is the same impersonation without the declaration, and a syntactic name check cannot otherwise see it. Destructive steps are attributed to the method that actually performs them, including private helpers several calls below the migration step, and each needs a register entry authorizing one operation against one named object; an entry matching no step or several steps fails, so an authorization can neither go stale nor widen into a standing bypass. Justifications are machine-checked: a contract-phase removal must name a strictly older release as the one that introduced the object, making expand and contract in the same release impossible, and a claim that an object never reached a customer must name the database object it is about, which is then searched for in the source of every stable release tag. The version number alone is an unverifiable assertion, since an object that shipped in an old release can be declared as introduced in the unreleased one and the version check would still clear it; naming a commit instead merely moves the assertion, because any recent untagged commit would satisfy it. Searching the released source checks the claim itself. It fails if the object is present in any released tree, if it cannot be bound to the object the entry authorizes, or if the released source cannot be read — which is why CI now checks out with full history. The claim also has to be bound to the object the entry actually operates on. A schema operation names its object directly, so the claim must equal it. Raw SQL is read at the operand position — the identifier following `drop table`, `alter table`, `delete from`, and the like — rather than anywhere in the statement, because matching the object anywhere accepts it appearing in a trailing comment while a different table is dropped. Reconstruction is what makes that position readable, resolving constants, interpolation holes, table quoting, schema qualification, and index-table naming conventions; the interpolation case in particular required recursing into the holes, without which `$"drop table {quotedTable}"` reconstructed to `drop table ?`. Every operand in the statement must be the claimed object rather than only the first, so a batch that drops the authorized table and then a second, unauthorized one is rejected instead of being covered by one claim, and an operand that cannot be read is a finding rather than a pass. Without that binding, changing the constant that names the dropped table would leave the statement classification, the authorization, and the claim all unchanged while dropping something else entirely. `UninstallAsync` is exempt, and only `UninstallAsync`, because uninstall is not an upgrade path. Because the gate finds migrations by folder convention while Orchard finds them by registration, that convention is verified rather than assumed: every type passed to `AddDataMigration` must appear in the scanned surface.
- Established one hub cancellation convention and stopped a flaky connection from silently deafening an agent. The Contact Center hub joins one SignalR group per signed-in queue, and it passed the connection's own token to every one of those joins, so a token that tripped part-way through left the connection in some of its queues' groups and not others. Nothing later repairs that: the durable session still says the agent is signed into every queue, so the agent stays connected, appears available, and receives no work for the queues whose joins never happened — and the moment the connection token is most likely to trip, a flaky or reconnecting client, is exactly when that costs the most. Hub work is now classified explicitly. Work whose only product is a value returned to the calling connection still honours the connection token, because if the caller is gone the answer has nowhere to go. Work that changes durable state or group membership runs to completion under a named token that never cancels — including three Telephony hub methods that read like queries: two refresh interactions through a store that commits per interaction, and one rotates the provider's OAuth refresh tokens, where losing the replacement locks the agent out. A gate scans every SignalR group membership call under `src` and `tests` and fails the build if any is passed the connection token, so the convention holds for hubs that do not exist yet; it enumerates the calls rather than the hubs, because a hub need not be named or shaped like one and group membership is also changed outside hub classes. The same harm was reachable without any cancellation, and is closed with it: when registration threw, the hub logged the failure and carried on reporting a successful connection, so a store outage produced the same silently deaf agent. Registration failure now aborts the connection. The remedy is not that the client comes back — its automatic reconnect is bounded and gives up after roughly forty seconds without telling the user — but that the aborted client stops heartbeating, and the availability service refuses an agent whose last heartbeat has gone stale. Marking the session offline on disconnect is only the fast path: in the store outage that caused the registration failure, that write fails too. The agent becomes visibly broken instead of silently deaf. This is a deliberate behaviour change, and it aborts a user who is both an agent and a supervisor rather than leaving them connected with only the supervisor half working.
- Scoped Asterisk call teardown to the events that actually end a channel. A live channel emits a continuous stream of non-terminal events and ends exactly once, but the real-time voice dispatcher invoked every registered call-teardown service for every one of them, relying on each implementation to recognise a non-terminal event and refuse the work. Nothing was round-tripping per event in practice — the one shipped implementation refuses on a string comparison before it touches a store or ARI — but the seam is an extension point whose contract told implementers they would be called for every event, so any future implementation that read a binding before deciding would have issued a store round trip per event on a per-channel event stream. The terminal test now lives in the dispatcher where the fan-out happens, so no registered service can reintroduce that cost, and the set of terminal events now has a single named owner shared by the dispatcher and the teardown service instead of living as a private detail of one implementation. That set stays deliberately narrower than the one the state mapper uses: the mapper also treats a hangup request as terminal so it can project the call as ending, while teardown must not, because destroying bridges or hanging up the peer leg on a request would tear a conversation down before the channel ended. Teardown still runs for a terminal event when a call-control bridge absorbs it and when a bridge throws; the test that claimed to prove the latter was dispatching a StasisStart, so it never exercised a terminal event at all, and now does.
- Shortened the Contact Center reservation critical section and established what actually makes it safe. Creating a reservation holds two distributed locks across roughly ten sequential round trips, and those locks carry a fixed expiration that is never renewed — so a critical section that outruns its lease keeps working under a lock it has already lost while a second caller is admitted. Lease renewal was considered and deliberately not added: it shortens that window without closing it, and would replace a deterministic defence with a probabilistic one. The measurable defect was duplicated work rather than a correctness hole. Availability is the canonical answer to whether an agent may take work, and producing it already reads the agent profile and counts that agent's active interactions; the reservation path called it, then read the same agent and counted the same interactions again, and re-derived the capacity decision from those second reads. Those duplicate checks were applied conjunctively, so they could only ever add a redundant rejection — they never admitted an agent availability had refused. What they did cost was two further round trips inside a critical section holding two unrenewed leases, and a second derivation of a decision that already had an owner. The reservation path now uses the availability snapshot as the single authority. No behaviour changed: the caller-supplied agent fallback that went with the duplicate read was unreachable, because the availability service reads the same document through the same session and returns nothing when it is missing, so the reservation was already refused in that case. What makes an expired lease survivable is the compare-and-set at commit, and that is now proved for accepting a reservation as well as for creating one, by granting the lock to both callers and requiring exactly one acceptance to reach storage — removing the version check makes both succeed, which is what shows the gate measures the compare-and-set rather than the lock.
- Fixed two invisible costs in Contact Center agent presence. A heartbeat rewrites the whole session document to move one timestamp and arrives from every connected agent on a timer, making it the most frequent write the desktop performs — and the document it rewrites also carries the connection list connect and disconnect maintain. Two requirements applied at once: the heartbeat must not write back a connection list read before a concurrent connect committed, and losing the version check that prevents exactly that must not fail the agent's hub call over a write carrying nothing the agent needs. Neither a lock nor a second read delivers this, which is worth recording because both look like they would: writes are staged rather than committed, so the version check runs when the shell scope commits — after any lock taken inside the method has been released — and a second read on the same unit of work is answered from its identity map, so it returns the instance already read rather than the row a concurrent connect committed. The stamp now runs in its own unit of work, whose read reflects what is committed and which commits before returning, so a lost version check is handled rather than thrown at the agent; it is treated as success and not retried, for a reason that differs by writer: connect and the cleanup pass carry a newer heartbeat, so a retry would write an older timestamp over a newer one, while disconnect and a membership sync do not advance the heartbeat at all, so a heartbeat lost to one of those is tolerated because neither fires on a timer and the stale threshold spans several heartbeat intervals. The heartbeat takes no distributed lock at all, removing two round trips per agent per interval. Separately, the pass that signs out agents whose heartbeats stopped runs every minute against a table holding a row for every agent who has ever connected, and it both read that table end to end and returned every stale session at once. It now selects stale sessions from the index alone, ordered by heartbeat time and bounded, then fetches those documents in one bounded read. Reading the index rather than the documents is what makes the bound work: a document query groups by document identity, no ordering over the index columns can satisfy that grouping, and YesSql supplies an ordering by document identity when a page is requested without one — so bounding a document query adds a sort of the entire backlog instead of removing one. Four properties are gated on the statement the store actually issues: no scan of the session index, a seek of `IDX_AgentSessionIndex_Retention`, no temporary tree, and oldest heartbeats first, without which a stale agent can sit unexpired behind a page that keeps being answered with someone else. `ExpireStaleAsync` now documents that one pass expires a bounded number of sessions rather than clearing the backlog.
- Corrected four Contact Center query-plan assertions that could never fail. They required the plan not to contain `SCAN <table>` using the physical index table name, but SQLite reports the query alias and never the table name, so the assertion matched nothing regardless of how the table was reached. The interaction, queue item, and metric contribution budgets — and the new agent session budget — now assert against the alias, which is what the planner actually prints.
- Fixed a write hot spot in Contact Center daily event counts. Each day and event type had a single row, and recording an event read that row, added one and wrote it back, so every handler counting the same kind of event on the same day met on one row: concurrent creates collide on its unique constraint and concurrent updates fail the optimistic-concurrency check, leaving one writer to either lose its whole request or overwrite a count it never read. Twenty-four concurrent sessions counting the same event now succeed where the previous shape fails with a unique-constraint violation. A recorded count is appended as its own contribution and never updated, and a background roller folds the contributions into the daily totals under the same distributed lock the other Contact Center background tasks use. Four consequences are gated because each is invisible in normal operation: the roller deletes exactly the contributions it read, so a contribution appended between the read and the delete survives to be counted by the next fold rather than being destroyed by a predicate delete; a fold adds to the total already stored rather than replacing it, which would look correct after the first fold of a day and discard every earlier hour; a summary adds the contributions not yet folded and stops once they are, so it neither lags the traffic it describes nor counts it twice; and drift detection and rebuild account for the contributions not yet folded, without which every one of them reads as a projection that has lost counts. They account for them without folding them: detecting drift is a read and must not commit the caller's unit of work, and folding before a rebuild reads the event log would count anything recorded in between twice, permanently. Drift detection adds them in memory and a rebuild subtracts them from the totals it writes so the later fold lands on the log. A rebuild is a repair that converges rather than a snapshot that is exact: a contribution is written by a post-commit scope rather than by the unit of work that writes the event, so an event is in the log for a window before its contribution exists, and a rebuild inside that window leaves the day high until it is run again once the projection has settled. That residual is documented, reported by drift detection, and gated. The roller runs under the feature that does the counting, so a tenant that counts events always folds them; registered elsewhere, its totals would stay empty and retention would purge the contributions before anything read them. The drain is deliberately unordered and the contribution table carries no index for it: the document query groups by document identity, so any ordering asked of the drain makes the engine sort the whole backlog before returning one batch, and an index the drain never uses would only be another cost paid on the append path this change exists to keep free. The table does carry an index on the day, because adding unfolded contributions to a summary is a request-path read that asks for them by day. The rebuild's own read of the unfolded contributions walks the whole contribution table, and it resumes from a position rather than from an offset, because the roller deletes the rows it folds from anywhere in that table and an offset would step over rows that are still waiting once earlier ones are gone, leaving the rebuild to write a total that is permanently short. Query-plan budgets measured on the statements the store actually issues hold the drain to never sorting the backlog, the summary read to seeking that index, and the walk to answering its ordering from the index it resumes by rather than sorting the table once per page.
- Fixed a schema divergence that made a freshly installed Contact Center tenant and an upgraded one run different databases for the same release. The reservation and queue-item claim keys were declared with an inline unique constraint and no default on the create path, but added with a named unique index and an empty-string default on the upgrade path. A tenant installed today therefore enforced uniqueness through a different database object than a tenant that upgraded, and only the upgraded one could accept a write from a node that did not yet know the column — so the two would have diverged further on the next rolling upgrade. Both create steps now build the constraints exactly the way the upgrade path builds them. The divergence was found by a new rolling-upgrade harness rather than by inspection, because the existing additive-migration gate reads migrations without running them and cannot see it: the gate rejects what is visibly destructive, while adding a non-nullable column with no default is entirely additive, passes the gate, and still breaks every write a still-running previous version performs. The harness builds two real databases from the shipped migrations — one installed fresh, one installed at the previous schema version and then upgraded — has a previous-version writer and a current-version writer both insert into the upgraded tables, reads the previous version's projection back, and then compares every column definition and every unique constraint between the two. One related hazard is documented as an operator constraint rather than enforced, because no portable fix exists within a single release: an upgrade that adds a non-nullable column with a shared default and then constrains it uniquely admits only one previous-version write, since every previous-version node writes that same default. Filtered indexes are unavailable or incompatible across the supported engines and a nullable column does not help, because not every engine treats nulls as distinct in a unique index, so the supported answer is to expand and contract across two releases.
- Bound the Asterisk integration to the protocol Asterisk actually publishes. Every Asterisk test previously asserted against a `TestAriClient` stub declared in the same file, so the suite could only prove the code agreed with itself and an Asterisk version bump could not break the build. Contract tests prove a payload is well formed, but a well-formed payload still arrives out of order, twice, or stamped by a clock that is not the clock that stamped the event before it, and the previous tests only exercised the orderly case. A generator now emits a real call lifecycle and then corrupts its delivery with duplicates, whole-stream replays, arbitrary reordering, clock skew wider than the spacing between events, mostly-unsequenced streams, late backward state regressions carrying the freshest timestamp and highest sequence number, and competing terminal reports that disagree about how the call ended. Four hundred seeded sequences per property are driven through the production ingest service and the production event publisher, and the session must converge to one terminal outcome regardless of delivery order, never regress its lifecycle rank, never resurrect a terminated call, never strand a call the provider reported terminated, never publish a lifecycle domain event twice, and never leave live-only state such as mute set on a terminated call. A companion property asserts floors on how often the generator produces each hard case, so the suite cannot quietly become vacuous as the generator evolves. Sabotage probing drove three of those generator capabilities into existence, each because a deliberately broken state machine still passed: corrupting the lifecycle ranking was masked by the staleness guards until late regressions were generated, removing terminal absorption was invisible until a second competing terminal was generated, and the reordering oracle itself was measuring list length rather than order. The same probing established that the service-level and publisher-level duplicate suppression are individually redundant and only observable when both are removed, which is recorded rather than presented as coverage.
- Fixed two provider call state machine defects the new property tests found. A terminal delivery carrying a stale mute flag re-applied it after termination had already cleared it, leaving an ended call flagged muted and publishing a mute event for a call that had just ended. More seriously, the sequence-number and timestamp staleness guards were applied to terminal deliveries: because provider nodes do not share a clock and do not sequence every event type, a hangup stamped fractionally behind the state change preceding it, or arriving without a sequence number, was silently discarded. The session then stayed live forever, `CallEnded` never published, wrap-up never started, and the agent and their reservation were never released. Terminal states now bypass those guards, and the provider-event watermark advances monotonically so accepting a late terminal cannot rewind it. Double-ending is not a new risk, because an already-terminal session is rejected before the guards run and exact redeliveries are rejected as duplicates.
- Collapsed two competing call-state vocabularies into one and gave every call ending a recorded reason. Contact Center reasons about a call with twelve states and the soft phone renders it with seven, and every call site translated between them with its own switch. Those switches disagreed with one another — an unrecognized state widened to `Dialing` in one place and to `Ended` in another — and in the widening direction all of them discarded the outcome, so a busy number, an unanswered dial, an abandoned call, and a completed conversation became the same ended call the moment a provider event crossed into Contact Center. Asterisk reports its release reason as a Q.850 cause code on every hangup event, and that code was captured only as an uninterpreted metadata string, so outbound compliance reporting and abandon analytics had nothing to count and no way to reconstruct it later. There is now one provider-neutral hangup-cause vocabulary covering normal clearing, busy, no answer, rejection, congestion, permanent failure, caller abandonment, and machine answer, with an explicit unknown for a provider that reports no cause at all rather than presenting it as a normal clearing. Translation between the two call vocabularies may be written in exactly one place, enforced by a source scan over every production file. Every Q.850 cause an Asterisk release can report is normalized, with the standard cause text used when only it is present and answer detection taking precedence over the release cause; DialPad, which publishes no release cause, derives one from the call-state token it already reports. Because Q.850 has no distinct cause for an abandoned call — a caller who hangs up while the far end is still alerting releases the channel exactly as a completed call does — that one distinction is resolved by the state machine, the only component that knows whether the call was ever answered. No session can now reach a terminal state without a recorded cause and end time, which is asserted over the same adversarial delivery sequences that prove the state machine converges.
- Closed a lost-update class in the soft phone's telephony interaction store, the last store still writing without an optimistic-concurrency check. Three writers touch that record independently — real-time provider events, the reconciliation pass that asks the provider for authoritative call state, and inbound dispatch — and each of them read it, mutated the copy it was holding, and saved, so whichever committed last silently discarded the others' work. The damaging case is not a lost cosmetic field: the reconciliation pass applies a provider snapshot that is already seconds old, so it could reinstate a live call over a hangup a real-time event had committed while the pass was running, leaving the call shown as active to the agent until a later pass happened to catch it. Every write is now concurrency-checked, and read-modify-write callers no longer perform their own read: they hand the store a mutation, and the store opens a dedicated session, reads the current version, applies the mutation, and commits, re-reading and reapplying against the winner when another writer commits first. The mutation may also decline after seeing the fresh version, which is what makes the real-time dispatcher's terminal check correct rather than merely retried — an event arriving just behind a hangup now declines instead of resurrecting the call. Proven against a real database rather than a mocked session, because a mocked session cannot reproduce a version conflict at all.
- **Breaking change:** split the telephony provider interface into per-capability contracts. `ITelephonyProvider` declared thirteen call operations, so every provider had to supply an implementation for every operation whether or not its backend could perform it, and the only honest way to decline was to accept the call and return a failure string. The shipped Asterisk adapter did exactly that for warm transfer, because attended transfer shared a capability flag with blind transfer and there was no way to advertise one without the other. `ITelephonyProvider` now declares only the provider's display name and its advertised capabilities; each operation moved to its own contract — `ITelephonyCallControlProvider`, `ITelephonyInboundCallProvider`, `ITelephonyHoldProvider`, `ITelephonyMuteProvider`, `ITelephonyTransferProvider`, `ITelephonyAttendedTransferProvider`, `ITelephonyConferenceProvider`, `ITelephonyDtmfProvider`, `ITelephonyVoicemailProvider`, and `ITelephonySoftPhoneCredentialsProvider` — and a provider that can only place and end calls is now complete after two methods. Attended transfer became its own `TelephonyCapabilities.AttendedTransfer` flag, so a backend that can release a call but cannot consult the destination first no longer has to claim it can. `TelephonyCapabilityContracts` records the contract each capability requires in one place, and dispatch is gated on both halves: an operation runs only when the resolved provider advertises the capability **and** implements its contract, so advertising without implementing and implementing without advertising both fail closed rather than dispatching into a missing implementation. The two Contact Center call sites that resolve a telephony provider by name instead of through the shared service now repeat the same check before dialing. Existing custom providers must add the contracts for the capabilities they already advertise; a build-time check holds the shipped providers to the same rule by reading the widest capability set each one's own capability source can ever advertise.
- **Breaking change:** removed one vendor's implementation vocabulary from the provider-neutral telephony and Contact Center contracts. The shared contracts declared a snoop channel identifier, a supervisor bridge identifier, and a bridge identifier plus a provider channel identifier for transfer, conference, and attended transfer. No provider-neutral code read any of them and only the Asterisk adapter ever wrote them, so what looked like the platform's contract was really one vendor's media engine documented as an obligation every future provider inherited. Those ten result keys moved into `AsteriskVoiceResultMetadata` inside the Asterisk module with their exact wire values unchanged, so previously stored metadata keeps its meaning. The three `AgentUserId` request keys stay in `ContactCenterConstants` because the platform genuinely supplies them to every provider. `RecordingMetadata.RecordingName` is now `RecordingMetadata.ProviderRecordingId`, `CallSession.BridgeId` is now `CallSession.MediaTopologyId`, and `MergeRequest.PrimaryCallId`/`MergeRequest.SecondaryCallId` were deleted in favor of the `CallIds` collection that superseded them; removing the legacy pair also fixed a latent defect, because the telephony hub's diagnostic log described a merge using only those two fields and therefore logged nothing at all for requests sent by the current client. Custom providers that populated the relocated keys should declare their own equivalents inside their own module; a build-time architecture check now fails the build when provider-specific vocabulary reappears in a provider-neutral project.
- Documented several operator-facing truths that the shipped code already enforces but the docs left implicit. **Not an emergency service:** the platform is not an E911/112/999 calling service and has no emergency-origination, location, or PSAP-routing code path; `ExternalDestinationPolicy` rejects emergency and premium destinations, but only on the Contact Center server-side paths (`DialProviderCommandTypeExecutor` first-dial and `TransferDestinationResolver`), while the Telephony soft-phone keypad and transfer field reach the provider unfiltered — so operators must block emergency codes at the Asterisk dialplan / SIP trunk and provide emergency access by independent means. The voice-routing guide now states this as a prominent warning with the residual obligation spelled out. **Recordings are mono:** the Asterisk provider records the mixed audio of the conversation bridge as a single mono WAV rather than a dual-channel recording with the caller and agent on separate tracks (supervisor monitor and whisper legs, which run on a separate bridge, are not captured; a barge is), so per-speaker attribution requires diarization; the recording-governance guide now says so. **CRM message content is plaintext:** `OmnichannelMessage.Content`, `CustomerAddress`, and `ServiceAddress` are stored unencrypted in the tenant database (the addresses are additionally projected into `OmnichannelMessageIndex`), unlike recording media which the media-execution layer encrypts at rest, so protecting them is a deployment responsibility (database- or disk-level encryption); the omnichannel management guide now discloses this and records that comprehensive per-contact subject erasure across activities, messages, and contacts is a known general-availability blocker, since the activity **Purge** action removes an activity from the work queue without deleting the underlying content. **Data residency is the operator's responsibility:** the production-support guide now names every system that holds or processes customer data — tenant database, recording media store, the Asterisk host's transient unencrypted source file, the Redis backplane, the third-party SMS/email providers (Twilio, Azure Communication Services), the third-party voice provider (DialPad, which holds all of its own call media), and the configured AI completion provider (which receives inbound SMS bodies) — and states the product does not constrain their physical placement.
- Made base-voice deployment verification an explicit release gate and turned recording off by default. Whether the end-to-end WebRTC audio path works — trusted certificates, TURN relay, direct-ICE media, restart drain, and a measured capacity floor — is a property of a deployment and its infrastructure, not of the capability code, and it cannot be proven in the application build. A production host now **withholds tenant readiness** until an operator declares the base-voice path verified through `CrestApps_ContactCenter:BaseVoiceVerification:AudioVerificationAcknowledged` (which every host rejects at startup unless it is accompanied by an `AudioVerificationEvidenceReference` pointing at the retained proof, so the acknowledgment can never be a bare boolean flip), surfaced by a new `contactcenter-base-voice-verification` readiness check (registered by the Voice feature and tagged `contactcenter-ready`) that fails closed in production and only warns outside it — the same deliberate exception to the "readiness must differ between nodes" rule as the topology check, because an unverified media path is fixed infrastructure that no amount of waiting repairs. The production-support guide gains a base-voice acceptance procedure (direct-ICE audio, forced-TURN relay, restart-drain, dependency-failure, and a capacity floor), an evidence template, and the configuration to declare the result. No automated test exercises the browser↔Asterisk WebRTC signaling or media path itself — it is proven only by the deployment acceptance step; CI covers adjacent surfaces (the Asterisk ARI control plane via recorded-cassette contract tests, and the soft-phone UI/adapter contract via the Playwright gate against a stubbed media adapter). Separately, because the unverified-audio risk compounds with the recording media-lifecycle and erasure risk, `ContactCenterRecordingSettings.RecordingEnabled` now defaults to `false`: a fresh tenant records nothing until an operator enables it after the acceptance run passes. The `Recording` provider capability stays advertised and `Monitor`, `Whisper`, and `Barge` remain advertised and enabled — only the recording policy defaults off.
- Fixed a dependency-injection cycle that made the Contact Center Recording feature unusable once enabled. The recording-media-deletion event handler is registered as a Contact Center event handler and, to record its confirmed-deletion receipt, took the event publisher in its constructor. But the publisher resolves the outbox, and the outbox resolves the whole set of event handlers — so enabling Recording closed the loop publisher → outbox → handlers → recording-media-deletion handler → publisher, and the container refused to construct the publisher (and every service that depends on it) the moment the feature was enabled, which is the moment an operator turns recording on. The handler now resolves the publisher lazily when it actually handles an erasure rather than at construction, breaking the cycle while preserving the confirmed-deletion receipt; a feature-activation audit that constructs every service each feature registers, on a tenant with only that feature enabled, now passes for Recording. This changes the `RecordingMediaDeletionHandler` public constructor signature from taking `IContactCenterEventPublisher` to taking `IServiceProvider` — a breaking change for any code that constructs the handler directly.
- Bounded the Contact Center dialer-pacing and agent-availability-recovery background tasks so a slow run can no longer outlive its distributed lock and overlap the next tick on another node. Both tasks held a 60-second lock while work ran with no matching run deadline, so a run that exceeded the lease let a second node begin an overlapping pacing cycle — dropping the per-invocation cap that constrains aggregate call rate — or race agent-state transitions. Each task now raises the lock expiration to twice the one-minute schedule and bounds every run to a wall-clock budget kept strictly below that expiration, enforced by a linked `CancelAfter` token that cancels in-flight work (and, for pacing, a between-profile deadline check that defers the remaining profiles to the next tick). Shutdown cancellation is still rethrown so the lease releases promptly, while a budget-exhausted run is logged and deferred. This adopts the same bounded-run pattern already used by the reservation-and-assignment task.
- Made the Contact Center agent workspace and supervisor dashboard accessible to assistive technology and keyboard-only operators. The two real-time surfaces previously carried no ARIA semantics: incoming-call offers, presence, queue depth, and the active-call panel were injected into containers with no live-region roles, the presence menu had no menu semantics or keyboard support, and failures surfaced through blocking `window.alert()` dialogs. The incoming-offer container is now an assertive live region that moves keyboard focus to **Accept** when a call rings, the active-interaction, queue, summary, tiles, and agent-board regions are polite live regions with accessible names, and the per-second countdown and talk-time nodes are hidden from assistive technology so state is announced once rather than every tick. The presence control is a proper ARIA menu with `aria-haspopup`/`aria-expanded`/`aria-controls`, `role="menu"`/`role="menuitem"`, first-item focus on open, Arrow/Home/End roving focus, Escape-to-close with focus return, and click-away close. Both surfaces replace `window.alert()` with a non-blocking inline `role="alert"` error region and add a `role="status"` connection indicator that announces connected, reconnecting, and disconnected states, driven by new connection-lifecycle callbacks surfaced from the shared real-time helper. All new user-facing strings are localizable.
- Stopped the Contact Center routing hot paths from materializing an entire queue's waiting backlog to pick a single item. The assignment loop and the voice and generic offer paths each loaded every waiting item for a queue and then discarded all but the one winner, so a queue spike produced roughly quadratic query traffic and allocations exactly when assignment latency matters most. A new bounded `IQueueItemStore.FindNextWaitingAsync` returns only the top row under the same `Priority` descending, then oldest-first ordering the full listing used, and a new `IQueueItemManager.FindNextWaitingAsync(queue, utcNow)` routes to it whenever the queue does not apply SLA aging — where an item's effective priority equals its base priority, so the bounded query is provably identical to the in-memory selection — and falls back to the full scan only for queues that opt into SLA aging, whose wait-time-based reordering genuinely requires scoring every candidate. `ListWaitingAsync` is retained for the aging fallback and for overflow processing, which legitimately walks the whole backlog.
- Removed the supervisor-dashboard poll's per-agent query fan-out. The dashboard refreshes every ten seconds, and each refresh previously issued several queries for every queue and — the dominant cost, since agents far outnumber queues — three queries per agent: the active interaction, the active-interaction count, and a user lookup to resolve the display name. It also reissued the supervisor authorization lookup (which reloads the supervisor profile) once per queue and again per busy agent, and re-loaded each active interaction inside `GetAvailableModesAsync`. A few hundred watched agents therefore produced thousands of database round-trips per minute per supervisor, competing with the routing hot paths for the same connection pool. The poll now resolves the whole scoped set in fixed batches: waiting depth per authorized queue through the existing batched `IQueueItemManager.CountWaitingByQueueIdsAsync`, active interactions through a new index-backed `IInteractionManager.ListActiveByAgentIdsAsync` (a chunked `.IsIn` query, keeping the most recent by `CreatedUtc` per agent), active counts through the existing `CountActiveByAgentIdsAsync`, and display names by bulk-loading the agents' users with a single chunked `UserId.IsIn` query and feeding each already-materialized user to `IDisplayNameProvider.GetAsync`, which performs no further database access. Supervisor queue authorization is memoized per queue for the request so the per-agent monitoring gate no longer reissues the supervisor lookup for each busy agent, and a new `IContactCenterMonitoringService.GetAvailableModesAsync(Interaction)` overload resolves engagement modes from the already-batched interaction instead of reloading it through `FindByIdAsync`. No new hand-written SQL was added, so the query-plan budget gate is unaffected. The remaining per-queue longest-wait/SLA reads are bounded residuals — queues are far fewer than agents. This adds `ListActiveByAgentIdsAsync` to `IInteractionStore`, `IInteractionManager`, and their default implementations, and `GetAvailableModesAsync(Interaction)` to `IContactCenterMonitoringService`.
- Stopped Contact Center recording ingestion from buffering whole recordings in memory. The encrypted media store protected the full recording as one `byte[]` on write, and on read copied the file into a `MemoryStream`, materialized it to an array, unprotected the whole array, and returned yet another `MemoryStream` — so a single long recording cost several times its size in managed memory and pushed large recordings onto the large-object heap, exactly when several ingests could overlap. The Asterisk download side compounded it by pulling the stored file into a byte array before handing it over. Recording media is now streamed end to end through a chunked authenticated-encryption container: a fresh random AES-256-GCM data key encrypts the media as a sequence of independently authenticated 64 KiB frames, and that per-recording data key is itself wrapped by the data-protection provider, so key management — tenant isolation and rotation — stays with data protection while the bulk media flows a fixed chunk at a time in both directions. Every frame binds its ordinal position, its length, and an end-of-stream marker into the authenticated associated data, so a tampered, reordered, or truncated container is rejected on read rather than yielding altered or partial audio. The write request now carries a `Stream` instead of a `byte[]`, the store reads and writes straight through the tenant file store without a whole-recording copy, and the Asterisk client streams the download response headers-first and holds it open only for the duration of the store call. Recording is off by default and the media format is new, so there is no stored media to migrate. This changes `RecordingMediaWriteRequest.Content` from `byte[]` to `System.IO.Stream` — a breaking change for any code that constructs the request directly.
- Bounded the two remaining Contact Center query paths that materialized an entire unbounded result set. Expired-reservation cleanup previously loaded every expired pending reservation in one query before processing, so a spike that expired thousands of offers at once was pulled into memory in a single pass. `ListExpiredAsync` now takes a keyset cursor (`afterExpiresUtc`, `afterDocumentId`) plus a `maxResults` bound and returns an `ExpiredReservationPage`, ordering deterministically by expiry (oldest first) then document id against the existing reservation index, and the sweep drains the backlog in fixed 100-row pages using keyset (seek) paging: each page advances the cursor past the last row it observed. Because the cursor is an absolute position in the key space rather than a numeric offset, concurrent expirations or insertions never shift the window, so a live reservation is never skipped and a locked oldest page never starves the drainable reservations behind it — the locked candidates are simply retried on the next scheduled run. Separately, the interactive analytics reports materialized every interaction and activity in the requested window with no maximum range, and silently trimming rows would have corrupted the aggregate totals, so an over-wide request now fails fast instead: a new `ContactCenterReportingOptions.MaximumReportRange` (bound from `CrestApps_ContactCenter:Reporting`, default 400 days, validated on start) is enforced by a shared guard at the top of every report query path, including the enterprise report providers, before any rows are read — the 400-day default comfortably covers the built-in day, week, month, quarter, and year presets. Pre-aggregated rollup indexes and streaming exports remain a documented enhancement. This changes the `ListExpiredAsync` signature on `IActivityReservationStore` and `IActivityReservationManager` — a breaking change for any code that calls them directly — and adds an `IOptions<ContactCenterReportingOptions>` constructor parameter to `ContactCenterReportingService`.
