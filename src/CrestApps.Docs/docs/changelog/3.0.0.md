# Version 3.0.0 Release Notes

This page highlights the changes in the `3.0.0` line.

## New Modules

### Products, Payments, and Subscriptions

This release introduces a new commerce stack for selling recurring plans on Orchard Core content:

- **[Products](../modules/products)** (`CrestApps.OrchardCore.Products`) — attaches a reusable `ProductPart` (price + product type) to any content type, turning content items into purchasable products.
- **[Payments](../modules/payments)** — a provider-agnostic payment framework (`IPaymentEvent`, `PaymentMethodOptions`) with a production-hardened **Stripe** provider (`CrestApps.OrchardCore.Stripe`). Stripe supports both the on-site **Payment Elements** integration and the Stripe-recommended **Hosted Checkout** (redirect), selectable from settings. Linking a Stripe account is one step: paste the account's secret key and click **Connect** — the app verifies the key, resolves the account, and provisions the webhook (capturing its signing secret) automatically, and can be disconnected with one click. When the **Workflows** feature is enabled, Stripe also contributes workflow events for the payment lifecycle (payment received, subscription created, payment failed/canceled/refunded, dispute created) and a **Stripe Request Failed** event for authentication or connectivity problems, so administrators can build custom alerting or automation. New payment gateways (for example PayPal) can be added and surfaced as checkout options without changing the consuming modules.
- **[Subscriptions](../modules/subscriptions)** (`CrestApps.OrchardCore.Subscriptions`) — sells recurring subscriptions built on a `SubscriptionPart`, with a multi-step checkout flow, a subscriber dashboard, an admin management console, and optional **reCaptcha** and **Tenant Onboarding** features. Subscriptions depends on the new **[Checkout](../modules/checkout)** framework for payment handling. Payment options are contributed by other modules: enable the **Stripe** module to accept card payments (wired in automatically when both are enabled — there is no separate *Subscriptions - Stripe* feature), and enable the **[Pay Later](../modules/pay-later)** module to offer an offline pay-later option.
- **[Pay Later](../modules/pay-later)** (`CrestApps.OrchardCore.PayLater`) — a standalone module that adds an offline "pay later" option to the Checkout framework, reusable by subscriptions and one-time goods purchases. It records an offline commitment through the same durable ledger and reconciliation as a real gateway, without ever fabricating a *paid* record a processor could contradict, and now records the balance it leaves owing as a trackable outstanding **[Transaction](../modules/transactions)** so it can be reported, reminded about, and settled later.

The payment path was hardened for multi-instance, production use: deterministic Stripe idempotency keys, distributed-lock–serialized checkout finalization, currency-aware minor-unit conversion, rate-limited anonymous checkout endpoints, idempotent payment-intent confirmation (a PaymentIntent already confirmed client-side by Payment Elements is reconciled to its authoritative state instead of failing the webhook), and signature-verified, de-duplicated, retry-safe Stripe webhooks.

See [Products](../modules/products), [Payments](../modules/payments), and [Subscriptions](../modules/subscriptions) for details.

- **Managed currencies for products and subscriptions.** Products now owns a document-backed **Commerce → Currencies** catalog that stores the allowed currencies without a query index, seeds a default list through a migration-executed recipe, and exposes recipe (`Currencies`) and deployment support for managing the catalog as configuration. Product prices, product default currencies, and the subscription settings currency now use friendly dropdowns sourced from that catalog instead of free-form text entry.
- **Subscription editor and checkout polish.** The product and subscription editors now group related pricing and billing inputs so the amount/currency and billing-duration/duration-type pairs read together, and the subscription part now explains what **Billing Cycle Limit** and **Subscription Day Delay** do. The checkout payment step now presents payment methods as cards, shows clearer Stripe and Pay Later panels, and surfaces Pay Later errors inline instead of falling back to generic alerts.
- **Safer Pay Later completion for tenant onboarding.** The tenant-onboarding subscription completion handler now skips validation when the subscribed plan does not actually require tenant onboarding, which prevents Pay Later completions from failing with a misleading "Unable to locate the saved new site information" error on plans that do not collect tenant-setup data.
- **Subscriptions now reuses the shared Wizard feature.** The public subscription signup routes now delegate to the common wizard host and completion engine instead of maintaining a separate controller/session-completion pipeline, while subscription-specific steps and persisted `SubscriptionSession` documents remain in place for payments, reporting, and onboarding flows.

### Checkout

This release also introduces **[Checkout](../modules/checkout)** (`CrestApps.OrchardCore.Checkout`) — a provider-agnostic checkout and payment framework that any purchase flow can build on, so the wizard, invoice, taxation seam, and money-handling safety guarantees are written once and reused by recurring subscriptions and one-time goods purchases alike.

Checkout is hardened for sensitive, multi-node money handling:

- A **durable payment ledger** (`PaymentAttempt` / `IPaymentAttemptStore`) persisted in the tenant database, written *before* every provider call and updated with the provider's authoritative reference immediately after — so a crash, cache eviction, or partial multi-obligation failure can never strand an untracked charge.
- **Reconciliation against the provider's authoritative API** (`ICheckoutReconciliationService`) that records a payment *only* when the provider confirms it and marks the checkout complete only when **every** obligation is settled, so our side never shows *paid* while the gateway failed.
- A first-class **`ICheckoutPaymentProvider`** contract (begin / verify / cancel + capabilities) for adding gateways.
- **Currency-correct money** (`Money` / `CurrencyScale`) for every ISO-4217 currency, including zero-decimal (JPY) and three-decimal (KWD) currencies.
- **Distributed coordination** via `IDistributedCache` and `IDistributedLock` (`PaymentSessionCache`, `IPaymentAttemptLimiter`), where the cache is a notification-only optimization and never the source of truth.
- A **taxation seam** (`ICheckoutTaxService`) that folds tax into the charged amount when Taxation is enabled and is a no-op when it is not.

See [Checkout](../modules/checkout) for details.

### Transactions

This release introduces **[Transactions](../modules/transactions)** (`CrestApps.OrchardCore.Transactions`) — a provider-agnostic ledger of *money owed* that answers one question for the whole tenant, **"what has not been paid yet?"**, no matter which provider or purchase flow created the obligation.

- A durable **`Transaction`** ledger entry (persisted in the tenant database) captures the amounts, owner, optional due date, provider-neutral `Source`, a neutral `ReferenceType` / `ReferenceId` reference, and an audit timeline, moving through a full `TransactionStatus` lifecycle (`Pending`, `Outstanding`, `PartiallyPaid`, `Paid`, `Canceled`, `Failed`, `Abandoned`, `Refunded`).
- A customer **"My Transactions"** statement — consistent with the administrator report, offering a search bar, a status filter, and a pager — lists what a user owes and lets them **pay an outstanding balance online**: the module starts a [Checkout](../modules/checkout) session that references the transaction, contributes the outstanding balance as a one-time billing item, and marks the transaction paid only when the gateway confirms the settlement.
- An administrator **report and management console** (**Commerce → Transactions**) lists the tenant's transactions and lets managers send a reminder, record a full or partial offline payment, mark paid, cancel, or add a note — one provider-agnostic place to chase, settle, or annotate any unpaid balance. The report filters by status, searches by title, and filters by **source** through a dropdown of the sources registered by the enabled features (a module registers its friendly, localizable source name with `AddTransactionSource`).
- **Reminders delivered through the notification system.** `ITransactionReminderService` sends reminders through OrchardCore's `INotificationService`, so each reminder honors the owner's preferred channel instead of assuming email only. A background task sweeps outstanding transactions and reminds on a configurable cadence (first-reminder delay, interval, and a maximum), and managers can also send a reminder manually. Reminders are gated behind the separate opt-in **Transaction Reminders** feature (`CrestApps.OrchardCore.Transactions.Notification`), which depends on the OrchardCore **Notifications** feature; the core ledger, report, statements, and settlement work without it.
- **Authenticated and guest ownership.** A transaction now records an `OwnerKind` (`Authenticated` or `Guest`) alongside its owner id, so a purchase made without an account is owned by a stable, tenant-scoped guest customer id instead of being orphaned under a null owner. An authenticated owner is still reminded through the notification system; a guest owner is reminded by email through the optional email service using the contact captured at purchase time, and the reminder degrades gracefully when no email service or guest contact is available. The owner kind is a mapped index column (defaulting to `Authenticated` for existing rows through a schema migration) and is a filter on the transaction query. The customer-facing statement and the pay/detail authorization now require the `Authenticated` owner kind, so a guest obligation can never be viewed or paid by an authenticated user who happens to share an id.
- **Confirmed-amount, idempotent, concurrency-safe settlement.** Online settlement is applied against the amount the payment provider **actually confirmed** — read from the durable payment-attempt ledger — instead of the requested total, and the attempt currency must match the transaction currency (a mismatch is rejected, never converted). A confirmed amount that covers the balance marks the transaction `Paid`; a smaller amount marks it `PartiallyPaid`. Settlement is idempotent (re-completing the same checkout never double-applies), records the settling `PaymentAttemptId` for gateway reconciliation, and is guarded by optimistic concurrency so two nodes can never silently overwrite each other. The outstanding balance is also persisted as a mapped `OutstandingAmount` index column (normalized to the currency's precision) so a report can query and sort by what is owed without loading every document.
- New permissions gate the feature: **Manage transactions**, **Manage transaction settings**, and **View own transactions**.

The **[Pay Later](../modules/pay-later)** module is the first consumer: every succeeded Pay Later commitment records an idempotent outstanding transaction (with a due date derived from a configurable net term), so an offline "pay later" balance becomes a first-class, trackable obligation. Online settlement requires the Checkout feature and degrades gracefully when it is not enabled.

See [Transactions](../modules/transactions) for details.

### Reusable buyer identity (Customers foundation)

Two new foundation projects establish a reusable, provider-neutral way to describe *who a purchase belongs to*, so the future commerce domain (Orders, Carts) can attribute records to a buyer without every module hard-coding the authenticated user service:

- **`CrestApps.OrchardCore.Customers.Abstractions`** contributes the `CustomerOwnerKind` enum (`Authenticated`/`Guest`), an immutable `CustomerOwner` value with `ForUser` / `ForGuest` factories, the `ICustomerContact` contact value, and the `ICustomerContactResolver` contract that addresses an owner uniformly.
- **`CrestApps.OrchardCore.Customers.Core`** provides the default resolver (registered with `AddCustomersCore()`): an authenticated owner resolves through OrchardCore's user service, and a guest owner resolves from the contact captured at purchase time.

Transactions is the first consumer, using the owner value to attribute and reach both authenticated and guest buyers. A guest buyer's contact is captured on the checkout through a provider-neutral `CheckoutContactInfo` snapshot and copied onto each guest transaction so reminders can reach them. Capturing a durable guest access credential remains deliberate future hardening; the foundation records a stable guest owner id today so no obligation is orphaned.


### Commerce

This release adds **[Commerce](../modules/commerce)** (`CrestApps.OrchardCore.Commerce`) — a small module that owns the shared **Commerce** top-level admin menu and its icon. Commerce-related modules (Transactions and Taxation) now depend on it and contribute their screens under one consistently branded menu, instead of each declaring the top-level node and icon on their own (which made the icon appear or disappear depending on which module was enabled). The feature is **enabled by dependency only**, so it has no standalone function and is activated automatically whenever a module that depends on it is enabled.

Commerce is deliberately a **thin orchestration shell**: it owns no persistence, migrations, indexes, or domain data models. A new `CommerceModuleBoundaryTests` architecture test locks this in by failing the build if the Commerce assembly ever references a domain persistence assembly (or YesSql) or defines a migration, index, or index provider. This keeps the future commerce domain (Orders, Carts, Customers) in its own reusable modules with Commerce composing them.

A new provider-neutral **`CrestApps.OrchardCore.Commerce.Abstractions`** project adds the **financial-document policy seam** — the contract that decides which financial documents a money event issues (a receipt, or a persisted numbered invoice, credit note, or refund document) without the money-moving modules (Checkout, Payments, Transactions) hard-coding that decision. It contains only contracts (`IFinancialDocumentPolicy`, `FinancialDocumentContext`, `FinancialDocumentPolicyResult`, the `FinancialDocumentKind`/`FinancialDocumentReason` enums, and an `IFinancialDocumentNumberGenerator` with `FinancialDocumentNumberRequest`/`FinancialDocumentNumber`) and takes no package or project references. The shipped default, `ReceiptsOnlyFinancialDocumentPolicy`, issues a receipt only — it never persists an immutable copy and never requires a formal number — so today's behavior is unchanged and the existing `IReceiptService` printable path stays the only runtime dependency. `IFinancialDocumentNumberGenerator` deliberately ships with **no default implementation**: correct, node-safe legal numbering needs durable persistence that only exists once an Orders domain owns it, and a speculative generator would risk duplicate or reused numbers. Because the receipts-only default never requires a number, nothing resolves the generator at runtime. A future Orders domain can register a replacement policy (and a real generator) that persists numbered invoices and credit notes without changing any caller. The boundary test also asserts that `Commerce.Abstractions` references no domain persistence or providers, keeping it a pure cross-domain contract.

See [Commerce](../modules/commerce) for details.

### Refunds and reusable payment foundations

Foundation-hardening changes turn the commerce stack into a clean, reusable base a future e-commerce module can build on without another architectural rewrite. Because there is no previously released commerce stack to preserve, these are intentionally **breaking within the 3.0.0 line** in exchange for a single forward-only foundation:

- **Money is `decimal` end to end.** Every monetary amount across Payments, Checkout, Subscriptions, Stripe, and Products (`Money`, `CheckoutInvoice`, `PaymentAttempt`, `Invoice`, `ProductPart.Price`, and the payment/subscription event contexts) is now `decimal` instead of `double`, so amounts are never subject to binary floating-point drift. The `long` minor-unit representation Stripe requires stays confined to the gateway adapter (`StripeCurrency.ToMinorUnits` / `FromMinorUnits`), which converts with `MidpointRounding.AwayFromZero`; the legacy `double` overloads were removed so a caller can no longer bypass the currency-aware boundary. `System.Text.Json` reads previously persisted numeric values into `decimal` without a data migration.

- A **durable refund ledger** (`PaymentRefund` / `IPaymentRefundStore`) and an authoritative **`ICheckoutRefundService`** that resolves the settled payment, enforces the remaining refundable amount, allocates refunded tax from the original payment's immutable `TaxSnapshot`, persists the refund *before* calling the gateway, and serializes concurrent refunds of the same payment with `IDistributedLock` so two nodes can never over-refund. Gateways opt in with the additive **`ICheckoutPaymentRefundProvider`** contract; a provider with no executable refund records the refund as `PendingManualReview`.
- **Provider-neutral lifecycle events and inbound refund reconciliation.** `IPaymentEvent` now covers payment failure, cancellation, refund, and dispute/chargeback in addition to success, so every gateway raises the same normalized stream. The Stripe webhook dispatcher maps `payment_intent.payment_failed`, `payment_intent.canceled`, `charge.refunded`, `charge.refund.updated`, `refund.updated`, `refund.failed`, and `charge.dispute.created` onto these events, forwarding gateway metadata (including the checkout idempotency key) and falling back to the charge id when a refund carries no payment-intent id. A new **`ICheckoutRefundReconciliationService`** applies a refund observed at the gateway — including one issued from the provider dashboard — to the durable ledger under the same per-payment lock: it correlates by provider reference, context or metadata idempotency key, a deterministic aggregate key, or an amount-and-currency match against an open local request. It adopts the gateway's authoritative status (a blank status is treated as `Pending`, never fabricated as succeeded), never regresses a terminal local status on a stale or out-of-order event, and quarantines an unmatched remote refund idempotently as `PendingManualReview` (`remote_refund_without_local_request`) instead of losing it or fabricating a result the gateway never confirmed.
- **A canonical order-to-checkout reference contract.** `CheckoutReferenceTypes.Order` fixes the well-known `ReferenceType` an ecommerce order uses on a `CheckoutSession` (with the order's item id as `ReferenceId` and an optional version id), and `ICheckoutSessionStore.GetByReferenceAsync` resolves the most recent session for a reference. Payment stays authoritative in the attempt ledger, so an order is never marked paid from a session status alone.
- **Architecture guard tests for the reusable module graph.** New reference-direction tests keep the payment/checkout/taxation/addresses abstractions one-way and independent of concrete providers: abstraction projects may reference only other abstraction projects, and foundation projects never reference provider or presentation modules (parsed directly from each `.csproj`). A capability-truthfulness test auto-discovers every concrete provider in all loaded `CrestApps.OrchardCore.*` module assemblies and asserts that any provider advertising `Capabilities.SupportsRefunds` actually implements `ICheckoutPaymentRefundProvider`, so the flag can never lie and a provider added in any module is checked automatically.
- **Verified taxation baseline.** `TaxTable` is an effective-dated catalog document: `TaxService` never applies a table outside its effective window for the transaction date, and a rule that requires a table with no table in effect on that date is skipped instead of silently taxing at zero. Table rows are validated on write (non-negative minimums, at most one open-ended row, ordered non-overlapping bounded ranges, and an open-ended row starting at or above the highest bounded maximum), a table still referenced by a rule cannot be deleted, and recipe import validates a candidate before overwriting an existing table.
- **Stripe as a generic checkout provider.** When both **Stripe** and **Checkout** are enabled, Stripe now registers a generic `ICheckoutPaymentProvider` and `ICheckoutPaymentRefundProvider`, so any checkout can collect and refund a card payment through a Stripe PaymentIntent without depending on the subscription-specific endpoints. New Stripe services (`CreateForCheckoutAsync`, `RetrieveAsync`, `CancelAsync`, and `IStripeRefundService`) route every amount through `StripeCurrency`.
- **Consistent catalog persistence and identity.** The durable `PaymentAttempt` and `PaymentRefund` ledgers now derive from `CatalogItem` and their stores (`IPaymentAttemptStore` / `IPaymentRefundStore`) build on the shared `DocumentCatalog<T, TIndex>` base, so they inherit the same CRUD, paging, index registration (`PaymentAttemptIndex` / `PaymentRefundIndex` keyed on `ItemId`), and `IClock`-driven timestamping used everywhere else in the solution instead of a bespoke store. The business identifier on every commerce value object and ledger entry — `BillingItem`, `CheckoutLineItem`, `InvoiceLineItem`, `PaymentAttempt`, and `PaymentRefund` — is now named **`ItemId`**, freeing the `Id` name for the YesSql document identity and matching the naming convention used across the rest of the platform.
- **Products sellable seam.** `ProductPart` gains an optional **`Sku`**, and a new `ISellableProduct` snapshot with `IProductSnapshotResolver` captures what was purchasable at the moment of purchase (money as `decimal`), so an order of record is stable and self-contained. `ProductPart` and its settings now live in **`CrestApps.OrchardCore.Products.Core`**, so the sellable catalog contract can be referenced by other modules without depending on the Products module's UI and services. YesSql keys content parts by CLR type *name*, so relocating the namespace does not affect stored content. The catalog stays purchase-agnostic: the Products assemblies never reference Payments or Checkout (enforced by an architecture guard test), so payment and checkout depend on the catalog and never the other way around.
- **Product-owned currency and pricing seam.** A product now owns the currency it is sold in: `ProductPart` gains a **`Currency`** and `ProductPartSettings` a **`DefaultCurrency`** fallback, so a price is no longer implicitly tied to a single site currency. A new **`IPriceResolver`** resolves an immutable, currency-tagged **`PriceResult`** (unit price, currency, quantity, and subtotal) from a `ProductSnapshotContext`, giving checkout, payment, and future ordering flows a stable seam instead of reading `ProductPart.Price` directly. The default resolver never converts between currencies — a requested currency that differs from the product's currency is rejected (returns `null` and logs a warning) rather than silently priced with an implied exchange rate — so a future pricing engine (price schedules, quantity breaks, or customer-specific pricing) can replace it without changing any consumer. Every currency-consuming path now derives its currency from this one seam: `PriceResult` refuses to be constructed without a currency, the taxable-item projection stamps each item with the product-owned currency and the tax service rejects an item whose currency differs from the calculation context (never converting), and subscription billing — both the invoice currency and Stripe price synchronization — bills in the product-owned currency and skips (with a warning) any request to relabel it into a different currency, so no path can silently apply an implicit exchange rate.

### Addresses

A new provider-agnostic **`CrestApps.OrchardCore.Addresses.Abstractions`** project now owns the shared `Address` model — the recipient name and company, both street lines, country, region, county, city, district, postal code, and delivery phone — used across the commerce stack. Taxation, Checkout, and Subscriptions consume this shared abstraction instead of each carrying their own address type, so a single address contract is reused wherever a postal or geographic location is needed (for example tax jurisdiction resolution). The flat `Address` is a money-safe value snapshot: once captured on an order or shipment it is never mutated by a later edit to the content item it was resolved from, and it carries the complete postal contract so an order billing/shipping snapshot needs no second lookup.

This release also adds the **[Addresses](../modules/addresses)** module (`CrestApps.OrchardCore.Addresses`), which models every geographic component of an address &mdash; except the postal code &mdash; as managed content:

- A complete geographic content-type hierarchy: **Country**, **Region**, **County**, **City**, and **District** (with `CountryPart`, `RegionPart`, `CountyPart`, `CityPart`, and `DistrictPart`). Each geographic part standardizes on a money-safe **`Code`** field, and each type references its parent (region → country, county → region, city → region with an optional county, district → city).
- A reusable, attachable **`AddressPart`** you can add to any content type that needs a postal address. It captures the recipient name, company, both street lines, phone, and postal code as text and every geographic component (country, region, county, city, district) as a content-item selector, and `IAddressResolver` preserves all of them on the resolved flat `Address`.
- An **`IAddressResolver`** that reduces an `AddressPart` to the flat, money-safe `Address` model (each selector resolved to its stable `Code`, or its display name as a fallback), so Taxation, Checkout, and Subscriptions keep operating on the string-based `Address` contract without ever storing a content item id.
- The canonical country list is **seeded on enable** as `Country` content items, so administrators manage countries, regions, counties, cities, and districts through the standard content management experience.
- A content-backed **`ICountryService`** populates country selectors across the platform (for example the taxation jurisdiction editor) from the managed `Country` content, indexed by the shared `GeographicAreaIndex`, and falls back to the canonical ISO list when no country content exists. When the feature is disabled, the default `ICountryService` returns the canonical list. Taxation keeps storing the ISO alpha-2 code, so enabling or disabling the feature never orphans existing tax jurisdictions or rules.
- A single **`GeographicAreaIndex`** covers all five geographic content types. Each row records the content type, money-safe code, parent reference, display name, and published/latest flags, powering country selectors, ISO code uniqueness, cascading parent/child lookups, and address resolution without loading full content items.

### Receipts

A new reusable **[Receipts](../modules/receipts)** module (`CrestApps.OrchardCore.Receipts`) turns purchase data into a branded, printable proof-of-purchase receipt that any module can consume. A consumer supplies only what it knows (billed-to party, line items, taxes, total, and payment status) through a `ReceiptRequest`, and `IReceiptService.BuildAsync` merges the tenant's configured issuer branding and computes the subtotal to produce a `ReceiptDocument`.

- Provider-agnostic abstractions (`ReceiptRequest`, `ReceiptDocument`, `ReceiptLineItem`, `ReceiptTaxLine`, `ReceiptStatus`, `ReceiptSettings`, `IReceiptService`) depend on nothing commerce-specific, so subscriptions, future e-commerce, and other modules can reference them without pulling in payments, checkout, or taxation.
- Branding is configured once under **Settings → Commerce → Receipts** (header title, business name, logo, address, contact details, footer, and a test-payment badge toggle), guarded by the **Manage receipt settings** permission.
- The module ships a self-contained, printable receipt view that consumers render with a full-path partial (`~/Areas/CrestApps.OrchardCore.Receipts/Views/ReceiptDocument.cshtml`), so every receipt looks the same while each consumer owns its surrounding page. Printing a receipt outputs only the receipt itself — the surrounding page chrome (site header and admin menu) is suppressed by the print stylesheet.
- The module holds **no persistence** of its own: receipts are generated on demand from the consumer's own ledger, so there is no duplicated financial store. **[Subscriptions](../modules/subscriptions)** now renders its subscriber payment receipt through this module instead of carrying its own receipt view model and view.

### Wizard

A new reusable **[Wizard](../modules/wizard)** module (`CrestApps.OrchardCore.Wizard`) provides a decoupled, multi-step **wizard** (stepper) framework that any guided experience can build on — sign-up, onboarding, surveys, checkout, and more.

- **Two consumption models over one engine.** Build a wizard **via content items** by enabling **Wizard Contents** and attaching the `WizardPart` to a content type (steps are contained content items, authored just like the `OrchardCore.Flows` `BagPart`, with part settings to constrain allowed step types by content type or stereotype and a selectable editor), or **via code** by registering an `IWizardDefinition`, an `IWizardHandler`, and an `IDisplayDriver<WizardFlow>`. Both share the same flow engine, session store, public host controller, and workflow events.
- **Production-hardened completion.** Finalization runs through `IWizardEngine.CompleteAsync`, which serializes completion for a session under a distributed lock, reloads the authoritative session, verifies every data-collecting step has data, and runs the completing/completed handlers **exactly once** even under concurrent or repeated attempts. An optional `prepareUnderLock` callback lets a consumer validate and record external evidence (for example a payment return) inside the same lock before the wizard is finalized.
- **Workflow integration.** Enable **Wizard Workflows** to raise **Wizard Started**, **Wizard Step Displayed**, **Wizard Completed**, and **Wizard Failed** events, each with an optional wizard-type filter and correlated by session id.

See [Wizard](../modules/wizard) for details.

## Breaking Changes

### Subscriptions

- **The session-based subscription signup flow has been removed.** Buying a plan now runs through the [Checkout](../modules/checkout) framework like any other purchase, so there is one path that takes money and one ledger that records it. The public route is unchanged — `Subscription/Signup/{contentItemId}` still starts a purchase — but everything behind it is different, and a signup that was in progress when the site was upgraded cannot be resumed.

  Removed with it: `SubscriptionFlow` and its handler contexts, `ISubscriptionHandler`, `SubscriptionSession` and `ISubscriptionSessionStore`, the anonymous Stripe and Pay Later signup endpoints, the hosted-checkout return route, the subscription session admin list, the subscriber dashboard, `StripePriceSyncService` and the **Sync prices** screen, and `PaymentMethodOptions` / `PaymentMethod`. Payment methods are now discovered from the `ICheckoutPaymentProvider` implementations registered on the tenant, so the payment step can never offer a method the framework cannot execute.

- **Two sub-features were removed.** *Subscriptions - reCaptcha* guarded a step that no longer exists. *Subscriptions - Tenant Onboarding* is replaced by **Subscriptions - Sites** (`CrestApps.OrchardCore.Subscriptions.Tenants`), which provisions from a durable job instead of inline during the request that took the money. Sites already provisioned by the old feature keep running; re-enable the new feature to sell more.

- **The default payment method moved.** It is configured under the Checkout settings rather than the Subscription settings, because it applies to every purchase and not only to subscriptions.

- **Subscription reports now read the payment ledger and the durable agreement** instead of checkout sessions, and revenue is reported per currency instead of being summed into a single site-currency total. Figures will differ from 3.0 previews wherever a checkout was abandoned or failed: those were previously counted as revenue and no longer are.

### Configuration and options

Several site-settings screens no longer **release the tenant shell** when you save them. Instead, the options class that projects those settings is refreshed live through `IOptionsMonitor<TOptions>`, using Orchard Core's options update-notifier (`IOptionsUpdateNotifier.RequestUpdate<TOptions>()` and `services.AddSignalOptionsChangeTokenSource<TOptions>()`, introduced in `OrchardCore` `4.0.0-preview-19118`). Saving these settings now takes effect without restarting the tenant, and the "the tenant will be reloaded" warning has been removed from the affected editors.

The options classes changed this way are: `GeneralAIOptions`, `AIDataSourceOptions`, `McpServerOptions`, `AIMemoryOptions`, `ChatInteractionMemoryOptions`, `UserAvatarOptions`, and the telephony provider options `TelnyxOptions` and the shared `TelephonyProviderOptions` aggregate (which the Telnyx and Asterisk provider modules contribute to).

**Breaking:** `IOptions<TOptions>` resolves a process-lifetime singleton that is computed once and never observes the update signal. Any custom or external code that read one of the options above through `IOptions<TOptions>` will keep serving the value captured at first resolution and no longer pick up a settings change until the process restarts. Such code must switch to `IOptionsMonitor<TOptions>` and read `CurrentValue` (or `IOptionsSnapshot<TOptions>` in a scoped context) to observe live updates.

Settings whose consumers still read them through a singleton `IOptions<TOptions>` — currently the anonymous **AI Visitor Identity**, **Prompt Security**, and **AI Documents interaction** settings, whose readers live in the `CrestApps.Core` packages — continue to release the shell on save until those consumers are migrated to `IOptionsMonitor`.

### AI

- **The MCP Server no longer exposes tools by default.** Previously every registered AI tool was listed and callable by any connected MCP client. Tool exposure is now **opt-in**: nothing is listed or callable until you either select the tools and tool instances on the new **MCP Server** card under **Settings → Artificial Intelligence**, add their names to `McpServerOptions.Tools`, or set `McpServerOptions.ExposeAllTools` to `true`. **Expose all tools** now exposes only *selectable* tools; system tools and hidden tools are never exposed, even when it is enabled. Deployments that relied on the previous "expose everything" behavior must enable **Expose all tools** (or populate the allow-list) to keep exposing their tools. Prompts and resources are unaffected. See [MCP Server](../ai/mcp/server#tool-exposure) for details.
- **A2A host cards now use A2A 1.0 supported interfaces.** Agent cards no longer publish the endpoint through the deprecated top-level `url` field. Clients should read the endpoint from `supportedInterfaces`, and multi-agent mode still points each interface to `/a2a?agent={agentName}`. See [A2A Host](../ai/a2a/host) for details.
- **The deployment purpose is gone; deployments declare model capabilities.** `AIDeploymentPurpose` and `AIDeploymentType` were removed from the framework, along with `AIDeployment.Purpose`, `AIDeployment.Type`, `SupportsPurpose`, `SupportsType`, `CanServeTextCompletion`, and the purpose overloads on `IAIDeploymentManager`. A deployment now says what its model can do (a **capability**), and where it gets used is a **slot** resolved from site settings and the selection on the profile, template, or interaction. `GetByPurposeAsync` / `GetAllByPurposeAsync` become `GetAllBySlotAsync`, and `ResolveOrDefaultAsync(purpose, …)` becomes `ResolveSlotAsync(AIDeploymentSlotNames.X, …)`.
  - The **Purposes** checkbox group is removed from the deployment editor. **Model capabilities** is the single place a deployment describes itself, and at least one is now required. The deployment list shows capabilities in place of purposes.
  - **Stored data needs no migration.** A record that still carries a `Purpose`, `Capability`, or `Type` — in the store, in a recipe, or in `appsettings.json` — is projected onto capabilities every time it is read. The projection is permanent, not a one-time upgrade step.
  - A deployment that had never declared capabilities used to be shown an *empty* capability list when opened, and saving anything unrelated wrote `Features = []`, silently turning it from *unconstrained* to *declares nothing*. It is now offered the defaults, which is how it already behaves at run time.
- **`ChatMode.Realtime` and the separate realtime deployment field are removed.** Whether an AI profile or a chat interaction is a speech-to-speech conversation now follows from its **chat deployment** declaring the `realtime` capability, rather than from a second stored answer that could disagree with the deployment actually selected. This is how chat interactions already worked; AI profiles now match.
  - The chat deployment picker lists text-capable **and** realtime-capable deployments; the utility picker stays text-only.
  - The **Chat mode** selector and the **text-to-speech playback** switch are hidden when the selected chat deployment is realtime, and the **Voice** picker switches to that deployment's realtime voices.
  - A site can no longer force realtime globally through the chat interaction chat mode.
  - **Stored data needs no migration.** A profile that named a `RealtimeDeploymentName` folds it onto `ChatDeploymentName` when read, and its old chat deployment moves to `UtilityDeploymentName` when the profile has not named one — so background work keeps running on the model it always did. A stored `ChatMode` of `"Realtime"` reads as `TextInput` instead of failing the settings load. `ProfileTemplateMetadata.RealtimeDeploymentName` is obsolete and still applies, supplying the chat deployment.

  See [Model Capabilities](../ai/model-capabilities) and [Realtime Voice](../ai/realtime-voice) for details.
- **One chat thread now carries both typed messages and a spoken conversation.** Pointing a profile at a speech-to-speech model used to turn the whole surface voice-only: the message box was hidden and typed messages were rejected. The chat deployment goes back to meaning only "the text model this profile talks to", and a new **Conversation deployment** names the model that carries a spoken conversation. A surface in the **Conversation** chat mode offers a voice toggle *beside* a working message box, and the user decides turn by turn which to use.
  - `ChatModeProfileSettings.ConversationDeploymentName` and `ChatInteraction.ConversationDeploymentName` name that model. Left empty, the realtime slot's own chain applies — the site's default realtime deployment, then the first realtime-capable deployment. Nothing records *how* the conversation is carried: whether the resolved deployment speaks natively or chains speech-to-text, chat, and text-to-speech is read off the deployment itself.
  - The **Chat deployment** picker lists text-capable deployments only, on the profile editor, the AI Profile Template editor, and the chat interaction settings panel. A speech-to-speech model belongs in the **Conversation deployment** picker beside it.
  - The **Chat mode** selector and the **text-to-speech playback** switch no longer disappear when a realtime model is selected, because the deployment no longer decides the mode. **Conversation** is offered whenever either a realtime deployment or the speech-to-text plus text-to-speech cascade can serve it.
  - While a voice session runs, the message box and send give way to the voice settings and the **End Conversation** button takes the width they leave; they come straight back when it ends. Sending a typed message ends the session first, so the two kinds of turn take turns rather than overlapping. The dictation microphone is suppressed while a realtime session carries the conversation, which already owns the microphone.
  - A chat interaction has no chat mode of its own, so naming a conversation deployment on the interaction is itself the opt-in to speaking.
  - Because the chain falls through to the first realtime-capable deployment, a site with *any* such deployment will carry conversations with it even with no site default configured and nothing named on the profile. There is deliberately no per-profile switch back to the cascade: to keep the cascade, have no deployment declare `realtime`; to speak without a speech-to-speech model, use a cascaded realtime deployment.
  - A conversation deployment that is named but cannot run a realtime session is reported rather than quietly replaced, so a typo does not silently move the conversation to a different model.
  - **Stored data needs no migration.** A profile stored in the old shape is folded when the editor reads it: its realtime chat deployment is shown as the **Conversation deployment** with the chat mode set to **Conversation**, and saving the profile persists that shape. Nothing is rewritten behind the user's back. `ProfileTemplateMetadata.RealtimeDeploymentName` is obsolete and still applies, now supplying `ConversationDeploymentName` and putting the generated profile in **Conversation** mode.

  See [Realtime Voice](../ai/realtime-voice) for the full resolution order.

### AI

#### Every AI request is metered, per model, category and purpose

The **AI Usage Analytics** report has a new **Metered usage** table that counts every request sent to an AI
provider, whatever the provider and whatever the kind: chat completions, embeddings, images, speech-to-text,
text-to-speech and realtime voice. Before, only chat completions were recorded.

- **One row per request.** Planning, search-query rewrites, image descriptions, each step of a tool-calling loop
  and each batch of embeddings are counted on their own, so the request count matches what the provider billed.
- **Every billable unit.** Cached input, reasoning and audio tokens are kept apart from plain tokens, with audio
  minutes for transcription, characters for text-to-speech and images for image generation.
- **Group metered usage by** **Model**, **Model and category** (chat sessions, chat interactions, `Sms`, `Voice`,
  `Api`, `Workflow`, `A2A`) or **Model and purpose** (answering, planning, retrieval, indexing, transcription,
  conversation conclusions, handoff summaries and more). A module labels its own requests with
  `UseUsageLabels(...)` on the client it creates, or with an `AIUsageScope`.
- **Voice calls show their audio tokens.** The realtime provider's usage is now recorded, so the voice table fills
  its **Audio tokens** column, and **Text tokens** include the text part of realtime responses.
- The **Chat completions** table now counts only chat completions; the embeddings and voice requests made for the
  same sessions are in the metered table.

Requires the CrestApps.Core release that meters every AI client. See
[AI Usage Analytics](../ai/usage-analytics.md#metered-usage).

#### The AI profile and template editors group the model with how it is spoken to

The **Deployments** card on the AI Profile and AI Profile Template editors is now **Deployments &
Interactions**, and the **Chat mode**, **Voice**, and **Enable text-to-speech playback** fields move into it
from the *General* card. They sit directly under the chat deployment and its model parameters, because the
chat deployment is what decides whether they apply at all — with the fields a card away, selecting a
realtime model made three fields vanish off-screen. The card now reads in one pass: chat deployment, its
model parameters, how you converse with it, then the utility deployment and its parameters. Chat
interactions already grouped these in their settings panel and are unchanged.

#### Stored deployments are rewritten to declare their capabilities

A new migration step persists the model capabilities implied by each stored deployment's legacy purpose, so
the stored JSON says what the editors and the deployment list already show, and the dead legacy field stops
being carried around. Deployments that come from configuration are untouched, being read-only and outside
the store.

**A chat or utility deployment is migrated with `textGeneration`, `toolCalling`, and `streaming`.** The
framework's read-time projection maps those two purposes onto `textGeneration` alone, because they are the
only purposes that never named a single capability. In practice a deployment on the legacy purpose was
driven through a chat client that called tools and streamed its response, with no switch to turn either
off — so declaring text generation by itself would migrate a working site into one where tools and streamed
responses are silently disabled. The migration credits all three. Anything a particular model cannot really
do stays one checkbox away in the deployment editor.

Every other purpose still maps onto the one capability that named the same thing: `Embedding` to
`textEmbedding`, `Image` to `imageOutput`, `Vision` to `imageInput`, and so on. A deployment that already
declares `realtime` is left alone: it is a speech-to-speech model stored under the chat purpose, it answers
a text completion with an HTTP 400, and the purpose says nothing about it beyond that it is conversational.

Recipe, configuration, and API imports that still carry a legacy `Purpose`, `Capability`, or `Type` are
credited the same way, so an imported deployment and a migrated one end up declaring the same set.

### Reports

- `ReportFilter` no longer exposes `FromUtc`, `ToUtc`, or `DateRangeKey` as first-class properties, and `ReportContext` no longer exposes `FromUtc` or `ToUtc`. The date range is now contributed and stored like any other filter, so reports that do not need a date selector can omit it. Read and write the period through the new `ReportFilter` helpers (`GetDateRange()` / `SetDateRange()` — for example `context.Filter.GetDateRange()` inside a report), and read or write any filter value with the typed `TryGet<T>(string key, out T value)`, `GetOrDefault<T>(string key)`, and `Set<T>(string key, T value)` extension methods.

### Telephony

The following public contracts changed in the Telephony module and its abstractions. External providers and callers that build on these types must update to the new signatures.

- The `CrestApps.OrchardCore.Telephony.Admin` feature has been removed. The provider settings screen and administration menu are now part of `CrestApps.OrchardCore.Telephony`, and provider features register their settings drivers directly. Remove the old feature ID from recipes and deployment plans.
- `TelephonyConstants.Feature.Admin` has been removed. Use `TelephonyConstants.Feature.Area` when declaring a dependency on Telephony.
- The public `TelephonyAdminStartup` and `AsteriskAdminStartup` classes have been removed because their registrations now live in each module's primary `Startup` class.
- `ITelephonyAuthenticationProvider.RevokeTokensAsync` now returns `Task<TelephonyResult>` instead of `Task`. Callers receive a typed confirmed-success, definitive-failure, or indeterminate result instead of relying on an exception or assuming success. External implementations of this interface must update their signature.
- `ITelephonyAuthenticationService.DisconnectAsync` now returns `Task<TelephonyResult>` instead of `Task`, for the same reason.
- `RecordingMediaWriteRequest.Content` is now a `System.IO.Stream` instead of a `byte[]`, so recording media streams to storage rather than being buffered in memory. Any code that constructs this request directly must supply a stream.
- `ITelephonyUserAccessor` exposes `ReloadCurrentUserAsync()` and `PersistCurrentUserAsync(Func<IUser, bool> mutate)`. The persist method loads the current user in an isolated unit of work, applies the mutation, and durably commits only that user document, so a serialized token refresh or a disconnect makes its write visible to other requests without flushing unrelated changes staged by the ambient request. Custom implementations of this interface must implement these members.

## Change Logs

### A working checkout

The Checkout framework shipped its contracts, durable ledgers, reconciliation, and refund machinery, but nothing drove them: no component created a payment attempt, called a provider, or moved a session out of `Pending`. The generic Stripe card provider, the Pay Later provider, and the refund service were all registered and unreachable, and the *Pay* action on an outstanding transaction started a checkout there was no page to complete. This release makes the framework real.

- **A checkout engine.** `ICheckoutEngine` is now the single entry point for every money-moving step — start, begin payment, complete, cancel. Controllers, endpoints, webhooks, and background tasks all go through it and never touch a payment provider or the ledger directly. It creates one durable attempt per obligation, persists each **before** contacting the provider, stores the provider's reference the moment it returns, and completes a checkout only when every obligation is confirmed against the provider's own API.
- **A public checkout.** Enabling the feature adds a customer-facing checkout at `/Checkout/{sessionId}/{step}` with a progress stepper, an invoice summary, payment-method selection, and a confirmation page. Steps are contributed by display drivers, so a feature adds a step without touching the page, and a theme can restyle the whole frame by overriding one shape.
- **Payment methods come from the registered providers.** The payment step lists the providers actually registered on the tenant and hides any that cannot settle what the invoice owes, so the page can never offer a method the framework is unable to execute. Stripe contributes an embedded card panel and Pay Later an offline confirmation panel, each through its own display driver.
- **Completion no longer blocks a request.** It previously polled the provider for up to 60 seconds inside the web request. Completion is now a fast, idempotent call driven from three directions — the customer's browser, a provider webhook, and the reconciliation sweep — so a customer who pays and then closes the browser still has their purchase fulfilled, server-side.
- **Compensation.** When one obligation fails at the provider, the obligations that already settled are refunded through the durable refund service, so a customer is never left paying for half a purchase.
- **Settling a balance online works.** Choosing *Pay* on an outstanding transaction now takes the customer into the checkout with the balance already loaded, instead of returning them to a page that could not collect it.

Subscriptions still runs its own signup pipeline and does not yet start every purchase through the engine; a subscription bought through the public checkout, however, now produces a durable agreement.

### Recurring payments are real agreements

A recurring line on an invoice used to become a single charge. The customer paid once, nothing renewed, and nobody found out until the money stopped arriving.

- **A recurring capability.** A payment provider that bills on a cycle now implements `ICheckoutRecurringPaymentProvider` under its own provider key. The checkout groups the recurring lines by interval, makes one obligation of each, and routes it there. A provider that claims recurring support but ships no implementation is refused before any money moves, so a wiring mistake cannot turn a subscription into a one-off charge.
- **Stripe subscriptions at any price point.** The Stripe adapter creates a real Stripe subscription with the price defined inline, so nothing has to be synchronized to Stripe before it can be sold; per-customer, computed, and one-off amounts all work. Verification reads the subscription's latest invoice back from Stripe, so an agreement only settles once its first cycle is genuinely paid, and rolling back a checkout cancels the agreement rather than leaving it billing.
- **Card details still never reach the site.** A gateway cannot create an agreement without a reusable payment method, so a provider's client script may tokenize the card in the browser first and hand back only the token. The first invoice is then confirmed against that very payment method rather than attaching a second one.
- **Pay Later can back a subscription too.** An offline recurring commitment records its own schedule on the ledger, and a sweep invoices the next period once the current one ends. Each cycle is created exactly once even across retries and multiple nodes.

### Subscriptions that outlive their checkout

A completed checkout used to be the only record that somebody had subscribed, which made every ordinary question expensive: who is subscribed right now, whose payment failed last night, what renews next month.

- **A durable subscription agreement.** Every recurring obligation a checkout settles now creates an agreement carrying what it bills, on what cycle, through which gateway, the period paid through, when the next cycle is due, and a full event history. It is created only from payment attempts the checkout actually confirmed, and looked up by obligation first, so an unpaid checkout never grants access and a checkout that completes twice never produces two agreements.
- **One place state changes.** A gateway webhook, a nightly sweep, an administrator, and the customer all edit subscription state, and they race. Every transition now goes through one lifecycle service that locks the single agreement, re-reads it, and is idempotent. Reporting the same renewal twice advances it once; a second payment failure inside the same dunning window does not restart the grace clock; a gateway status arriving after a local cancellation cannot revive it.
- **Access outlives cancellation.** Whether a subscriber currently has access is answered separately from the status, so a customer who cancels mid-cycle keeps the time they paid for and a past-due one keeps access through the configurable grace window (7 days by default).
- **A sweep that closes the loop.** Agreements whose grace window elapsed are expired, and those that billed every cycle they were sold for are closed, so nothing sits past due forever or looks due to bill something it must not.
- **Screens for both sides.** Administrators get a **Commerce → Subscriptions → Agreements** report with cancel, pause, and resume actions, each written to the agreement's history. Subscribers get **My Plans**, where they can cancel their own subscription; cancelling defaults to ending at the close of the period they already paid for.

### Payments and refunds an operator can see

Every charge already left a durable record, but there was no way to look at one. An operator asked whether a customer had paid had to read the database, and a refund that a payment method could not settle automatically sat in the ledger with nobody to act on it.

- **A payments ledger.** **Commerce → Payments** lists every attempt with what was expected, what settled, and the gateway's transaction reference, filtered by state and method.
- **Refunds start in one place.** The refund form shows what was collected and what has already gone back, refuses an amount above what is still refundable, and issues the refund through the refund service so the ledger, the original payment's tax allocation, and the over-refund protection all apply. An in-flight refund counts against the remaining amount, so a second refund cannot be started for money already on its way back.
- **Manual settlements have a home.** **Commerce → Refunds** surfaces refunds needing manual settlement and lets an operator record the reference once they have moved the money. Only a refund in that state can be closed that way.
- **A separate permission.** Giving money back is the one action in the suite that cannot be undone, so it needs **Manage payments and refunds** rather than coming free with the ability to read the outstanding report.

### Subscriptions can grant member-only access

A subscription used to be a billing record and nothing more: somebody paid and nothing about the site changed for them, and somebody stopped paying and kept everything.

- **Entitlements on the plan.** Attach the **Subscription Entitlements** part to a plan and pick the roles a subscriber holds. The entitlement lives on the plan because different tiers grant different things, and what it grants is copied onto the subscription at creation so editing the plan later cannot change what an existing subscriber was sold.
- **Access follows the agreement, not the status.** The role is granted while the subscription is *current* and removed when it stops being current. A subscriber who cancels mid-cycle keeps it through the period they paid for, and one whose renewal failed keeps it through the grace window.
- **A question the rest of the site can ask.** `ISubscriptionAccessService` answers whether a user currently holds an entitlement, so content, features, and permissions become subscription-aware without any of them knowing subscriptions exist. Implement `ISubscriptionEntitlementApplier` to grant something other than a role.

### Workflow events for the whole subscription life

Subscription lifecycle events — started, renewed, past due, canceled, expired — are now raised as workflow
events, so a site owner builds the reaction they want without writing code. Each carries the subscription,
its owner, both statuses, and the dates access depends on, and is correlated by the subscription so one
workflow can wait for a later stage of the same agreement. Only a genuine status change raises an event,
so a sweep that only moves dates does not message anyone.

### A Commerce starter recipe

A **Commerce starter** recipe enables the suite, creates a `Member` role, defines a Membership Plan content
type, and publishes a monthly plan that grants that role, so a new site can take a real recurring payment
without wiring anything by hand. Each of the seven Commerce modules also gained a README explaining what it
is for and which decisions it makes on the caller's behalf.

### A site sale that survives a restart

Selling an Orchard Core site used to create the tenant inline, in the request that completed the checkout. A slow recipe, a brief database outage, or a deployment restarting the process left a customer who had paid with no site and nothing to retry.

- **The purchase and the build are now separate.** The checkout records a durable provisioning job; a sweep builds the site from it and keeps trying. A job stranded by a process that died is reclaimed rather than lost.
- **Everything the customer can fix is checked before payment.** A site name that is taken, a domain that belongs to another site, a prefix already in use: all are refused while they can still change them, instead of after their card is charged.
- **Failure is visible and finite.** Each attempt records its error and backs off; after enough failures the job is marked abandoned rather than retried forever, and appears on an admin screen where an operator can retry it. Customers watch their own site being built under **My Sites**.
- **The site follows the subscription.** A site sold on a plan is disabled when the subscription lapses and runs again when it resumes. Disabled, never deleted, so a late payment restores the site exactly as it was.

### Coupons, and discounts that are taxed correctly

- **Discounts run before tax.** Taxing the full price and discounting the total charges the customer tax on money they never paid. `ICheckoutDiscountService` applies reductions to the untaxed invoice, keeps a total from going below zero, and reduces the one-time amount and the first cycle separately so a setup-fee coupon never eats a monthly charge.
- **A coupon catalog.** Percentage or fixed amount, targeting the one-time amount or the first cycle, with a validity window, a minimum, and a usage limit. A fixed-amount coupon only applies in its own currency.
- **A code is consumed on purchase, not on entry.** A customer who applies a single-use code and abandons the checkout does not burn it, so a leaked code cannot be exhausted by people who never bought anything. Redemption takes a lock, so two checkouts finishing together cannot both take the last one.

### Fixes found by running the checkout

Standing the suite up and buying something surfaced defects that no unit test could see, because in each case the page returned `200` and simply did the wrong thing:

- **A concealed step's charges vanished from the invoice.** The plan a subscriber chose is billed on a step that is never drawn, and the invoice was built only from visible steps, so a subscription checkout totalled `0.00` and completed for nothing.
- **Three catalogs had no database table.** Subscriptions, coupons, and site-provisioning jobs each live in their own YesSql collection, and a collection's document table is only created when the collection is declared in `StoreCollectionOptions`. Their index migrations ran clean and the first read threw *no such table*.
- **Five editors rendered as empty boxes**, including the payment method list — the one thing a customer needs in order to pay. Orchard Core builds a shape by deriving a proxy from the view model, a sealed model cannot be derived from, and the resulting `TypeLoadException` is swallowed by the display manager.
- **The checkout's scripts never loaded.** `OrchardCore.ResourceManagement` is not a transitive dependency of `OrchardCore.DisplayManagement`, so `<script asp-name>` rendered as literal markup and the payment page had no behaviour at all.
- **Two admin screens threw on their first page load** because a partial view sat in `Views/` rather than `Views/Shared`.
- **A promotion code was silently ignored.** The payment script owns the form's submit, so a code typed into the box was never posted and the customer was charged full price with no error shown.
- **The guards that stop payment being reached early never ran.** `Initializing`, `Loading` and their pairs were declared on `ICheckoutHandler` but never raised by anything.

Each of these now has a regression test, including two that read the source tree so a missing collection declaration or a missing package reference fails the build rather than a customer's purchase.

### One product, several prices

A product carried a single amount, so selling the same thing monthly and annually, per seat, or for
whatever the buyer thinks it is worth meant creating a separate product for each.

The new **Product prices** part offers a product at as many prices as it needs — one-time or recurring,
each with its own interval, cycle limit, trial, start delay, setup fee, optional buyer-named amount within
bounds, optional quantity, and an availability window. A recurring price is what makes a product
subscribable, so the same product can offer a one-time purchase and a monthly plan side by side. A product
with no prices of its own is still sold at the single amount on its product part, so the part is opt-in.

The plan card becomes a chooser when there is a choice to make and stays a single button when there is
not, and the chosen price rides on the checkout rather than the request — a checkout outlives the request
that began it, and a purchase completed by a provider notification has no browser to re-read a query string
from. Nothing the buyer sends is trusted: a withdrawn price, an amount outside the bounds, and a quantity
beyond the maximum are each refused when the price is resolved, not only in the editor.

At Stripe a fixed price now becomes one reusable price identified by a key that includes the amount, so the
same offer is not recreated for every customer, and raising a price creates a new one instead of silently
repricing everyone already subscribed to it. An amount the buyer named has no reusable offer behind it and
stays inline.

### The payment ledger moved to Transactions

The durable record of payment attempts and refunds lived in Checkout while the module that reports on it,
settles from it, and administers it is Transactions. The ledger types now live where they are owned, and
the dependency points one way: the checkout writes to the ledger, and the ledger knows nothing about the
checkout. The financial-document contracts moved with it — a receipt or invoice number belongs to the
ledger that issues it — which emptied `CrestApps.OrchardCore.Commerce.Abstractions`, so that package is
gone.

This is a namespace move: `CrestApps.OrchardCore.Checkout.Models.PaymentAttempt` and friends are now
`CrestApps.OrchardCore.Transactions.Models`, and the stores and indexes are under
`CrestApps.OrchardCore.Transactions.Core`. Nothing about the stored data or the tables changed.

### Fixes found by selling a site

Selling an Orchard Core site through the checkout was then run end to end on a live installation: a plan
carrying the tenant-onboarding part, a buyer naming their site and its administrator, a real card, and the
provisioning sweep building the tenant. Two defects made the feature impossible to use at all:

- **A purchased site could never be created.** Nothing gave the new tenant a database, so setup refused every
  attempt with *"DatabaseProvider setting is required"* — the customer was charged and no site ever appeared.
  The database new sites are created on is now configured once under **Subscriptions → Tenant onboarding**,
  and defaults to Sqlite so that selling a site works before anything is configured. Sites that share a
  database each get a table prefix derived from their name.
- **A job that failed once could never succeed.** Setup registers the tenant before it creates anything, so a
  failed attempt left the name behind in the running process, and every retry then failed with a name
  collision the previous attempt had invented. An uninitialized shell left by a failed attempt is no longer
  read as a name that is taken.
- A setup failure reported as a message rather than an exception left nothing in the log, and the job keeps
  only the newest message — so the first attempt's reason, usually the real one, was lost. Every failed
  attempt is now logged with its own reason.

### Fixes found by running the integration against Stripe

The commerce suite was then exercised against a real Stripe test account, including Stripe test clocks to
advance time through real billing cycles. That confirmed the money paths end to end — a trial that collects
nothing and converts when it ends, a fixed-cycle plan that stops after the cycles it was sold for, a
first-cycle coupon that does not recur, a renewal recorded from the gateway's own notification, a failed
renewal that starts dunning, and a refund — and it found four defects that no test with a fake gateway could
have shown:

- **A plan with a setup fee could not be paid by card at all.** The browser tokenizes one card for the whole
  checkout and confirms both obligations with it, but the one-time payment intent was created with no
  customer, while the agreement had attached that card to one. Stripe refused the confirmation outright:
  *"the payment_method supplied belongs to the Customer …"*. The two obligations of a checkout now resolve a
  single customer, keyed by the checkout, and the client data the recurring path already received now
  reaches the one-time path too.
- **Cancelling never reached the gateway.** `CancelRecurringAsync` was implemented by both providers and
  called by nothing at all, so a subscriber who cancelled saw their subscription end, lost access at the end
  of the period, and kept being charged every month. Cancelling — at period end or immediately — now stops
  billing at the gateway.
- **Suspending an agreement did not suspend billing.** The admin reported "billing was suspended" while the
  gateway kept collecting. Pausing and resuming now reach the gateway, through a new provider capability
  that Stripe implements with `pause_collection` and offline providers satisfy locally.
- **A gateway notification could quietly undo a local suspension.** A gateway that suspends collection still
  reports the agreement as *active*, so the next synchronization read that as "resumed" and put it back on
  the schedule. A local suspension, like a local cancellation, is now treated as a decision the gateway
  cannot express. Synchronizations also name the gateway they came from, so a change the gateway reported is
  never sent back to it.

### Fixes from an independent review of the implementation

Reading the finished code against the plan, rather than against the intent, found a second set of defects. None of these were visible in the browser, because each shows up only over time, at a gateway, or under failure:

- **A free trial could never complete.** The gateway honestly reported zero collected, and reconciliation refused it for falling short of the cycle amount. A deferred first cycle now expects nothing, so a trial settles; the gateway is still told the real price and the deferral.
- **First-cycle coupons were display-only.** The attempt and the Stripe price were both built from the undiscounted line, so the customer saw a discount and paid full price. Worse, the recurring price was derived from the first attempt, so a discount that had applied would have recurred forever. The recurring price now comes from the plan's cycle amount; the first-cycle reduction is expressed at Stripe as a single-use coupon and locally as a smaller first debt.
- **Billing-cycle limits were ignored at Stripe** for inline prices, so a plan sold as "three cycles" billed until the customer cancelled. Inline agreements now carry a `cancel_at` for the end of the last cycle.
- **Gateway renewals never advanced the local agreement.** `invoice.payment_succeeded` for a cycle now records the renewal against the period the gateway named, idempotently.
- **Offline agreements were never renewed.** Pay Later's sweep created the next debt but nothing moved the agreement; the lifecycle sweep now advances any agreement whose provider has no gateway, and converts an ended offline trial into its first billed cycle.
- **Webhook and sweep completion was blocked for signed-in buyers**, because the account step decided whether it applied from the *request's* user, which a webhook does not have. It now decides from the checkout's owner.
- **A fulfillment failure after payment lost its write and was never retried.** YesSql discards everything written after a cancel, so "mark failed" silently did nothing while the customer had paid. Confirmed payments are now committed before fulfillment runs; a fulfillment that throws leaves the checkout for the sweep to retry rather than marking it failed or refunding.
- **Abandoned checkouts never expired.** `ICheckoutEngine.ExpireAsync` and a **Session lifetime** setting release what a provider was holding; a checkout that collected money is never expired, only fulfilled.
- **A completed checkout existed twice.** `CheckoutSession` had no YesSql identity, so saving it again after a commit inserted a second document rather than updating the first. It now has one, and a SQLite-backed store test pins it.
- Smaller: a begin that failed part-way committed after its lock was released; a provisioning job's claim was not committed before the slow work; the payment-status endpoint did not check ownership; a checkout submitted before any payment was begun was moved to a state its own page refused to show.

### Free trials

A recurring plan can start with a free trial. The gateway is told about the trial and starts billing when it ends, so the schedule survives a restart of this application rather than depending on the site remembering to charge later.

### Guest checkouts belong to one browser

A pending guest checkout was recognized by IP address and user agent. That identifies a population rather than a person: everyone behind one office router or mobile carrier shares an address, and a user agent is neither secret nor unique. Anyone who could observe or guess both could resume a stranger's checkout and read the contact details and amounts on it.

A guest checkout is now issued a 32-byte random ownership token in a data-protected, HTTP-only cookie. Only its SHA-256 hash is stored, and the comparison is fixed-time, so a leaked database does not hand an attacker the ability to resume live checkouts. The same token protects wizard and subscription sessions; the IP address and user agent remain as audit fields only.

### Subscription renewals, failures, and cancellation

A subscription previously had no life after its first payment: renewals were recorded but nothing else moved, and the site had no way to learn that a subscription had failed or been cancelled. This release closes that gap.

- **Renewals now extend the subscription.** A successful cycle payment advances the recorded expiration by exactly one billing cycle, measured from the previous expiration rather than from the moment the notification was processed, so a late-handled renewal never shortens a paid period. Previously every subscription looked like it expired at the end of its first cycle no matter how long the customer kept paying, which is what the expiring-subscriptions report read.
- **Payments carry their own dates.** Each recorded payment now stores the date it was collected. Renewals were previously indexed and receipted under the date the subscription was created, so revenue-by-month, tax-collected, and product-performance reports attributed every renewal to the signup month, and a renewal receipt showed the signup date.
- **Failed renewals and cancellations are recorded.** The Stripe webhook now subscribes to `invoice.payment_failed`, `customer.subscription.updated`, and `customer.subscription.deleted`, delivered through two new provider-neutral events (`SubscriptionPaymentFailedAsync`, `SubscriptionStatusChangedAsync`). A failed renewal moves the subscription to **Past due** and records when it first fell behind; a cancellation made in the gateway dashboard is reflected locally with its cancellation date and paid-through date. A recorded subscription now carries a `SubscriptionLifecycleStatus`.
- Stale and out-of-order notifications are handled deliberately: an unrecognized gateway status leaves local state untouched instead of guessing, and a late payment failure never resurrects an already-cancelled subscription.

:::warning Reconnect Stripe after upgrading
An auto-provisioned webhook endpoint subscribes to the event list that existed when it was created. Click **Connect** on the Stripe settings page again so the endpoint is re-provisioned with the new subscription lifecycle events; otherwise they are never delivered.
:::

These states are recorded but not yet enforced — there is no automatic access revocation, dunning sequence, or customer/admin cancel action yet.

### Tenant onboarding administrator password

Provisioning a subscribed tenant passed the administrator password to the setup service **still data-protected**, so every site sold through tenant onboarding was created with an administrator account nobody could sign in to. The password is now unprotected immediately before setup, provisioning aborts with a reported failure if it cannot be unprotected (rather than creating an unusable tenant), and the protected secret is removed from the durable session once provisioning reaches a terminal outcome instead of being retained for the life of the subscription.

### Transaction management guards

The transaction management screens now share a single set of rules about which operations a transaction accepts:

- Recording a payment, marking paid, cancelling, and sending a reminder are refused on a transaction that already reached a terminal state (paid, cancelled, refunded, or abandoned), with a message explaining why. Previously a cancelled obligation could be marked paid and a paid one cancelled.
- Recorded payments are rounded at the transaction currency's own scale, so a zero-decimal currency is never recorded with fractions it cannot be paid in.
- A concurrent edit now surfaces as "reload and try again" instead of an unhandled server error. The ledger checks document versions so two managers cannot silently overwrite each other; the loser of that race previously saw a `500`.

### Checkout compensation refunds

When the checkout framework rolls back a payment attempt whose charge already succeeded, the compensating refund is now written to the durable refund ledger before the gateway is called. Previously the refund was issued directly, so the gateway's own refund notification found no matching local request and had to be quarantined for an operator to resolve by hand — for a refund the application itself had issued.

### Taxation admin UI

The **Taxation** management screens (Categories, Types, Jurisdictions, and Rules under **Commerce → Taxation**) were fixed and polished:

- The Create and Edit forms now render their fields. The editor view models were `sealed`, but the display manager builds a runtime proxy of each editor view model; a sealed type made the proxy creation throw a `TypeLoadException` that the display pipeline swallowed, silently rendering an empty form. The view models are now open, so every field displays.
- The top-level **Commerce** admin menu now shows an icon, following the Orchard Core `NavigationItemText-{id}.Id.cshtml` convention.
- Jurisdiction and Rule **effective from/to** dates are now date-only pickers without a time component or UTC label, so a rule's validity window is captured as a plain calendar date.
- The Jurisdiction **Country** field is now a dropdown populated from the canonical ISO 3166-1 country list provided by the Addresses module (the stored value is still the ISO country code). Region, county, and city remain free text pending a subdivision reference source.
- Tax **Rules are now source-aware and extensible by calculation method**, following the same source-aware pattern used elsewhere in the platform (for example AI data sources and deployments). Clicking **Add Tax Rule** opens a dialog that lists every registered calculation method — Percentage, Fixed amount, Per unit, Per weight, Per volume, Progressive, Threshold, and Tax table lookup. The method you pick becomes the rule's **source** (stored on the new `TaxRule.Source` property, replacing the former `CalculationMethod` property) and is fixed for the life of the rule. A shared display driver renders the fields common to every rule, while a per-source driver renders only the calculation fields the selected method needs: each `ITaxCalculationMethod` declares its required inputs through the `TaxCalculationMethodInputs` flags, so the percentage method shows the **Rate** field, the fixed/per-unit/per-weight/per-volume methods show the **Fixed amount** field, and the table-driven methods (Tax table, Progressive, Threshold) show a **Tax table** selector. This removes the previous calculation-method dropdown and its client-side field toggling. Third-party calculation methods contribute their own field requirements (and can register their own per-source driver) without changing the editor, and fields not used by the selected method are cleared on save so a rule never stores misleading configuration. Save-time validation still blocks money-affecting misconfiguration: a table-driven method cannot be saved without a **Tax table**. The **Display name** (`TaxName`) is now optional and falls back to the rule **Name** on invoices and receipts when left empty. Jurisdictions also preserve a stored country code that is not in the dropdown, so re-saving can never blank the country and accidentally broaden the rule to every country.
- Tax **Types are now a user-managed catalog** with their own **Commerce → Taxation → Types** screen (add, edit, delete), recipe step, and deployment step. The rule editor's **Tax type** field is a dropdown populated from this catalog instead of a hardcoded list, and a rule that already stores a value not present in the catalog keeps it. The catalog is seeded with the well-known types (`SalesTax`, `VAT`, `GST`, and more) on first run so existing behavior is preserved, while operators can now curate the tax types their business actually uses. A tax type remains a reporting and grouping label that never changes how an amount is calculated.
- The commerce content parts now contribute **recipe JSON Schema** when the **`CrestApps.OrchardCore.Recipes`** feature is enabled, matching the rest of the platform. `ProductPart` (Products), and `SubscriptionPart`, `SubscriptionSummaryPart`, and `TenantOnboardingPart` (Subscriptions) each contribute their settings and payload schema, so authoring `ContentDefinition` recipes for products and subscription plans gains editor validation and IntelliSense. The parts continue to import/export through Orchard Core's built-in `ContentDefinition` and `Content` steps; no part-specific recipe or deployment step was added.

### Taxation tables, treatments, and nexus thresholds

The taxation engine gained the pieces needed to configure and calculate every supported tax type end to end:

- **Tax tables are now manageable.** A new **Commerce → Taxation → Tables** screen (add, edit, delete), plus a `TaxTable` recipe step and deployment step, let you build the named, versioned bracket tables that the **Tax table lookup**, **Progressive**, and **Threshold** calculation methods depend on. Previously those methods were selectable in the rule editor but unusable because there was no way to create a table for them to read. Each table row captures a **Minimum**, optional **Maximum**, **Rate**, **Fixed amount**, and **Base amount**, and saving a table increments its **Version**, which is captured on every tax line and snapshot that used it.
- **Exempt, zero-rated, and reverse-charge supplies now produce a visible line.** Instead of silently dropping a tax when the customer is exempt, holds a valid exemption certificate, or the rule is a reverse-charge rule for a B2B customer, the engine emits a `TaxLine` with `TaxAmount = 0` and a `Treatment` (`Exempt`, `ZeroRated`, `ReverseCharge`, or `OutOfScope`) plus a human-readable `TreatmentReason`, so compliant invoices and receipts can show the tax as exempt or reverse-charged rather than omitting it. Only a rule the merchant has no nexus for produces no line at all. A new **Reverse charge** flag on tax rules drives the EU-style B2B reverse-charge behavior.
- **Inclusive fixed-amount taxes are un-grossed.** Tax-inclusive pricing previously extracted only inclusive **percentage** taxes from the gross price. The engine now also subtracts inclusive **fixed-amount** taxes (`FixedAmount`, `PerUnit`, `PerWeight`, `PerVolume`) before dividing out the combined percentage rate (clamping the net base at zero), so an inclusive fixed fee no longer leaves the net base overstated.
- **Economic-nexus thresholds are supported.** `MerchantTaxRegistration` gains an optional `ThresholdAmount` and a host-maintained `ThresholdAccumulatedAmount`, so a registration establishes nexus only once accumulated sales into the jurisdiction reach the threshold. This models destination-based economic-nexus rules (for example the US *Wayfair* thresholds) while keeping the engine deterministic and free of a sales ledger.

### Subscriber dashboard

The **My Subscriptions** subscriber dashboard and the admin subscription editor were improved:

- Each payment in the **Payments** list now has a **Print** action that opens a printable receipt (site name, billed-to details, service plan, tax breakdown, total, and transaction reference). The receipt is served only to the subscriber that owns the transaction.
- The **Payments** and **Subscriptions** lists on the subscriber dashboard are now paged (each with its own independent pager) and sorted latest-first — payments by payment date and subscriptions by their start date — so a subscriber with a long history sees the most recent records first without an unbounded page.
- Editing a subscription from **Manage subscriptions** no longer renders a blank page. `SubscriptionsMetadata` was `sealed`, which made the editor view-model proxy throw; it is now open.
- The commerce reports (revenue, tax collected, product performance, expiring/new subscription trends, and dashboards) are now grouped under a single **Reports → Commerce** category instead of being scattered across generic categories.
- The **Settings → Subscriptions** and **Settings → Payments** menu entries no longer show a decorative icon (the top-level **Subscriptions** tab and the **Payments → Stripe** entry keep theirs).

### Subscriptions checkout

The subscription checkout flow was hardened so that a hosted, redirect-based payment (Stripe Hosted Checkout) and offline **Pay Later** work reliably for both authenticated and anonymous customers:

- The pending subscription session is now persisted when the signup page is first rendered, so the payment step always references a durable, distributed-safe session. Previously an authenticated customer — whose registration step is skipped, making Payment the first step — reached the payment endpoints with a session that had never been saved, so Stripe Hosted Checkout and Pay Later failed. A returning visitor resumes the same pending session (tracked in a cookie) instead of orphaning a new one, and a resumed session is never re-saved on render, so a concurrent checkout completion can never be reverted to *Pending*.
- Checkout completion started from the standard signup POST (used by Pay Later) is now serialized with the same per-session distributed lock already used by the Stripe return, so a duplicate submission cannot run the provisioning handlers twice.
- The Stripe Checkout Session UI mode was updated to `hosted_page`, matching the current Stripe API (the previous `hosted` value is no longer accepted).
- The Subscriptions feature now depends on `OrchardCore.Title`, so a plan that uses the Title part always renders (the service plans list no longer errors when Title is not separately enabled).
- The signup wizard header was redesigned as a horizontal **line-with-circles stepper** that visualizes progress: completed steps are green (with a check), the current step is highlighted, and upcoming steps are muted. The payment-step invoice was rebuilt as a standard Bootstrap table using Bootstrap 5.3 contextual colors, so both rely on native Bootstrap classes with minimal custom CSS.
- The payment step now always shows the chosen payment method, even when only one method is available. Previously a single method was submitted through a hidden field and never displayed; it now appears as a selected option so nothing about the payment is hidden from the customer.

### Contact Center

Version `3.0.0` introduces the **Contact Center**, a new module family that turns the Omnichannel CRM into a full contact center. It sits between the CRM and the Telephony module: the CRM owns the business work, Telephony executes the media, and the Contact Center orchestrates routing, reservations, dialing, disposition, and supervision. Every capability ships as its own feature, so a tenant enables only what it needs.

Highlights:

- **Orchestration core** — a headless interaction lifecycle with a durable, append-only domain event log and baseline permissions, so every call and work item has a reliable, auditable history.
- **Agents, presence, and availability** — agent profiles with presence states, capacity, and skills, plus durable agent sessions with heartbeat and after-call recovery that work with or without a real-time connection.
- **Queues and reservations** — work queues with prioritized items and concurrency-safe reservations, so an activity is offered to exactly one agent at a time.
- **Policy-based routing** — capacity- and skill-aware assignment with sticky-agent, SLA-aging, business-hours, and overflow strategies that match each interaction to the right agent.
- **Inbound and outbound voice** — a provider-agnostic Voice Contact Center Call Router with inbound entry points, caller qualification, and business-hours decisions, plus an optional soft-phone incoming-call experience. Entry points now support a **Route to** target of either a queue or a **specific agent**: an agent-target entry point offers the dialed number (DID) directly to the named agent as a personal line and falls back to the target queue when that agent is unavailable. Agent profiles also define an **outbound caller id** field intended for presenting an agent's assigned number on outbound calls with providers that support per-call caller id (such as Telnyx); the field is on the model but is not yet surfaced in the agent editor or resolved on the dial path, so outbound calls currently present the tenant default (or a per-call/campaign) caller id.
- **Dialer** — Manual, Preview, Power, and Progressive dialing strategies with scheduled pacing and outbound activity batches routed through Contact Center voice providers.
- **Dialer attempts that never reach an agent are dispositioned by the dialer** — a call that rings out, is busy, rejected or failed, is screened out as an answering machine, or that the customer hangs up on before the agent is connected is completed with the disposition for its outcome (new outcomes *Rejected*, *Call failed* and *Disconnected*), as the system, and never pops on, rings for or asks a disposition of the agent. The record opens only once the agent is connected. A disposition's **Try Again** action, or the new **Schedule Dialer Retry** workflow task, puts the next attempt back in the same campaign with the same dialer profile, honoring **Max attempts** (now counted correctly from the first call) and the retry delay, which is also checked before an agent is reserved. **Activity disposition applied** now carries the attempt number, the maximum and remaining attempts, the dialer outcome and the dialer profile.
- **Abandoned calls on automated dialing** — when a person answers a Power or Progressive call and the reserved agent cannot be connected, the profile's **Abandoned call message** (with `{company}` and `{number}` placeholders) is spoken before the call ends, instead of silence. Each profile now measures its abandonment rate from new **Dialer call answered by a person** and **Dialer call abandoned** events (a call no agent reached within two seconds), shows it on the editor, and the abandonment-rate cap enforces it. Automated calls ring for a configurable **Ring time**, never less than 15 seconds.
- **Predictive dialing mode** — the **Contact Center Paced Dialing** feature now offers the **Predictive** mode on dialer profiles, alongside Power and Progressive. A Predictive profile reserves an agent for every call, like Power, and places fewer calls per cycle as the abandonment rate nears the cap. A new **Predictive pacing** card shows the profile's measured answer rate, ring time and connect time, and holds the settings over-dialing will use (target abandonment rate, lines per agent, calls in flight, answer-rate floor and window, agents about to free up, connect wait). Tenant timings live under `CrestApps:ContactCenter:PredictiveDialing`.
- **Predictive over-dialing** — a Predictive profile on the new **Over-dial** pacing model places more calls than there are free agents, sized from the measured answer rate so the abandonment rate stays near its target, and connects the free agent who has waited longest when a person answers. When nobody is free, the person hears the abandoned-call message at once and the call counts as abandoned. Over-dialing requires the abandonment cap, the abandoned-call message and a target below the cap, and falls back to one call per reserved agent whenever its measurements cannot be trusted or the abandonment rate nears the cap. Campaigns are paced as agents free up and calls are answered or end, not only once a minute.
- **Over-dialing safeguards** — an agent who is Available on a campaign has their soft phone stand by and answer the call they are connected to at once, without waiting for the platform's notice, which shortens the silence after a person answers; inbound offers still ring for the agent to accept. An agent whose phone does not pick up within a few seconds (`AgentLegAnswerTimeout`) is put back to work and the person hears the abandoned-call message, and a minute sweep settles any answered call nothing connected. A connect wait can only be saved when the measured time to connect an agent leaves room for it within two seconds. The next attempt that **Try again** or a workflow creates for a contact whose call was abandoned is dialed only with an agent reserved for it. The **Predictive pacing** card shows the last pacing decision of every campaign the profile dials. A campaign whose pacing lock was busy is paced again a second later, and agents also waiting on inbound queues can optionally be left out of the over-dial (`DiscountAgentsWithWaitingInbound`).
- **Consolidated, less-confusing features** — the agent capability (**Contact Center Agents**, `…ContactCenter.Agents`) now owns agent profiles, presence, and canonical availability together, and the work-distribution capability (**Contact Center Work Distribution**, `…ContactCenter.Queues`) now owns queues, reservations, and routing together, so there are fewer overlapping toggles to reason about. Capability features use clear, business-oriented names — **Contact Center Outbound Dialer**, **Contact Center Paced Dialing** (Power and Progressive), **Contact Center Inbound Voice**, **Contact Center Call Recording**, and **Contact Center Supervision & Live Dashboard** — with plain-language descriptions. Contact Center capabilities include their own administration screens instead of requiring a separate Administration feature; the server-side **Contact Center Voice** orchestration and the shared **Contact Center Real-Time** hub are enabled automatically as dependencies of the capabilities that use them instead of being standalone toggles; the Contact Center soft-phone projection and the CRM-integrated **Agent Workspace** are integration glue that activate automatically once the capabilities they compose (Contact Center Voice, Contact Center Real-Time, the Telephony soft phone, and — for the workspace — Contact Center Agents) are enabled, rather than separate toggles; each provider's **contact center voice adapter** (Telnyx, Asterisk) likewise activates automatically once that provider module and Contact Center Voice are both enabled, so there is no per-provider toggle to match the provider you already configured; mandatory outbound compliance is part of the base Dialer; and the certified inbound-voice recipes enable Inbound Voice. Enabling Paced Dialing therefore activates a complete Dialer Profiles, compliance, and runtime surface.
- **Outbound compliance** — a mandatory eligibility gate with suppression auditing, retry limits, and calling-window enforcement, so outbound campaigns stay compliant.
- **Real-time agent and supervisor experience** — a shared SignalR hub that broadcasts presence, offers, and queue depth; a CRM-integrated agent workspace; and a live supervisor dashboard with capability-gated monitoring.
- **Docked agent bar** — a persistent bar injected into the admin chrome (the layout footer) on every admin page for signed-in agents, holding its own live Contact Center hub connection outside the soft phone. It keeps work reaching the agent — popping the matched record and driving disposition — even when the soft phone runs in its own window or the browser extension, and it self-manages with the agent's live state. It rides the same integration glue as the Agent Workspace (Contact Center Agents, Real-Time, Voice, and the Telephony soft phone), and is deliberately not injected on the standalone `/softphone` page. See [Agent Desktop & Dashboard](../contact-center/agent-desktop#the-docked-agent-bar).
- **Recording and monitoring** — provider-capability-gated recording orchestration and recording-state events for voice interactions, including an **agent secure pause** that lets an agent suppress recording while a customer reads out sensitive data (card or identity numbers) and resume it afterward. Secure pause is ownership-checked and policy-gated, blocks new supervisor monitoring while a capture is in progress and force-stops any supervisor who was already engaged, and is bounded by a background automatic-resume guard so a pause can never silently outlive its purpose. It is off by default and enabled per tenant in the Recording settings.
- **Hosted secure data capture** — an optional **Contact Center Secure Data Capture** feature that lets an agent send a live customer to a dedicated secure page to enter sensitive data (such as a card number) instead of reading it aloud. The value is tokenized at submission, so the agent, the supervisor, and the recording only ever see a masked representation and a durable token reference; values that must never be retained, such as a card security code, are validated and then discarded with no token or mask kept. Captures are ownership-checked, limited to one in-progress capture per interaction, authorized by a one-time link whose SHA-256 hash is all that is stored and served with no-store/no-referrer headers, bounded by a configurable expiry with a background safety net, and pause recording during the capture as defense in depth with a self-healing recovery pass so recording can never be left paused permanently. The built-in masking sink is registered only in Development and is for development only; outside Development secure capture fails closed until an operator supplies an `ISecureCaptureTokenSink` backed by a PCI-DSS-compliant vault. It is off by default and enabled per tenant in the Secure Data Capture settings.
- **Reports and analytics** — executive, interaction, queue and SLA, agent, transfer, recording, campaign, and subject reports contributed to the admin **Reports** area.
- **Workflows bridge** — an optional Contact Center domain-event activity, so Orchard Core Workflows can react to contact center events.
- **Recipe and workflow schema validation** — the CrestApps Recipes feature now ships JSON schemas for the Contact Center and Omnichannel configuration steps (skills, queue groups, business-hours calendars, queues, agent entitlements, agent state reason codes, entry points, dialer profiles, campaign groups, campaigns, channel endpoints, dispositions, and subject actions) and for the Contact Center workflow activities, so recipe authors and AI tooling get per-step validation and property guidance.
- **Administration** — Contact Center settings screens plus each enabled capability's own administration screens.

See [Contact Center](../contact-center/index.md) for setup and configuration.

### Telephony

- The soft phone now plays a ringback tone while a number dialed from the keypad (or a colleague's extension) is ringing, and shows *Ringing...* without a call timer until it answers. On Telnyx the agent's own line answers before the number is dialed, so the carrier's ringback never reached the agent and they heard silence. The server tells the phone where the other party stands through the new `ITelephonyRemotePartyNotifier` and the `RemotePartyChanged` hub message; the tone stops the moment the number answers, is busy, does not answer or is not in service, or the agent hangs up.
- Provider HTTP clients no longer auto-replay unsafe requests. The phone-number-verification resilience pipeline now retries only idempotent safe methods, so a lost response can no longer place a second call or double-spend an OAuth grant, while transient failures on safe reads are still retried.
- Recording media now streams end to end through the tenant file store instead of being buffered in memory, so large recordings no longer pressure the managed heap during ingestion. See **Breaking Changes** for the related `RecordingMediaWriteRequest.Content` change.
- Token revocation and disconnect now report a typed result, so callers can tell confirmed success from a definitive or indeterminate failure. See **Breaking Changes** for the signature changes.
- The **Settings → Communication → Telephony** admin menu entry now displays a phone icon, matching the Orchard Core convention of a per-item navigation icon view.
- The soft phone keypad now uses a country-aware [intl-tel-input](https://intl-tel-input.com/) phone number field with a flag/country selector. A valid national number typed on the keypad is normalized to canonical E.164 before it is dialed, so outbound compliance screening (do-not-call and calling-window checks) can canonicalize the destination instead of rejecting a bare national number. Other non-number entries are dialed exactly as typed rather than being turned into an invalid international number. A new **Default country** soft phone setting controls the initially selected country and defaults to **Automatic**, deriving the country from the current culture and falling back to the browser's locale and then the United States when a region cannot be determined, so a country is always selected. The country selector dropdown renders above the floating widget so it is always visible, and opening it no longer scrolls the page the first time the flag is clicked. Call history and active-call numbers are still formatted for readability by the widget's own display formatter, independently of the input library.
- The soft phone can now dial internal extensions. A **Dial extension** toggle below the number field switches the keypad into extension mode, hides the country selector, accepts a free-form extension, and flags the dial request as an extension (`DialRequest.IsExtension`). Extension calls skip outbound compliance screening (do-not-call and calling-window enforcement) because an internal extension is not consumer outreach and cannot be canonicalized to E.164, while every real phone number still passes the fail-closed screening gate.
- The soft phone widget no longer briefly flashes the keypad before showing the correct state. While the provider and connection status are still resolving, the keypad, the call buttons, and every status message stay hidden until the real state (unavailable, connect, or operating) is known.
- The soft phone no longer stretches to nearly full screen height when a provider that requires a per-user OAuth connection is enabled. The height-reserving keypad body is now collapsed behind the **Connect to provider** panel, so the widget keeps its normal height.
- The **Connect to provider** button now reliably opens the provider's authorization window in a new browser tab and surfaces an inline error inside the connect panel when the authorization URL cannot be resolved or the browser blocks the popup, instead of appearing to do nothing.
- When the default provider uses OAuth 2.0 and the current user is connected, the soft phone header now shows a **Disconnect provider** action so the user can clear that provider connection directly from the widget instead of going through provider-specific settings pages.
- OAuth connect failures are no longer silent. When a provider's authorization callback cannot complete the token exchange, the soft phone now shows a safe reason inline in the connect panel, and the server logs the failure category without writing provider-supplied callback text to application logs. Client secret decryption failures and missing OAuth state cookies are logged as distinct categories instead of quietly closing the window with the soft phone still showing **Not connected**.
- The soft phone now applies successful dial responses immediately instead of waiting for a later provider state event, so users see the new outbound call as soon as a provider accepts it.
- The soft phone now refreshes active provider state while a call is active, so REST-only providers can move the UI out of `Connecting` even when no real-time event arrives. The active-call display now lets the phone-number input library own country-code rendering, avoiding a duplicate `+1` in the disabled call display.
- The standalone `/softphone` page no longer shows its incoming-call modal at the same time as the notification of a desktop app that embeds it (such as the CrestApps Soft Phone for Windows). The page sends the ringing call, with its queue and matched records, to the app through the WebView2 message channel, and hides the modal only when the app confirms that its notification for that call is on screen. If the app does not confirm within 2 seconds, or its notification closes without an answer, the modal shows as before. Answer, Decline, and Voicemail in the app's notification run in the page, through the same paths as the modal buttons. A normal browser tab and the browser extension are not affected. See [Notifications from a desktop app](../telephony/index.md#notifications-from-a-desktop-app).

### Providers

#### Asterisk

Adds the new **Asterisk** provider (`CrestApps.OrchardCore.Asterisk`), which integrates the Asterisk telephony platform with the Telephony soft phone through the Asterisk REST Interface (ARI).

Highlights:

- A per-tenant Asterisk provider with its own settings, plus an optional host-configured **Default Asterisk** provider.
- The host-configured **Default Asterisk** provider is now available to every tenant where the module is enabled, not only the default shell. Each tenant resolves the shared connection under a unique per-tenant ARI application name (`<ApplicationName>-<ShellName>`) so their Stasis event streams stay isolated. Existing default-shell deployments that rely on inbound routing must update their Asterisk dialplan to target `Stasis(<ApplicationName>-Default)` for the default shell.
- The `CrestApps.OrchardCore.Cms.Web` host launch profile now injects the **Default Asterisk** environment variables, so running the CMS host directly configures the provider by default without the full Aspire host.
- Soft-phone calls placed through the host-configured **Default Asterisk** provider now update live over SignalR (connected, held, and disconnected states) without a manual page refresh. The interaction store canonicalizes the provider identity so calls recorded under the **Default Asterisk** alias correlate with the real-time voice events that the listener tags with the canonical `Asterisk` provider name.
- Contact Center voice and media features that adapt Asterisk call execution, real-time call events, and bidirectional RTP media to Contact Center orchestration.
- A local Aspire container and an **Asterisk Web** sample for trying end-to-end routing and agent offers during development.

#### Telnyx

Adds the new **Telnyx** provider (`CrestApps.OrchardCore.Telnyx`), which integrates the Telnyx voice platform with the Telephony soft phone and the Contact Center. Unlike a click-to-call provider, Telnyx exposes a SIP-over-WebSocket registrar and a server-side Call Control API, so the browser soft phone carries the call audio itself (WebRTC) and the Contact Center can bridge live calls to agents server-side (`ServerSideAcd`) — the basis for true power dialing.

Highlights:

- A single-API-key Telnyx provider that places and controls calls through the Telnyx Call Control (Voice API), advertising dialing, hang up, hold, resume, mute, blind and attended transfer, merge, DTMF, and inbound calls.
- A browser **WebRTC soft phone**: the server mints a short-lived Telnyx telephony credential per session and the browser logs in to Telnyx's WebRTC gateway through the **Telnyx WebRTC SDK** (`@telnyx/webrtc`, the vendored `telnyx-webrtc` media adapter), which owns the peer connection, media, and SDP/codec negotiation end to end — replacing the earlier shared SIP.js adapter and its browser-side SDP workarounds. Outbound calls use a **server-side originate-and-bridge**: the platform rings the agent's registered browser leg (which the soft phone auto-answers) and bridges it to the destination, so the agent hears the call in the browser. Credentials are per-user capped, expire on their own, and are revoked at Telnyx on sign-out.
- **Ed25519-signed webhooks** at `/api/telnyx/webhook/call`. Telnyx signs each delivery over `{timestamp}|{body}` and this module verifies it against the account public key configured in settings (no shared secret is generated); the endpoint rejects unsigned, stale, or oversized deliveries and processes accepted events through the durable provider webhook inbox.
- A **Telnyx contact center voice adapter** that advertises the `ServerSideAcd` delivery model and supports dialer dialing, agent connect (originate the agent's browser SIP leg and bridge it to the caller), call transfer, and — with the **Contact Center Call Recording** feature — recording. Recording is driven by Contact Center governance (`record_start` / `record_pause` / `record_resume` / `record_stop`); the `call.recording.saved` webhook is ingested into the encrypted media store and the Telnyx-hosted copy is deleted afterward, so no plaintext recording lingers off-platform. It is integration glue rather than a separate feature: it activates automatically whenever the **Telnyx** module and **Contact Center Voice** are both enabled.
- **Bidirectional media streaming** over the `api/telnyx/media/stream` WebSocket (G.711 mu-law) — the Telnyx equivalent of Asterisk ARI External Media — giving the Contact Center a live server-side media leg.
- **Extension dialing** (`CrestApps.OrchardCore.Telnyx` advertises `ExtensionDial | ExtensionConference`): call another on-platform user by extension, or add an extension into a call as a conference participant, by originating and bridging two Telnyx SIP-over-WebSocket registrations. See [Extension Dialing](../telephony/extension-dialing).
- A new **Telnyx AI Voice Agent** feature (`CrestApps.OrchardCore.Telnyx.AiVoice`): the Phone-channel omnichannel processor dials a contact over Telnyx and runs an automated conversation using Telnyx text-to-speech and real-time transcription driven by an AI chat profile, then settles the omnichannel activity with a summary and disposition — the voice counterpart to automated SMS.
- A new **Telnyx SMS** feature (`CrestApps.OrchardCore.Telnyx.Sms`): a Telnyx SMS/MMS provider (configured from the `OrchardCore_Sms_Telnyx` appsettings section or the SMS settings screen) with an Ed25519-signed messaging webhook at `/api/telnyx/webhook/sms` for inbound `message.received` events and `message.finalized` delivery receipts, so Telnyx numbers can send and receive text through the SMS Portal and SMS Automation.
- See [Telnyx](../telephony/telnyx) for setup and troubleshooting.

### Omnichannel Messaging Workspace

Version `3.0.0` adds the **Omnichannel Messaging Workspace** (`CrestApps.OrchardCore.Omnichannel.Messaging`, category **Contact Center**), a **human-operated**, channel-agnostic messaging inbox: one customer list and one conversation view for every non-voice channel, with a tab per channel above each customer's conversation and a live unread badge on each tab. Channels are separate features; the first is the **SMS Messaging Channel** (`CrestApps.OrchardCore.Omnichannel.Messaging.Sms`), and email, WhatsApp, Messenger and others can be added by implementing `IMessagingChannel`. The workspace provides a shared team inbox, threaded conversations (one per customer address on each channel), a composer with canned-response templates, live contact search, claim/assign/transfer, close/spam/reopen, and 1:1 broadcasts processed by a durable background task, with real-time inbound and delivery-receipt updates over its own SignalR hub, a notice on every other admin page when a customer writes or a conversation is transferred to the agent or their queue, and a count of the conversations waiting on the agent on the **Messaging** admin menu item. It is the human counterpart to the AI-driven [SMS Automation](../omnichannel/sms) and shares the same Omnichannel message store, so an AI conversation can hand off to a human on the same number.

It deliberately reuses existing building blocks: each address it sends from (an SMS number, for the SMS channel) is an **Omnichannel channel endpoint** that carries its provider and inbound routing (target agent/queue, distribution mode, auto-reply), so the earlier separate `SmsNumberRoute` concept was retired. Operators are Contact Center **agent profiles** resolved through a dependency-only **Agent Services** feature (a bare profile is provisioned automatically on first access, with no Contact Center administration required), and SMS sending goes through a per-number `ISmsDispatcher` so different numbers can send through different carriers. The workspace depends only on Omnichannel Channel Endpoints, Contact Center Agent Services and `OrchardCore.SignalR`; the SMS channel adds `OrchardCore.Sms`. See [Messaging Workspace](../omnichannel/messaging-workspace).

#### Agents see only their own conversations and their queues' unclaimed ones

Every messaging permission listed **Use the messaging workspace** as a permission that implies it, so every agent who could use the workspace also held **View all messaging conversations**, **Send group messages** and **Send messages outside business hours**: an agent saw, and could open, the conversations their colleagues had claimed. Using the workspace now implies none of them, and which conversations a user sees follows Orchard Core's content pattern. Two permissions are added beside **View all messaging conversations**: **View your own messaging conversations** (`ViewOwnMessagingConversations`), for the conversations assigned to the agent or sent to an endpoint they own that no colleague has claimed, and **View your own and your queues' unclaimed messaging conversations** (`ViewQueueMessagingConversations`), which adds the unclaimed conversations of the queues they serve. A conversation is authorized against `ViewAllMessagingConversations`, and an authorization handler grants anybody without it the conversations that are theirs; the list, the menu count and the notifications follow the same rule. A conversation no route gave to an agent or a queue is now a supervisor's to triage. An agent can still finish a conversation they hold after leaving its queue. The `IMessagingConversationAuthorizationService` service is removed: authorize a conversation with `IAuthorizationService.AuthorizeConversationAsync`.

The **Agent** role gets `UseMessagingWorkspace` and `ViewQueueMessagingConversations`; the **Supervisor** role gets `UseMessagingWorkspace`, `ViewAllMessagingConversations`, `SendGroupMessages`, `SendMessagesDuringQuietHours` and `ManageMessaging`. On an existing tenant, a migration grants `ViewQueueMessagingConversations` to every role that could use the workspace, so its agents keep their queues' inbox. See [Messaging Workspace](../omnichannel/messaging-workspace#permissions).

#### Contact index migration no longer stalls on PostgreSQL

The `OmnichannelContactsMigrations` upgrade steps rebuild the default contact index by re-issuing `CREATE TABLE`, `ADD COLUMN`, and `CREATE INDEX` statements and swallowing the "already exists" errors with `try`/`catch`. Orchard Core runs every migration step through a single `SchemaBuilder` that shares the migration's database transaction. On PostgreSQL, the first failing DDL statement aborts that whole transaction, so even though the .NET exception is caught, the shared transaction stays poisoned and the final version bump can never commit — leaving the migration permanently stuck on an old version (most often version 6). Each idempotent schema change now runs behind its own savepoint inside the migration transaction, so an "already exists" failure only rolls back that one statement and can no longer poison the migration transaction. The isolation deliberately stays inside that transaction: a change moved onto a second connection waits for locks the migration transaction already holds (on SQLite, the database's only write lock), times out, and is skipped as if it already existed. MySQL, which commits DDL implicitly and so discards savepoints, runs each change on its own connection instead. The migration now advances correctly on PostgreSQL, SQL Server, MySQL, and SQLite.

-----

#### Activity batch index migration no longer loses the `CreatedUtc` column

The activity batches admin screen orders batches by a `CreatedUtc` column added to `OmnichannelActivityBatchIndex` by an upgrade step. That step ran through the feature's shared migration `SchemaBuilder`, so when any sibling migration in the same feature threw, Orchard Core cancelled the shared session and rolled back the column addition together with the migration's version record. On databases with transactional DDL (PostgreSQL and SQL Server), the tenant was left with the migration record still pointing at the old version and the physical `CreatedUtc` column missing, so the screen failed with `Invalid column name 'CreatedUtc'`. The column additions now run as isolated, idempotent schema changes, shared with the contact index migration through the new `OmnichannelIndexMigration` base class, so a change that cannot be applied no longer takes its sibling steps down with it. A follow-up repair step now also verifies the `Source` and `CreatedUtc` columns and adds only the ones that are missing, so tenants whose migration record was already advanced past the original upgrade steps while the physical columns were rolled back are healed on the next start.

### DNC Registry

#### Local registry migration no longer blocks other feature migrations

The **Local** DNC registry repair migration checked whether its index tables already existed by comparing the database schema against an **unprefixed** table name. On installations that use a table prefix (for example multi-tenant deployments), the check always reported the tables as missing, so the migration tried to recreate them and threw a duplicate-object error. Because Orchard Core runs every feature's automatic migration on a shared session, that uncaught error cancelled the session and silently rolled back every other feature's migration in the same run — most visibly leaving the Omnichannel contact migration stuck on an old version. The existence check now resolves the physical (prefixed) table name, and the repair step no longer rethrows if the table is already present, so a single feature can no longer stall the rest of the migration batch.

Configure the TURN Token ID and API token under `OrchardCore:CrestApps:AI:RealtimeTransport:Cloudflare`. See [Realtime Voice](../ai/realtime-voice#cloudflare-realtime-turn).
- **Cascaded realtime deployments.** Realtime voice no longer requires a provider that ships a speech-to-speech model. Create a deployment under the new **Cascaded Realtime** provider and pick the three deployments it chains — one that transcribes, one that generates the reply, and one that speaks it. The three may come from different providers, and the profile, chat UI, transcripts, and turn persistence all behave exactly as they do with a native realtime model. Tools, data sources, and the profile's instructions are applied to the chat deployment, so a voice profile keeps everything a text profile has. The deployment declares the **Realtime** feature itself, and its **Voice** picker lists the text-to-speech deployment's voices. Importable through the `aideployment` recipe step via `CascadedRealtimeMetadata`. See [Realtime Voice](../ai/realtime-voice#cascaded-realtime-when-no-provider-speaks).
- **The anonymous visitor cookie can be configured to survive inside a frame on another site.** The **Visitor Identity** card under **Settings → Artificial Intelligence** gains **Allow cross-site embedding** and **Partition the cookie per embedding site**, alongside the cookie name and lifetime it already had. The visitor cookie is written `SameSite=Lax` by default, which a browser refuses in a third-party context, so a chat embedded in a frame on a customer's site looked like a brand new visitor on every request: the conversation did not survive a page load, and the visitor rate-limit partition never accumulated. Turning cross-site embedding on writes the cookie `SameSite=None; Secure` instead, which is the only combination a browser keeps in a frame; a request that did not arrive over HTTPS keeps the `SameSite=Lax` cookie rather than losing it altogether. Partitioning is on by default and keeps that cookie apart from the first-party one of the same name. Cross-site embedding is off by default, so nothing changes for a chat served from its own site. Importable through the `Settings` recipe step via `AIVisitorIdentityOptions`. See [Chat](../ai/chat#anonymous-visitor-identity).
- **An anonymous visitor sees their own chat history.** `DefaultAIChatSessionManager.PageAsync` answered an empty list for anyone who was not signed in, so a chat serving anonymous visitors — an embedded widget, most of all — showed them no history at all, even though `FindAsync` would happily open any one of those sessions by id. It now lists the sessions the caller's visitor identity owns, the same `ClientId` the session was created with, and still answers nothing when no visitor identity has been issued. A signed-in user is unaffected.

#### Tiered anonymous chat rate limits

The **Prompt Security** section under **Settings → Artificial Intelligence** now exposes the tiered anonymous rate limits added in `CrestApps.Core`:

- **Anonymous message rate-limit tiers** and **Anonymous session-start rate-limit tiers** accept one tier per line as `limit, window` (the window is a .NET `TimeSpan`, for example `00:00:30` or `1.00:00:00` for a day). A request is throttled when it would exceed any tier, so a short burst tier can sit alongside longer sustained tiers. Both default to the same tiers as `CrestApps.Core`, and clearing a field falls back to the matching single-window limit.
- Tiers apply to **anonymous** callers only. **Maximum messages per window** and **Message rate-limit window** now govern authenticated callers, and anonymous callers only when no message tiers are configured; **Maximum anonymous sessions per window** and **Anonymous session window** are likewise the fallback for the session-start tiers.
- The default for **Maximum anonymous sessions per window** changed from `5` to `20` to match `CrestApps.Core`. Sites that already saved this setting keep their stored value.
- Both tier lists can be set from a recipe through the `PromptSecurityOptions` site settings step.
- Individual AI profiles (and profile-source AI profile templates) can override both tier lists from their **Prompt Security** tab. A blank field inherits the site tiers; entering tiers replaces them for that profile; and a **Do not use tiered ... limits for this profile** checkbox opts the profile out of tiered limits entirely so it falls back to its own single-window values.
- The message shown when a visitor is throttled while starting a new chat no longer discloses the configured limit, the current count, or the retry delay, and is now localizable. Those values would let an abuser tune their traffic to sit just under the throttle.
- A throttled session start is now signalled to the client as a dedicated rejection (`ReceiveSessionStartRejected`) rather than a generic error, so the embedded chat widget shows the message instead of treating it as recoverable, clearing the visitor's state, and silently retrying. This also covers the OrchardCore-specific TemplatePrompt path, which replaces the framework's generated-prompt handler outright.
- The chat UI no longer leaves a throttled visitor waiting on a hung request. The chat scripts were updated to `@crestapps/ai-chat-ui` `2.0.0-preview.154`, which rejects the pending new-session request, clears the typing indicator, and shows the message instead of failing silently. The `AIChatApp`, `AIChatWidgetApp`, `ChatInteractionApp`, `document-drop-zone`, and `technical-name-generator` resources moved to version `2.0.0`, so cached copies of the old scripts are replaced.
- Documented that the tier lists take precedence over the single-window settings, so lowering **Maximum anonymous sessions per window** has no effect while the default tiers are still in place.

See [Prompt Security](../ai/chat#prompt-security) for details.

### Taxation

#### New provider-agnostic taxation framework

A new **Taxation** module (`CrestApps.OrchardCore.Taxation`) introduces a provider-agnostic, extensible taxation framework for Orchard Core. It models tax as a **determination** — derived from *what* is sold, *who* buys it, *where* it is sourced, *when* it happens, and *how* it is calculated — rather than a static rate stored on a product.

Highlights:

- A new **Taxation** part lets any content type participate in taxation by classification only (tax category and classification), never a stored rate.
- A deterministic engine (`ITaxService`) produces an auditable, line-by-line breakdown with references to the exact tax rule and tax table versions used.
- Built-in calculation methods cover percentage, fixed amount, per-unit, per-weight, per-volume, tax table, progressive, and threshold taxes, with tax-inclusive and tax-exclusive pricing.
- Extensible tax types, hierarchical jurisdictions, categories, versioned rules, tax tables, sourcing strategies, exemption certificates, and merchant nexus registrations.
- Historical tax snapshots (`ITaxSnapshotFactory`) keep transactions immutable, so changing a rate, rule, or table never alters past transactions, and refunds reverse the original determination.
- Clean extension points (`ITaxableItemProvider`, `ITaxCalculationMethod`, `ITaxSourcingStrategy`, `ITaxDeterminationProvider`, and more) let Products, Subscriptions, Commerce, Bookings, Services, custom content types, and external tax providers integrate without modifying the Taxation source.

See [Taxation](../modules/taxation) for details.

#### Taxation integrated across Products, Subscriptions, Checkout, and Payments

Taxation is now the single authoritative tax engine for the commerce stack. The integration is native — no product-, subscription-, checkout-, or payment-specific tax calculation remains — and it stays optional through Orchard Core feature dependencies, so every module keeps working when Taxation is disabled.

- **Products** contribute an `ITaxableItemProvider` that turns a product (via the **Product** and **Taxation** parts) into a taxable item — price, product-type–derived kind, tax category, classification, and external code — without ever calculating tax itself.
- **Checkout** determines tax on the amount due now and captures it on the invoice as a tax amount, detailed tax lines, and an immutable snapshot. Exclusive tax is folded into the up-front charge so the payment provider collects the exact taxed total.
- **Recurring subscription billing** re-taxes each renewal with the rules in effect at billing time and stores a fresh per-cycle snapshot, so rate changes and customer address changes apply to future cycles while historical transactions never change.
- **Payments** stay tax-agnostic: providers charge the final, already-taxed transaction amount and never interpret tax rules.
- **Refunds** derive their tax from the original transaction snapshot through a new `ITaxRefundCalculator` (full and proportional refunds allocated across the original tax lines), never from current rules.

#### Subscription and commerce reports

When the **Reports** feature is enabled, the Subscriptions module now contributes admin reports: subscription revenue, a subscriptions dashboard (active, new, and expiring), expiring subscriptions, a new-subscription trend, tax collected, and product performance. A `TaxAmount` column added to the subscription transaction index makes collected tax queryable.

See [Subscriptions](../modules/subscriptions#taxation) and [Products](../modules/products#taxation) for details.

### Localization

Permissions and deployment steps declare their labels the way Orchard Core now does, with
`LocalizationSource.Create(...)`
([OrchardCore#19972](https://github.com/OrchardCMS/OrchardCore/pull/19972)). Each permission description carries
its declaring type as the translation context, so the roles editor translates it from PO files. Every deployment
step now has a title, so its add and edit screens are headed with the step's name ("Contact Center Queues")
instead of a name derived from its type. Category and title sources are shared static fields rather than
allocated for each step. Descriptions of per-item permissions, such as **Query AI profile - {0}**, stay plain
templates, as in Orchard Core.
