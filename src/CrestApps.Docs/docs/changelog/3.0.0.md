# Version 3.0.0 Release Notes

This page highlights the changes in the `3.0.0` line.

## New Modules

### Products, Payments, and Subscriptions

This release introduces a new commerce stack for selling recurring plans on Orchard Core content:

- **[Products](../modules/products)** (`CrestApps.OrchardCore.Products`) — attaches a reusable `ProductPart` (price + product type) to any content type, turning content items into purchasable products.
- **[Payments](../modules/payments)** — a provider-agnostic payment framework (`IPaymentEvent`, `PaymentMethodOptions`) with a production-hardened **Stripe** provider (`CrestApps.OrchardCore.Stripe`). Stripe supports both the on-site **Payment Elements** integration and the Stripe-recommended **Hosted Checkout** (redirect), selectable from settings. Linking a Stripe account is one step: paste the account's secret key and click **Connect** — the app verifies the key, resolves the account, and provisions the webhook (capturing its signing secret) automatically, and can be disconnected with one click. When the **Workflows** feature is enabled, Stripe also contributes workflow events for the payment lifecycle (payment received, subscription created, payment failed/canceled/refunded, dispute created) and a **Stripe Request Failed** event for authentication or connectivity problems, so administrators can build custom alerting or automation. New payment gateways (for example PayPal) can be added and surfaced as checkout options without changing the consuming modules.
- **[Subscriptions](../modules/subscriptions)** (`CrestApps.OrchardCore.Subscriptions`) — sells recurring subscriptions built on a `SubscriptionPart`, with a multi-step checkout flow, a subscriber dashboard, an admin management console, and optional **reCaptcha** and **Tenant Onboarding** features. Subscriptions depends on the new **[Checkout](../modules/checkout)** framework for payment handling. Payment options are contributed by other modules: enable the **Stripe** module to accept card payments (wired in automatically when both are enabled — there is no separate *Subscriptions - Stripe* feature), and enable the **[Pay Later](../modules/pay-later)** module to offer an offline pay-later option.
- **[Pay Later](../modules/pay-later)** (`CrestApps.OrchardCore.PayLater`) — a standalone module that adds an offline "pay later" option to the Checkout framework, reusable by subscriptions and one-time goods purchases. It records an offline commitment through the same durable ledger and reconciliation as a real gateway, without ever fabricating a *paid* record a processor could contradict, and now records the balance it leaves owing as a trackable outstanding **[Transaction](../modules/transactions)** so it can be reported, reminded about, and settled later.

The payment path was hardened for multi-instance, production use: deterministic Stripe idempotency keys, distributed-lock–serialized checkout finalization, currency-aware minor-unit conversion, rate-limited anonymous checkout endpoints, idempotent payment-intent confirmation (a PaymentIntent already confirmed client-side by Payment Elements is reconciled to its authoritative state instead of failing the webhook), and signature-verified, de-duplicated, retry-safe Stripe webhooks.

See [Products](../modules/products), [Payments](../modules/payments), and [Subscriptions](../modules/subscriptions) for details.

- **Managed currencies for products and subscriptions.** Products now owns a document-backed **Commerce → Currencies** catalog that stores the allowed currencies without a query index, seeds a default list through a migration-executed recipe, and exposes recipe (`Currencies`) and deployment support for managing the catalog as configuration. Product prices, product default currencies, and the subscription settings currency now use friendly dropdowns sourced from that catalog instead of free-form text entry.
- **Products can be listed without being sold, and listed on the front end.** A product type now has a sales mode (*Purchasable*, *Listing only* or *Per item*) and a price display (*Show*, *On request* or *Hidden*), and a product can carry a compare-at price. A product that cannot be bought is refused when its snapshot is resolved, so no checkout path can sell it. The new **[Product Listing](../modules/products#product-listing)** feature (`CrestApps.OrchardCore.Products.Listing`) adds listing pages with filters built from the product type's own fields, sorting, keyword search, grid and list layouts and paging, plus a product page layout with a gallery, breadcrumbs through Orchard Core's breadcrumb shapes, readable term slugs in URLs, color swatch and button filters, ready-made price ranges, cached search results and search engine tags through Orchard Core's SEO module. Every part of the pages is a shape that a theme can override in Razor or Liquid. Store, real estate and vehicle dealership sample recipes show it end to end. Subscription plans are products too: the Subscription stereotype now adds the Product part, plans list through a Product Listing with their billing period and **Sign up** button, and the built-in `/ServicePlans` page is removed. A plans listing offers a **Recommended** sort that orders plans by the **Position** on their **Product** part, and the Commerce starter recipe publishes a **Plans** listing at `/plans` sorted that way; see [Listing your plans](../modules/subscriptions#listing-your-plans). The **Commerce** admin menu gains **Products** and **Product Listings**. A listing can hide its filters, its sorting, or both. Filter styles are extensible: a module registers one in `ProductFacetStyleOptions` with a `ProductFacet-{Style}` template. A field's **Swatch colors**, or a color field on taxonomy terms, set swatch colors, and a range filter can offer ready-made ranges you type, such as `-25, 25-75, 75+`. The listing editor groups its filters and sorts by product type and shows only those of the types it lists, and a field's **Product listing** settings appear only on product types.
- **Subscription editor and checkout polish.** The product and subscription editors now group related pricing and billing inputs so the amount/currency and billing-duration/duration-type pairs read together, and the subscription part now explains what **Billing cycle limit** and **Subscription day delay** do. The checkout payment step now presents payment methods as cards, shows clearer Stripe and Pay Later panels, and surfaces Pay Later errors inline instead of falling back to generic alerts.
- **Carts and orders for products sold online.** The new **[Carts](../modules/carts-and-orders)** feature (`CrestApps.OrchardCore.Carts`) adds *Add to cart* to listing cards and product pages, a cart page at `/cart` and a cart link in the site's navigation bar. Guests get a cart without an account, and it joins their account's cart when they sign in. A cart holds one-time prices only and prices every line again when it is shown. The new **Orders** feature (`CrestApps.OrchardCore.Orders`) checks a cart out through the Checkout framework as an order, shows the order number on the confirmation, and adds **Commerce > Orders** and **My Orders**. Checkout billing items can now carry a quantity, a SKU and the product's tax category, classification and kind.
- **Inventory.** The new **[Inventory](../modules/inventory)** feature (`CrestApps.OrchardCore.Inventory`) counts the units of each product and variant on hand. Add the **Inventory** part to a product type to count it. Each product, or each variant, gets a stock item, kept in step as the product is saved, with removed variants archived. **Commerce > Inventory** lists stock, fewest available first, with search and filters for low, out-of-stock and backordered items. Receiving, adjusting and counting stock are each a movement in an append-only ledger with who, why and when, and two changes to one item can't overwrite each other. An item's count can be rebuilt from its history. The low-stock threshold is set per product, or under **Settings > Commerce > Inventory** for the rest. With Orders enabled, starting checkout holds the units an order needs, all or none. An order short of stock is refused, and the buyer is sent back to the cart with what's left. Paying sells the held units, recorded as **Sold** in the item's history, and a canceled or abandoned checkout, or a hold past **Hold stock for** (60 minutes), releases them. `IOrderEventHandler` gains `CreatedAsync`, which can refuse an order, and `PaidAsync`. Shoppers see *In stock*, *Only N left* (at or below the threshold), *Out of stock* or *Available on backorder* under **Add to cart**, following the chosen variant. An out-of-stock variant can't be added, and the cart caps quantities at what's left, counting a buyer's own held units as theirs. Products gain `IProductAvailabilityProvider`, which Inventory implements. Listings can offer an **In stock** filter, kept current as products sell out and come back. Users in chosen roles are notified when a product runs low or sells out, and a **Low Stock** workflow event fires. Stock counts can be exported and imported as CSV under **Commerce > Inventory**, and set or copied with a **Stock** recipe and deployment step. Products gain `IProductSearchIndexRefresher` for modules that change what a search record holds.
- **Shipping.** The new **[Shipping](../modules/shipping)** feature (`CrestApps.OrchardCore.Shipping`) prices shipping. **Commerce > Shipping** sets zones of countries, optionally narrowed to some regions, tried in order with a zone for the rest of the world. Each zone offers methods priced by a rate provider: a flat rate per order and per item, a table by weight, subtotal or number of items, or free from an order subtotal, with surcharges per shipping class. **Try rates** shows what an address would pay. The **Shipping** part gives products a weight, a weight per variant and a shipping class, in the unit set under **Settings > Commerce > Shipping**. `IShippingRateProvider` lets a carrier module add live rates. Zones are set and copied with a **ShippingZones** recipe and deployment step. An order with goods gets a **Shipping** step at checkout, after **Contact**: the buyer picks an address from their address book or enters one, then a method from the address's zone, priced on the server. Shipping becomes a taxed line of the order, and the order, its page and its confirmation email keep where it ships and how (`Order.ShippingAddress`, `Order.Shipping`). Checkout tax now uses the shipping address as the destination, else the billing address (`CheckoutShippingInfo`), so rules for a jurisdiction apply to orders; before, orders had no destination and only rules without a jurisdiction applied. A paid order is shipped from its page in one or several shipments, each with its carrier, tracking number and link (made from the carrier's template in the settings); a shipment can be set aside while packed, then shipped, delivered or returned. The buyer is emailed when a shipment leaves and sees each shipment and its tracking link on their order page, and orders show *Unfulfilled*, *Partially fulfilled* or *Fulfilled* (`Order.FulfillmentStatus`). **Shipment Created**, **Shipped**, **Delivered** and **Returned** workflow events fire. Other modules can add sections to the order pages through `IDisplayManager<Order>` (`OrderConstants.DisplayTypes`). The online store sample now counts stock (a few products running low, one sold out), weighs its products and sets up shipping zones and carriers.
- **Customers.** The new **[Customers](../modules/customers)** feature (`CrestApps.OrchardCore.Customers`) keeps a record of everyone who buys: a person or a business, with an account or as a guest, with how to address them, a company and tax id, and a marketing consent. A customer with an account is linked to its Orchard Core user, which keeps the sign-in and email. **Commerce > Customers** lists, searches, adds and edits them. An order placed by a signed-in user belongs to their customer (`Order.CustomerId`), and statements and receipts address the customer by their customer record. Each customer keeps an address book of up to 20 addresses, with a default billing and a default shipping address, managed on the customer's admin page or by the customer under **My Account** (the new **Manage own customer profile and addresses** permission, granted to authenticated users), all with the Addresses module's address editor. With Orders on, an order's checkout gains a **Contact** step: a name, an email and a phone, and a billing address as **Settings > Commerce > Customers** asks (Optional by default, Required or Off). A signed-in buyer can bill a saved address. The paid order keeps its own copy of the contact and billing address (`Order.CustomerPhone`, `Order.BillingAddress`), a guest becomes a guest customer with that address, and Pay Later puts the guest's contact on its transaction so reminders reach them. Guests reach their orders through signed links that work for 60 days, on the confirmation page and in the confirmation email, which open a read-only order page with a pay link when something is still owed. **Find my order** (`orders/find`) emails a guest those links without ever saying whether orders exist. When a user signs in, registers or confirms their email with a verified email, their guest customers merge into their customer: orders, Pay Later transactions and addresses move to the account, and the customer page lists the customer's orders and merged guest checkouts. Customers can be exported as JSON and erased from the admin for access and erasure requests, with each one logged; erasing anonymizes the customer's orders too, keeping their lines and totals. A daily task erases guests inactive for 24 months and anonymizes settled guest orders after 12, both set under Settings › Commerce › Customers. A `Customers` recipe step adds guest and business customers, and the online store sample now enables Orders and Customers with two sample customers. Unpaid orders now close: an order is canceled, with its reason, when its checkout fails, is canceled or expires, through new `Canceled` and `Expired` checkout handler stages, and a sweep every 15 minutes cancels any left behind. `IOrderEventHandler` lets modules act when an order is canceled. Paying for an order now leaves the other variants of the same product in the cart. A paid order's confirmation is emailed to the customer (order number, lines, total, billing address) when the site has an email service, controlled by **Send order confirmations** under **Settings > Commerce > Orders** (on by default).
- **Commerce personal data: export and anonymize.** The new `ICommercePersonalDataService` (`CrestApps.OrchardCore.Customers.Abstractions`, registered by the Commerce feature) exports and anonymizes what commerce keeps about one person, found by their owner, their email or both, for access and erasure requests. Each enabled feature contributes through `ICommercePersonalDataContributor`: Checkout (checkout sessions, with the payments and refunds taken in them, and coupon redemptions), Transactions, Subscriptions, Installment Plans and Stripe (the Stripe customer's name, email and phone, redacted through the Stripe customer API). Anonymizing removes names, emails, phone numbers, addresses, IP addresses, user agents, saved checkout steps, plan notes and card descriptions, and keeps amounts, dates, statuses and invoice and receipt numbers. `ICheckoutSessionStore` gains `GetByCustomerAsync` (by owner and email, on the new `CheckoutSessionCustomerIndex`, which indexes existing sessions when it is created) and `GetManyAsync`. Erasing or downloading a customer under **Commerce > Customers** now covers all of it. See [Personal data requests](../modules/commerce#personal-data-requests).
- **Checkout sessions forget an erased buyer.** Anonymizing an order, at the customer's request or after the guest order retention window, now also anonymizes every checkout session behind it, including earlier attempts to pay and the sessions paying the order's transactions. `CheckoutSession.Anonymize(now, replacementName)` clears the owner, the buyer's contact (keeping the billing country and region), the IP address, the user agent and the saved steps, and records `CheckoutSession.AnonymizedUtc`; the personal data contributor uses it too, so its sessions now lose their owner as well. The new `ICheckoutSessionAnonymizer` (`AnonymizeAsync(sessionId)`, `AnonymizeByReferenceAsync(referenceType, referenceId)`) lets any module or application anonymize the sessions of its own checkout source, such as a transaction checkout, and `ICheckoutSessionStore.ListByReferenceAsync` returns every session for a reference rather than only the newest. `ICustomerPrivacyHandler.Order` orders the privacy handlers, so the commerce personal data handler identifies a customer's guest records before the order handler erases the details it follows. See [Checkout](../modules/checkout).
- **Product listings: search servers, variants, merchandising and more.** A listing can search an index held by **Elasticsearch**, **Lucene** or **Azure AI Search** through three new optional modules (`CrestApps.OrchardCore.Products.Elasticsearch`, `.Lucene` and `.AzureAI`) on Orchard Core Indexing, with the same filter counts, ranges, sorts and paging as the database search, relevance-ranked keyword search, and a fallback to the database when the server cannot be reached; each listing picks its **Search index**. The new **Product variants** part sells a product in versions such as sizes and colors: the type names the options, each product gets one variant per combination with its own SKU, price, compare-at price and image, and the variant flows through pricing, the cart and the order; listings filter on options and show *From* the lowest price. Every product has **Featured** and **Position** on its **Product** part, and every listing offers **Recommended** and **Featured first** sorts and a *Featured* filter (`IProductPositionProvider` is removed). Time, link, HTML, Markdown and user picker fields can take part in listings, dates filter by range with ready-made ranges by year, and text and taxonomy fields sort A to Z. A listing chooses numbered pages, a *Load more* button or infinite scroll. Listings show the products of the visitor's culture plus products that are not localized. The listing editor folds its filters and sorts into compact rows that reorder by dragging, with the less used settings under **More settings**.
- **Safer Pay Later completion for tenant onboarding.** The tenant-onboarding subscription completion handler now skips validation when the subscribed plan does not actually require tenant onboarding, which prevents Pay Later completions from failing with a misleading "Unable to locate the saved new site information" error on plans that do not collect tenant-setup data.
- **Subscriptions now reuses the shared Wizard feature.** The public subscription signup routes now delegate to the common wizard host and completion engine instead of maintaining a separate controller/session-completion pipeline, while subscription-specific steps and persisted `SubscriptionSession` documents remain in place for payments, reporting, and onboarding flows.

### Checkout

This release also introduces **[Checkout](../modules/checkout)** (`CrestApps.OrchardCore.Checkout`) — a provider-agnostic checkout and payment framework that any purchase flow can build on, so the wizard, invoice, taxation seam, and money-handling safety guarantees are written once and reused by recurring subscriptions and one-time goods purchases alike.

Checkout is hardened for sensitive, multi-node money handling:

- A **durable payment ledger** (`PaymentAttempt` / `IPaymentAttemptStore`) persisted in the tenant database, written *before* every provider call and updated with the provider's authoritative reference immediately after — so a crash, cache eviction, or partial multi-obligation failure can never strand an untracked charge.
- **Reconciliation against the provider's authoritative API** (`ICheckoutReconciliationService`) that records a payment *only* when the provider confirms it and marks the checkout complete only when **every** obligation is settled, so our side never shows *paid* while the gateway failed.
- A first-class **`ICheckoutPaymentProvider`** contract (begin / verify / cancel + capabilities) for adding gateways.
- **Currency-correct money** (`Money` / `CurrencyScale`) for every ISO-4217 currency, including zero-decimal (JPY) and three-decimal (KWD) currencies.
- **Distributed coordination** via `IDistributedCache` and `IDistributedLock` (`PaymentSessionCache`, `IPaymentAttemptLimiter`), where the cache is a notification-only optimization and never the source of truth.
- A **taxation seam** (`ICheckoutTaxService`) that folds tax into the charged amount when Taxation is enabled and is a no-op when it is not.

See [Checkout](../modules/checkout) for details.

### Transactions

This release introduces **[Transactions](../modules/transactions)** (`CrestApps.OrchardCore.Transactions`) — a provider-agnostic ledger of *money owed* that answers one question for the whole tenant, **"what has not been paid yet?"**, no matter which provider or purchase flow created the obligation.

- A durable **`Transaction`** ledger entry (persisted in the tenant database) captures the amounts, owner, optional due date, provider-neutral `Source`, a neutral `ReferenceType` / `ReferenceId` reference, and an audit timeline, moving through a full `TransactionStatus` lifecycle (`Pending`, `Outstanding`, `PartiallyPaid`, `Paid`, `Canceled`, `Failed`, `Abandoned`, `Refunded`).
- A customer **"My Transactions"** statement — consistent with the administrator report, offering a search bar, a status filter, and a pager — lists what a user owes and lets them **pay an outstanding balance online**: the module starts a [Checkout](../modules/checkout) session that references the transaction, contributes the outstanding balance as a one-time billing item, and marks the transaction paid only when the gateway confirms the settlement.
- An administrator **report and management console** (**Commerce → Transactions**) lists the tenant's transactions and lets managers send a reminder, record a full or partial offline payment, mark paid, cancel, or add a note — one provider-agnostic place to chase, settle, or annotate any unpaid balance. The report filters by status, searches by title, and filters by **source** through a dropdown of the sources registered by the enabled features (a module registers its friendly, localizable source name with `AddTransactionSource`).
- **Reminders delivered through the notification system.** `ITransactionReminderService` sends reminders through OrchardCore's `INotificationService`, so each reminder honors the owner's preferred channel instead of assuming email only. A background task sweeps outstanding transactions and reminds on a configurable cadence (first-reminder delay, interval, and a maximum), and managers can also send a reminder manually. Reminders are gated behind the separate opt-in **Transaction Reminders** feature (`CrestApps.OrchardCore.Transactions.Notification`), which depends on the OrchardCore **Notifications** feature; the core ledger, report, statements, and settlement work without it.
- **Authenticated and guest ownership.** A transaction now records an `OwnerKind` (`Authenticated` or `Guest`) alongside its owner id, so a purchase made without an account is owned by a stable, tenant-scoped guest customer id instead of being orphaned under a null owner. An authenticated owner is still reminded through the notification system; a guest owner is reminded by email through the optional email service using the contact captured at purchase time, and the reminder degrades gracefully when no email service or guest contact is available. The owner kind is a mapped index column (defaulting to `Authenticated` for existing rows through a schema migration) and is a filter on the transaction query. The customer-facing statement and the pay/detail authorization now require the `Authenticated` owner kind, so a guest obligation can never be viewed or paid by an authenticated user who happens to share an id.
- **Confirmed-amount, idempotent, concurrency-safe settlement.** Online settlement is applied against the amount the payment provider **actually confirmed** — read from the durable payment-attempt ledger — instead of the requested total, and the attempt currency must match the transaction currency (a mismatch is rejected, never converted). A confirmed amount that covers the balance marks the transaction `Paid`; a smaller amount marks it `PartiallyPaid`. Settlement is idempotent (re-completing the same checkout never double-applies), records the settling `PaymentAttemptId` for gateway reconciliation, and is guarded by optimistic concurrency so two nodes can never silently overwrite each other. The outstanding balance is also persisted as a mapped `OutstandingAmount` index column (normalized to the currency's precision) so a report can query and sort by what is owed without loading every document.
- New permissions gate the feature: **Manage transactions**, **Manage transaction settings**, and **View own transactions**.

The **[Pay Later](../modules/pay-later)** module is the first consumer: every succeeded Pay Later commitment records an idempotent outstanding transaction (with a due date derived from a configurable net term), so an offline "pay later" balance becomes a first-class, trackable obligation. Online settlement requires the Checkout feature and degrades gracefully when it is not enabled.

See [Transactions](../modules/transactions) for details.

### Reusable buyer identity (Customers foundation)

Two new foundation projects establish a reusable, provider-neutral way to describe *who a purchase belongs to*, so the future commerce domain (Orders, Carts) can attribute records to a buyer without every module hard-coding the authenticated user service:

- **`CrestApps.OrchardCore.Customers.Abstractions`** contributes the `CustomerOwnerKind` enum (`Authenticated`/`Guest`), an immutable `CustomerOwner` value with `ForUser` / `ForGuest` factories, the `ICustomerContact` contact value, and the `ICustomerContactResolver` contract that addresses an owner uniformly.
- **`CrestApps.OrchardCore.Customers.Core`** provides the default resolver (registered with `AddCustomersCore()`): an authenticated owner resolves through OrchardCore's user service, and a guest owner resolves from the contact captured at purchase time.

Transactions is the first consumer, using the owner value to attribute and reach both authenticated and guest buyers. A guest buyer's contact is captured on the checkout through a provider-neutral `CheckoutContactInfo` snapshot and copied onto each guest transaction so reminders can reach them. Capturing a durable guest access credential remains deliberate future hardening; the foundation records a stable guest owner id today so no obligation is orphaned.

### Commerce

This release adds **[Commerce](../modules/commerce)** (`CrestApps.OrchardCore.Commerce`) — a small module that owns the shared **Commerce** top-level admin menu and its icon. Commerce-related modules (Transactions and Taxation) now depend on it and contribute their screens under one consistently branded menu, instead of each declaring the top-level node and icon on their own (which made the icon appear or disappear depending on which module was enabled). The feature is **enabled by dependency only**, so it has no standalone function and is activated automatically whenever a module that depends on it is enabled.

Commerce is deliberately a **thin orchestration shell**: it owns no persistence, migrations, indexes, or domain data models. A new `CommerceModuleBoundaryTests` architecture test locks this in by failing the build if the Commerce assembly ever references a domain persistence assembly (or YesSql) or defines a migration, index, or index provider. This keeps the future commerce domain (Orders, Carts, Customers) in its own reusable modules with Commerce composing them.

A new provider-neutral **`CrestApps.OrchardCore.Commerce.Abstractions`** project adds the **financial-document policy seam** — the contract that decides which financial documents a money event issues (a receipt, or a persisted numbered invoice, credit note, or refund document) without the money-moving modules (Checkout, Payments, Transactions) hard-coding that decision. It contains only contracts (`IFinancialDocumentPolicy`, `FinancialDocumentContext`, `FinancialDocumentPolicyResult`, the `FinancialDocumentKind`/`FinancialDocumentReason` enums, and an `IFinancialDocumentNumberGenerator` with `FinancialDocumentNumberRequest`/`FinancialDocumentNumber`) and takes no package or project references. The shipped default, `ReceiptsOnlyFinancialDocumentPolicy`, issues a receipt only — it never persists an immutable copy and never requires a formal number — so today's behavior is unchanged and the existing `IReceiptService` printable path stays the only runtime dependency. `IFinancialDocumentNumberGenerator` deliberately ships with **no default implementation**: correct, node-safe legal numbering needs durable persistence that only exists once an Orders domain owns it, and a speculative generator would risk duplicate or reused numbers. Because the receipts-only default never requires a number, nothing resolves the generator at runtime. A future Orders domain can register a replacement policy (and a real generator) that persists numbered invoices and credit notes without changing any caller. The boundary test also asserts that `Commerce.Abstractions` references no domain persistence or providers, keeping it a pure cross-domain contract.

See [Commerce](../modules/commerce) for details.

### Refunds and reusable payment foundations

Foundation-hardening changes turn the commerce stack into a clean, reusable base a future e-commerce module can build on without another architectural rewrite. Because there is no previously released commerce stack to preserve, these are intentionally **breaking within the 3.0.0 line** in exchange for a single forward-only foundation:

- **Money is `decimal` end to end.** Every monetary amount across Payments, Checkout, Subscriptions, Stripe, and Products (`Money`, `CheckoutInvoice`, `PaymentAttempt`, `Invoice`, `ProductPart.Price`, and the payment/subscription event contexts) is now `decimal` instead of `double`, so amounts are never subject to binary floating-point drift. The `long` minor-unit representation Stripe requires stays confined to the gateway adapter (`StripeCurrency.ToMinorUnits` / `FromMinorUnits`), which converts with `MidpointRounding.AwayFromZero`; the legacy `double` overloads were removed so a caller can no longer bypass the currency-aware boundary. `System.Text.Json` reads previously persisted numeric values into `decimal` without a data migration.

- A **durable refund ledger** (`PaymentRefund` / `IPaymentRefundStore`) and an authoritative **`ICheckoutRefundService`** that resolves the settled payment, enforces the remaining refundable amount, allocates refunded tax from the original payment's immutable `TaxSnapshot`, persists the refund *before* calling the gateway, and serializes concurrent refunds of the same payment with `IDistributedLock` so two nodes can never over-refund. Gateways opt in with the additive **`ICheckoutPaymentRefundProvider`** contract; a provider with no executable refund records the refund as `PendingManualReview`.
- **Provider-neutral lifecycle events and inbound refund reconciliation.** `IPaymentEvent` now covers payment failure, cancellation, refund, and dispute/chargeback in addition to success, so every gateway raises the same normalized stream. The Stripe webhook dispatcher maps `payment_intent.payment_failed`, `payment_intent.canceled`, `charge.refunded`, `charge.refund.updated`, `refund.updated`, `refund.failed`, and `charge.dispute.created` onto these events, forwarding gateway metadata (including the checkout idempotency key) and falling back to the charge id when a refund carries no payment-intent id. A new **`ICheckoutRefundReconciliationService`** applies a refund observed at the gateway — including one issued from the provider dashboard — to the durable ledger under the same per-payment lock: it correlates by provider reference, context or metadata idempotency key, a deterministic aggregate key, or an amount-and-currency match against an open local request. It adopts the gateway's authoritative status (a blank status is treated as `Pending`, never fabricated as succeeded), never regresses a terminal local status on a stale or out-of-order event, and quarantines an unmatched remote refund idempotently as `PendingManualReview` (`remote_refund_without_local_request`) instead of losing it or fabricating a result the gateway never confirmed.
- **A canonical order-to-checkout reference contract.** `CheckoutReferenceTypes.Order` fixes the well-known `ReferenceType` an ecommerce order uses on a `CheckoutSession` (with the order's item id as `ReferenceId` and an optional version id), and `ICheckoutSessionStore.GetByReferenceAsync` resolves the most recent session for a reference. Payment stays authoritative in the attempt ledger, so an order is never marked paid from a session status alone.
- **Architecture guard tests for the reusable module graph.** New reference-direction tests keep the payment/checkout/taxation/addresses abstractions one-way and independent of concrete providers: abstraction projects may reference only other abstraction projects, and foundation projects never reference provider or presentation modules (parsed directly from each `.csproj`). A capability-truthfulness test auto-discovers every concrete provider in all loaded `CrestApps.OrchardCore.*` module assemblies and asserts that any provider advertising `Capabilities.SupportsRefunds` actually implements `ICheckoutPaymentRefundProvider`, so the flag can never lie and a provider added in any module is checked automatically.
- **Verified taxation baseline.** `TaxTable` is an effective-dated catalog document: `TaxService` never applies a table outside its effective window for the transaction date, and a rule that requires a table with no table in effect on that date is skipped instead of silently taxing at zero. Table rows are validated on write (non-negative minimums, at most one open-ended row, ordered non-overlapping bounded ranges, and an open-ended row starting at or above the highest bounded maximum), a table still referenced by a rule cannot be deleted, and recipe import validates a candidate before overwriting an existing table.
- **Stripe as a generic checkout provider.** When both **Stripe** and **Checkout** are enabled, Stripe now registers a generic `ICheckoutPaymentProvider` and `ICheckoutPaymentRefundProvider`, so any checkout can collect and refund a card payment through a Stripe PaymentIntent without depending on the subscription-specific endpoints. New Stripe services (`CreateForCheckoutAsync`, `RetrieveAsync`, `CancelAsync`, and `IStripeRefundService`) route every amount through `StripeCurrency`.
- **Consistent catalog persistence and identity.** The durable `PaymentAttempt` and `PaymentRefund` ledgers now derive from `CatalogItem` and their stores (`IPaymentAttemptStore` / `IPaymentRefundStore`) build on the shared `DocumentCatalog<T, TIndex>` base, so they inherit the same CRUD, paging, index registration (`PaymentAttemptIndex` / `PaymentRefundIndex` keyed on `ItemId`), and `IClock`-driven timestamping used everywhere else in the solution instead of a bespoke store. The business identifier on every commerce value object and ledger entry — `BillingItem`, `CheckoutLineItem`, `InvoiceLineItem`, `PaymentAttempt`, and `PaymentRefund` — is now named **`ItemId`**, freeing the `Id` name for the YesSql document identity and matching the naming convention used across the rest of the platform.
- **Products sellable seam.** `ProductPart` gains an optional **`Sku`**, and a new `ISellableProduct` snapshot with `IProductSnapshotResolver` captures what was purchasable at the moment of purchase (money as `decimal`), so an order of record is stable and self-contained. `ProductPart` and its settings now live in **`CrestApps.OrchardCore.Products.Core`**, so the sellable catalog contract can be referenced by other modules without depending on the Products module's UI and services. YesSql keys content parts by CLR type *name*, so relocating the namespace does not affect stored content. The catalog stays purchase-agnostic: the Products assemblies never reference Payments or Checkout (enforced by an architecture guard test), so payment and checkout depend on the catalog and never the other way around.
- **Product-owned currency and pricing seam.** A product now owns the currency it is sold in: `ProductPart` gains a **`Currency`** and `ProductPartSettings` a **`DefaultCurrency`** fallback, so a price is no longer implicitly tied to a single site currency. A new **`IPriceResolver`** resolves an immutable, currency-tagged **`PriceResult`** (unit price, currency, quantity, and subtotal) from a `ProductSnapshotContext`, giving checkout, payment, and future ordering flows a stable seam instead of reading `ProductPart.Price` directly. The default resolver never converts between currencies — a requested currency that differs from the product's currency is rejected (returns `null` and logs a warning) rather than silently priced with an implied exchange rate — so a future pricing engine (price schedules, quantity breaks, or customer-specific pricing) can replace it without changing any consumer. Every currency-consuming path now derives its currency from this one seam: `PriceResult` refuses to be constructed without a currency, the taxable-item projection stamps each item with the product-owned currency and the tax service rejects an item whose currency differs from the calculation context (never converting), and subscription billing — both the invoice currency and Stripe price synchronization — bills in the product-owned currency and skips (with a warning) any request to relabel it into a different currency, so no path can silently apply an implicit exchange rate.

### Addresses

A new provider-agnostic **`CrestApps.OrchardCore.Addresses.Abstractions`** project owns the shared `Address` value used across the commerce stack: the recipient name and company, both street lines, the dependent locality, city, region, postal code, sorting code and country, the county and district used for tax, and a delivery phone. Taxation, Checkout and Subscriptions all hold this one type. It is immutable, so a copy kept on an order or shipment never changes when the address it came from is edited.

This release also adds the **[Addresses](../modules/addresses)** module, with two features:

- **Addresses** (`CrestApps.OrchardCore.Addresses`) needs no content features. It registers the address formats of every country from the new **`CrestApps.OrchardCore.Addresses.Core`**, built from Google's address data (CC BY 4.0, credited in the package's `THIRD-PARTY-NOTICES.md`): the parts a country uses and their order, which are required, what they are called, the postal code pattern, and the country's regions with their ISO 3166-2 codes. `IAddressFormatProvider` gives a country's `AddressFormat`. `IAddressValidator` checks an address against it (required parts, postal code pattern, region list, postal code within the region) and stores the region by its code. `IAddressFormatter` prints an address the way its country's post expects, in Latin order for a Latin-script address in Japan, China or Korea. The data is a snapshot in the package; a site never contacts Google. Countries come from the ISO list.
- **Address Field** (`CrestApps.OrchardCore.ContentFields.Address`, in the CrestApps Content Fields module) puts an address on any content type, as many as it needs, edited with the address editor and checked against the chosen country's rules. Its settings choose whether it is required, which of the recipient, company and phone it asks for, the countries offered and the default country, and `AddressFieldIndex` indexes each address by country, region, city and postal code.
- **Address Countries** (`CrestApps.OrchardCore.Addresses.Countries`) keeps the countries a site serves as `Country` content items, seeded from the ISO list when it is enabled, so administrators can rename, add or remove them. Its content-backed `ICountryService` then fills every country list on the platform, falling back to the ISO list while there are none, and `CountryIndex` indexes the countries by their ISO code. Taxation keeps storing codes, so enabling or disabling it never orphans tax data.

### Receipts

A new reusable **[Receipts](../modules/receipts)** module (`CrestApps.OrchardCore.Receipts`) turns purchase data into a branded, printable proof-of-purchase receipt that any module can consume. A consumer supplies only what it knows (billed-to party, line items, taxes, total, and payment status) through a `ReceiptRequest`, and `IReceiptService.BuildAsync` merges the tenant's configured issuer branding and computes the subtotal to produce a `ReceiptDocument`.

- Provider-agnostic abstractions (`ReceiptRequest`, `ReceiptDocument`, `ReceiptLineItem`, `ReceiptTaxLine`, `ReceiptStatus`, `ReceiptSettings`, `IReceiptService`) depend on nothing commerce-specific, so subscriptions, future e-commerce, and other modules can reference them without pulling in payments, checkout, or taxation.
- Branding is configured once under **Settings → Commerce → Receipts** (header title, business name, logo, address, contact details, footer, and a test-payment badge toggle), guarded by the **Manage receipt settings** permission.
- The module ships a self-contained, printable receipt view that consumers render with a full-path partial (`~/Areas/CrestApps.OrchardCore.Receipts/Views/ReceiptDocument.cshtml`), so every receipt looks the same while each consumer owns its surrounding page. Printing a receipt outputs only the receipt itself — the surrounding page chrome (site header and admin menu) is suppressed by the print stylesheet.
- The module holds **no persistence** of its own: receipts are generated on demand from the consumer's own ledger, so there is no duplicated financial store. **[Subscriptions](../modules/subscriptions)** now renders its subscriber payment receipt through this module instead of carrying its own receipt view model and view.

### Wizard

A new reusable **[Wizard](../modules/wizard)** module (`CrestApps.OrchardCore.Wizard`) provides a decoupled, multi-step **wizard** (stepper) framework that any guided experience can build on — sign-up, onboarding, surveys, checkout, and more.

- **Two consumption models over one engine.** Build a wizard **via content items** by enabling **Wizard Contents** and attaching the `WizardPart` to a content type (steps are contained content items, authored just like the `OrchardCore.Flows` `BagPart`, with part settings to constrain allowed step types by content type or stereotype and a selectable editor), or **via code** by registering an `IWizardDefinition`, an `IWizardHandler`, and an `IDisplayDriver<WizardFlow>`. Both share the same flow engine, session store, public host controller, and workflow events.
- **Production-hardened completion.** Finalization runs through `IWizardEngine.CompleteAsync`, which serializes completion for a session under a distributed lock, reloads the authoritative session, verifies every data-collecting step has data, and runs the completing/completed handlers **exactly once** even under concurrent or repeated attempts. An optional `prepareUnderLock` callback lets a consumer validate and record external evidence (for example a payment return) inside the same lock before the wizard is finalized.
- **Workflow integration.** Enable **Wizard Workflows** to raise **Wizard Started**, **Wizard Step Displayed**, **Wizard Completed**, and **Wizard Failed** events, each with an optional wizard-type filter and correlated by session id.

See [Wizard](../modules/wizard) for details.

### Reports (PDF)

A new **Reports (PDF)** add-on (`CrestApps.OrchardCore.Reports.Pdf`) exports any report, and any report built with the Report Builder, to PDF next to CSV and Excel. The PDF is laid out like the report on screen: metric cards, tables with their headers repeated on every page and their cell colors, progress bars, and line, bar, area and pie charts, with numbered pages. A wide table turns the pages to landscape. Report subscriptions and workflow activities can attach the PDF like any other export format. ## Breaking Changes

### Subscriptions

- **The session-based subscription signup flow has been removed.** Buying a plan now runs through the [Checkout](../modules/checkout) framework like any other purchase, so there is one path that takes money and one ledger that records it. The public route is unchanged — `Subscription/Signup/{contentItemId}` still starts a purchase — but everything behind it is different, and a signup that was in progress when the site was upgraded cannot be resumed.

  Removed with it: `SubscriptionFlow` and its handler contexts, `ISubscriptionHandler`, `SubscriptionSession` and `ISubscriptionSessionStore`, the anonymous Stripe and Pay Later signup endpoints, the hosted-checkout return route, the subscription session admin list, the subscriber dashboard, `StripePriceSyncService` and the **Sync prices** screen, and `PaymentMethodOptions` / `PaymentMethod`. Payment methods are now discovered from the `ICheckoutPaymentProvider` implementations registered on the tenant, so the payment step can never offer a method the framework cannot execute.

- **Two sub-features were removed.** *Subscriptions - reCaptcha* guarded a step that no longer exists. *Subscriptions - Tenant Onboarding* is replaced by **Subscriptions - Sites** (`CrestApps.OrchardCore.Subscriptions.Tenants`), which provisions from a durable job instead of inline during the request that took the money. Sites already provisioned by the old feature keep running; re-enable the new feature to sell more.

- **The default payment method moved.** It is configured under the Checkout settings rather than the Subscription settings, because it applies to every purchase and not only to subscriptions.

- **Subscription reports now read the payment ledger and the durable agreement** instead of checkout sessions, and revenue is reported per currency instead of being summed into a single site-currency total. Figures will differ from 3.0 previews wherever a checkout was abandoned or failed: those were previously counted as revenue and no longer are.

### Configuration and options

Several site-settings screens no longer **release the tenant shell** when you save them. Instead, the options class that projects those settings is refreshed live through `IOptionsMonitor<TOptions>`, using Orchard Core's options update-notifier (`IOptionsUpdateNotifier.RequestUpdate<TOptions>()` and `services.AddSignalOptionsChangeTokenSource<TOptions>()`, introduced in `OrchardCore` `4.0.0-preview-19118`). Saving these settings now takes effect without restarting the tenant, and the "the tenant will be reloaded" warning has been removed from the affected editors.

The options classes changed this way are: `GeneralAIOptions`, `AIDataSourceOptions`, `McpServerOptions`, `AIMemoryOptions`, `ChatInteractionMemoryOptions`, `UserAvatarOptions`, and the telephony provider options `TelnyxOptions` and the shared `TelephonyProviderOptions` aggregate (which the Telnyx and Asterisk provider modules contribute to).

**Breaking:** `IOptions<TOptions>` resolves a process-lifetime singleton that is computed once and never observes the update signal. Any custom or external code that read one of the options above through `IOptions<TOptions>` will keep serving the value captured at first resolution and no longer pick up a settings change until the process restarts. Such code must switch to `IOptionsMonitor<TOptions>` and read `CurrentValue` (or `IOptionsSnapshot<TOptions>` in a scoped context) to observe live updates.

Settings whose consumers still read them through a singleton `IOptions<TOptions>` — currently the anonymous **AI Visitor Identity**, **Prompt Security**, and **AI Documents interaction** settings, whose readers live in the `CrestApps.Core` packages — continue to release the shell on save until those consumers are migrated to `IOptionsMonitor`.

### AI

- **AI usage tracking is a feature, not a setting.** The **Enable AI usage tracking** checkbox is removed from **Settings → Artificial Intelligence**, along with `EnableAIUsageTracking` in the `GeneralAISettings` recipe schema. Enable the new **AI Usage Analytics** feature (`CrestApps.OrchardCore.AI.UsageAnalytics`) instead: usage is recorded only while it is on, and the **AI Usage Analytics** report and its menu entry now come with it rather than with **AI Chat**. A site that had the setting ticked gets the feature enabled automatically the first time it starts after the upgrade. See [AI Usage Analytics](../ai/usage-analytics).
- **The MCP Server no longer exposes tools by default.** Previously every registered AI tool was listed and callable by any connected MCP client. Tool exposure is now **opt-in**: nothing is listed or callable until you either select the tools and tool instances on the new **MCP Server** card under **Settings → Artificial Intelligence**, add their names to `McpServerOptions.Tools`, or set `McpServerOptions.ExposeAllTools` to `true`. **Expose all tools** now exposes only *selectable* tools; system tools and hidden tools are never exposed, even when it is enabled. Deployments that relied on the previous "expose everything" behavior must enable **Expose all tools** (or populate the allow-list) to keep exposing their tools. Prompts and resources are unaffected. See [MCP Server](../ai/mcp/server#tool-exposure) for details.
- **A2A host cards now use A2A 1.0 supported interfaces.** Agent cards no longer publish the endpoint through the deprecated top-level `url` field. Clients should read the endpoint from `supportedInterfaces`, and multi-agent mode still points each interface to `/a2a?agent={agentName}`. See [A2A Host](../ai/a2a/host) for details.
- **The deployment purpose is gone; deployments declare model capabilities.** `AIDeploymentPurpose` and `AIDeploymentType` were removed from the framework, along with `AIDeployment.Purpose`, `AIDeployment.Type`, `SupportsPurpose`, `SupportsType`, `CanServeTextCompletion`, and the purpose overloads on `IAIDeploymentManager`. A deployment now says what its model can do (a **capability**), and where it gets used is a **slot** resolved from site settings and the selection on the profile, template, or interaction. `GetByPurposeAsync` / `GetAllByPurposeAsync` become `GetAllBySlotAsync`, and `ResolveOrDefaultAsync(purpose, …)` becomes `ResolveSlotAsync(AIDeploymentSlotNames.X, …)`.
  - The **Purposes** checkbox group is removed from the deployment editor. **Model capabilities** is the single place a deployment describes itself, and at least one is now required. The deployment list shows capabilities in place of purposes.
  - **Stored data needs no migration.** A record that still carries a `Purpose`, `Capability`, or `Type` — in the store, in a recipe, or in `appsettings.json` — is projected onto capabilities every time it is read. The projection is permanent, not a one-time upgrade step.
  - A deployment that had never declared capabilities used to be shown an *empty* capability list when opened, and saving anything unrelated wrote `Features = []`, silently turning it from *unconstrained* to *declares nothing*. It is now offered the defaults, which is how it already behaves at run time.
- **`ChatMode.Realtime` and the separate realtime deployment field are removed.** Whether an AI profile or a chat interaction is a speech-to-speech conversation now follows from its **chat deployment** declaring the `realtime` capability, rather than from a second stored answer that could disagree with the deployment actually selected. This is how chat interactions already worked; AI profiles now match.
  - The chat deployment picker lists text-capable **and** realtime-capable deployments; the utility picker stays text-only.
  - The **Chat mode** selector and the **text-to-speech playback** switch are hidden when the selected chat deployment is realtime, and the **Voice** picker switches to that deployment's realtime voices.
  - A site can no longer force realtime globally through the chat interaction chat mode.
  - **Stored data needs no migration.** A profile that named a `RealtimeDeploymentName` folds it onto `ChatDeploymentName` when read, and its old chat deployment moves to `UtilityDeploymentName` when the profile has not named one — so background work keeps running on the model it always did. A stored `ChatMode` of `"Realtime"` reads as `TextInput` instead of failing the settings load. `ProfileTemplateMetadata.RealtimeDeploymentName` is obsolete and still applies, supplying the chat deployment.

  See [Model Capabilities](../ai/model-capabilities) and [Realtime Voice](../ai/realtime-voice) for details.
- **One chat thread now carries both typed messages and a spoken conversation.** Pointing a profile at a speech-to-speech model used to turn the whole surface voice-only: the message box was hidden and typed messages were rejected. The chat deployment goes back to meaning only "the text model this profile talks to", and a new **Conversation deployment** names the model that carries a spoken conversation. A surface in the **Conversation** chat mode offers a voice toggle *beside* a working message box, and the user decides turn by turn which to use.
  - `ChatModeProfileSettings.ConversationDeploymentName` and `ChatInteraction.ConversationDeploymentName` name that model. Left empty, the realtime slot's own chain applies — the site's default realtime deployment, then the first realtime-capable deployment. Nothing records *how* the conversation is carried: whether the resolved deployment speaks natively or chains speech-to-text, chat, and text-to-speech is read off the deployment itself.
  - The **Chat deployment** picker lists text-capable deployments only, on the profile editor, the AI Profile Template editor, and the chat interaction settings panel. A speech-to-speech model belongs in the **Conversation deployment** picker beside it.
  - The **Chat mode** selector and the **text-to-speech playback** switch no longer disappear when a realtime model is selected, because the deployment no longer decides the mode. **Conversation** is offered whenever either a realtime deployment or the speech-to-text plus text-to-speech cascade can serve it.
  - While a voice session runs, the message box and send give way to the voice settings and the **End Conversation** button takes the width they leave; they come straight back when it ends. Sending a typed message ends the session first, so the two kinds of turn take turns rather than overlapping. The dictation microphone is suppressed while a realtime session carries the conversation, which already owns the microphone.
  - A chat interaction has no chat mode of its own, so naming a conversation deployment on the interaction is itself the opt-in to speaking.
  - Because the chain falls through to the first realtime-capable deployment, a site with *any* such deployment will carry conversations with it even with no site default configured and nothing named on the profile. There is deliberately no per-profile switch back to the cascade: to keep the cascade, have no deployment declare `realtime`; to speak without a speech-to-speech model, use a cascaded realtime deployment.
  - A conversation deployment that is named but cannot run a realtime session is reported rather than quietly replaced, so a typo does not silently move the conversation to a different model.
  - **Stored data needs no migration.** A profile stored in the old shape is folded when the editor reads it: its realtime chat deployment is shown as the **Conversation deployment** with the chat mode set to **Conversation**, and saving the profile persists that shape. Nothing is rewritten behind the user's back. `ProfileTemplateMetadata.RealtimeDeploymentName` is obsolete and still applies, now supplying `ConversationDeploymentName` and putting the generated profile in **Conversation** mode.

  See [Realtime Voice](../ai/realtime-voice) for the full resolution order.

### AI

#### Every AI request is metered, per model, category and purpose

The **AI Usage Analytics** report has a new **Metered usage** table that counts every request sent to an AI
provider, whatever the provider and whatever the kind: chat completions, embeddings, images, speech-to-text,
text-to-speech and realtime voice. Before, only chat completions were recorded.

- **One row per request.** Planning, search-query rewrites, image descriptions, each step of a tool-calling loop
  and each batch of embeddings are counted on their own, so the request count matches what the provider billed.
- **Every billable unit.** Cached input, reasoning and audio tokens are kept apart from plain tokens, with audio
  minutes for transcription, characters for text-to-speech and images for image generation.
- **Group metered usage by** **Model**, **Model and category** (chat sessions, chat interactions, `Sms`, `Voice`,
  `Api`, `Workflow`, `A2A`) or **Model and purpose** (answering, planning, retrieval, indexing, transcription,
  conversation conclusions, handoff summaries and more). A module labels its own requests with
  `UseUsageLabels(...)` on the client it creates, or with an `AIUsageScope`.
- **Voice calls show their audio tokens.** The realtime provider's usage is now recorded, so the voice table fills
  its **Audio tokens** column, and **Text tokens** include the text part of realtime responses.
- The **Chat completions** table now counts only chat completions; the embeddings and voice requests made for the
  same sessions are in the metered table.

Requires the CrestApps.Core release that meters every AI client. See
[AI Usage Analytics](../ai/usage-analytics.md#metered-usage).

#### Audio usage report: hours, characters and size for speech-to-text and text-to-speech

The **AI Usage Analytics** report has a new **Audio usage** table for speech-to-text and text-to-speech. It shows
requests, total hours of audio, hours of speech, characters, audio size, segments and tokens per model, and can be
grouped by voice or language with **Group audio usage by**. Requires the CrestApps.Core release that records audio
usage details. See [Audio usage](../ai/usage-analytics.md#audio-usage).

#### The AI profile and template editors group the model with how it is spoken to

The **Deployments** card on the AI Profile and AI Profile Template editors is now **Deployments &
Interactions**, and the **Chat mode**, **Voice**, and **Enable text-to-speech playback** fields move into it
from the *General* card. They sit directly under the chat deployment and its model parameters, because the
chat deployment is what decides whether they apply at all — with the fields a card away, selecting a
realtime model made three fields vanish off-screen. The card now reads in one pass: chat deployment, its
model parameters, how you converse with it, then the utility deployment and its parameters. Chat
interactions already grouped these in their settings panel and are unchanged.

#### Stored deployments are rewritten to declare their capabilities

A new migration step persists the model capabilities implied by each stored deployment's legacy purpose, so
the stored JSON says what the editors and the deployment list already show, and the dead legacy field stops
being carried around. Deployments that come from configuration are untouched, being read-only and outside
the store.

**A chat or utility deployment is migrated with `textGeneration`, `toolCalling`, and `streaming`.** The
framework's read-time projection maps those two purposes onto `textGeneration` alone, because they are the
only purposes that never named a single capability. In practice a deployment on the legacy purpose was
driven through a chat client that called tools and streamed its response, with no switch to turn either
off — so declaring text generation by itself would migrate a working site into one where tools and streamed
responses are silently disabled. The migration credits all three. Anything a particular model cannot really
do stays one checkbox away in the deployment editor.

Every other purpose still maps onto the one capability that named the same thing: `Embedding` to
`textEmbedding`, `Image` to `imageOutput`, `Vision` to `imageInput`, and so on. A deployment that already
declares `realtime` is left alone: it is a speech-to-speech model stored under the chat purpose, it answers
a text completion with an HTTP 400, and the purpose says nothing about it beyond that it is conversational.

Recipe, configuration, and API imports that still carry a legacy `Purpose`, `Capability`, or `Type` are
credited the same way, so an imported deployment and a migrated one end up declaring the same set.

### Reports

- `ReportFilter` no longer exposes `FromUtc`, `ToUtc`, or `DateRangeKey` as first-class properties, and `ReportContext` no longer exposes `FromUtc` or `ToUtc`. The date range is now contributed and stored like any other filter, so reports that do not need a date selector can omit it. Read and write the period through the new `ReportFilter` helpers (`GetDateRange()` / `SetDateRange()` — for example `context.Filter.GetDateRange()` inside a report), and read or write any filter value with the typed `TryGet<T>(string key, out T value)`, `GetOrDefault<T>(string key)`, and `Set<T>(string key, T value)` extension methods.
- What describes a report is now static, like the data sources of Orchard Core's Data Pipelines. `IReport` declares `static abstract` `Name`, `DisplayName` and `Description` (each a `LocalizationSource` instead of a `LocalizedString`), `Category` and `Permission`, and gets `RunAsync` from the new `IReportRunner`. Register a report with `services.AddReport<TReport>()` instead of `services.AddScoped<IReport, TReport>()`. `IReportManager.GetReports()` and `GetDescriptor(name)` return `ReportDescriptor`s, so reports are listed, routed to and authorized without being created, and `GetReport(name)` creates a report to run it; `FindByName` is gone. `IReportProvider` is replaced by `ReportOptions`: a class that runs a family of reports implements `IReportRunner`, and a module adds a `ReportDescriptor` per report, with a function that creates it. Localize a descriptor's `DisplayName` and `Description` with `IStringLocalizerFactory.Localize`.
- Designed reports run with a bounded amount of memory: rows stream from the data sources through Orchard Core's `DataJoin`, `DataAggregator` and `DataSorter`, which write the rows that don't fit in memory to temporary files, instead of being held in lists. `ReportQueryLimits` gains `MemoryLimitMegabytes`, `TemporaryDirectory` and `MaxConcurrentRuns`. A grouped `ReportQueryResult` is regrouped while the query runs, so ask for its groupings in `ReportQueryExecutionContext.Groupings` (`ReportDesignDocumentBuilder.GetGroupings` lists those of a report's visuals) before calling `Regroup` or `GetTotals`; `ReportQueryEngine.ReadAsync` streams the result rows of a query, and a live view streams its rows to the reports that read it. A calculated field that calls an aggregate function a report can't compute as the rows arrive is refused.
- `IReportExportFormat` likewise declares a static `Name`, `DisplayName` (a `LocalizationSource`), `Extension` and `ContentType`. Register a format with `services.AddReportExportFormat<TFormat>()`; `IReportExportManager.GetFormats()` returns `ReportExportFormatDescriptor`s.

### Telephony

The following public contracts changed in the Telephony module and its abstractions. External providers and callers that build on these types must update to the new signatures.

- The `CrestApps.OrchardCore.Telephony.Admin` feature has been removed. The provider settings screen and administration menu are now part of `CrestApps.OrchardCore.Telephony`, and provider features register their settings drivers directly. Remove the old feature ID from recipes and deployment plans.
- `TelephonyConstants.Feature.Admin` has been removed. Use `TelephonyConstants.Feature.Area` when declaring a dependency on Telephony.
- The public `TelephonyAdminStartup` and `AsteriskAdminStartup` classes have been removed because their registrations now live in each module's primary `Startup` class.
- `ITelephonyAuthenticationProvider.RevokeTokensAsync` now returns `Task<TelephonyResult>` instead of `Task`. Callers receive a typed confirmed-success, definitive-failure, or indeterminate result instead of relying on an exception or assuming success. External implementations of this interface must update their signature.
- `ITelephonyAuthenticationService.DisconnectAsync` now returns `Task<TelephonyResult>` instead of `Task`, for the same reason.
- `RecordingMediaWriteRequest.Content` is now a `System.IO.Stream` instead of a `byte[]`, so recording media streams to storage rather than being buffered in memory. Any code that constructs this request directly must supply a stream.
- `ITelephonyUserAccessor` exposes `ReloadCurrentUserAsync()` and `PersistCurrentUserAsync(Func<IUser, bool> mutate)`. The persist method loads the current user in an isolated unit of work, applies the mutation, and durably commits only that user document, so a serialized token refresh or a disconnect makes its write visible to other requests without flushing unrelated changes staged by the ambient request. Custom implementations of this interface must implement these members.
- `IVoiceMediaProvisioner` gains `GetAvailabilityAsync(string mediaReference, CancellationToken)`, which reports whether the provider still holds a clip (`VoiceMediaAvailability.Available`, `Missing` or `Unknown`), so a lost copy can be made again from the platform's master copy. It has a default implementation that answers `Unknown`, so an existing provisioner keeps compiling and behaving as before; override it to let a lost copy be made again. `IRecordingMediaStore` now also holds voice media master copies, and `RecordingMediaWriteRequest.InteractionId` is `null` for them.
- In Contact Center Core, `ProviderCallActionCommandTypeExecutor` and its `Reject` and `SendToVoicemail` executors take an `IVoiceMediaProvisioningService` and an `IVoiceMediaCopyRecorder`, and `WarmTransferService` and the Telnyx `TelnyxIvrProvider` and `TelnyxQueueTreatmentProvider` take an `IVoiceMediaProvisioningService`, in place of reading `VoiceMediaItem.MediaReference` (the Telnyx providers no longer take `IVoiceMediaItemManager`). `VoiceMediaItem` implements the new `IVoiceMediaAsset` and gains `MasterStorageReference`, `ContentType` and `ProviderReferences`; `AgentProfile` gains `VoicemailGreetingMedia`. Code that read `VoiceMediaItem.MediaReference` to play a clip should call `IVoiceMediaProvisioningService.ResolveAsync` with the provider's technical name instead.

### Omnichannel contact methods

Code that reads or writes a contact's phone numbers and emails, or builds these services by hand, must update:

- `OmnichannelSubjectWriter.GetContactEmail(ContentItem)` is removed; use `IContactMethodsAccessor.Get(contact).GetPrimaryEmailAddress()`. `OmnichannelSubjectWriter.TryApplyContactEmailAsync` takes an `IContactMethodsWriter` in place of an `IContentManager`.
- `SmsMessagingChannel`, `DefaultContactActivityBatchLoader` and `OmnichannelContactPartContentImportHandler` take an `IContactMethodsAccessor`, and `ActivitiesController` takes one too. Register the services with `services.AddContactMethods()` when you build them outside a module startup that already does.

### Admin lists

Every admin list now renders through Orchard Core's `AdminList` shape (`OrchardCore` `4.0.0-preview-19191`). Code that customized or built on the old list markup must update:

- A list view model exposes its records as an `AdminListContext` (`List`, or `ScheduledList`/`CompletedList` on pages with two lists), and the controllers no longer build `SummaryAdmin` row shapes. `CatalogEntryViewModel<T>.Shape` is no longer filled by the shipped controllers, `ListCatalogEntryWithReadOnlyViewModel<T>.ReadOnlyModels` became `ReadOnlyList`, and several row view models moved to `Models` as the row's display model (for example `NotInServiceNumberEntry`, `SubjectFlowEntry`, `SubjectActionEntry`, `ProfileBuilderSessionEntry`, `PhoneNumberVerificationRecord`). `ActivitiesController` no longer takes an `IDisplayManager<OmnichannelActivityContainer>`.
- Each row is the `{Model}_SummaryAdmin` shape in the **List** layout and the `{Model}_SummaryAdminGrid` zones in the **Grid** layout. A theme override of a whole row template only applies to the List layout; the Grid layout is customized with `SummaryAdminGrid` placement or an `AdminListCell-{List}-{Column}.cshtml` template. A driver that adds a shape to one of these rows must also give it a `SummaryAdminGrid` location, or it does not show in the grid.
- Items of a row's `ActionsMenu` zone are bare `<a class="dropdown-item">` elements. A template that wraps them in `<li>` renders an empty menu.

## Change Logs

### A working checkout

The Checkout framework shipped its contracts, durable ledgers, reconciliation, and refund machinery, but nothing drove them: no component created a payment attempt, called a provider, or moved a session out of `Pending`. The generic Stripe card provider, the Pay Later provider, and the refund service were all registered and unreachable, and the *Pay* action on an outstanding transaction started a checkout there was no page to complete. This release makes the framework real.

- **A checkout engine.** `ICheckoutEngine` is now the single entry point for every money-moving step — start, begin payment, complete, cancel. Controllers, endpoints, webhooks, and background tasks all go through it and never touch a payment provider or the ledger directly. It creates one durable attempt per obligation, persists each **before** contacting the provider, stores the provider's reference the moment it returns, and completes a checkout only when every obligation is confirmed against the provider's own API.
- **A public checkout.** Enabling the feature adds a customer-facing checkout at `/Checkout/{sessionId}/{step}` with a progress stepper, an invoice summary, payment-method selection, and a confirmation page. Steps are contributed by display drivers, so a feature adds a step without touching the page, and a theme can restyle the whole frame by overriding one shape.
- **Payment methods come from the registered providers.** The payment step lists the providers actually registered on the tenant and hides any that cannot settle what the invoice owes, so the page can never offer a method the framework is unable to execute. Stripe contributes an embedded card panel and Pay Later an offline confirmation panel, each through its own display driver.
- **Completion no longer blocks a request.** It previously polled the provider for up to 60 seconds inside the web request. Completion is now a fast, idempotent call driven from three directions — the customer's browser, a provider webhook, and the reconciliation sweep — so a customer who pays and then closes the browser still has their purchase fulfilled, server-side.
- **Compensation.** When one obligation fails at the provider, the obligations that already settled are refunded through the durable refund service, so a customer is never left paying for half a purchase.
- **Settling a balance online works.** Choosing *Pay* on an outstanding transaction now takes the customer into the checkout with the balance already loaded, instead of returning them to a page that could not collect it.

Subscriptions still runs its own signup pipeline and does not yet start every purchase through the engine; a subscription bought through the public checkout, however, now produces a durable agreement.

### Recurring payments are real agreements

A recurring line on an invoice used to become a single charge. The customer paid once, nothing renewed, and nobody found out until the money stopped arriving.

- **A recurring capability.** A payment provider that bills on a cycle now implements `ICheckoutRecurringPaymentProvider` under its own provider key. The checkout groups the recurring lines by interval, makes one obligation of each, and routes it there. A provider that claims recurring support but ships no implementation is refused before any money moves, so a wiring mistake cannot turn a subscription into a one-off charge.
- **Stripe subscriptions at any price point.** The Stripe adapter creates a real Stripe subscription with the price defined inline, so nothing has to be synchronized to Stripe before it can be sold; per-customer, computed, and one-off amounts all work. Verification reads the subscription's latest invoice back from Stripe, so an agreement only settles once its first cycle is genuinely paid, and rolling back a checkout cancels the agreement rather than leaving it billing.
- **Card details still never reach the site.** A gateway cannot create an agreement without a reusable payment method, so a provider's client script may tokenize the card in the browser first and hand back only the token. The first invoice is then confirmed against that very payment method rather than attaching a second one.
- **Pay Later can back a subscription too.** An offline recurring commitment records its own schedule on the ledger, and a sweep invoices the next period once the current one ends. Each cycle is created exactly once even across retries and multiple nodes.

### Subscriptions that outlive their checkout

A completed checkout used to be the only record that somebody had subscribed, which made every ordinary question expensive: who is subscribed right now, whose payment failed last night, what renews next month.

- **A durable subscription agreement.** Every recurring obligation a checkout settles now creates an agreement carrying what it bills, on what cycle, through which gateway, the period paid through, when the next cycle is due, and a full event history. It is created only from payment attempts the checkout actually confirmed, and looked up by obligation first, so an unpaid checkout never grants access and a checkout that completes twice never produces two agreements.
- **One place state changes.** A gateway webhook, a nightly sweep, an administrator, and the customer all edit subscription state, and they race. Every transition now goes through one lifecycle service that locks the single agreement, re-reads it, and is idempotent. Reporting the same renewal twice advances it once; a second payment failure inside the same dunning window does not restart the grace clock; a gateway status arriving after a local cancellation cannot revive it.
- **Access outlives cancellation.** Whether a subscriber currently has access is answered separately from the status, so a customer who cancels mid-cycle keeps the time they paid for and a past-due one keeps access through the configurable grace window (7 days by default).
- **A sweep that closes the loop.** Agreements whose grace window elapsed are expired, and those that billed every cycle they were sold for are closed, so nothing sits past due forever or looks due to bill something it must not.
- **Screens for both sides.** Administrators get a **Commerce → Subscriptions → Agreements** report with cancel, pause, and resume actions, each written to the agreement's history. Subscribers get **My Plans**, where they can cancel their own subscription; cancelling defaults to ending at the close of the period they already paid for.

### Payments and refunds an operator can see

Every charge already left a durable record, but there was no way to look at one. An operator asked whether a customer had paid had to read the database, and a refund that a payment method could not settle automatically sat in the ledger with nobody to act on it.

- **A payments ledger.** **Commerce → Payments** lists every attempt with what was expected, what settled, and the gateway's transaction reference, filtered by state and method.
- **Refunds start in one place.** The refund form shows what was collected and what has already gone back, refuses an amount above what is still refundable, and issues the refund through the refund service so the ledger, the original payment's tax allocation, and the over-refund protection all apply. An in-flight refund counts against the remaining amount, so a second refund cannot be started for money already on its way back.
- **Manual settlements have a home.** **Commerce → Refunds** surfaces refunds needing manual settlement and lets an operator record the reference once they have moved the money. Only a refund in that state can be closed that way.
- **A separate permission.** Giving money back is the one action in the suite that cannot be undone, so it needs **Manage payments and refunds** rather than coming free with the ability to read the outstanding report.

### Subscriptions can grant member-only access

A subscription used to be a billing record and nothing more: somebody paid and nothing about the site changed for them, and somebody stopped paying and kept everything.

- **Entitlements on the plan.** Attach the **Subscription Entitlements** part to a plan and pick the roles a subscriber holds. The entitlement lives on the plan because different tiers grant different things, and what it grants is copied onto the subscription at creation so editing the plan later cannot change what an existing subscriber was sold.
- **Access follows the agreement, not the status.** The role is granted while the subscription is *current* and removed when it stops being current. A subscriber who cancels mid-cycle keeps it through the period they paid for, and one whose renewal failed keeps it through the grace window.
- **A question the rest of the site can ask.** `ISubscriptionAccessService` answers whether a user currently holds an entitlement, so content, features, and permissions become subscription-aware without any of them knowing subscriptions exist. Implement `ISubscriptionEntitlementApplier` to grant something other than a role.

### Workflow events for the whole subscription life

Subscription lifecycle events — started, renewed, past due, canceled, expired — are now raised as workflow
events, so a site owner builds the reaction they want without writing code. Each carries the subscription,
its owner, both statuses, and the dates access depends on, and is correlated by the subscription so one
workflow can wait for a later stage of the same agreement. Only a genuine status change raises an event,
so a sweep that only moves dates does not message anyone.

### A Commerce starter recipe

A **Commerce starter** recipe enables the suite, creates a `Member` role, defines a Membership Plan content
type, and publishes a monthly plan that grants that role, so a new site can take a real recurring payment
without wiring anything by hand. Each of the seven Commerce modules also gained a README explaining what it
is for and which decisions it makes on the caller's behalf.

### A site sale that survives a restart

Selling an Orchard Core site used to create the tenant inline, in the request that completed the checkout. A slow recipe, a brief database outage, or a deployment restarting the process left a customer who had paid with no site and nothing to retry.

- **The purchase and the build are now separate.** The checkout records a durable provisioning job; a sweep builds the site from it and keeps trying. A job stranded by a process that died is reclaimed rather than lost.
- **Everything the customer can fix is checked before payment.** A site name that is taken, a domain that belongs to another site, a prefix already in use: all are refused while they can still change them, instead of after their card is charged.
- **Failure is visible and finite.** Each attempt records its error and backs off; after enough failures the job is marked abandoned rather than retried forever, and appears on an admin screen where an operator can retry it. Customers watch their own site being built under **My Sites**.
- **The site follows the subscription.** A site sold on a plan is disabled when the subscription lapses and runs again when it resumes. Disabled, never deleted, so a late payment restores the site exactly as it was.

### Installment plans an administrator sets up

The new **Subscriptions - Installment Plans** feature lets an administrator sell on a payment plan without the
customer going through the storefront. See [Installment plans](../modules/installment-plans).

- **One screen to set it up.** Pick the customer (or create one from a name and email), enter the total, the
  down payment, the number of later payments, how often they fall due and when the first does, and see the
  schedule before saving. The balance is split evenly at the currency's precision and always adds up to the total.
- **The down payment is taken by card on the next page,** entered by the administrator, and the card is kept for
  the schedule. The scheduled payments are then charged to it on each due date, or invoiced to the customer.
- **Every payment is an ordinary transaction and every charge goes through the checkout,** so payments show in the
  Transactions report and in **My Transactions**, can be paid early or recorded by hand, are verified against the
  gateway, and can be refunded like any other.
- **A declined card is retried** on a configurable schedule (1, 3 and 5 days by default) and the customer is told
  each time; after the last retry the payment is left for the customer to pay. A charge still settling at the
  gateway is finished, never repeated.
- The plan's page shows every payment, the card on file and its expiry, and the history, with **Charge now** and
  **Cancel the plan**.

Supporting it, across the suite:

- **Stripe keeps a card and charges it without the customer.** `PaymentProviderCapabilities.SupportsSavedPaymentMethods`,
  `ICheckoutSavedPaymentMethodProvider` and `CheckoutPaymentDataKeys` (`savePaymentMethod`, `offSession`) make it
  provider-neutral.
- **A checkout can be started for someone else** with `StartCheckoutRequest.OwnerId`, including from a background
  task with no request.
- **A declined charge is recorded as one.** `PaymentBeginResult.Decline` fails the attempt with the gateway's reason,
  `PaymentBeginOutcome` carries it as `ProviderErrorMessage`, and the next attempt gets its own idempotency key.
- **Customers are told a payment is coming due,** once, a few days before it does (**Remind before the due date**
  under the transaction reminder settings). A payment that will be charged names the card.
- **A receipt after every payment.** The new **Send Payment Receipts** feature of Transactions sends one for each
  payment applied to a transaction, however it was paid. Printable receipts, linked from each payment on a
  transaction's timeline, and printable invoices are available whenever Transactions and the Receipts module are both
  enabled, whether or not receipts are sent. `ITransactionPaymentHandler` is raised for every payment, online or
  offline.
- **Apple Pay and Google Pay on the card panel.** The Stripe panel of the checkout offers the device's wallet above
  the card form, so a down payment (or any checkout) can be taken on a phone with a tap. Connecting Stripe registers
  the site's domain for wallets. See [Apple Pay and Google Pay](../modules/payments#apple-pay-and-google-pay).
- **A charge is never taken twice when recording it fails.** Before charging a scheduled payment, a plan applies any
  charge the gateway already accepted for it, read from the durable payment attempts
  (`IPaymentAttemptStore.GetByReferenceAsync`). Applying confirmed attempts to a transaction moved into
  `ITransactionSettlementService`, shared by the checkout and the plans.
- **The commerce lists look like the rest of the admin.** Installment plans, subscriptions, My Plans, My Sites,
  site provisioning, transactions, My Transactions, payments, refunds and coupons are list-group lists. Search sits in the action bar; status, source and method
  filters sit in the list header; each row shows its details as badges; Orchard Core's pager sits below and offers
  a page size selector when **Allow users to change the page size** is on in the general settings. Coupons, My Plans,
  My Sites and site provisioning gained paging, with a status filter where it helps.
- **The page size selector shows up.** The admin theme's `Pager_PageSizeSelector` template reads `Model.Items`, which
  binds to the shape's own (empty) child list rather than the page sizes, so it rendered nothing on any listing. The
  Commerce feature adds an alternate that reads the sizes from the shape's properties, and centers the pager with the
  selector at the right.
- **My Sites and Site provisioning are part of Subscriptions - Sites.** Their pages answer only when that feature is
  on, instead of failing.
- **Sensitive actions ask first.** Charge now, Cancel the plan, Record payment, Mark as paid, Cancel transaction,
  Refund and Mark settled each ask for confirmation.
- **Invoices with a link that pays them.** A transaction its owner pays themselves is numbered `INV-1001`, … the
  first time they are told about it, and every reminder carries a signed, expiring link that pays it without signing
  in, which customers created by an administrator (who have no password) and guests need. The invoice has a printable
  page, administrators can copy the pay link from it, and the receipt names the invoice it settled. See
  [Invoices and pay links](../modules/transactions#invoices-and-pay-links).
- **Fixed: paying a transaction online looped back to an empty step.** The checkout's payment step sent the payer
  back to any earlier step it did not find saved, including the transaction's balance step, which collects nothing
  and so is never saved. Steps that collect nothing are no longer waited for, and the balance step is hidden, so the
  checkout opens on the payment.
- **Fixed: customers got "You do not have access" on their own pages.** My Plans, My Sites, My Transactions and
  their invoices and receipts are admin pages, and customers who buy through the checkout have no admin access. Pages
  marked `[CustomerAdminPage]` now open for any signed-in user; they still check the customer's own permission, and the
  rest of the admin stays closed. See [Customer pages in the admin](../modules/commerce#customer-pages-in-the-admin).
- **Confirmations on subscription actions.** Cancel subscription, Pause billing and Resume on an agreement ask
  before they act.
- **Fixed: a plan with no price could be signed up to for nothing.** A plan the site couldn't price (for example,
  no currency and no default currency on its type) still started a checkout that billed nothing, said *No payment is
  required*, and completed: registering the buyer and, for a site plan, creating the site. Sign up now shows *This
  plan can't be bought right now* and logs what to fix, and a subscription checkout that bills nothing recurring is
  never completed. See [A plan that can't be sold](../modules/subscriptions#a-plan-that-cant-be-sold).
- **Fixed: paying a balance with Pay Later marked it paid.** Pay Later was offered when a customer paid an outstanding
  transaction, and its commitment counted as a payment, so the transaction became *Paid* with nothing collected.
  Providers that record a promise to pay now say so (`PaymentProviderCapabilities.DefersPayment`); a checkout that
  settles an existing balance neither offers nor accepts them, and settlement ignores their attempts. See
  [Not for paying an existing balance](../modules/pay-later#not-for-paying-an-existing-balance).
- **Fixed: tax rules for a jurisdiction taxed everyone.** When no jurisdiction was resolved for a buyer (the
  checkout supplies no address), every enabled rule for the item's category applied, whatever its jurisdiction, so
  a California sales tax was charged to buyers anywhere. A rule for a jurisdiction now applies only where that
  jurisdiction is resolved; rules with no jurisdiction still apply everywhere. See
  [Tax sourcing](../modules/taxation#tax-sourcing).
- **Fixed: a rule for a parent tax category skipped its child categories.** A rule for *Electronics* didn't tax an
  item classified as *Television*, although *Television*'s parent is *Electronics*. A rule now covers its category
  and every category under it.
- **Receipts have short numbers.** Each receipt is numbered `R-1001`, `R-1002`, … per site instead of carrying the
  transaction and payment identifiers. `IFinancialDocumentNumberGenerator` now has a shipped, node-safe sequential
  implementation.
- **Customers are told about refunds and canceled plans.** Send Payment Receipts sends a notice for every refund that
  succeeds, through the new `IPaymentRefundHandler`; a customer whose installment plan had started is told when it
  is canceled.
- **Fixed: installment plans grew on every save.** Their computed properties were stored and read back into the
  plan's own payments, doubling a list each time, until a plan reached hundreds of megabytes and its pages took
  seconds to open. They are no longer stored.
- **Fixed: settling a transaction through the checkout taxed it a second time.** The transaction already carries its
  tax; its balance is now left out of the tax determination (`BillingItem.ExcludeFromTax`).
- **Refunds update their transaction.** A finished refund adds a *Refunded* entry to the transaction's timeline and
  to its new `AmountRefunded`; once everything paid is refunded, the transaction becomes *Refunded*, a status nothing
  set before. See [Reacting to a refund](../modules/transactions#reacting-to-a-refund).
- **Commerce screens speak plainly.** Payment states, refund statuses, subscription and site provisioning statuses,
  timeline and history events, payment methods, transaction sources, price intervals and jurisdiction levels are
  shown by name instead of by stored value (`PastDue`, `PendingManualReview`, `pay-later`). Amounts use the
  currency's own precision, and plan prices show the plan's currency instead of the server's. The agreement page
  names its owner. Page titles match the menu (*Agreements*, *My Plans*, *My Sites*), and the subscription editor's
  labels are in sentence case.
- **Fixed: commerce pages showed UTC times.** The transaction, agreement and plan pages and the My Plans list printed
  their stored UTC times, so a payment taken in the evening could show the next day's date. Times and dates are now
  shown in the site's time zone, as the lists already did; due dates, which are calendar dates, are unchanged.
  Invoices and receipts are dated in the site's time zone too.
- **Commerce buttons match what will work.** Record payment, Mark as paid, Cancel transaction and Send reminder are
  only available while a transaction can be collected, and Send reminder asks first. Customers are only offered
  *Pay now* on a transaction they can still pay. Refund isn't offered on a Pay Later promise, and a refund the
  service refuses shows a message instead of an error page. Site provisioning offers *Retry now* only on a job that
  can finish, and an abandoned job whose site was created by hand can be closed with *Mark as created*.
- **Fixed: Commerce settings that blocked or misled.** Tenant Onboarding settings could not be saved without a
  domain option that nothing reads; the domain options (*Use custom domains*, *Local domains*, *Generated domain
  template*) are removed, since the buyer enters the site's address while checking out. The Feature profile editor for tenant onboarding rendered with the wrong model
  and never showed the saved profile. Stripe's *Checkout Mode*, which nothing reads, is no longer offered, and
  *Disconnect* warns that the keys are deleted. A coupon's currency is chosen from the site's currencies, and a
  currency that products are priced in can't be deleted. The tax table editor no longer shows the unused *Base
  amount* column.

### Installment plans that belong to a record, and that customers choose at checkout

Installment plans can now be tied to another module's record, can start without a down payment, and can be chosen by the customer when they pay an outstanding balance. See [Installment plans](../modules/installment-plans).

- **A plan names the record it pays for.** `CreateInstallmentPlanRequest` gains `ReferenceType`, `ReferenceId` and `Properties`, copied onto the plan. Every transaction of the plan gets the reference as its new `Transaction.ParentReferenceType` / `ParentReferenceId` (indexed in the new `TransactionParentReferenceIndex`) and a copy of the properties, so a module finds its record from any plan payment without a mapping table of its own. `ITransactionStore.GetByParentReferenceAsync` lists every payment of a record and `IInstallmentPlanStore.GetByReferenceAsync` finds its plans. Additive migrations add the index table and three columns to `InstallmentPlanIndex`.
- **No down payment needed.** `DownPaymentAmount = 0` is accepted: the first scheduled payment is then due at once and is taken in its place, and the schedule runs from today. The administrator's form accepts **0** too, with the first payment due today.
- **"Choose how to pay" at checkout.** A checkout that pays an outstanding transaction can offer **Pay in full** or installments, such as *3 monthly payments*. The options come from `IInstallmentOptionProvider` implementations, one per transaction source; the built-in one offers what **Settings > Installment Plans > Installments at checkout** configures. Choosing installments turns the transaction into a plan (`IInstallmentPlanService.CreateFromTransactionAsync`), takes the first payment in the same checkout and keeps the card (the new `CheckoutSession.SavePaymentMethod`), and the remaining payments are charged automatically like any other plan. The original transaction is canceled once the first payment is received; a plan whose checkout is left is closed and the balance stays owed.
- **The browser can't decide to keep or spend a card.** The public begin-payment endpoint now drops the saved-card provider-data keys, and the engine adds `savePaymentMethod` itself when the session keeps the card, refusing a provider that can't.
- **Installment plans no longer need Subscriptions or Products.** The **Subscriptions - Installment Plans** feature now depends on Transactions, Checkout and Users only. Its settings moved from a card on **Settings > Subscriptions** to their own page, **Settings > Installment Plans** (permission *Manage installment plans and charge customers' saved cards*; *Manage subscriptions settings* still works). Without Products, the admin form asks for the currency code instead of listing managed currencies.

### Coupons, and discounts that are taxed correctly

- **Discounts run before tax.** Taxing the full price and discounting the total charges the customer tax on money they never paid. `ICheckoutDiscountService` applies reductions to the untaxed invoice, keeps a total from going below zero, and reduces the one-time amount and the first cycle separately so a setup-fee coupon never eats a monthly charge.
- **A coupon catalog.** Percentage or fixed amount, targeting the one-time amount or the first cycle, with a validity window, a minimum, and a usage limit. A fixed-amount coupon only applies in its own currency.
- **A discount comes off the items, and each line is taxed on what's left.** A one-time discount no longer takes anything off shipping, and its percentage and minimum count the items only. What it takes off is spread across the item lines by price (`CheckoutLineItem.DiscountAmount`) and passed to tax per line (`TaxableItem.DiscountAmount`); before, each line was taxed on its full price, so a coupon order was over-taxed. Orders keep their discounts (`Order.Discounts`, `Order.DiscountTotal`), and the order pages, the guest page and the confirmation email list them, so the lines, discounts, shipping and tax add up to the total. See [Discounts and coupons](../modules/checkout#discounts-and-coupons).
- **Fixed: checkout charged no tax on some tenants.** The no-op tax service registered without Taxation replaced the real one whenever the Checkout startup ran after the Taxation one, which depends on which other features a tenant has on. It is now a fallback (`TryAddScoped`).
- **Product reviews.** The new **[Product Reviews](../modules/reviews)** feature (`CrestApps.OrchardCore.Reviews`) lets buyers rate and review products they bought, marked as verified purchases. The store approves them under **Commerce > Reviews** (settings under **Settings > Commerce > Reviews**). Approved reviews show on the product's page with its stars, and the average rating goes into the product's listing record, so listings offer a **Customer rating** filter and a **Customer rating: highest first** sort. Products gain `IProductListingEntryProvider`, for modules to add automatic listing filters and sorts, and `ProductAttributeKeys.Rating` and `ReviewCount`.
- **Tax-exempt customers and the store's origin reach checkout tax.** A customer can be marked **Exempt from tax**, with why; a signed-in exempt customer pays no tax at checkout, and business customers are taxed as businesses with their tax id. The store's address under **Settings > Commerce > Tax origin** is the origin for taxes sourced where the seller is. Both reach the tax profile through the new `ICheckoutTaxProfileHandler`, run by the default profile provider. Before, the checkout never passed the customer or the origin to tax.
- **Digital downloads.** The new **[Digital Downloads](../modules/downloads)** feature (`CrestApps.OrchardCore.Downloads`) delivers digital products. The **Digital files** part uploads a product's files to a private store under the tenant's App_Data, never the media library, once Orchard Core's file creation pipeline (an antivirus scanner, for one) has accepted them. A paid order gives its buyer each file (`DownloadEntitlement`) through a signed link on their order page and in the confirmation email, which works for a number of downloads and days set under **Settings > Commerce > Downloads** or on the product, and stops when the order is canceled or refunded in full. The store can take a download back or give it back from the order's page. Orders gain `IOrderEmailSectionProvider` for modules to add sections to the confirmation email. A **Digital downloads sample** recipe adds a Digital Product type with two ebooks.
- **Order reports.** With Reports on, **Reports > Commerce** gains **Sales** (gross, discounts, shipping, tax, total, refunded and net by day or month, per currency), **Sales by product**, **Sales by country**, **Tax on orders**, **Discounts on orders**, **Refunds** and **Orders to ship** from the Orders feature, and **Stock on hand** from Inventory. Before, every commerce report read subscription payments. See [Reports](../modules/carts-and-orders#reports).
- **Refund, cancel and annotate an order from its page.** An order's page gains a **Manage** box: refund an amount or everything (to the card for an order paid online, through its transaction for Pay Later), cancel it with a reason, refunding everything, canceling what Pay Later still owes and putting the stock back, and send its confirmation again. **Notes** keep what the store writes and what happened, with who did it. Refunds started anywhere, including the payment screens, are recorded on the order (`Order.Refunds`, `OrderRefundRecorder`), which shows *Partially refunded* or *Refunded* (`Order.RefundStatus`). ### Fixes found by running the checkout

Standing the suite up and buying something surfaced defects that no unit test could see, because in each case the page returned `200` and simply did the wrong thing:

- **A concealed step's charges vanished from the invoice.** The plan a subscriber chose is billed on a step that is never drawn, and the invoice was built only from visible steps, so a subscription checkout totalled `0.00` and completed for nothing.
- **Three catalogs had no database table.** Subscriptions, coupons, and site-provisioning jobs each live in their own YesSql collection, and a collection's document table is only created when the collection is declared in `StoreCollectionOptions`. Their index migrations ran clean and the first read threw *no such table*.
- **Five editors rendered as empty boxes**, including the payment method list — the one thing a customer needs in order to pay. Orchard Core builds a shape by deriving a proxy from the view model, a sealed model cannot be derived from, and the resulting `TypeLoadException` is swallowed by the display manager.
- **The checkout's scripts never loaded.** `OrchardCore.ResourceManagement` is not a transitive dependency of `OrchardCore.DisplayManagement`, so `<script asp-name>` rendered as literal markup and the payment page had no behaviour at all.
- **Two admin screens threw on their first page load** because a partial view sat in `Views/` rather than `Views/Shared`.
- **A promotion code was silently ignored.** The payment script owns the form's submit, so a code typed into the box was never posted and the customer was charged full price with no error shown.
- **The guards that stop payment being reached early never ran.** `Initializing`, `Loading` and their pairs were declared on `ICheckoutHandler` but never raised by anything.

Each of these now has a regression test, including two that read the source tree so a missing collection declaration or a missing package reference fails the build rather than a customer's purchase.

### One product, several prices

A product carried a single amount, so selling the same thing monthly and annually, per seat, or for
whatever the buyer thinks it is worth meant creating a separate product for each.

The new **Product prices** part offers a product at as many prices as it needs — one-time or recurring,
each with its own interval, cycle limit, trial, start delay, setup fee, optional buyer-named amount within
bounds, optional quantity, and an availability window. A recurring price is what makes a product
subscribable, so the same product can offer a one-time purchase and a monthly plan side by side. A product
with no prices of its own is still sold at the single amount on its product part, so the part is opt-in.

The plan card becomes a chooser when there is a choice to make and stays a single button when there is
not, and the chosen price rides on the checkout rather than the request — a checkout outlives the request
that began it, and a purchase completed by a provider notification has no browser to re-read a query string
from. Nothing the buyer sends is trusted: a withdrawn price, an amount outside the bounds, and a quantity
beyond the maximum are each refused when the price is resolved, not only in the editor.

At Stripe a fixed price now becomes one reusable price identified by a key that includes the amount, so the
same offer is not recreated for every customer, and raising a price creates a new one instead of silently
repricing everyone already subscribed to it. An amount the buyer named has no reusable offer behind it and
stays inline.

### The payment ledger moved to Transactions

The durable record of payment attempts and refunds lived in Checkout while the module that reports on it,
settles from it, and administers it is Transactions. The ledger types now live where they are owned, and
the dependency points one way: the checkout writes to the ledger, and the ledger knows nothing about the
checkout. The financial-document contracts moved with it — a receipt or invoice number belongs to the
ledger that issues it — which emptied `CrestApps.OrchardCore.Commerce.Abstractions`, so that package is
gone.

This is a namespace move: `CrestApps.OrchardCore.Checkout.Models.PaymentAttempt` and friends are now
`CrestApps.OrchardCore.Transactions.Models`, and the stores and indexes are under
`CrestApps.OrchardCore.Transactions.Core`. Nothing about the stored data or the tables changed.

### Fixes found by selling a site

Selling an Orchard Core site through the checkout was then run end to end on a live installation: a plan
carrying the tenant-onboarding part, a buyer naming their site and its administrator, a real card, and the
provisioning sweep building the tenant. Two defects made the feature impossible to use at all:

- **A purchased site could never be created.** Nothing gave the new tenant a database, so setup refused every
  attempt with *"DatabaseProvider setting is required"* — the customer was charged and no site ever appeared.
  The database new sites are created on is now configured once under **Subscriptions → Tenant onboarding**,
  and defaults to Sqlite so that selling a site works before anything is configured. Sites that share a
  database each get a table prefix derived from their name.
- **A job that failed once could never succeed.** Setup registers the tenant before it creates anything, so a
  failed attempt left the name behind in the running process, and every retry then failed with a name
  collision the previous attempt had invented. An uninitialized shell left by a failed attempt is no longer
  read as a name that is taken.
- A setup failure reported as a message rather than an exception left nothing in the log, and the job keeps
  only the newest message — so the first attempt's reason, usually the real one, was lost. Every failed
  attempt is now logged with its own reason.

### Fixes found by running the integration against Stripe

The commerce suite was then exercised against a real Stripe test account, including Stripe test clocks to
advance time through real billing cycles. That confirmed the money paths end to end — a trial that collects
nothing and converts when it ends, a fixed-cycle plan that stops after the cycles it was sold for, a
first-cycle coupon that does not recur, a renewal recorded from the gateway's own notification, a failed
renewal that starts dunning, and a refund — and it found four defects that no test with a fake gateway could
have shown:

- **A plan with a setup fee could not be paid by card at all.** The browser tokenizes one card for the whole
  checkout and confirms both obligations with it, but the one-time payment intent was created with no
  customer, while the agreement had attached that card to one. Stripe refused the confirmation outright:
  *"the payment_method supplied belongs to the Customer …"*. The two obligations of a checkout now resolve a
  single customer, keyed by the checkout, and the client data the recurring path already received now
  reaches the one-time path too.
- **Cancelling never reached the gateway.** `CancelRecurringAsync` was implemented by both providers and
  called by nothing at all, so a subscriber who cancelled saw their subscription end, lost access at the end
  of the period, and kept being charged every month. Cancelling — at period end or immediately — now stops
  billing at the gateway.
- **Suspending an agreement did not suspend billing.** The admin reported "billing was suspended" while the
  gateway kept collecting. Pausing and resuming now reach the gateway, through a new provider capability
  that Stripe implements with `pause_collection` and offline providers satisfy locally.
- **A gateway notification could quietly undo a local suspension.** A gateway that suspends collection still
  reports the agreement as *active*, so the next synchronization read that as "resumed" and put it back on
  the schedule. A local suspension, like a local cancellation, is now treated as a decision the gateway
  cannot express. Synchronizations also name the gateway they came from, so a change the gateway reported is
  never sent back to it.

### Settings pages open for roles that hold only their permission

Each settings page checks its own module permission in its menu item and its editor, but Orchard Core's settings screen only lets a user in when that permission is registered for the page's settings group. Without the registration, a role that held, for example, only **Manage Stripe Settings** saw **Settings > Payments > Stripe** in the menu and then got access denied (#900).

- The Stripe (`stripe`), Transactions (`transactions`), Pay Later (`paylater`) and Receipts (`receipts`) groups were registered first, in the module startup that registers each driver.
- Every other settings group whose driver checks a module permission is now registered too, in the startup of the feature that brings the driver: Subscriptions, Telephony (with the soft phone widget, Asterisk and Telnyx), Contact Center (with agent numbers, recording and secure capture), every AI feature on **Settings > Artificial Intelligence** (each with the permission its section checks), the DNC registries, Phone Number Verifications and its providers, and User Display Name and User Avatars.
- The Telnyx SMS section of **Settings > Communication > SMS** now requires **Manage SMS Settings**, as Orchard Core's own SMS and Twilio sections do, and registers that permission for the `sms` group.
- An architecture test fails when a new settings driver with its own permission is added without registering it. See [Settings groups and the permissions that open them](../feature-reference#settings-groups-and-the-permissions-that-open-them).

### Stripe from the application configuration

Stripe can now be configured from the tenant's application configuration as well as from **Settings > Payments > Stripe**, so CI, staging and demo tenants can take test-mode payments with environment variables alone, tenants can be provisioned with their keys automatically, and secrets can stay in a vault (#908).

- **A `CrestApps_Stripe` configuration section.** It is read per tenant from `IShellConfiguration` and holds `IsLive` and, for each of the `Test` and `Live` modes, `PublishableKey`, `SecretKey` and `WebhookSecret`, for example `OrchardCore__CrestApps_Stripe__Test__SecretKey`. Configuration wins over the settings page one value at a time; a value it leaves out falls back to the stored setting. See [Configuration from the application settings](../modules/payments#configuration-from-the-application-settings).
- **The settings page shows where each value comes from.** A configured value is shown read-only with *Configured from the application settings.*, a configured secret is never shown, and saving the page never overwrites it. **Connect** uses a configured secret key without copying it into the database, and does not create a webhook when the signing secret is configured.
- **A `StripeSettings` recipe step and deployment step.** The deployment step exports the stored settings without the secret keys, the webhook signing secrets, or the connected account and webhook identifiers. The recipe step protects clear-text secrets before it stores them, keeps the stored secret when the step carries none, checks every key's Stripe prefix, and ignores account and webhook identifiers. See [Moving Stripe settings between environments](../modules/payments#moving-stripe-settings-between-environments).

### Fixes from an independent review of the implementation

Reading the finished code against the plan, rather than against the intent, found a second set of defects. None of these were visible in the browser, because each shows up only over time, at a gateway, or under failure:

- **A free trial could never complete.** The gateway honestly reported zero collected, and reconciliation refused it for falling short of the cycle amount. A deferred first cycle now expects nothing, so a trial settles; the gateway is still told the real price and the deferral.
- **First-cycle coupons were display-only.** The attempt and the Stripe price were both built from the undiscounted line, so the customer saw a discount and paid full price. Worse, the recurring price was derived from the first attempt, so a discount that had applied would have recurred forever. The recurring price now comes from the plan's cycle amount; the first-cycle reduction is expressed at Stripe as a single-use coupon and locally as a smaller first debt.
- **Billing-cycle limits were ignored at Stripe** for inline prices, so a plan sold as "three cycles" billed until the customer cancelled. Inline agreements now carry a `cancel_at` for the end of the last cycle.
- **Gateway renewals never advanced the local agreement.** `invoice.payment_succeeded` for a cycle now records the renewal against the period the gateway named, idempotently.
- **Offline agreements were never renewed.** Pay Later's sweep created the next debt but nothing moved the agreement; the lifecycle sweep now advances any agreement whose provider has no gateway, and converts an ended offline trial into its first billed cycle.
- **Webhook and sweep completion was blocked for signed-in buyers**, because the account step decided whether it applied from the *request's* user, which a webhook does not have. It now decides from the checkout's owner.
- **A fulfillment failure after payment lost its write and was never retried.** YesSql discards everything written after a cancel, so "mark failed" silently did nothing while the customer had paid. Confirmed payments are now committed before fulfillment runs; a fulfillment that throws leaves the checkout for the sweep to retry rather than marking it failed or refunding.
- **Abandoned checkouts never expired.** `ICheckoutEngine.ExpireAsync` and a **Session lifetime** setting release what a provider was holding; a checkout that collected money is never expired, only fulfilled.
- **A completed checkout existed twice.** `CheckoutSession` had no YesSql identity, so saving it again after a commit inserted a second document rather than updating the first. It now has one, and a SQLite-backed store test pins it.
- Smaller: a begin that failed part-way committed after its lock was released; a provisioning job's claim was not committed before the slow work; the payment-status endpoint did not check ownership; a checkout submitted before any payment was begun was moved to a state its own page refused to show.

### The module that starts a checkout sets where the customer returns

A checkout started from a family portal, a registration form or a pay link used to end on the generic *Order confirmation* (*your purchase is complete*) with no way back, and a customer who abandoned the payment step had no link back either. Every consumer had to add its own confirmation driver to fix that.

- **`StartCheckoutRequest.ReturnUrl`, `ReturnText` and `Title`.** They are stored on the session as `CheckoutReturnInfo`. The confirmation page shows a **Continue** button to the return URL, the payment step (and the first step) shows a **Back** link to it, and `Title` replaces the *Order confirmation* heading.
- **Local URLs only.** `ICheckoutEngine.StartAsync` throws `ArgumentException` for a return URL that is not local (`CheckoutReturnInfo.IsLocalUrl`, the same rule as `IUrlHelper.IsLocalUrl`), before the session is created.
- **A page for a checkout that ended.** Opening a canceled, expired or failed checkout shows *This checkout is no longer available.* with the reason and the **Back** link instead of a `404`, and opening a completed one redirects to its confirmation.
- **The pay-link page passes itself.** `TransactionPayController` starts its checkout with the pay page as the return URL, *Back to the payment page*, and the heading *Payment received*.

See [Where the customer returns](../modules/checkout#where-the-customer-returns).

### Free trials

A recurring plan can start with a free trial. The gateway is told about the trial and starts billing when it ends, so the schedule survives a restart of this application rather than depending on the site remembering to charge later.

### Guest checkouts belong to one browser

A pending guest checkout was recognized by IP address and user agent. That identifies a population rather than a person: everyone behind one office router or mobile carrier shares an address, and a user agent is neither secret nor unique. Anyone who could observe or guess both could resume a stranger's checkout and read the contact details and amounts on it.

A guest checkout is now issued a 32-byte random ownership token in a data-protected, HTTP-only cookie. Only its SHA-256 hash is stored, and the comparison is fixed-time, so a leaked database does not hand an attacker the ability to resume live checkouts. The same token protects wizard and subscription sessions; the IP address and user agent remain as audit fields only.

### Subscription renewals, failures, and cancellation

A subscription previously had no life after its first payment: renewals were recorded but nothing else moved, and the site had no way to learn that a subscription had failed or been cancelled. This release closes that gap.

- **Renewals now extend the subscription.** A successful cycle payment advances the recorded expiration by exactly one billing cycle, measured from the previous expiration rather than from the moment the notification was processed, so a late-handled renewal never shortens a paid period. Previously every subscription looked like it expired at the end of its first cycle no matter how long the customer kept paying, which is what the expiring-subscriptions report read.
- **Payments carry their own dates.** Each recorded payment now stores the date it was collected. Renewals were previously indexed and receipted under the date the subscription was created, so revenue-by-month, tax-collected, and product-performance reports attributed every renewal to the signup month, and a renewal receipt showed the signup date.
- **Failed renewals and cancellations are recorded.** The Stripe webhook now subscribes to `invoice.payment_failed`, `customer.subscription.updated`, and `customer.subscription.deleted`, delivered through two new provider-neutral events (`SubscriptionPaymentFailedAsync`, `SubscriptionStatusChangedAsync`). A failed renewal moves the subscription to **Past due** and records when it first fell behind; a cancellation made in the gateway dashboard is reflected locally with its cancellation date and paid-through date. A recorded subscription now carries a `SubscriptionLifecycleStatus`.
- Stale and out-of-order notifications are handled deliberately: an unrecognized gateway status leaves local state untouched instead of guessing, and a late payment failure never resurrects an already-cancelled subscription.

:::warning Reconnect Stripe after upgrading
An auto-provisioned webhook endpoint subscribes to the event list that existed when it was created. Click **Connect** on the Stripe settings page again so the endpoint is re-provisioned with the new subscription lifecycle events; otherwise they are never delivered.
:::

These states are recorded but not yet enforced — there is no automatic access revocation, dunning sequence, or customer/admin cancel action yet.

### Tenant onboarding administrator password

Provisioning a subscribed tenant passed the administrator password to the setup service **still data-protected**, so every site sold through tenant onboarding was created with an administrator account nobody could sign in to. The password is now unprotected immediately before setup, provisioning aborts with a reported failure if it cannot be unprotected (rather than creating an unusable tenant), and the protected secret is removed from the durable session once provisioning reaches a terminal outcome instead of being retained for the life of the subscription.

### Transaction management guards

The transaction management screens now share a single set of rules about which operations a transaction accepts:

- Recording a payment, marking paid, cancelling, and sending a reminder are refused on a transaction that already reached a terminal state (paid, cancelled, refunded, or abandoned), with a message explaining why. Previously a cancelled obligation could be marked paid and a paid one cancelled.
- Recorded payments are rounded at the transaction currency's own scale, so a zero-decimal currency is never recorded with fractions it cannot be paid in.
- A concurrent edit now surfaces as "reload and try again" instead of an unhandled server error. The ledger checks document versions so two managers cannot silently overwrite each other; the loser of that race previously saw a `500`.

### Customer invoices, receipts and statements in the site theme

Customers who never use the admin can now see their transactions in the site theme. The Transactions module adds front-end pages beside the `[CustomerAdminPage]` admin pages: the statement at `my-transactions`, the printable invoice at `my-transactions/invoices/{itemId}` and the printable receipt of a payment at `my-transactions/receipts/{itemId}/{paymentId}` (named routes in `TransactionsConstants.RouteNames`). Each renders a shape a theme can override: `TransactionStatement`, `TransactionInvoice` and `TransactionReceipt` (`TransactionsConstants.Shapes`).

- **Same ownership rules.** The admin invoice and receipt pages and the new pages build their documents through the new `ITransactionCustomerPageService`: a customer sees only what their account owns, a manager sees any invoice or receipt, and someone else's transaction is `404`. A visitor who is not signed in is sent to sign in.
- **Builders in the abstractions.** `ITransactionInvoiceBuilder`, `ITransactionReceiptBuilder`, `TransactionInvoiceViewModel` and `TransactionReceiptViewModel` moved to `CrestApps.OrchardCore.Transactions.Abstractions`, keeping their namespaces, so another module can build and render the documents without referencing the Transactions module. The implementations and their registration stay where they were. `TransactionReceiptViewModel` gains the `Payment` event.
- **Links in messages.** Receipts and reminders sent to a signed-up customer now link to the receipt (**View your receipt online**) or, for an invoiced payment, the invoice (**View your invoice**). `CrestApps:Transactions:CustomerPages:LinkTarget` decides whether they open the admin pages (`Admin`, the default) or the site pages (`Site`). See [Transactions](../modules/transactions.md#links-in-messages).
- The admin invoice page shows the copyable payment link to administrators only, as before; customers keep the **Pay now** button.

### Transaction lifecycle events

A module that keeps its own state in step with a transaction could only see payments and refunds; a console cancel, a declined installment charge and a payment becoming overdue only saved the record. `ITransactionEventHandler` (with `TransactionEventHandlerBase`) now reports `CreatedAsync`, `StatusChangedAsync(previous, current)`, `CanceledAsync(reason)` and `BecameOverdueAsync`:

- `TransactionManager` raises them after the save, diffing the status against what was loaded, so every change through the manager is covered and a save that leaves the status as it was (a reminder, a note) raises nothing. Handlers are wrapped in try/log and never undo the change.
- The reminder sweep raises `BecameOverdueAsync` once per transaction, the first time it finds one unpaid after its due day, and records it in the new `Transaction.BecameOverdueUtc`. It runs even when scheduled reminders are turned off.
- A declined installment charge that will be retried (or that an administrator charged on or after the due date) now marks its transaction `Failed` instead of leaving it `Pending`, so the decline is a real status change.
- A cancellation keeps the reason that was entered in the new `TransactionEvent.Reason`, which `CanceledAsync` receives.

See [Transactions](../modules/transactions.md#reacting-to-lifecycle-changes).

### A transaction command service, with adjustments and invoices

The logic for **Record payment**, **Mark as paid** and **Cancel** lived in the Transactions admin controller, so a module could not offer the same actions with the same side effects. `ITransactionCommandService` now holds them, the console delegates to it, and it adds what was missing:

- `RecordOfflinePaymentAsync` (now with a payment reference), `MarkPaidAsync` and `CancelAsync`, with the same timeline entries, receipts and `ITransactionPaymentHandler` / `ITransactionEventHandler` calls as before.
- `AdjustAsync` with a `TransactionAdjustmentKind` (`Discount`, `Waiver`, `Credit`, `WriteOff`). It adds the new `Transaction.AmountAdjusted` and a `TransactionEventType.Adjusted` event; `OutstandingAmount` is now `TotalAmount - AmountAdjusted - AmountPaid`. An adjustment never exceeds what is owed, and a transaction left owing nothing is settled (`Paid`, settlement method `adjusted`) and never reminded. Invoices list each adjustment as a line and receipts note it. The console has a new **Adjust or waive** card.
- `SendInvoiceAsync` issues the invoice number and sends an *Invoice INV-1001* notice with the pay link (`TransactionEventType.InvoiceSent`), counted as the first notice. The console has a new **Send invoice** card when Transaction Reminders is enabled. `ITransactionReminderService` gains `SendInvoiceAsync`.
- `RefundAsync` refunds the confirmed payments of a transaction through `ICheckoutRefundService`, newest first, up to the amount.
- Each command returns a `TransactionCommandResult` with errors instead of throwing, runs under a distributed lock on the transaction and commits before releasing it.
- Marking paid after an adjustment records only what was still owed as paid, and online settlement treats a transaction as paid once the payments and adjustments cover it.

See [Transaction commands](../modules/transactions.md#transaction-commands).

### Coupons on transaction payments, and coupons limited to a source or a customer

Paying an existing transaction (from **My Transactions**, a pay link, or a checkout with `ReferenceType = "Transaction"`) runs a checkout that settles an existing balance. A coupon there used to leave the transaction `PartiallyPaid` (a partial code) or `Outstanding` with the code still used up (a 100% code). The first fix (#938) stopped offering and applying coupons on such checkouts; they are now accepted and recorded properly:

- `CheckoutSession.AcceptsDiscountsOnBalance` says the module settling the balance takes the discounts off it. Without it, a settlement checkout still shows no promotion code box and applies no discount, as #938 made it. The Transactions module sets it.
- On completion, `TransactionSettlementCheckoutHandler` records each code as a `Discount` adjustment of exactly what the invoice took off (`ITransactionCommandService.AdjustAsync`), then applies the payment. A 100% code settles the transaction with no payment; a partial code plus the payment settles it in full.
- A code on a settlement checkout is redeemed only once the transaction is settled: `CouponRedemptionCheckoutHandler` leaves such sessions to the settling module, which calls `ICheckoutDiscountProvider.RedeemAsync` when nothing is owed.
- `Coupon.Sources`, `Coupon.ReferenceTypes`, `Coupon.CustomerId` and `Coupon.CustomerEmail` limit a code to transaction sources, checkout or transaction reference types, and one customer. `CouponScopeEvaluator` checks them when the code is entered and in `CouponDiscountProvider`, against the session and the new `CheckoutDiscountScope` the Transactions module stores on a settlement checkout. The coupon editor has a **Who and what it is for** section.

See [Coupons on a checkout that settles an existing balance](../modules/checkout.md#coupons-on-a-checkout-that-settles-an-existing-balance).

### Pay several outstanding transactions in one checkout

One checkout can now settle several outstanding transactions of one customer with one payment, so a customer who owes several charges pays them together instead of once each (#1008).

- `StartCheckoutRequest.References` lists the things to pay for, all of one reference type (`CheckoutReference`: `ReferenceType`, `ReferenceId`). The session keeps them in the new `CheckoutSession.References`, and its `ReferenceId` is empty. A list of one starts exactly the checkout `ReferenceType`/`ReferenceId` start, and a checkout started with `ReferenceId` is unchanged. Mixing reference types, naming an id twice, or setting both `ReferenceId` and `References` throws `ArgumentException`.
- A handler can now refuse a checkout while it is being activated: `CheckoutFlowActivatingContext.Reject(error)`. `ICheckoutEngine.StartAsync` then throws the new `CheckoutRejectedException`, with the reasons in `Errors`, and saves nothing.
- For `ReferenceType = "Transaction"`, `TransactionSettlementCheckoutHandler` refuses transactions that don't exist, have nothing left to pay or can no longer be paid, belong to different customers, or are in different currencies. Each transaction is a line of the checkout at what it still owes, and no promotion code is offered, as on any balance whose module takes no discounts.
- On completion the confirmed payment is split across the transactions in the order they were listed, each up to what it still owes, through the new `ITransactionSettlementService.ApplyShareAsync`. Each records its share as its own payment naming the one payment attempt, so status, receipts, payment handlers and lifecycle events work per transaction.
- Refunds stay per transaction. **Refund** on a transaction gives back only its share of the shared payment, and the refund names it (`PaymentRefund.ReferenceType`/`ReferenceId`, from the new `RequestPaymentRefundContext.ReferenceType`/`ReferenceId`), so it is recorded on that transaction only. A refund of the whole payment from **Commerce → Payments** or the gateway is split back over the transactions in order.

See [Paying several transactions at once](../modules/transactions.md#paying-several-transactions-at-once).

### Checkout compensation refunds

When the checkout framework rolls back a payment attempt whose charge already succeeded, the compensating refund is now written to the durable refund ledger before the gateway is called. Previously the refund was issued directly, so the gateway's own refund notification found no matching local request and had to be quarantined for an operator to resolve by hand — for a refund the application itself had issued.

### A test payment provider ships with Checkout

Consumers that take payments through the checkout had to write their own fake provider to test the whole flow without Stripe keys or a browser that can drive a card form. The new **Test payments** feature (`CrestApps.OrchardCore.Checkout.TestProvider`, category Payment Providers) ships one.

- **Pay with two requests.** `POST checkout/{sessionId}/payment/begin` with `{"providerKey":"test"}` succeeds with no client action, and `POST checkout/{sessionId}/payment/status` completes the checkout and settles the transaction it pays. Verification reports the attempt's amount as authoritative, in `GatewayMode.Testing`, so the checkout cross-checks it exactly as it does for a real gateway.
- **Refunds, saved payment methods and recurring agreements.** The provider implements `ICheckoutPaymentRefundProvider`, `ICheckoutSavedPaymentMethodProvider` and `ICheckoutRecurringPaymentProvider`, so refunds flow back to the transaction and installment plans and subscriptions can be tested.
- **Magic amounts.** An amount ending in `.02` is declined; one ending in `.05` stays pending until the reconciliation sweep completes it.
- **Never offered in production by mistake.** The provider is registered only in the Development environment, or when `CrestApps:Checkout:TestProvider:AllowOutsideDevelopment` is `true`. When the feature is on but the provider is inactive, a warning is logged.
- **A one-line panel** on the payment step says that no money moves.

See [Test payments](../modules/checkout#test-payments).

### Charging a kept card for a new transaction

A module could keep a customer's card at checkout and an installment plan could charge its own copy later, but nothing let a module find the cards a customer kept, or charge one for a new, unrelated transaction, such as renewing a subscription charged to the card on file.

- **Kept payment methods.** The new `ISavedPaymentMethodStore` (Checkout) holds each customer's kept cards as `CustomerPaymentMethod` records, from any provider: list, find (scoped to the owner), default card, make default, remove, and remove all. Every checkout that keeps the card (`CheckoutSession.SavePaymentMethod`), such as an installment plan's first payment or a booking deposit, adds it when it completes. Erasing a customer's personal data forgets them.
- **Charging one.** `ITransactionCommandService.ChargeSavedPaymentMethodAsync(transactionId, savedPaymentMethodId)` charges what is owed to the owner's kept card without them present, through the checkout, so the payment is verified, recorded, receipted and raised to the payment and lifecycle handlers like any checkout payment. `TransactionCommandResult.ChargeStatus` (`SavedPaymentMethodChargeStatus`) reports `Succeeded`, `Pending`, `Declined`, `RequiresAuthentication`, `Failed` or `NotCharged`, so the caller can fall back to the invoice. A charge that is not taken is recorded as the new `TransactionEventType.PaymentFailed` (**Payment failed**) timeline event. A card that is not the owner's is refused, and a charge still settling is finished instead of repeated.
- **Telling a decline from a bank that wants the cardholder.** `PaymentBeginResult.RequiresAuthentication` (with `PaymentBeginResult.AuthenticationRequired(...)`) and `PaymentBeginOutcome.RequiresAuthentication` carry it from the provider through the engine. Stripe reports it for `authentication_required`.
- **Test payments.** An off-session charge ending in `.03` is refused as needing the cardholder's approval, so all three outcomes can be tested without a gateway.
- **The account page.** With Stripe enabled, **Payment methods** in the storefront account lists the kept cards under **Cards for automatic payments**, with **Make default** and **Remove**.

See [Kept payment methods](../modules/checkout.md#kept-payment-methods) and [Charging a kept card](../modules/transactions.md#charging-a-kept-card).

### Taxation admin UI

The **Taxation** management screens (Categories, Types, Jurisdictions, and Rules under **Commerce → Taxation**) were fixed and polished:

- The Create and Edit forms now render their fields. The editor view models were `sealed`, but the display manager builds a runtime proxy of each editor view model; a sealed type made the proxy creation throw a `TypeLoadException` that the display pipeline swallowed, silently rendering an empty form. The view models are now open, so every field displays.
- The top-level **Commerce** admin menu now shows an icon, following the Orchard Core `NavigationItemText-{id}.Id.cshtml` convention.
- Jurisdiction and Rule **effective from/to** dates are now date-only pickers without a time component or UTC label, so a rule's validity window is captured as a plain calendar date.
- The Jurisdiction **Country** field is now a dropdown populated from the canonical ISO 3166-1 country list provided by the Addresses module (the stored value is still the ISO country code). Region, county, and city remain free text pending a subdivision reference source.
- Tax **Rules are now source-aware and extensible by calculation method**, following the same source-aware pattern used elsewhere in the platform (for example AI data sources and deployments). Clicking **Add Tax Rule** opens a dialog that lists every registered calculation method — Percentage, Fixed amount, Per unit, Per weight, Per volume, Progressive, Threshold, and Tax table lookup. The method you pick becomes the rule's **source** (stored on the new `TaxRule.Source` property, replacing the former `CalculationMethod` property) and is fixed for the life of the rule. A shared display driver renders the fields common to every rule, while a per-source driver renders only the calculation fields the selected method needs: each `ITaxCalculationMethod` declares its required inputs through the `TaxCalculationMethodInputs` flags, so the percentage method shows the **Rate** field, the fixed/per-unit/per-weight/per-volume methods show the **Fixed amount** field, and the table-driven methods (Tax table, Progressive, Threshold) show a **Tax table** selector. This removes the previous calculation-method dropdown and its client-side field toggling. Third-party calculation methods contribute their own field requirements (and can register their own per-source driver) without changing the editor, and fields not used by the selected method are cleared on save so a rule never stores misleading configuration. Save-time validation still blocks money-affecting misconfiguration: a table-driven method cannot be saved without a **Tax table**. The **Display name** (`TaxName`) is now optional and falls back to the rule **Name** on invoices and receipts when left empty. Jurisdictions also preserve a stored country code that is not in the dropdown, so re-saving can never blank the country and accidentally broaden the rule to every country.
- Tax **Types are now a user-managed catalog** with their own **Commerce → Taxation → Types** screen (add, edit, delete), recipe step, and deployment step. The rule editor's **Tax type** field is a dropdown populated from this catalog instead of a hardcoded list, and a rule that already stores a value not present in the catalog keeps it. The catalog is seeded with the well-known types (`SalesTax`, `VAT`, `GST`, and more) on first run so existing behavior is preserved, while operators can now curate the tax types their business actually uses. A tax type remains a reporting and grouping label that never changes how an amount is calculated.
- The commerce content parts now contribute **recipe JSON Schema** when the **`CrestApps.OrchardCore.Recipes`** feature is enabled, matching the rest of the platform. `ProductPart` (Products), and `SubscriptionPart`, `SubscriptionSummaryPart`, and `TenantOnboardingPart` (Subscriptions) each contribute their settings and payload schema, so authoring `ContentDefinition` recipes for products and subscription plans gains editor validation and IntelliSense. The parts continue to import/export through Orchard Core's built-in `ContentDefinition` and `Content` steps; no part-specific recipe or deployment step was added.
- The `Customers`, `Stock`, `StripeSettings` and `IndexUsers` recipe steps now have **recipe JSON Schema**, each registered only while the feature that runs the step is enabled (Customers, Inventory, Stripe, and CrestApps Users with Orchard Core Users), so the AI agent's recipe tools and the MCP recipe-step resource list and describe them.

### Taxation tables, treatments, and nexus thresholds

The taxation engine gained the pieces needed to configure and calculate every supported tax type end to end:

- **Tax tables are now manageable.** A new **Commerce → Taxation → Tables** screen (add, edit, delete), plus a `TaxTable` recipe step and deployment step, let you build the named, versioned bracket tables that the **Tax table lookup**, **Progressive**, and **Threshold** calculation methods depend on. Previously those methods were selectable in the rule editor but unusable because there was no way to create a table for them to read. Each table row captures a **Minimum**, optional **Maximum**, **Rate**, **Fixed amount**, and **Base amount**, and saving a table increments its **Version**, which is captured on every tax line and snapshot that used it.
- **Exempt, zero-rated, and reverse-charge supplies now produce a visible line.** Instead of silently dropping a tax when the customer is exempt, holds a valid exemption certificate, or the rule is a reverse-charge rule for a B2B customer, the engine emits a `TaxLine` with `TaxAmount = 0` and a `Treatment` (`Exempt`, `ZeroRated`, `ReverseCharge`, or `OutOfScope`) plus a human-readable `TreatmentReason`, so compliant invoices and receipts can show the tax as exempt or reverse-charged rather than omitting it. Only a rule the merchant has no nexus for produces no line at all. A new **Reverse charge** flag on tax rules drives the EU-style B2B reverse-charge behavior.
- **Inclusive fixed-amount taxes are un-grossed.** Tax-inclusive pricing previously extracted only inclusive **percentage** taxes from the gross price. The engine now also subtracts inclusive **fixed-amount** taxes (`FixedAmount`, `PerUnit`, `PerWeight`, `PerVolume`) before dividing out the combined percentage rate (clamping the net base at zero), so an inclusive fixed fee no longer leaves the net base overstated.
- **Economic-nexus thresholds are supported.** `MerchantTaxRegistration` gains an optional `ThresholdAmount` and a host-maintained `ThresholdAccumulatedAmount`, so a registration establishes nexus only once accumulated sales into the jurisdiction reach the threshold. This models destination-based economic-nexus rules (for example the US *Wayfair* thresholds) while keeping the engine deterministic and free of a sales ledger.

### Subscriptions checkout

The subscription checkout flow was hardened so that a hosted, redirect-based payment (Stripe Hosted Checkout) and offline **Pay Later** work reliably for both authenticated and anonymous customers:

- The pending subscription session is now persisted when the signup page is first rendered, so the payment step always references a durable, distributed-safe session. Previously an authenticated customer — whose registration step is skipped, making Payment the first step — reached the payment endpoints with a session that had never been saved, so Stripe Hosted Checkout and Pay Later failed. A returning visitor resumes the same pending session (tracked in a cookie) instead of orphaning a new one, and a resumed session is never re-saved on render, so a concurrent checkout completion can never be reverted to *Pending*.
- Checkout completion started from the standard signup POST (used by Pay Later) is now serialized with the same per-session distributed lock already used by the Stripe return, so a duplicate submission cannot run the provisioning handlers twice.
- The Stripe Checkout Session UI mode was updated to `hosted_page`, matching the current Stripe API (the previous `hosted` value is no longer accepted).
- The Subscriptions feature now depends on `OrchardCore.Title`, so a plan that uses the Title part always renders (the service plans list no longer errors when Title is not separately enabled).
- The signup wizard header was redesigned as a horizontal **line-with-circles stepper** that visualizes progress: completed steps are green (with a check), the current step is highlighted, and upcoming steps are muted. The payment-step invoice was rebuilt as a standard Bootstrap table using Bootstrap 5.3 contextual colors, so both rely on native Bootstrap classes with minimal custom CSS.
- The payment step now always shows the chosen payment method, even when only one method is available. Previously a single method was submitted through a hidden field and never displayed; it now appears as a selected option so nothing about the payment is hidden from the customer.

### Contact Center

Version `3.0.0` introduces the **Contact Center**, a new module family that turns the Omnichannel CRM into a full contact center. It sits between the CRM and the Telephony module: the CRM owns the business work, Telephony executes the media, and the Contact Center orchestrates routing, reservations, dialing, disposition, and supervision. Every capability ships as its own feature, so a tenant enables only what it needs.

Highlights:

- **Orchestration core** — a headless interaction lifecycle with a durable, append-only domain event log and baseline permissions, so every call and work item has a reliable, auditable history.
- **Agents, presence, and availability** — agent profiles with presence states, capacity, and skills, plus durable agent sessions with heartbeat and after-call recovery that work with or without a real-time connection.
- **Queues and reservations** — work queues with prioritized items and concurrency-safe reservations, so an activity is offered to exactly one agent at a time.
- **Policy-based routing** — capacity- and skill-aware assignment with sticky-agent, SLA-aging, business-hours, and overflow strategies that match each interaction to the right agent.
- **Inbound and outbound voice** — a provider-agnostic Voice Contact Center Call Router with inbound entry points, caller qualification, and business-hours decisions, plus an optional soft-phone incoming-call experience. Entry points now support a **Route to** target of either a queue or a **specific agent**: an agent-target entry point offers the dialed number (DID) directly to the named agent as a personal line and falls back to the target queue when that agent is unavailable. Agent profiles also define an **outbound caller id** field intended for presenting an agent's assigned number on outbound calls with providers that support per-call caller id (such as Telnyx); the field is on the model but is not yet surfaced in the agent editor or resolved on the dial path, so outbound calls currently present the tenant default (or a per-call/campaign) caller id.
- **Dialer** — Manual, Preview, Power, and Progressive dialing strategies with scheduled pacing and outbound activity batches routed through Contact Center voice providers.
- **Dialer attempts that never reach an agent are dispositioned by the dialer** — a call that rings out, is busy, rejected or failed, is screened out as an answering machine, or that the customer hangs up on before the agent is connected is completed with the disposition for its outcome (new outcomes *Rejected*, *Call failed* and *Disconnected*), as the system, and never pops on, rings for or asks a disposition of the agent. The record opens only once the agent is connected. A disposition's **Try Again** action, or the new **Schedule Dialer Retry** workflow task, puts the next attempt back in the same campaign with the same dialer profile, honoring **Max attempts** (now counted correctly from the first call) and the retry delay, which is also checked before an agent is reserved. **Activity disposition applied** now carries the attempt number, the maximum and remaining attempts, the dialer outcome and the dialer profile.
- **Abandoned calls on automated dialing** — when a person answers a Power or Progressive call and the reserved agent cannot be connected, the profile's **Abandoned call message** (with `{company}` and `{number}` placeholders) is spoken before the call ends, instead of silence. Each profile now measures its abandonment rate from new **Dialer call answered by a person** and **Dialer call abandoned** events (a call no agent reached within two seconds), shows it on the editor, and the abandonment-rate cap enforces it. Automated calls ring for a configurable **Ring time**, never less than 15 seconds.
- **Predictive dialing mode** — the **Contact Center Paced Dialing** feature now offers the **Predictive** mode on dialer profiles, alongside Power and Progressive. A Predictive profile reserves an agent for every call, like Power, and places fewer calls per cycle as the abandonment rate nears the cap. A new **Predictive pacing** card shows the profile's measured answer rate, ring time and connect time, and holds the settings over-dialing will use (target abandonment rate, lines per agent, calls in flight, answer-rate floor and window, agents about to free up, connect wait). Tenant timings live under `CrestApps:ContactCenter:PredictiveDialing`.
- **Predictive over-dialing** — a Predictive profile on the new **Over-dial** pacing model places more calls than there are free agents, sized from the measured answer rate so the abandonment rate stays near its target, and connects the free agent who has waited longest when a person answers. When nobody is free, the person hears the abandoned-call message at once and the call counts as abandoned. Over-dialing requires the abandonment cap, the abandoned-call message and a target below the cap, and falls back to one call per reserved agent whenever its measurements cannot be trusted or the abandonment rate nears the cap. Campaigns are paced as agents free up and calls are answered or end, not only once a minute.
- **Over-dialing safeguards** — an agent who is Available on a campaign has their soft phone stand by and answer the call they are connected to at once, without waiting for the platform's notice, which shortens the silence after a person answers; inbound offers still ring for the agent to accept. An agent whose phone does not pick up within a few seconds (`AgentLegAnswerTimeout`) is put back to work and the person hears the abandoned-call message, and a minute sweep settles any answered call nothing connected. A connect wait can only be saved when the measured time to connect an agent leaves room for it within two seconds. The next attempt that **Try again** or a workflow creates for a contact whose call was abandoned is dialed only with an agent reserved for it. The **Predictive pacing** card shows the last pacing decision of every campaign the profile dials. A campaign whose pacing lock was busy is paced again a second later, and agents also waiting on inbound queues can optionally be left out of the over-dial (`DiscountAgentsWithWaitingInbound`).
- **Consolidated, less-confusing features** — the agent capability (**Contact Center Agents**, `…ContactCenter.Agents`) now owns agent profiles, presence, and canonical availability together, and the work-distribution capability (**Contact Center Work Distribution**, `…ContactCenter.Queues`) now owns queues, reservations, and routing together, so there are fewer overlapping toggles to reason about. Capability features use clear, business-oriented names — **Contact Center Outbound Dialer**, **Contact Center Paced Dialing** (Power and Progressive), **Contact Center Inbound Voice**, **Contact Center Call Recording**, and **Contact Center Supervision & Live Dashboard** — with plain-language descriptions. Contact Center capabilities include their own administration screens instead of requiring a separate Administration feature; the server-side **Contact Center Voice** orchestration and the shared **Contact Center Real-Time** hub are enabled automatically as dependencies of the capabilities that use them instead of being standalone toggles; the Contact Center soft-phone projection and the CRM-integrated **Agent Workspace** are integration glue that activate automatically once the capabilities they compose (Contact Center Voice, Contact Center Real-Time, the Telephony soft phone, and — for the workspace — Contact Center Agents) are enabled, rather than separate toggles; each provider's **contact center voice adapter** (Telnyx, Asterisk) likewise activates automatically once that provider module and Contact Center Voice are both enabled, so there is no per-provider toggle to match the provider you already configured; mandatory outbound compliance is part of the base Dialer; and the certified inbound-voice recipes enable Inbound Voice. Enabling Paced Dialing therefore activates a complete Dialer Profiles, compliance, and runtime surface.
- **Outbound compliance** — a mandatory eligibility gate with suppression auditing, retry limits, and calling-window enforcement, so outbound campaigns stay compliant.
- **Real-time agent and supervisor experience** — a shared SignalR hub that broadcasts presence, offers, and queue depth; a CRM-integrated agent workspace; and a live supervisor dashboard with capability-gated monitoring.
- **Docked agent bar** — a persistent bar injected into the admin chrome (the layout footer) on every admin page for signed-in agents, holding its own live Contact Center hub connection outside the soft phone. It keeps work reaching the agent — popping the matched record and driving disposition — even when the soft phone runs in its own window or the browser extension, and it self-manages with the agent's live state. It rides the same integration glue as the Agent Workspace (Contact Center Agents, Real-Time, Voice, and the Telephony soft phone), and is deliberately not injected on the standalone `/softphone` page. See [Agent Desktop & Dashboard](../contact-center/agent-desktop#the-docked-agent-bar).
- **Recording and monitoring** — provider-capability-gated recording orchestration and recording-state events for voice interactions, including an **agent secure pause** that lets an agent suppress recording while a customer reads out sensitive data (card or identity numbers) and resume it afterward. Secure pause is ownership-checked and policy-gated, blocks new supervisor monitoring while a capture is in progress and force-stops any supervisor who was already engaged, and is bounded by a background automatic-resume guard so a pause can never silently outlive its purpose. It is off by default and enabled per tenant in the Recording settings.
- **Hosted secure data capture** — an optional **Contact Center Secure Data Capture** feature that lets an agent send a live customer to a dedicated secure page to enter sensitive data (such as a card number) instead of reading it aloud. The value is tokenized at submission, so the agent, the supervisor, and the recording only ever see a masked representation and a durable token reference; values that must never be retained, such as a card security code, are validated and then discarded with no token or mask kept. Captures are ownership-checked, limited to one in-progress capture per interaction, authorized by a one-time link whose SHA-256 hash is all that is stored and served with no-store/no-referrer headers, bounded by a configurable expiry with a background safety net, and pause recording during the capture as defense in depth with a self-healing recovery pass so recording can never be left paused permanently. The built-in masking sink is registered only in Development and is for development only; outside Development secure capture fails closed until an operator supplies an `ISecureCaptureTokenSink` backed by a PCI-DSS-compliant vault. It is off by default and enabled per tenant in the Secure Data Capture settings.
- **Voice media master copies** — the platform now keeps the master copy of every voice media clip (hold music, IVR prompts) and of every recorded agent voicemail greeting in the Telephony media store, where recordings live: the tenant's application-data folder, or Azure Blob Storage with **Telephony - Azure Blob Storage**. A telephony provider's copy is a cache made from it: a provider that has no copy of a clip, or reports its copy missing, is given one the first time a call needs it, so hold music, prompts and greetings keep playing after a change of provider and after a clip is deleted at the provider (a provider's confirmation that it holds a copy is trusted for ten minutes, so a copy lost at the provider is made again within that window rather than on the very next call). Each entry records the copy every provider holds (`ProviderReferences`) beside the older single `ProviderName`/`MediaReference` pair, which is still carried and folded in. The **Voice Media** screen shows **Master copy** or **Provider copy only** on each clip, flags clips uploaded before master copies were kept so they can be uploaded again, and offers **Re-sync media** to check and refresh every provider's copy. Deleting a clip removes its master copy and every provider copy. Consumers resolve what to play through the new `IVoiceMediaProvisioningService` instead of reading a stored reference.
- **Reports and analytics** — executive, interaction, queue and SLA, agent, transfer, recording, campaign, and subject reports contributed to the admin **Reports** area.
- **Workflows bridge** — an optional Contact Center domain-event activity, so Orchard Core Workflows can react to contact center events.
- **Recipe and workflow schema validation** — the CrestApps Recipes feature now ships JSON schemas for the Contact Center and Omnichannel configuration steps (skills, queue groups, business-hours calendars, queues, agent entitlements, agent state reason codes, entry points, dialer profiles, campaign groups, campaigns, channel endpoints, dispositions, and subject actions) and for the Contact Center workflow activities, so recipe authors and AI tooling get per-step validation and property guidance.
- **Administration** — Contact Center settings screens plus each enabled capability's own administration screens.

See [Contact Center](../contact-center/index.md) for setup and configuration.

#### Power, Progressive and Predictive calls connect to the agent without an Answer click

A call the dialer placed for an agent rang on the agent's soft phone with **Answer** and **Decline** once the customer picked up, when it should connect by itself, as dialers do. The phone answers that call's leg only for a reservation it knows was accepted for its user, and the accept's single real-time push was the only thing that told it. A phone that missed that push (the page reloaded, the hub reconnected, or the phone was opened while the customer was ringing) treated the leg as an unexpected call. The agent then had to click Answer while the customer waited, and the customer was more likely to hang up or be counted as abandoned.

- The hub snapshot (`AgentDesktopSnapshot`) and every presence push (`AgentPresenceNotification`) now carry `DialHoldReservationId`, the dial the agent is held for. The soft phone re-reads the snapshot at every connect, so it always knows which leg to answer, and still answers only legs tagged for its own user.
- The Contact Center soft phone learns its own user from the snapshot even on a page without the presence header.

#### The soft phone no longer replaces its credential under a parked dialer call

An agent on a Power, Progressive or Predictive campaign could have the soft phone register a new SIP credential while the platform was ringing or holding their leg, which hung the leg up, and the platform's next leg was refused on the credential being replaced (SIP 480) and rung again.

- The soft phone counts every call its provider client holds as a live call, including the leg parked for a dialer call and a call the server has not told it about yet. It no longer renews its credential, re-registers after a failed microphone recovery or moves region under one. A renewal held off this way now runs the moment the last such call ends, instead of waiting for the next minute's check, so an agent parked on one leg after another still renews before the credential expires.
- After its hub connection comes back, the soft phone reports again the credential it kept. A closed connection marks its credential as closed, and the phone's only credential otherwise ranked as a closed window's until it next registered.
- **Credential lifetime (minutes)** in the Telnyx settings must now be at least 30. The soft phone renews in the last 10 minutes, so a shorter lifetime renewed every few minutes, or on every check. A shorter value is refused on save, and one already stored, set by a recipe or bound from configuration is raised to 30 (`TelnyxCredentialLifetime`).

#### A dialer call the agent is talking on is no longer shown as "Waiting for a connected call"

With a Power, Progressive or Predictive profile, an agent could be talking to the customer while the platform still held them **Reserved**: their screens read *Waiting for a connected call*, no activity opened, and when the call ended it was dispositioned automatically as *Disconnected before an agent was connected*. The agent's phone line, rung and parked while the customer rang, had been joined to the customer, but the join was recorded only afterwards and could be lost:

- When the customer answered after the agent's phone had picked the parked leg up, the join was recorded only by the answer command's own projection. A command that ran past its timeout, which waiting on the offer's lock counts against, settled as unknown and never recorded it, and its reconciliation carried no agent leg to record. The join is now recorded the moment the bridge succeeds, committed on its own, and the bridge is never cancelled once asked for.
- A webhook whose work failed after the bridge (a concurrent update of the call refused its save) was retried as a redelivery and did nothing. The retry now records the join; recording it twice changes nothing.
- An agent whose profile was locked by other work when they were connected had the join undone with the failed state change. The join is now kept, and the failure is logged as a warning.

A successful bridge of a parked agent leg is now logged at Information, so a call like this can be traced in the server log.

#### Agents see the activity of every call the dialer connects them to

#### An agent is Reserved, not on a call, while the dialer reaches the customer

A power, progressive or reserved predictive dial accepted its reservation, and made the agent *Busy* (*On a call*), before the customer's phone even rang. Supervisors saw them on a call, the agent's screens had to hide it, and every dial nobody answered counted as a call taken: *Calls today*, *Busy* time and occupancy all grew with ring time and unanswered dials. Contact-center dialers keep the agent held, but not on a call, until a person answers and the agent is connected, and the platform now does the same.

- The agent stays **Reserved** while the customer is dialed and screened, held by `AgentProfile.DialHoldReservationId` (set by the new `IActivityReservationService.AcceptForDialAsync`), and goes **On a call** (`Busy`, source `Connected`) when connected, through the new `IAgentPresenceManager.ConnectHeldAgentAsync`. A dial that ends without the agent returns them to ready as before, keeping their place in line. Preview and callback dials are unchanged: the agent started them, so they are on them at once.
- A break or other state chosen while held waits for the call, and the stranded-Reserved recovery leaves a held agent alone while their call is live.
- The agent's screens now read *Reserved* and **Waiting for a connected call**, without the customer, while they are held. The new dialer-profile option **Show each dial to the agent** (`ShowDialProgressToAgent`, off by default) brings back who is being dialed and *Dialing…*, *Screening…*, *Connecting…*. The workspace state's `pendingDial` gains `showsProgress`.
- The live dashboard's agent badges show each state as the agent's screens do (*On a call*, *Wrap-up*) instead of the stored name (`Busy`, `WrapUp`), and its **On a call** filter no longer counts a *Reserved* agent whose call is still ringing.

#### Agents see "Dialing…" and "Screening…", not "On a call", while the dialer reaches the customer

A power, progressive or predictive dial reserves its agent before it is placed, so the docked agent bar and **My workspace** read *On a call* while the customer was only ringing, and again while their answer was screened for an answering machine. An agent who saw it took it that they were already on the call. While the dialer places a call for the agent, both now show what it is doing: *Dialing…* with the customer's name or number while the customer rings, *Screening…* while an answered call waits for the machine verdict (only when answering-machine detection was requested), and *Connecting…* once a person has answered and the agent is being joined. *On a call* appears once the agent is connected. #### Changing an activity's dialer profile now queues it for the dialer

**Manage Activities > Change Dialer Profile** only relabeled the activities. An activity loaded by hand was never queued for the dialer, and one already queued kept its old profile, so neither was dialed under the new profile. The action now records the profile on each activity and queues it on its campaign, or keeps its place in the queue under the new profile. It also always clears the assignment: the dialer offers each activity to whichever agent signed in to the campaign is free, and an assignee left on it kept the activity in that user's own list too. An activity with no campaign is left unchanged, with a message saying so.

**Manage Activities** gains a **Dialer profile** filter and a **Change Campaign** action, and **Change Dialer Profile** can move the activities to a campaign in the same step. Moving a dialer activity to another campaign moves its place in the dialer too: it leaves the old campaign's dialer queue and waits in the new one under its profile, where only an activity with nothing being dialed is moved. The activity index gains a `DialerProfileId` column; open dialer activities saved before it are indexed by a background task after the upgrade. Every bulk action now leaves alone an activity the dialer is dialing or an agent is on a call for, **Purge** included, so a live call is never pulled out from under the agent. `IActivityDialerContributor` gains `MoveToCampaignAsync` and `GetActivitiesInFlightAsync` for this.

Activity loads gain a **Count matching records** button, which runs the load's filters without loading anything and says how many records would be loaded and why the rest would be skipped, and a **Last activity attempts** filter that takes `4`, `4+`, `4-` or `2..5`. A load that stops part-way, for example on a restart, used to stay *Loading* for good. Each page of a load now commits with a heartbeat and a cursor, a watchdog resumes a load whose heartbeat goes quiet after the last records it committed, and a load that fails or is given up goes back to *New* with the reason shown on its row and page. `IActivityBatchLoadCoordinator` gains `ResumeAsync` and `PreviewAsync`.

The **Imported file** filter of a lead load listed no file imported before it shipped on a large tenant: the backfill that records past imports on their leads ran during activation, outlived the command timeout, and was never retried. It now runs as a resumable background task, one pass over the leads a few thousand at a time.

A dialer profile's **Max attempts** is now the fallback limit, and the subject flow decides first. A **Try Again** that sets **Maximum attempts** uses that number for dialer work, above or below the profile's; one that leaves it empty stops at the profile's **Max attempts**. When the subject has no disposition for how a dialed call ended, the dialer no longer borrows the disposition **Try Again** is wired to: it dispositions the call with the matching outcome and, for a call that rang out, was busy, reached a machine or was dropped, calls the contact again after the retry delay, up to the profile's **Max attempts**. `OmnichannelActivity.MaxAttempts` records the subject's maximum on each attempt, `ActivityDispositionResult.HandledBySubjectFlow` says whether the flow had a rule for the outcome, and `IDialerRetryScheduler` gains `ScheduleUnhandledOutcomeRetryAsync`. A retry already scheduled for a record is found rather than created twice when a workflow asks too. The profile's **Retry delay** is the fallback for when, too: a **Try Again** that leaves **Default schedule hours** empty, with no date picked when the call was dispositioned, is dialed after the retry delay instead of 24 hours later. `FollowUpActivityContext.HasChosenSchedule` says whether the follow-up's due time was chosen.

A campaign's waiting dialer records are worked under the profile of the record at the front of the queue, so records under a second profile behind it were never dialed. A dialer activity load, or a dialer profile change, that would leave a campaign's waiting records under more than one profile is now refused, and the message names the profile already waiting. `IActivityDialerContributor` gains `GetWaitingRecordsAsync`, and `EnqueueAsync` re-tags an activity that is already waiting in the campaign's queue.

#### A filtered activity load reads only the records its filters picked

An activity load filtered down to a few records of a large list stayed on *Loading* with nothing loaded for many minutes. The load read every record of its type, a hundred whole documents at a time, with a round of lookups and a commit for each hundred, and passed over the records its filters had not picked. Its row kept showing recent progress the whole time, because each hundred committed. When the phone number, time zone, last activity or lead filters pick the records, the load now finds them through the index first and reads only those, so a load of twenty records commits once. The count shown when the limit stops a load comes from the same records. **Count matching records** and resumed loads work the same way. Each load logs how many records its filters picked before it reads any.

#### A report that says why an available agent is not getting calls

Nothing showed how long an agent had waited for a call, or why an agent who looked available was not getting any. For every queue and campaign the agent is entitled to or signed in to it says whether they can be given work now and why not: not entitled, not signed in, no live session, not Available, at capacity, a closed or turned-off queue, or the verdict routing gives for the next waiting item, such as a missing skill or having transferred or declined the call. It flags stale states (Available with no live session, Busy or Reserved with nothing behind it, an unresolved soft-phone call record, a held reservation) and notes when the agent's recorded history disagrees with their profile, such as the time summary counting an agent with no recorded sign-out as Available up to now while they have no live session. A supervisor who oversees queues sees every agent entitled to or signed in to one of them, including agents the live dashboard leaves out. #### Dialed calls reach their agent within two seconds of the answer

A Power, Progressive or Predictive call rang its reserved agent only once the customer answered, or once answering-machine screening said a person answered. Placing that leg and waiting for the agent's phone to answer it took about three and a half seconds, so every connected call broke the two-second rule and was counted as abandoned, and the person who answered heard silence.

The agent's phone is now rung while the customer's phone is still ringing. It answers that leg at once and holds it, silent, until the customer answers. The answer, or the verdict that a person answered, then only joins the two. When a machine answers, nobody answers or the customer hangs up first, the held leg is hung up, and the agent goes back to Ready with no wrap-up. A held leg lost before the customer answers fails nothing: the answer rings the agent as before. Preview calls and Predictive calls with an agent reserved for each call are held the same way.

The platform no longer asks Telnyx to answer the customer's leg of an outbound call before connecting the agent. Telnyx refused that on every call and logged a warning. The abandonment tracker now also logs the answer-to-agent time of every connected call, not only of the late ones.

`CrestApps:ContactCenter:Coordination:DialerAgentParkingEnabled` (on by default) turns this off, and `DialerAgentParkWindow` (10 minutes) bounds how long a held leg is kept. `IAgentPreDialCoordinator` gains `ParkForDialedCallAsync` and `TakeParkedLegAsync`, `ContactCenterAgentPreDialRequest` gains `AnswerOnArrival`, and `ContactCenterConnectRequest` gains `CallerAnswered`. See [Answer to agent time](../user-manual/dialer-profiles.md#answer-to-agent-time).

#### Power and Progressive campaigns dial as soon as an agent is free

Power, Progressive and reserved-per-call Predictive campaigns were dialed only by the minute dialer pacing task, so an agent who signed in, came back from a call, or had a number go unanswered waited up to a minute for the next call. With a run of numbers that don't answer, that added minutes of idle time per agent. A campaign is now paced within about a second of an agent becoming available or signing in, an offer being released or expiring, a dialed call ending without reaching an agent, or records being loaded into it, and keeps being paced while its cycles place calls. Each cycle applies the profile's limits exactly as before; only the timing changed.

The new `IDialerPacingScheduler` debounces requests per campaign (300 ms by default) and merges bursts, and runs each cycle on its own scope under a per-campaign pacing lock (`ContactCenterDialerPacing:{queueId}`), committing before the lock is released. A node that finds the lock held tries again a second later. The minute `DialerPacingBackgroundTask` now re-arms every campaign with waiting work unconditionally (`RequestBackstop`) instead of dialing inline, and stays as the backstop: it never merges into a pending request, so a run dropped before it started cannot stop a campaign dialing for more than a minute, and such a run is logged as a warning. `QueueItemAdded` now carries `QueueItemAddedEventData` with the queue. The timings are in the new `CrestApps:ContactCenter:DialerPacing` section. See [Pacing cadence](../contact-center/agents-queues-dialer.md#pacing-cadence) and [When calls are placed](../user-manual/dialer-profiles.md#when-calls-are-placed).

#### An entry point's AI voice agent speaks on Telnyx calls, and its calls are listed as inbound

An entry point routed to an AI voice agent answered the call and the caller heard silence. `TelnyxInboundAIVoiceAnswerer` passed an already base64-encoded client state to `TelnyxApiClient.AnswerAsync`, which encodes it again, so `call.answered` matched no AI voice leg and no media stream, recording or session started. The answerer now passes the JSON, as the calls the AI places already do. Those calls were also listed on the call recordings page as outbound, with the business's own number as the customer: the direction was read from `call.answered`, which Telnyx sends without one. The AI voice leg's state now marks the call inbound, and its recording takes the caller as the customer.

#### An inbound caller is no longer hung up on when the agent who accepted cannot be reached

An agent whose soft phone could not receive calls (its registration with the phone service had lapsed while the Contact Center hub stayed connected) could still accept a queue offer. Every leg rung to the phone was refused (SIP 480), and the platform then settled the call as failed and hung up on the caller: no voicemail was taken, the caller was not put back in the queue, and the agent stayed Available to be offered the next call, which failed the same way. A busy phone behaved better only because it refused the leg before the accept, so the offer rang out and the queue's action applied.

A caller whose accepted agent cannot be reached now gets what the queue does with an offer nobody answers, its **Unanswered offer action**: back to the queue for another agent, to the voicemail of the agent the offer was made to, or rejected. The agent is set **Away** with the reason *Phone unreachable* until they set their own state again, so the next caller is not sent to a phone that cannot ring. A redelivered failure releases the caller once. Dialer campaign calls, queued callbacks and personal-line calls keep their failed-call handling. `IActivityReservationService` gains `ReleaseUnreachableAgentAsync`, and the recorded agent state transition carries `AgentReleaseReasons.Unreachable`. #### A silent AI call ends itself, and "are you still there?" is just that

An automated call held as a live speech-to-speech session asked twice whether the caller was still there and then stopped asking, so a silent line stayed open, unheard, until somebody hung up (five minutes on one live call), using call and model minutes. After the two prompts, the next silence now ends the call with a goodbye, the way the end-call tool does (`RealtimeVoiceConversationContext.EndCallOnSilence`). A caller who answers a prompt starts the count again, as on turn-based calls.

The prompts were asked for as a continuation of the conversation, and on a silent line the model filled the gap by speaking for the customer ("I'm looking to schedule a haircut appointment") and then answering itself, which the call's review took as a conversation. The prompt and the goodbye are now standalone messages from fixed instructions, which say the call is under way and keep the call's language. Like any standalone message, each waits for a response still in flight to finish, so it never talks over the model; a response that never reports finishing holds it back for 20 seconds at most.

Both kinds of call wait 8 seconds before each step, down from 12, so a silent call ends about 30 seconds after the assistant's last word instead of about 40. See [A silent line is asked twice, then ended](../contact-center/voice-routing#a-silent-line-is-asked-twice-then-ended).

#### An AI call is concluded only with an outcome the customer decided

A call's disposition is what the subject flow acts on next, but three paths recorded outcomes nobody chose. Live, callers who never spoke were concluded *Appointment booked*, *Question answered* and *Handed to a person*, and a caller who asked to book and hung up was concluded *Handed to a person*.

- **The assistant talking alone was counted as a conversation.** Every answered call has the assistant's opening, and a silent line adds its "are you still there?" prompts, so a silent call went to the review, which wrote an outcome. `VoiceCallConclusionPolicy.HasConversation` now counts only the customer's own words.
- **An unanswered call looked for its outcome only in the subject's own list.** An inbound subject is wired to what callers ask for, not to *No answer*, so the first choice was taken. After the subject's own outcome and its **Try Again**, `ChooseUnansweredDisposition` now looks across every disposition, as the dialer does.
- **A conversation with no decision was given "the closest" disposition.** The review is told to decide from what the customer said, that the assistant's read-backs and goodbyes are not the customer's agreement, and to choose none when nothing fits. The new `VoiceCallConclusionPolicy.ChooseReviewedDisposition` then takes the subject's **Try Again** disposition, so the customer is called again, and failing that one with the *Disconnected* outcome. The outcome's label now names automated calls too.

The review prompt also covers inbound calls, not only outbound sales calls, and the list of dispositions it is given no longer asks it to choose one regardless. See [Dispositions](../user-manual/dispositions#outcomes).

#### A Greek goodbye is heard once

#### An AI call keeps its recording when its hand-off falls to voicemail

An automated voice agent's call is recorded from the answer. When the AI handed the caller to a queue and the call fell to voicemail, the voicemail's `record_start` went onto the same leg with its own client state, which Telnyx stamps on every later webhook of the call, so the conversation's recording was filed as the voicemail message and the call was left without a recording. The voicemail recording starter now stops a call recording still running on the leg before it starts, and a two-channel recording saved on a leg whose call recording is still running is filed as that call recording.

#### The briefing for the agent an AI call is handed to is no longer lost

When an AI call is handed to the queue, the model writes a short briefing of the conversation for the agent who takes it, after the handoff is committed. Writing it takes seconds, and routing writes the same activity meanwhile (the offer, the ring, the answer), so the save onto the copy read before the model was asked lost to those writes and the briefing was dropped with a warning: on a live call offered to an agent while it was being written, the agent saw no briefing. It is now saved onto a fresh read of the activity, in a scope of its own, setting only the briefing and its time so nothing written meanwhile is overwritten, and tried again up to three times when another write still wins (`VoiceAgentConversationLoop.SaveHandoffSummaryAsync`).

#### An AI call answered by voicemail leaves its message on a live session too

An automated call held as a live speech-to-speech session was told nothing when the telephony provider detected an answering machine: the detection arrived on a webhook request of its own, marked the activity, and the session holding the call in another request never learned of it. The model treated the greeting as a person, and the voicemail kept the end of the assistant's opening ("...is now a good time to talk?") and no message, while the activity was still concluded as having left one. The provider's report now reaches the session through the new `IAnsweringMachineSignals`, held in memory per node for the calls that are up. Once a machine is reported the session keeps the model's replies to the greeting off the line, waits for the provider to hear the greeting end or for three seconds of quiet, asks the model for one short message under the session's own instructions, so it is spoken in the campaign's voice and in the language the call was held in, and ends the call the way the end-call tool does on voicemail. The activity records the message as left (`RealtimeCallCompletion.ReachedVoicemail`) and is concluded as a voicemail. Turn-based calls are unchanged, and both paths now share one voicemail-message instruction. See [Automated calls held as a live speech-to-speech session](../contact-center/voice-routing#a-voicemail-is-left-one-message-in-the-sessions-own-voice).

#### An AI call handed to a person is not told twice, nor in the wrong language

When an AI call was handed to the queue, the model told the caller it was connecting them, as the transfer tool asks, and the conversation loop then spoke a fixed line of its own through the telephony provider: "I'm connecting you to a specialist now", "you are in the queue", or, with the queue closed, "we've scheduled a callback". The first repeated what the model had just said, in another voice, and all three were English: on a live call held in Greek the caller heard them in English, read by a provider that has no Greek voice. A call the model asked to transfer is no longer told again that it is being put through; a caller handed over because the assistant's session was lost, and told nothing yet, still is. The fixed lines are said only on a call held in English, the persona naming English or no language (`VoiceAgentConversationLoop.HandoffLine`); on a call in another language the caller hears only the model's own words, and an after-hours handoff ends the call after them. See [Automated AI](../user-manual/automated-ai.md#live-agent-handoff).

#### The voicemail message on a live session says who called and why, in the call's language

The message a live speech-to-speech session leaves on an answering machine was asked for inside the conversation, with the session's tools on. The machine's greeting was the latest thing the model had heard, so it sometimes answered the greeting ("message after the tone" read as a text message), left a message without saying who called or why, or called a tool and ended the response with nothing said; on live calls one message in four was right. The message is now asked for with `IRealtimeConversation.RequestStandaloneMessageAsync`: out of band, with its own context instead of the conversation, and with tools off. Without the conversation the model no longer knows the language the call was held in, so the instruction quotes the assistant's opening line on the call. The quote is the first line with any words in it (a line cut off before it had any no longer takes its place), and it is given for its language only: on a call where the model waited for the other end to speak first, that line can be its reply to the greeting, which the message must not carry on from.

#### An AI call's summary and handoff briefing are not about cars

Both voice prompts gave a car dealer's facts as their example of what to capture: «vehicle type, timeline, budget, trade-in». A model takes an example for a checklist, so a call to a plumbing firm came back briefed as «the customer gave no other details (for example vehicle or budget)». The examples in `voice-conclusion-analysis` and `voice-handoff-summary` are now generic: what the caller needs, the dates, places and details they gave, and their contact details. The review is also told to mention only what was said on the call.

#### An AI call's summary and handoff briefing are written in the call's language

The review that concludes an AI call and the briefing written for the agent a call is handed to are both asked for in English, and the model answered in English whatever language the call was held in: on a live call held in Greek, the activity's notes came back in English for an office that works in Greek. Both prompts (`voice-conclusion-analysis`, `voice-handoff-summary`) now take a `Language` variable, the English name of the language of the AI persona the profile speaks as (`Greek` for `el-GR`), and ask for the summary and the briefing in it. A persona with no **Language** leaves both as they were. See [Automated AI](../user-manual/automated-ai.md#when-the-conversation-ends).

#### Realtime AI calls speak again once the tenant has started

To hand live AI calls on when a node stops, `AIVoiceCallShutdown` was registered as a tenant singleton and, through a factory, as a scoped `IModularTenantEvents`. A scope disposes what its scoped factories return, so the scope that activates the tenant disposed the shutdown signal, and every realtime AI call after that failed as it was answered (`ObjectDisposedException` reading `Stopping`): the person called heard silence. The tenant-events registration is a singleton too now, so only the shell owns the instance.

#### A live AI call hears its caller in the persona's language

An automated call held as a live speech-to-speech session sent no language to the transcription of the caller, so each phrase's language was guessed: on a live call held in Greek, the caller's greeting was transcribed as Finnish, and the call's summary and outcome were written from that transcript. The session now takes the language of the AI persona the profile speaks as, as turn-based calls already did: the caller is transcribed in the language part of its tag (`el` for `el-GR`, the ISO-639-1 code the realtime transcription takes) and the model is held to that language (`RealtimeOrchestrationRequest.SpeechLanguage`). A persona with no **Language** leaves it to the model, as before. See [AI Personas](../ai/personas.md).

#### Records are found by id without scanning their table

Every catalog store finds a record by its id through the `ItemId` column of its index table, but 39 of those tables had no database index that starts with `ItemId`. On the busiest tables (interaction events, queue items and omnichannel activities) each such read scanned the whole table, and the cost grew with traffic. Each table now has an `IDX_<Index>_ItemId` index over `ItemId` and `DocumentId`, added by a migration in the Contact Center, Omnichannel Management, Omnichannel Messaging and Telephony modules. Existing tenants get it on the next start.

#### A stalled dialer no longer looks like an idle one

When pacing stopped, nothing showed it: a cycle's routing decisions were committed with the cycle, a cycle cut short by its time budget logged only at debug level and rolled back, and a dialer whose cycles had stopped looked exactly like one with no agents or nothing to call. **Contact Center Paced Dialing** now writes a compact `DialerPacingCycle` record for every way a pacing cycle ends (placed N, nothing due, no agents, held back, lock not acquired, time budget exceeded, failed, lost a write race), on a scope of its own after the cycle's scope ends, so a rolled-back or abandoned cycle is on record too. Repeated cycles that end the same way without placing a call are folded into one record an hour, and records are aged out after `CrestApps:ContactCenter:Retention:DialerPacingCycleRetentionDays` (14 days by default). What a cycle decided is read from the `RoutingDecisionMade`, `DialSuppressed` and `DialerAttemptStarted` events it publishes, through a wrapper around `IContactCenterEventPublisher`; a decision event carrying a `Count` is counted as that many. The minute dialer pacing task now logs a warning, and records each queue it did not reach, when it runs out of its time budget.

A new **Dialer activity and health** report (Operations) shows, per campaign queue and per dialer profile, the last cycle with its start, end and outcome, the last call placed and assigned (agent, campaign, record), calls placed, answered and abandoned per hour, campaign routing decisions per hour (routed versus no agent available), and suppressed attempts by reason. The live dashboard shows a one-line **dialer banner** (stalled, idle, holding back, dialing, or nothing to call) refreshed every 30 seconds from `GET Admin/contact-center/dashboard/dialer`. The heartbeat warning *Due work is waiting but no pacing cycle has completed for N minutes*, after `CrestApps:ContactCenter:DialerPacing:StalledAfter` (5 minutes by default), is also raised by the new `contactcenter-dialer-pacing` dependency health check. See [Pacing cycle records and dialer health](../contact-center/agents-queues-dialer.md#pacing-cycle-records-and-dialer-health), [Dialer activity and health](../user-manual/reports.md#dialer-activity-and-health) and [Dialer banner](../user-manual/live-dashboard.md#dialer-banner).

#### A Dialer queue inventory report shows what each campaign queue holds and why it is not dialing

A campaign's queue is virtual, so no screen showed what the dialer actually held. Records stamped with a turned-off dialer profile were skipped by the pacer without a word above Debug, pending records that were in no queue were invisible, and a queue correctly stamped with an enabled Power profile could still sit undialed because the item at its head carried a deleted profile. The new **Dialer queue inventory** report (*CRM & Campaigns*) has one row per campaign queue and stamped dialer profile: waiting, reserved and assigned items and the oldest waiting one; the stamped profile's name, mode and on/off state beside the profiles the activities carry; the source, interaction type and channel of the pending activities; how many are dialable now and why the rest are held back (profile off or deleted, scheduled for later, retry delay, out of attempts, calling window, do-not-call, number not in service and the other compliance reasons); how the queue is paced; when it last placed a call; and flags for items stamped differently from their activity, pending activities in no queue, and a stamped profile that no longer exists. The pending records of a campaign that are not in its queue get a row of their own. The classification is the one the live dashboard's *Why isn't this dialing?* card uses (`DialerRecordClassifier`, shared through `IDialerQueueInventoryService`), now with a *dialer profile no longer exists* reason (`DispatchBlocker.ProfileMissing`) for a record stamped with a deleted profile. `QueueItemIndex` now indexes `DialerProfileId` (`QueueItemIndexMigrations` step 7), so the report never reads a queue item's document; items saved before the upgrade are indexed by the *Contact Center Queue Item Dialer Profile Backfill* background task after the tenant starts. The minute pacing task now logs a warning, at most once every 15 minutes per queue, when a campaign queue is not dialed because its head item is stamped with a turned-off or deleted profile. See [Dialer queue inventory](../contact-center/agents-queues-dialer#dialer-queue-inventory).

#### Agent workforce reports over a month no longer time out

On a busy tenant the agent workforce reports (the *Workforce & Payroll* reports, the agent presence audit and the agent activity timeline) read every state change of every agent in the period in one statement, and past a few weeks the read outlasted the database command timeout and the page failed. The window index, the row cap on the presence audit and the timeout message shipped earlier; this completes the fix (#926):

- **A period limit.** These reports, the activity timeline and the reconciled payroll timecard refuse a period longer than 31 days with a *This period is too long for this report* message that names the limit and the days chosen, before any event is read. Exports have their own limit. Both are set with the new `MaximumWorkforceReportRange` and `MaximumWorkforceExportRange` keys of `CrestApps:ContactCenter:Reporting` (see [Configuration](../configuration.md#reporting)).
- **Paged reads.** `InteractionEventStore.GetByAggregateWindowAsync` reads the period in pages of 1,000 events, continuing after the last occurrence time and document id read, instead of one unbuffered statement, and `GetLatestBeforeAsync` finds each agent's opening state with one statement per 100 agents rather than one query per agent.
- **Daily agent time summaries.** A new **Contact Center Agent Time Summaries** background task summarizes each finished UTC day of agent time and backfills the days before it, up to `AgentTimeSummaryBackfill` (92 days by default). The agent time summary, presence status duration, ready versus not-ready, utilization, occupancy, presence reason, queue and campaign signed-in hours and payroll timecard inputs reports read whole days from those summaries and only the rest of the period from the log, with the same figures; a day the log changed for since it was summarized is read from the log. The new `AgentDailyTimeSummaryIndex` table is added by a migration on the next start.
- **The timeline builds only what it lists.** The agent activity timeline builds its first 5,000 entries and only counts the rest.
- Rows of the ready versus not-ready and payroll timecard inputs reports are now listed by agent, and rows that tie on the figure a report sorts by fall back to a fixed order, so the same period always lists the same way.

See [Agent workforce reports over long periods](../contact-center/report-catalog.md#agent-workforce-reports-over-long-periods).

#### The Campaign summary says how many pending records can be dialed now, and why the rest cannot

The Campaign summary's *Pending* counted activities in the inventory, which did not tell a supervisor what the dialer could call: a Power campaign showed 180 pending while its queue held 79, about 100 were in no queue, and a larger set was stuck on a turned-off profile, and nothing in the report could be filtered by dialer profile to find it. Each campaign's *Pending* is now split into **Dialable now**, **Held back** with **Held back because**, **Scheduled for later**, **Not in any queue**, **Assigned to a user** and **Not explained**, which always add up to it; the report also shows the **Attempts distribution**, **Last attempt**, **Next due** and **Stamped dialer profile** of each campaign, and new **Interaction type**, **Dialer profile** (the activity's or the one stamped on its queue item) and **Queue state** filters sit beside the existing ones. The split is computed by the Dialer queue inventory's `IDialerQueueInventoryService.Summarize`, so on the same records the two reports agree; it replaces the separate *Pending right now* section. A record assigned to a user is now reported as such (`DispatchBlocker.AssignedToUser`) on the live dashboard too. `IContactCenterReportingService` gains `GetCampaignActivitiesAsync` and `BuildCampaignSummaryAsync`, and `ContactCenterReportCriteria` gains `InteractionType`. See [Campaign summary split](../contact-center/agents-queues-dialer#campaign-summary-split).

#### Dialer decision log report, and repeated routing decisions counted instead of rewritten

Routing decisions and dial suppressions already recorded what routing and the dialer decided and why, but only as JSON inside events, so "why was this record not called?" needed hand-written SQL. Two new map indexes over interaction events, `DialerDecisionIndex` and `DialerDecisionAgentIndex`, now carry their queue, campaign, activity, queue item, agents, outcome, reason, count and times as they are written; `InteractionEventIndex` is unchanged. A background task (**Contact Center Dialer Decision Index Backfill**) indexes the decisions written before the indexes existed, once, and gives old suppressions their activity's campaign.

The new **Dialer decision log** report (**Reports > Queue & Routing**) filters by campaign, queue, agent, activity ID, reason and date range. It lists each decision with its queue, campaign, activity, outcome and reason; for a routing decision, every candidate agent and why each could not take the work; for a suppression, the reason and the destination. It counts the period's decisions by reason, and lists the queues with work due now with the time of their last routing decision, flagging any quiet for longer than `CrestApps:ContactCenter:Reporting:DecisionLogQuietThreshold` (default 15 minutes). Picking an activity or an agent shows the last decisions made about it and why.

While a queue has due work and nobody can take it, routing made the same failed decision every minute, writing an event and an outbox message each time. A failed decision that repeats the queue's last one exactly is now counted on the event that recorded it first. **Payload change:** `ActivityRoutingDecisionEventData` gains `OccurrenceCount` (`1` when absent) and `LastSeenUtc`, and `DialerSuppressionEventData` gains `CampaignId`, `QueueId` and `AgentId`. A handler or workflow that reacts to `RoutingDecisionMade` now runs once per run of identical failures; one that counts decisions should add `OccurrenceCount`, and one that asks when routing last decided should read `LastSeenUtc`. The *Why isn't this dialing?* card reads routing decisions by their last time, so a repeated failure still explains a queue.

See [Dialer decision log](../contact-center/agents-queues-dialer.md#dialer-decision-log) and [Reports](../user-manual/reports.md#dialer-decision-log).

#### Settings pages open on a tenant with Contact Center and without Telephony

With **Contact Center** enabled and Telephony not (for example Contact Center Agents or Work Distribution alone), every page under **Settings** failed with *Unable to resolve service for type 'IDialDestinationPolicy'*. The base feature registered the **External transfer destinations** tab, and its driver validates each number with the dial destination policy that only Telephony registers; Orchard Core builds every settings driver for each settings page, so one failing driver closed them all. The tab now comes with **Contact Center Voice**, which every voice capability (Inbound Voice, the Outbound Dialer, Voice Media, Call Recording, Supervision) brings together with Telephony, and whose transfers are the only ones that use those destinations. The feature dependency audit also builds the display drivers of every feature, so a driver whose dependency belongs to an undeclared feature fails the tests.

The **Settings > Contact Center** menu item now comes with the features that add a tab to that page (Call Recording, Secure Data Capture, Contact Center Voice, and the default numbers that come with Omnichannel Channel Endpoints). With the base feature alone it no longer leads to an empty page.

### Tenant Hierarchy

A new **Tenant Hierarchy** module lets the platform make a tenant a **parent** that creates, manages and opens its own **child tenants**, for example a bookkeeping firm that runs one site per client business. The Default tenant stays the platform root.

- **Platform screens** in the Default tenant make a tenant a parent, set its policy (child limit, setup recipes, database placement, blocked features, permissions denied to the children's own users, session limits, two-factor requirement, switcher mode and the words the screens use), and show, suspend, move and remove the whole tree.
- **Child tenant management** in the parent: create a child from a setup recipe with a live address check, then edit, suspend, resume, reload, remove (with an optional restore period) and turn features on or off, one at a time or in bulk.
- **Open without signing in again**: a parent user opens a child through a one-time code and PKCE flow brokered in process, arrives as a linked user with the roles that access rules give, and can switch between children, go back, or leave. Sessions end when the parent user signs out, is disabled, changes their password or loses their access.
- **Access rules** by parent role or by user, for every child or one child, and every event recorded in the Orchard Core **Audit Trail** with who did what, from where and how they signed in.
- **Isolation guards**, installed with `AddTenantHierarchy()`: a scope guard on `IShellHost`, a feature guard, an egress guard on `HttpClient`, `__Host-` cookies, a Fetch Metadata guard, a parent removal guard, and a guard that keeps the platform from answering at the address of a suspended or removed tenant.
- **Database provisioners** for a SQLite file, a database, a schema or a table prefix per child, on SQL Server and PostgreSQL, extensible through `IChildTenantDatabaseProvisioner`.

See [Tenant Hierarchy](../modules/tenant-hierarchy.md), and in the User Manual, [Child Tenants](../user-manual/administration/child-tenants.md) and [Tenant Hierarchy](../user-manual/administration/tenant-hierarchy.md).

### Telephony

- The soft phone now plays a ringback tone while a number dialed from the keypad (or a colleague's extension) is ringing, and shows *Ringing...* without a call timer until it answers. On Telnyx the agent's own line answers before the number is dialed, so the carrier's ringback never reached the agent and they heard silence. The server tells the phone where the other party stands through the new `ITelephonyRemotePartyNotifier` and the `RemotePartyChanged` hub message; the tone stops the moment the number answers, is busy, does not answer or is not in service, or the agent hangs up.
- Provider HTTP clients no longer auto-replay unsafe requests. The phone-number-verification resilience pipeline now retries only idempotent safe methods, so a lost response can no longer place a second call or double-spend an OAuth grant, while transient failures on safe reads are still retried.
- Recording media now streams end to end through the tenant file store instead of being buffered in memory, so large recordings no longer pressure the managed heap during ingestion. See **Breaking Changes** for the related `RecordingMediaWriteRequest.Content` change.
- Encrypted recordings can now be seeked. When the stored file can seek (local files and Azure blobs both can), the stream that `IRecordingMediaStore.OpenReadAsync` returns can seek too and reports the length of the recording. A read decrypts only the 64 KB frames it covers. Call recording playback serves each range request from that stream: it no longer decrypts the whole recording for each request, and it no longer writes decrypted audio to a temporary file for long calls. Voicemail playback now accepts range requests, so the player can seek in a voicemail. The stream authenticates the last frame when it opens, so a recording that is cut short or has data added after its end fails to open.
- Token revocation and disconnect now report a typed result, so callers can tell confirmed success from a definitive or indeterminate failure. See **Breaking Changes** for the signature changes.
- The **Settings → Communication → Telephony** admin menu entry now displays a phone icon, matching the Orchard Core convention of a per-item navigation icon view.
- The soft phone keypad now uses a country-aware [intl-tel-input](https://intl-tel-input.com/) phone number field with a flag/country selector. A valid national number typed on the keypad is normalized to canonical E.164 before it is dialed, so outbound compliance screening (do-not-call and calling-window checks) can canonicalize the destination instead of rejecting a bare national number. Other non-number entries are dialed exactly as typed rather than being turned into an invalid international number. A new **Default country** soft phone setting controls the initially selected country and defaults to **Automatic**, deriving the country from the current culture and falling back to the browser's locale and then the United States when a region cannot be determined, so a country is always selected. The country selector dropdown renders above the floating widget so it is always visible, and opening it no longer scrolls the page the first time the flag is clicked. Call history and active-call numbers are still formatted for readability by the widget's own display formatter, independently of the input library.
- The soft phone can now dial internal extensions. A **Dial extension** toggle below the number field switches the keypad into extension mode, hides the country selector, accepts a free-form extension, and flags the dial request as an extension (`DialRequest.IsExtension`). Extension calls skip outbound compliance screening (do-not-call and calling-window enforcement) because an internal extension is not consumer outreach and cannot be canonicalized to E.164, while every real phone number still passes the fail-closed screening gate.
- The soft phone widget no longer briefly flashes the keypad before showing the correct state. While the provider and connection status are still resolving, the keypad, the call buttons, and every status message stay hidden until the real state (unavailable, connect, or operating) is known.
- The soft phone no longer stretches to nearly full screen height when a provider that requires a per-user OAuth connection is enabled. The height-reserving keypad body is now collapsed behind the **Connect to provider** panel, so the widget keeps its normal height.
- The **Connect to provider** button now reliably opens the provider's authorization window in a new browser tab and surfaces an inline error inside the connect panel when the authorization URL cannot be resolved or the browser blocks the popup, instead of appearing to do nothing.
- When the default provider uses OAuth 2.0 and the current user is connected, the soft phone header now shows a **Disconnect provider** action so the user can clear that provider connection directly from the widget instead of going through provider-specific settings pages.
- OAuth connect failures are no longer silent. When a provider's authorization callback cannot complete the token exchange, the soft phone now shows a safe reason inline in the connect panel, and the server logs the failure category without writing provider-supplied callback text to application logs. Client secret decryption failures and missing OAuth state cookies are logged as distinct categories instead of quietly closing the window with the soft phone still showing **Not connected**.
- The soft phone now applies successful dial responses immediately instead of waiting for a later provider state event, so users see the new outbound call as soon as a provider accepts it.
- The soft phone now refreshes active provider state while a call is active, so REST-only providers can move the UI out of `Connecting` even when no real-time event arrives. The active-call display now lets the phone-number input library own country-code rendering, avoiding a duplicate `+1` in the disabled call display.
- The standalone `/softphone` page no longer shows its incoming-call modal at the same time as the notification of a desktop app that embeds it (such as the CrestApps Soft Phone for Windows). The page sends the ringing call, with its queue and matched records, to the app through the WebView2 message channel, and hides the modal only when the app confirms that its notification for that call is on screen. If the app does not confirm within 2 seconds, or its notification closes without an answer, the modal shows as before. Answer, Decline, and Voicemail in the app's notification run in the page, through the same paths as the modal buttons. A normal browser tab and the browser extension are not affected. See [Notifications from a desktop app](../telephony/index.md#notifications-from-a-desktop-app).

### Providers

#### Asterisk

Adds the new **Asterisk** provider (`CrestApps.OrchardCore.Asterisk`), which integrates the Asterisk telephony platform with the Telephony soft phone through the Asterisk REST Interface (ARI).

Highlights:

Existing default-shell deployments that rely on inbound routing must update their Asterisk dialplan to target `Stasis(<ApplicationName>-Default)` for the default shell.

The interaction store canonicalizes the provider identity so calls recorded under the **Default Asterisk** alias correlate with the real-time voice events that the listener tags with the canonical `Asterisk` provider name.
- Contact Center voice and media features that adapt Asterisk call execution, real-time call events, and bidirectional RTP media to Contact Center orchestration.

#### Telnyx

Adds the new **Telnyx** provider (`CrestApps.OrchardCore.Telnyx`), which integrates the Telnyx voice platform with the Telephony soft phone and the Contact Center. Unlike a click-to-call provider, Telnyx exposes a SIP-over-WebSocket registrar and a server-side Call Control API, so the browser soft phone carries the call audio itself (WebRTC) and the Contact Center can bridge live calls to agents server-side (`ServerSideAcd`) — the basis for true power dialing.

Highlights:

- A single-API-key Telnyx provider that places and controls calls through the Telnyx Call Control (Voice API), advertising dialing, hang up, hold, resume, mute, blind and attended transfer, merge, DTMF, and inbound calls.
- A browser **WebRTC soft phone**: the server mints a short-lived Telnyx telephony credential per session and the browser logs in to Telnyx's WebRTC gateway through the **Telnyx WebRTC SDK** (`@telnyx/webrtc`, the vendored `telnyx-webrtc` media adapter), which owns the peer connection, media, and SDP/codec negotiation end to end — replacing the earlier shared SIP.js adapter and its browser-side SDP workarounds. Outbound calls use a **server-side originate-and-bridge**: the platform rings the agent's registered browser leg (which the soft phone auto-answers) and bridges it to the destination, so the agent hears the call in the browser. Credentials are per-user capped, expire on their own, and are revoked at Telnyx on sign-out.
- **Ed25519-signed webhooks** at `/api/telnyx/webhook/call`. Telnyx signs each delivery over `{timestamp}|{body}` and this module verifies it against the account public key configured in settings (no shared secret is generated); the endpoint rejects unsigned, stale, or oversized deliveries and processes accepted events through the durable provider webhook inbox.
- A **Telnyx contact center voice adapter** that advertises the `ServerSideAcd` delivery model and supports dialer dialing, agent connect (originate the agent's browser SIP leg and bridge it to the caller), call transfer, and — with the **Contact Center Call Recording** feature — recording. Recording is driven by Contact Center governance (`record_start` / `record_pause` / `record_resume` / `record_stop`); the `call.recording.saved` webhook is ingested into the encrypted media store and the Telnyx-hosted copy is deleted afterward, so no plaintext recording lingers off-platform. It is integration glue rather than a separate feature: it activates automatically whenever the **Telnyx** module and **Contact Center Voice** are both enabled.
- **Bidirectional media streaming** over the `api/telnyx/media/stream` WebSocket (G.711 mu-law) — the Telnyx equivalent of Asterisk ARI External Media — giving the Contact Center a live server-side media leg.
- **Extension dialing** (`CrestApps.OrchardCore.Telnyx` advertises `ExtensionDial | ExtensionConference`): call another on-platform user by extension, or add an extension into a call as a conference participant, by originating and bridging two Telnyx SIP-over-WebSocket registrations. See [Extension Dialing](../telephony/extension-dialing).
- A new **Telnyx AI Voice Agent** feature (`CrestApps.OrchardCore.Telnyx.AiVoice`): the Phone-channel omnichannel processor dials a contact over Telnyx and runs an automated conversation using Telnyx text-to-speech and real-time transcription driven by an AI chat profile, then settles the omnichannel activity with a summary and disposition — the voice counterpart to automated SMS.
- A new **Telnyx SMS** feature (`CrestApps.OrchardCore.Telnyx.Sms`): a Telnyx SMS/MMS provider (configured from the `OrchardCore_Sms_Telnyx` appsettings section or the SMS settings screen) with an Ed25519-signed messaging webhook at `/api/telnyx/webhook/sms` for inbound `message.received` events and `message.finalized` delivery receipts, so Telnyx numbers can send and receive text through the SMS Portal and SMS Automation.
- See [Telnyx](../telephony/telnyx) for setup and troubleshooting.

### Omnichannel Messaging Workspace

Version `3.0.0` adds the **Omnichannel Messaging Workspace** (`CrestApps.OrchardCore.Omnichannel.Messaging`, category **Contact Center**), a **human-operated**, channel-agnostic messaging inbox: one customer list and one conversation view for every non-voice channel, with a tab per channel above each customer's conversation and a live unread badge on each tab. Channels are separate features; the first is the **SMS Messaging Channel** (`CrestApps.OrchardCore.Omnichannel.Messaging.Sms`), and email, WhatsApp, Messenger and others can be added by implementing `IMessagingChannel`. The workspace provides a shared team inbox, threaded conversations (one per customer address on each channel), a composer with canned-response templates, live contact search, claim/assign/transfer, close/spam/reopen, and 1:1 broadcasts processed by a durable background task, with real-time inbound and delivery-receipt updates over its own SignalR hub, a notice on every other admin page when a customer writes or a conversation is transferred to the agent or their queue, and a count of the conversations waiting on the agent on the **Messaging** admin menu item. It is the human counterpart to the AI-driven [SMS Automation](../omnichannel/sms) and shares the same Omnichannel message store, so an AI conversation can hand off to a human on the same number.

It deliberately reuses existing building blocks: each address it sends from (an SMS number, for the SMS channel) is an **Omnichannel channel endpoint** that carries its provider and inbound routing (target agent/queue, distribution mode, auto-reply), so the earlier separate `SmsNumberRoute` concept was retired. Operators are Contact Center **agent profiles** resolved through a dependency-only **Agent Services** feature (a bare profile is provisioned automatically on first access, with no Contact Center administration required), and SMS sending goes through a per-number `ISmsDispatcher` so different numbers can send through different carriers. The workspace depends only on Omnichannel Channel Endpoints, Contact Center Agent Services and `OrchardCore.SignalR`; the SMS channel adds `OrchardCore.Sms`. See [Messaging Workspace](../omnichannel/messaging-workspace).

#### Agents see only their own conversations and their queues' unclaimed ones

Every messaging permission listed **Use the messaging workspace** as a permission that implies it, so every agent who could use the workspace also held **View all messaging conversations**, **Send group messages** and **Send messages outside business hours**: an agent saw, and could open, the conversations their colleagues had claimed. Using the workspace now implies none of them, and which conversations a user sees follows Orchard Core's content pattern. Two permissions are added beside **View all messaging conversations**: **View your own messaging conversations** (`ViewOwnMessagingConversations`), for the conversations assigned to the agent or sent to an endpoint they own that no colleague has claimed, and **View your own and your queues' unclaimed messaging conversations** (`ViewQueueMessagingConversations`), which adds the unclaimed conversations of the queues they serve. A conversation is authorized against `ViewAllMessagingConversations`, and an authorization handler grants anybody without it the conversations that are theirs; the list, the menu count and the notifications follow the same rule. A conversation no route gave to an agent or a queue is now a supervisor's to triage. An agent can still finish a conversation they hold after leaving its queue. The `IMessagingConversationAuthorizationService` service is removed: authorize a conversation with `IAuthorizationService.AuthorizeConversationAsync`.

The **Agent** role gets `UseMessagingWorkspace` and `ViewQueueMessagingConversations`; the **Supervisor** role gets `UseMessagingWorkspace`, `ViewAllMessagingConversations`, `SendGroupMessages`, `SendMessagesDuringQuietHours` and `ManageMessaging`. On an existing tenant, a migration grants `ViewQueueMessagingConversations` to every role that could use the workspace, so its agents keep their queues' inbox. See [Messaging Workspace](../omnichannel/messaging-workspace#permissions).

### Omnichannel Management

#### The phone number backfill, the contact search and the Leads count no longer load the database

On a large tenant, the **Omnichannel Contact Phone Number Backfill** background task added with the phone number index kept the database at full load for as long as it ran: it read each page of records by joining the content item index to the contact index, which made SQL Server group and sort every record after its cursor to find the next 200, 25 times a minute. Each page is now read from `OmnichannelContactIndex` alone by document id (`OmnichannelContactIndex.DocumentId`, filled when the row is read and never written), then the records are loaded by id, and the task reads up to 2,000 records a minute instead of 5,000. A tenant whose backfill is in progress continues from its stored cursor.

The search box of the Contacts and Leads lists now compares a number with the start of the primary Cell and Home numbers, in a subquery on the contact index that seeks its phone number indexes, instead of joining the contact index to the list and matching any part of each number, which read every contact on each search and again for its count. Only a search written like a phone number, with at least three digits, is compared with numbers: a search with letters, such as `John 2`, matches names only. Use `phone:` or `phone-ends:` to find digits anywhere in a number.

The Leads list (`converted:false`) is now counted from the lead index alone, through `LeadContentsAdminListQueryService`, which wraps the content list query service, and the new `IDX_LeadIndex_ContentType_Converted` index (migration step 5 to 6). The list's own count joined the document table, the content item index and the lead index and counted the distinct documents, which outlived the command timeout on a large tenant. The lead index count is used only when it is certain to be the number the list shows: the list names only lead types the user may view in full, filters by lead terms with plain values and the latest, published or unpublished version, has no free-text search and carries no other filter. Every other list keeps its own count. See [Find a contact](../user-manual/contacts.md#find-a-contact) and [Phone number search](../omnichannel/management.md#phone-number-search).

#### Contact types can keep their phone numbers and emails in their own fields

A content type became an omnichannel contact by carrying `OmnichannelContactPart`, but its phone numbers and emails had to live in the `ContactMethods` bag, so a site whose people already keep them in typed fields of their own had to copy them into the bag on every save. Every reader now goes through the new `IContactMethodsAccessor` (`CrestApps.OrchardCore.Omnichannel.Core`), which reads the bag by default and an `IContactMethodsProvider` registered for a content type with `services.AddContactMethodsProvider<TProvider>(contentType)`. What the product writes (an email given in a conversation, a converted lead's numbers and addresses) goes through `IContactMethodsWriter`, and a type with a provider registers its own writer with `services.AddContactMethodsWriter<TWriter>(contentType)` or stays read-only. A type with a provider is not given the bag, and a bag it already has is left as it is. Sites that register nothing behave as before. See [Keep phone numbers and emails in your own fields](../omnichannel/management#keep-phone-numbers-and-emails-in-your-own-fields).

The readers now share one set of rules for phone types (`ContactPhoneTypes`): case and surrounding spaces are ignored, and a number typed `Mobile` counts as a cell number everywhere, including the contact index, SMS and the call order. Any item in the bag that carries a phone number or an email is read, whatever its content type. The contact header lists a contact's phone numbers before its email address.

Phone verification decides whether a number needs a lookup from the verification stored on the contact. A save that rebuilds the bag item holding the number no longer queues a new, paid lookup; the item gets the contact's copy of the verification back.

#### Calls and texts from a contact's work number are matched to the contact

A contact reached at a Work, Office or Other number, or at a second Cell number, was dialed and texted at that number, but when it called or texted back it showed as an unknown caller, because every lookup by number read only the first Cell and Home numbers of the contact index. The same gap let a record that saved a number as Work be dialed after another record holding the same number had asked not to be called.

The new `OmnichannelContactPhoneNumberIndex` holds one row per number of every contact and lead, and every lookup by an exact number now reads it through `IOmnichannelContactPhoneLookup`: the inbound call match, the SMS sender match, the shared-number opt-out, lead-to-contact matching, the import duplicate check and the dialer's check for leads that are already contacts. The SMS sender match no longer combines the Cell and Home columns with an OR, which kept SQL Server from seeking either column's index. Existing records are indexed by the **Omnichannel Contact Phone Number Backfill** background task after the upgrade; until it finishes, lookups also read the Cell and Home columns, so nothing that was found before is missed. The `phone:` search and the activity phone filters still search the first Cell and Home numbers. See [Matching a number to a contact](../omnichannel/management.md#matching-a-number-to-a-contact).

`ContactOptOutResolver`, `SmsMessagingChannel`, `LeadMatchFinder`, `OmnichannelContactDuplicateLookupService` and `DefaultContactActivityBatchLoader` take an `IOmnichannelContactPhoneLookup`. `IOmnichannelContactDuplicateLookupService.GetPhoneNumberOwnersAsync` and `OmnichannelContactMatches` take the new `IOmnichannelContactMatch`, which `OmnichannelContactIndex` implements, in place of `OmnichannelContactIndex`.

#### Contact index migration no longer stalls on PostgreSQL

The `OmnichannelContactsMigrations` upgrade steps rebuild the default contact index by re-issuing `CREATE TABLE`, `ADD COLUMN`, and `CREATE INDEX` statements and swallowing the "already exists" errors with `try`/`catch`. Orchard Core runs every migration step through a single `SchemaBuilder` that shares the migration's database transaction. On PostgreSQL, the first failing DDL statement aborts that whole transaction, so even though the .NET exception is caught, the shared transaction stays poisoned and the final version bump can never commit — leaving the migration permanently stuck on an old version (most often version 6). Each idempotent schema change now runs behind its own savepoint inside the migration transaction, so an "already exists" failure only rolls back that one statement and can no longer poison the migration transaction. The isolation deliberately stays inside that transaction: a change moved onto a second connection waits for locks the migration transaction already holds (on SQLite, the database's only write lock), times out, and is skipped as if it already existed. MySQL, which commits DDL implicitly and so discards savepoints, runs each change on its own connection instead. The migration now advances correctly on PostgreSQL, SQL Server, MySQL, and SQLite.

#### Activity batch index migration no longer loses the `CreatedUtc` column

The activity batches admin screen orders batches by a `CreatedUtc` column added to `OmnichannelActivityBatchIndex` by an upgrade step. That step ran through the feature's shared migration `SchemaBuilder`, so when any sibling migration in the same feature threw, Orchard Core cancelled the shared session and rolled back the column addition together with the migration's version record. On databases with transactional DDL (PostgreSQL and SQL Server), the tenant was left with the migration record still pointing at the old version and the physical `CreatedUtc` column missing, so the screen failed with `Invalid column name 'CreatedUtc'`. The column additions now run as isolated, idempotent schema changes, shared with the contact index migration through the new `OmnichannelIndexMigration` base class, so a change that cannot be applied no longer takes its sibling steps down with it. A follow-up repair step now also verifies the `Source` and `CreatedUtc` columns and adds only the ones that are missing, so tenants whose migration record was already advanced past the original upgrade steps while the physical columns were rolled back are healed on the next start.

### Content Transfer

#### An import stuck on a row no longer holds the import until a restart

A bulk import could stop just short of the end and stay in **Processing** with no error. One row's work never returned, so the run kept waiting and kept the import's lock. With the in-memory lock, which ignores its expiration, nothing could take the import over until the application restarted. **Resume import** reported success, and the run it started found the lock taken and returned without logging anything. Each run is now watched. A row that takes longer than a minute is named in a warning. A row still running after 10 minutes, or a run past 28 minutes, is abandoned, and its lock is released. The import then resumes from its last saved row on the next run. A row that stops two runs is skipped and listed in the error file with the reason. A run that wakes up after it was abandoned can no longer save progress. A batch whose caller has stopped waiting no longer holds the pacing gate that the bulk work of every tenant shares. Each run now logs where it started, where it stopped, and why. Finding the import's lock taken is reported as a warning once the import has gone 10 minutes without saving progress. **Resume import** on an import that is still running now says so. See [Content Transfer](../modules/content-transfer#import-processing).

Two related causes of an import that stops moving are fixed too. A do-not-call registry that timed out used to end the whole run, and the log reported it as a database timeout, so the import stopped at the same row on every run. The row is now skipped with the reason that the registry could not be reached, as for any other registry failure. A run whose preparation took past its time limit used to stop before its first row and start over the same way indefinitely. Each run now reads at least one row before it stops.

### DNC Registry

#### Local registry migration no longer blocks other feature migrations

The **Local** DNC registry repair migration checked whether its index tables already existed by comparing the database schema against an **unprefixed** table name. On installations that use a table prefix (for example multi-tenant deployments), the check always reported the tables as missing, so the migration tried to recreate them and threw a duplicate-object error. Because Orchard Core runs every feature's automatic migration on a shared session, that uncaught error cancelled the session and silently rolled back every other feature's migration in the same run — most visibly leaving the Omnichannel contact migration stuck on an old version. The existence check now resolves the physical (prefixed) table name, and the repair step no longer rethrows if the table is already present, so a single feature can no longer stall the rest of the migration batch.

Each instance binds one existing AI data source plus its own retrieval parameters — retrieval mode (matching chunks, or the full source documents they belong to), strictness, retrieved document count, and an OData filter — and is exposed to the model as its own callable function, so several knowledge bases can sit side by side under their own names. The model supplies only the search phrases, embedded with the same embedding deployment the knowledge base index was built with; results carry `[doc:N]` citations. Unlike a data source attached to a profile, retrieval runs when the model asks for it instead of on every turn. Importable through the `AIToolInstances` recipe step via `DataSourceSearchToolSettings`. See [AI Tool Instances](../ai/tool-instances#the-data-source-search-source).
- **Realtime TURN credentials can be minted by Cloudflare, per tenant.** Realtime voice can now source its TURN servers from Cloudflare Realtime, which issues short-lived credentials through an API instead of exposing a shared secret that could be signed locally. Configure the TURN Token ID and API token under `OrchardCore:CrestApps:AI:RealtimeTransport:Cloudflare`. Like the rest of the realtime transport section, it is read through `IShellConfiguration`, so each tenant can mint credentials from its own Cloudflare account rather than sharing the host's. A tenant that configures no token keeps using the `StunUrls` and `TurnUrls` it already had, and that same path also covers a Cloudflare outage. See [Realtime Voice](../ai/realtime-voice#cloudflare-realtime-turn).
- **Cascaded realtime deployments.** Realtime voice no longer requires a provider that ships a speech-to-speech model. Create a deployment under the new **Cascaded Realtime** provider and pick the three deployments it chains — one that transcribes, one that generates the reply, and one that speaks it. The three may come from different providers, and the profile, chat UI, transcripts, and turn persistence all behave exactly as they do with a native realtime model. Tools, data sources, and the profile's instructions are applied to the chat deployment, so a voice profile keeps everything a text profile has. The deployment declares the **Realtime** feature itself, and its **Voice** picker lists the text-to-speech deployment's voices. Importable through the `aideployment` recipe step via `CascadedRealtimeMetadata`. See [Realtime Voice](../ai/realtime-voice#cascaded-realtime-when-no-provider-speaks).
- **The anonymous visitor cookie can be configured to survive inside a frame on another site.** The **Visitor Identity** card under **Settings → Artificial Intelligence** gains **Allow cross-site embedding** and **Partition the cookie per embedding site**, alongside the cookie name and lifetime it already had. The visitor cookie is written `SameSite=Lax` by default, which a browser refuses in a third-party context, so a chat embedded in a frame on a customer's site looked like a brand new visitor on every request: the conversation did not survive a page load, and the visitor rate-limit partition never accumulated. Turning cross-site embedding on writes the cookie `SameSite=None; Secure` instead, which is the only combination a browser keeps in a frame; a request that did not arrive over HTTPS keeps the `SameSite=Lax` cookie rather than losing it altogether. Partitioning is on by default and keeps that cookie apart from the first-party one of the same name. Cross-site embedding is off by default, so nothing changes for a chat served from its own site. Importable through the `Settings` recipe step via `AIVisitorIdentityOptions`. See [Chat](../ai/chat#anonymous-visitor-identity).
- **Filters on an Elasticsearch knowledge base are applied again.** No `IODataFilterTranslator` was registered for Elasticsearch after the translators moved to CrestApps.Core, so the filter of an AI profile, a chat interaction or a data source search tool instance was ignored without a word, and every search returned rows the filter was written to keep out. The **AI Data Sources - Elasticsearch** feature now registers the CrestApps.Core translator. A filter is still not supported on an Azure AI Search knowledge base index, because the index declares no `filters` field; such a filter is ignored and a warning is now logged. See [Filtering retrieval](../ai/data-sources/index.md#filtering-retrieval).
- **The `search_data_sources` tool applies the filter of a chat interaction.** In a chat interaction, the tool that the model calls searched with no filter, strictness or retrieved document count, while the preemptive retrieval of the same turn applied them. Both now read the same settings.
- **A chat interaction no longer saves an invalid filter.** The **Knowledge** panel of a chat interaction saved any filter text, without the check the AI profile editor applies. An invalid filter now rejects the save with *"Invalid filter value. It must be a valid OData filter."*, and the interaction keeps its settings.
- **Chat with Preset Settings keeps the knowledge settings.** Cloning a chat interaction dropped its data source, filter, strictness, retrieved document count, scope restriction, tool instances, model parameters and prompt templates, because they were passed to the new interaction in a shape it did not read. The clone now copies them. Data that belongs to one user, such as the access tokens of a Copilot session, is not copied.
- **A blank Strictness or Retrieved documents uses the default.** On the **Knowledge** tab of an AI profile, a profile template and the **AI Completion using Direct Config** workflow task, the hints say to leave **Strictness** or **Retrieved documents** blank to use the default, but a blank was rejected as out of range. A blank now saves the **Default strictness** or **Default top documents** from the **Data Sources** card under **Settings → Artificial Intelligence**, and a value outside the allowed range is still rejected. The **Retrieved documents** hint on a profile no longer claims a default of 3: the built-in default is 5, and the site setting can change it.
- **A missing API key on an OpenAI connection shows under API key.** The OpenAI connection editor showed *"API key is required field."* under **Endpoint**. It now shows under **API key**.
- **AI personas.** The new **AI Personas** feature (`CrestApps.OrchardCore.AI.Personas`) adds reusable characters
  that AI profiles, Profile templates, chat interactions and the **AI completion with configuration** workflow task
  link to. A persona holds its own instructions, assistant name, language, voice and avatar. Personas have their own
  catalog under **Artificial Intelligence → Personas** and the **Manage AI personas** permission. A tenant starts with
  none: create them in the admin, import them with the new `AIPersonas` recipe step, export them with the new
  **AI Personas** deployment step, or register them in code, either as saved personas a migration creates or as
  persona files a module ships through `AddCoreAIPersonasFromAssembly`. The CrestApps Recipes feature exposes the
  schemas of the recipe step and the deployment step. The persona's instructions go first in the system message,
  the model is told the assistant name, and AI Chat sessions, the chat widgets and Chat Interactions show the name and
  avatar on assistant messages. Realtime voice, including Contact Center realtime calls, speaks with the persona's
  voice when neither the call nor the profile picks one. Turn-based automated calls speak with it when neither the
  activity nor the subject flow picks one, and speak and listen in the persona's language. An inbound turn-based call
  now also uses the voice picked on its subject flow, which it used to ignore. `AutomatedVoiceActivitySettingsResolver`
  takes an `IAIProfileManager` and the `IAIPersonaResolver`s. `AIChatSession.PersonaId` records the persona a session
  started with. See [AI Personas](../ai/personas).
- **A saved System Prompt template selected on an AI profile or chat interaction renders.** A template created under **Artificial Intelligence → Templates** with the **System Prompt** source could be picked on a profile or interaction, but nothing could find it when the chat ran. The selection failed, and the profile also lost its own system message, model parameters, tools and agents for that request. These templates now come from CrestApps.Core's `AIProfileSystemPromptTemplateProvider`, under their technical names, the same id the picker stores. They are read on every request instead of joining the tenant-wide template cache, so an edit renders on the next message. A template that ships with a module keeps priority over a saved template with the same name. `PromptTemplateSelectionService` no longer takes an `IAIProfileTemplateManager`; it lists and finds templates through `ITemplateService`.
- **An anonymous visitor sees their own chat history.** `DefaultAIChatSessionManager.PageAsync` answered an empty list for anyone who was not signed in, so a chat serving anonymous visitors — an embedded widget, most of all — showed them no history at all, even though `FindAsync` would happily open any one of those sessions by id. A signed-in user is unaffected.

The tool no longer asks for a workflow type and returns every activity, with its name, display text, category, and whether it is an event or a task.

#### Tiered anonymous chat rate limits

The **Prompt Security** section under **Settings → Artificial Intelligence** now exposes the tiered anonymous rate limits added in `CrestApps.Core`:

- **Anonymous message rate-limit tiers** and **Anonymous session-start rate-limit tiers** accept one tier per line as `limit, window` (the window is a .NET `TimeSpan`, for example `00:00:30` or `1.00:00:00` for a day). A request is throttled when it would exceed any tier, so a short burst tier can sit alongside longer sustained tiers. Both default to the same tiers as `CrestApps.Core`, and clearing a field falls back to the matching single-window limit.
- Tiers apply to **anonymous** callers only. **Maximum messages per window** and **Message rate-limit window** now govern authenticated callers, and anonymous callers only when no message tiers are configured; **Maximum anonymous sessions per window** and **Anonymous session window** are likewise the fallback for the session-start tiers.
- The default for **Maximum anonymous sessions per window** changed from `5` to `20` to match `CrestApps.Core`. Sites that already saved this setting keep their stored value.
- Both tier lists can be set from a recipe through the `PromptSecurityOptions` site settings step.
- Individual AI profiles (and profile-source AI profile templates) can override both tier lists from their **Prompt Security** tab. A blank field inherits the site tiers; entering tiers replaces them for that profile; and a **Do not use tiered ... limits for this profile** checkbox opts the profile out of tiered limits entirely so it falls back to its own single-window values.
- The message shown when a visitor is throttled while starting a new chat no longer discloses the configured limit, the current count, or the retry delay, and is now localizable. Those values would let an abuser tune their traffic to sit just under the throttle.
- A throttled session start is now signalled to the client as a dedicated rejection (`ReceiveSessionStartRejected`) rather than a generic error, so the embedded chat widget shows the message instead of treating it as recoverable, clearing the visitor's state, and silently retrying. This also covers the OrchardCore-specific TemplatePrompt path, which replaces the framework's generated-prompt handler outright.
- The chat UI no longer leaves a throttled visitor waiting on a hung request. The chat scripts were updated to `@crestapps/ai-chat-ui` `2.0.0-preview.154`, which rejects the pending new-session request, clears the typing indicator, and shows the message instead of failing silently. The `AIChatApp`, `AIChatWidgetApp`, `ChatInteractionApp`, `document-drop-zone`, and `technical-name-generator` resources moved to version `2.0.0`, so cached copies of the old scripts are replaced.
- Documented that the tier lists take precedence over the single-window settings, so lowering **Maximum anonymous sessions per window** has no effect while the default tiers are still in place.

See [Prompt Security](../ai/chat#prompt-security) for details.

### Taxation

#### New provider-agnostic taxation framework

A new **Taxation** module (`CrestApps.OrchardCore.Taxation`) introduces a provider-agnostic, extensible taxation framework for Orchard Core. It models tax as a **determination** — derived from *what* is sold, *who* buys it, *where* it is sourced, *when* it happens, and *how* it is calculated — rather than a static rate stored on a product.

Highlights:

- A new **Taxation** part lets any content type participate in taxation by classification only (tax category and classification), never a stored rate.
- A deterministic engine (`ITaxService`) produces an auditable, line-by-line breakdown with references to the exact tax rule and tax table versions used.
- Built-in calculation methods cover percentage, fixed amount, per-unit, per-weight, per-volume, tax table, progressive, and threshold taxes, with tax-inclusive and tax-exclusive pricing.
- Extensible tax types, hierarchical jurisdictions, categories, versioned rules, tax tables, sourcing strategies, exemption certificates, and merchant nexus registrations.
- Historical tax snapshots (`ITaxSnapshotFactory`) keep transactions immutable, so changing a rate, rule, or table never alters past transactions, and refunds reverse the original determination.
- Clean extension points (`ITaxableItemProvider`, `ITaxCalculationMethod`, `ITaxSourcingStrategy`, `ITaxDeterminationProvider`, and more) let Products, Subscriptions, Commerce, Bookings, Services, custom content types, and external tax providers integrate without modifying the Taxation source.

See [Taxation](../modules/taxation) for details.

#### Taxation integrated across Products, Subscriptions, Checkout, and Payments

Taxation is now the single authoritative tax engine for the commerce stack. The integration is native — no product-, subscription-, checkout-, or payment-specific tax calculation remains — and it stays optional through Orchard Core feature dependencies, so every module keeps working when Taxation is disabled.

- **Products** contribute an `ITaxableItemProvider` that turns a product (via the **Product** and **Taxation** parts) into a taxable item — price, product-type–derived kind, tax category, classification, and external code — without ever calculating tax itself.
- **Checkout** determines tax on the amount due now and captures it on the invoice as a tax amount, detailed tax lines, and an immutable snapshot. Exclusive tax is folded into the up-front charge so the payment provider collects the exact taxed total.
- **Recurring subscription billing** re-taxes each renewal with the rules in effect at billing time and stores a fresh per-cycle snapshot, so rate changes and customer address changes apply to future cycles while historical transactions never change.
- **Payments** stay tax-agnostic: providers charge the final, already-taxed transaction amount and never interpret tax rules.
- **Refunds** derive their tax from the original transaction snapshot through a new `ITaxRefundCalculator` (full and proportional refunds allocated across the original tax lines), never from current rules.

#### Subscription and commerce reports

When the **Reports** feature is enabled, the Subscriptions module now contributes admin reports: subscription revenue, a subscriptions dashboard (active, new, and expiring), expiring subscriptions, a new-subscription trend, tax collected, and product performance. A `TaxAmount` column added to the subscription transaction index makes collected tax queryable.

See [Subscriptions](../modules/subscriptions#taxation) and [Products](../modules/products#taxation) for details.
