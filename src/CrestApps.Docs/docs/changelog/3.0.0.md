# Version 3.0.0 Release Notes

This page highlights the changes in the `3.0.0` line.

## New Modules

### Products, Payments, and Subscriptions

This release introduces a new commerce stack for selling recurring plans on Orchard Core content:

- **[Products](../modules/products)** (`CrestApps.OrchardCore.Products`) — attaches a reusable `ProductPart` (price + product type) to any content type, turning content items into purchasable products.
- **[Payments](../modules/payments)** — a provider-agnostic payment framework (`IPaymentEvent`, `PaymentMethodOptions`) with a production-hardened **Stripe** provider (`CrestApps.OrchardCore.Stripe`). Stripe supports both the on-site **Payment Elements** integration and the Stripe-recommended **Hosted Checkout** (redirect), selectable from settings. New payment gateways (for example PayPal) can be added and surfaced as checkout options without changing the consuming modules.
- **[Subscriptions](../modules/subscriptions)** (`CrestApps.OrchardCore.Subscriptions`) — sells recurring subscriptions built on a `SubscriptionPart`, with a multi-step checkout flow, a subscriber dashboard, an admin management console, and optional **reCaptcha** and **Tenant Onboarding** features. Subscriptions depends on the new **[Checkout](../modules/checkout)** framework for payment handling. Payment options are contributed by other modules: enable the **Stripe** module to accept card payments (wired in automatically when both are enabled — there is no separate *Subscriptions - Stripe* feature), and enable the **[Pay Later](../modules/pay-later)** module to offer an offline pay-later option.
- **[Pay Later](../modules/pay-later)** (`CrestApps.OrchardCore.PayLater`) — a standalone module that adds an offline "pay later" option to the Checkout framework, reusable by subscriptions and one-time goods purchases. It records an offline commitment through the same durable ledger and reconciliation as a real gateway, without ever fabricating a *paid* record a processor could contradict.

The payment path was hardened for multi-instance, production use: deterministic Stripe idempotency keys, distributed-lock–serialized checkout finalization, currency-aware minor-unit conversion, rate-limited anonymous checkout endpoints, and signature-verified, de-duplicated, retry-safe Stripe webhooks.

See [Products](../modules/products), [Payments](../modules/payments), and [Subscriptions](../modules/subscriptions) for details.

### Checkout

This release also introduces **[Checkout](../modules/checkout)** (`CrestApps.OrchardCore.Checkout`) — a provider-agnostic checkout and payment framework that any purchase flow can build on, so the wizard, invoice, taxation seam, and money-handling safety guarantees are written once and reused by recurring subscriptions and one-time goods purchases alike.

Checkout is hardened for sensitive, multi-node money handling:

- A **durable payment ledger** (`PaymentAttempt` / `IPaymentAttemptStore`) persisted in the tenant database, written *before* every provider call and updated with the provider's authoritative reference immediately after — so a crash, cache eviction, or partial multi-obligation failure can never strand an untracked charge.
- **Reconciliation against the provider's authoritative API** (`ICheckoutReconciliationService`) that records a payment *only* when the provider confirms it and marks the checkout complete only when **every** obligation is settled, so our side never shows *paid* while the gateway failed.
- A first-class **`ICheckoutPaymentProvider`** contract (begin / verify / cancel + capabilities) for adding gateways.
- **Currency-correct money** (`Money` / `CurrencyScale`) for every ISO-4217 currency, including zero-decimal (JPY) and three-decimal (KWD) currencies.
- **Distributed coordination** via `IDistributedCache` and `IDistributedLock` (`PaymentSessionCache`, `IPaymentAttemptLimiter`), where the cache is a notification-only optimization and never the source of truth.
- A **taxation seam** (`ICheckoutTaxService`) that folds tax into the charged amount when Taxation is enabled and is a no-op when it is not.

See [Checkout](../modules/checkout) for details.

## Breaking Changes

### AI

- **The MCP Server no longer exposes tools by default.** Previously every registered AI tool was listed and callable by any connected MCP client. Tool exposure is now **opt-in**: nothing is listed or callable until you either select the tools and tool instances on the new **MCP Server** card under **Settings → Artificial Intelligence**, add their names to `McpServerOptions.Tools`, or set `McpServerOptions.ExposeAllTools` to `true`. **Expose all tools** now exposes only *selectable* tools; system tools and hidden tools are never exposed, even when it is enabled. Deployments that relied on the previous "expose everything" behavior must enable **Expose all tools** (or populate the allow-list) to keep exposing their tools. Prompts and resources are unaffected. See [MCP Server](../ai/mcp/server#tool-exposure) for details.
- **A2A host cards now use A2A 1.0 supported interfaces.** Agent cards no longer publish the endpoint through the deprecated top-level `url` field. Clients should read the endpoint from `supportedInterfaces`, and multi-agent mode still points each interface to `/a2a?agent={agentName}`. See [A2A Host](../ai/a2a/host) for details.

### Reports

- `ReportFilter` no longer exposes `FromUtc`, `ToUtc`, or `DateRangeKey` as first-class properties, and `ReportContext` no longer exposes `FromUtc` or `ToUtc`. The date range is now contributed and stored like any other filter, so reports that do not need a date selector can omit it. Read and write the period through the new `ReportFilter` helpers (`GetDateRange()` / `SetDateRange()` — for example `context.Filter.GetDateRange()` inside a report), and read or write any filter value with the typed `TryGet<T>(string key, out T value)`, `GetOrDefault<T>(string key)`, and `Set<T>(string key, T value)` extension methods.

### SignalR

The SignalR module has now been migrated into the Orchard Core framework.

If you are currently using `CrestApps.OrchardCore.SignalR`, you should migrate to the `OrchardCore.SignalR` module instead. Similarly, if you are using `CrestApps.OrchardCore.SignalR.Redis`, you can migrate to `OrchardCore.SignalR.Redis`.

For now, the CrestApps SignalR features have been marked as deprecated. However, if you are already using the CrestApps modules, they will automatically enable the corresponding Orchard Core features for you. `HubRouteManager` has been removed; modules now map hubs with `SignalRHubRoutes.GetHubPath<T>()`, and views generate tenant-aware client URLs with `Html.SignalRHubUrl<T>()`.

:::tip
Do not remove the CrestApps SignalR module yet if you want the automatic migration to take place. Once the migration has completed, you can remove the deprecated module. Alternatively, you can remove it immediately and manually enable the SignalR features provided by the Orchard Core framework.
::: 

### Telephony

- The Dialpad module, feature id, provider technical name, namespaces, and public types now use the `Dialpad` casing consistently.

### Resource Module

- The `crestapps-bootstrap-select` style and script have been removed from the `Resource` module. Instead you should use the `bootstrap-select` style and script which are registered by Orchard Core.

### Omnichannel Management

- The `OmnichannelContentTypeProvider` service is now registered as **scoped** instead of **singleton**, and its public query methods are now asynchronous and return `ValueTask`. Update any callers accordingly:

  | Old (synchronous) | New (asynchronous) |
  |---|---|
  | `bool IsSubjectContentType(string contentType)` | `ValueTask<bool> IsSubjectContentTypeAsync(string contentType)` |
  | `bool IsContactContentType(string contentType)` | `ValueTask<bool> IsContactContentTypeAsync(string contentType)` |
  | `IReadOnlyCollection<string> GetSubjectContentTypes()` | `ValueTask<IReadOnlyCollection<string>> GetSubjectContentTypesAsync()` |
  | `IReadOnlyCollection<string> GetContactContentType()` | `ValueTask<IReadOnlyCollection<string>> GetContactContentTypesAsync()` |

  The provider now caches its membership sets in a per-tenant `IMemoryCache`, so the initialization is handled internally and callers should simply `await` the query methods. `OmnichannelContentTypeProvider` no longer implements `IContentDefinitionEventHandler`; cache invalidation on content definition changes is handled by a separate internal handler.

## Change Logs

### Taxation admin UI

The **Taxation** management screens (Categories, Jurisdictions, and Rules under **Commerce → Taxation**) were fixed and polished:

- The Create and Edit forms now render their fields. The editor view models were `sealed`, but the display manager builds a runtime proxy of each editor view model; a sealed type made the proxy creation throw a `TypeLoadException` that the display pipeline swallowed, silently rendering an empty form. The view models are now open, so every field displays.
- The top-level **Commerce** admin menu now shows an icon, following the Orchard Core `NavigationItemText-{id}.Id.cshtml` convention.

### Subscriptions checkout

The subscription checkout flow was hardened so that a hosted, redirect-based payment (Stripe Hosted Checkout) and offline **Pay Later** work reliably for both authenticated and anonymous customers:

- The pending subscription session is now persisted when the signup page is first rendered, so the payment step always references a durable, distributed-safe session. Previously an authenticated customer — whose registration step is skipped, making Payment the first step — reached the payment endpoints with a session that had never been saved, so Stripe Hosted Checkout and Pay Later failed. A returning visitor resumes the same pending session (tracked in a cookie) instead of orphaning a new one, and a resumed session is never re-saved on render, so a concurrent checkout completion can never be reverted to *Pending*.
- Checkout completion started from the standard signup POST (used by Pay Later) is now serialized with the same per-session distributed lock already used by the Stripe return, so a duplicate submission cannot run the provisioning handlers twice.
- The Stripe Checkout Session UI mode was updated to `hosted_page`, matching the current Stripe API (the previous `hosted` value is no longer accepted).
- The Subscriptions feature now depends on `OrchardCore.Title`, so a plan that uses the Title part always renders (the service plans list no longer errors when Title is not separately enabled).

### Samples

The MCP and A2A sample client launch profiles now use the same fixed HTTPS ports documented for Aspire: `5002` for the MCP sample and `5003` for the A2A sample. This avoids stale browser launches to the previous random local ports.

### Resources

The shared AI chat UI resources now use `@crestapps/ai-chat-ui` 1.2.0. Local package references, CDN URLs, resource versions, and SRI hashes were updated together.

### Reports

#### Date range defaults now cover today through end-of-day

The shared date-range picker now seeds empty custom ranges with today's local date from `00:00` through `23:59`. Empty **On or before** pickers default to today at `23:59`, and reports treat submitted `23:59` upper bounds as `23:59:59` without showing seconds in the picker UI. Empty **On or after** pickers default to today at `00:00`. Report pages now use that same one-day default period instead of the previous last-30-days range.

See [Reports](../modules/reports#date-range-filter) and [Resources](../modules/resources#date-range-picker) for details.

#### Color-coded report cells and styled Excel export

Reports can now color-code their tables. A new `ReportStyle` (font color, background color, and bold) can be applied to column headers through `ReportColumn.HeaderStyle`, to an entire row through `ReportRow.WithStyle(...)`, and to an individual cell through `ReportRow.WithCellStyle(index, ...)`. A per-cell style takes precedence over the row style. Colors are supplied as hexadecimal values (for example `#2563EB`) so the same style renders in the browser and exports to Excel; the HTML renderer additionally honors simple named colors.

When the **Reports (OpenXml)** add-on is enabled, the Excel (`.xlsx`) export now writes these styles into the workbook (font color, cell background fill, and bold weight). Header, subtotal, and grand-total rows are exported bold automatically. CSV, which has no native styling, continues to export values only.

See [Reports](../modules/reports) for details.

### Omnichannel Management

#### Contacts menu in the Interaction Center

The **Interaction Center** admin menu now includes a **Contacts** item. It opens the standard Orchard Core content list restricted to the Omnichannel contact content types by passing every content type that attaches `OmnichannelContactPart` as a comma-separated `contentTypeId` to the content `List` action. The contact types come from the cached content-type provider, so the menu stays in sync as the part is attached or detached. The item is guarded by the **List content** permission.

See [Omnichannel Management](../omnichannel/management) for details.

#### Contact index migration no longer stalls on PostgreSQL

The `OmnichannelContactsMigrations` upgrade steps rebuild the default contact index by re-issuing `CREATE TABLE`, `ADD COLUMN`, and `CREATE INDEX` statements and swallowing the "already exists" errors with `try`/`catch`. Orchard Core runs every migration step through a single `SchemaBuilder` that shares the migration's database transaction. On PostgreSQL, the first failing DDL statement aborts that whole transaction, so even though the .NET exception is caught, the shared transaction stays poisoned and the final version bump can never commit — leaving the migration permanently stuck on an old version (most often version 6). Each idempotent schema change now runs in its own isolated transaction on a separate connection, so an "already exists" failure only rolls back that one statement and can no longer poison the migration transaction. The migration now advances correctly on PostgreSQL, SQL Server, MySQL, and SQLite.

-----

#### Activity batch index migration no longer loses the `CreatedUtc` column

The activity batches admin screen orders batches by a `CreatedUtc` column added to `OmnichannelActivityBatchIndex` by an upgrade step. That step ran through the feature's shared migration `SchemaBuilder`, so when any sibling migration in the same feature threw, Orchard Core cancelled the shared session and rolled back the column addition together with the migration's version record. On databases with transactional DDL (PostgreSQL and SQL Server), the tenant was left with the migration record still pointing at the old version and the physical `CreatedUtc` column missing, so the screen failed with `Invalid column name 'CreatedUtc'`. The column additions now run as isolated, idempotent schema changes on their own connection — shared with the contact index migration through the new `OmnichannelIndexMigration` base class — so they commit independently and survive a sibling migration failure. A follow-up repair step now also verifies the `Source` and `CreatedUtc` columns and adds only the ones that are missing, so tenants whose migration record was already advanced past the original upgrade steps while the physical columns were rolled back are healed on the next start.

### DNC Registry

#### Local registry migration no longer blocks other feature migrations

The **Local** DNC registry repair migration checked whether its index tables already existed by comparing the database schema against an **unprefixed** table name. On installations that use a table prefix (for example multi-tenant deployments), the check always reported the tables as missing, so the migration tried to recreate them and threw a duplicate-object error. Because Orchard Core runs every feature's automatic migration on a shared session, that uncaught error cancelled the session and silently rolled back every other feature's migration in the same run — most visibly leaving the Omnichannel contact migration stuck on an old version. The existence check now resolves the physical (prefixed) table name, and the repair step no longer rethrows if the table is already present, so a single feature can no longer stall the rest of the migration batch.

### AI Documents

#### File upload security scanning through Orchard Core

The **AI Documents** module now routes every uploaded file through Orchard Core's shared [`FileCreationService`](https://docs.orchardcore.net/en/latest/reference/core/file-upload-security/) pre-storage pipeline before the file is stored or processed.

Highlights:

- Uploads from chat interactions, profiles, chat sessions, and widgets are scanned before storage.
- Enabling the `OrchardCore.Antivirus` feature adds **ClamAV** virus scanning to all AI document uploads with no additional code.
- Rejections are fail-closed and logged at `Warning` level.

See [AI Documents](../ai/documents) for details.

### AI

#### Opt-in tool exposure for the MCP server

The **MCP Server** feature now exposes tools on an opt-in basis (see [Breaking Changes](#ai)). The server exposes only the AI tools and configured tool instances you explicitly allow, and the allow-list is enforced by both the list and the call handlers, so a tool that is not exposed can neither be discovered nor invoked.

Highlights:

- A new **MCP Server** card on the **Settings → Artificial Intelligence** page configures the authentication mode and selects which tools and tool instances are exposed, using the same selector as the AI Profile editor.
- An **Expose all tools** switch restores the previous "expose everything" behavior when it is explicitly enabled. It exposes only *selectable* tools, so system and hidden tools are never listed or callable even in this mode. Enabling it hides the **Tools** and **Tool instances** selectors, because the selection no longer applies.
- The settings are stored as site settings (`McpServerSettings`) and loaded into `McpServerOptions`; the existing `OrchardCore:CrestApps:AI:McpServer` configuration still overrides them for deployment scenarios.
- The **AI Tool Instances** feature now registers the built-in documentation search sources (sitemap crawl, prebuilt search index, and Algolia DocSearch), so a public documentation site can be declared as a tool instance and exposed to MCP clients on demand. The Algolia search-only API key is now encrypted with ASP.NET Core data protection at rest.

See [MCP Server](../ai/mcp/server#tool-exposure) and [AI Tool Instances](../ai/tool-instances#the-documentation-search-sources) for details.

#### Orchard Core SignalR migration

CrestApps modules now depend on `OrchardCore.SignalR` directly. The deprecated CrestApps SignalR
features remain only as compatibility features that enable the matching Orchard Core feature during
migration.

`HubRouteManager` has been removed. Use `SignalRHubRoutes.GetHubPath<T>()` when mapping hubs, and

Tenant group-name isolation remains backed by a dedicated test suite that treats tenant separation

Highlights:

- `TenantSignalRGroupName` uses length-prefixed encoding, so equal user, queue, or supervisor identifiers in different shells stay isolated and a crafted group name cannot spoof another tenant's destination.

### Taxation

#### New provider-agnostic taxation framework

A new **Taxation** module (`CrestApps.OrchardCore.Taxation`) introduces a provider-agnostic, extensible taxation framework for Orchard Core. It models tax as a **determination** — derived from *what* is sold, *who* buys it, *where* it is sourced, *when* it happens, and *how* it is calculated — rather than a static rate stored on a product.

Highlights:

- A new **Taxation** part lets any content type participate in taxation by classification only (tax category and classification), never a stored rate.
- A deterministic engine (`ITaxService`) produces an auditable, line-by-line breakdown with references to the exact tax rule and tax table versions used.
- Built-in calculation methods cover percentage, fixed amount, per-unit, per-weight, per-volume, tax table, progressive, and threshold taxes, with tax-inclusive and tax-exclusive pricing.
- Extensible tax types, hierarchical jurisdictions, categories, versioned rules, tax tables, sourcing strategies, exemption certificates, and merchant nexus registrations.
- Historical tax snapshots (`ITaxSnapshotFactory`) keep transactions immutable, so changing a rate, rule, or table never alters past transactions, and refunds reverse the original determination.
- Clean extension points (`ITaxableItemProvider`, `ITaxCalculationMethod`, `ITaxSourcingStrategy`, `ITaxDeterminationProvider`, and more) let Products, Subscriptions, Commerce, Bookings, Services, custom content types, and external tax providers integrate without modifying the Taxation source.

See [Taxation](../modules/taxation) for details.

#### Taxation integrated across Products, Subscriptions, Checkout, and Payments

Taxation is now the single authoritative tax engine for the commerce stack. The integration is native — no product-, subscription-, checkout-, or payment-specific tax calculation remains — and it stays optional through Orchard Core feature dependencies, so every module keeps working when Taxation is disabled.

- **Products** contribute an `ITaxableItemProvider` that turns a product (via the **Product** and **Taxation** parts) into a taxable item — price, product-type–derived kind, tax category, classification, and external code — without ever calculating tax itself.
- **Checkout** determines tax on the amount due now and captures it on the invoice as a tax amount, detailed tax lines, and an immutable snapshot. Exclusive tax is folded into the up-front charge so the payment provider collects the exact taxed total.
- **Recurring subscription billing** re-taxes each renewal with the rules in effect at billing time and stores a fresh per-cycle snapshot, so rate changes and customer address changes apply to future cycles while historical transactions never change.
- **Payments** stay tax-agnostic: providers charge the final, already-taxed transaction amount and never interpret tax rules.
- **Refunds** derive their tax from the original transaction snapshot through a new `ITaxRefundCalculator` (full and proportional refunds allocated across the original tax lines), never from current rules.

#### Subscription and commerce reports

When the **Reports** feature is enabled, the Subscriptions module now contributes admin reports: subscription revenue, a subscriptions dashboard (active, new, and expiring), expiring subscriptions, a new-subscription trend, tax collected, and product performance. A `TaxAmount` column added to the subscription transaction index makes collected tax queryable.

See [Subscriptions](../modules/subscriptions#taxation) and [Products](../modules/products#taxation) for details.
