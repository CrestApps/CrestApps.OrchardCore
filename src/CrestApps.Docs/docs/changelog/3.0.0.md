# Version 3.0.0 Release Notes

This page highlights the changes in the `3.0.0` line.

## Breaking Changes

### Configuration and options

Several site-settings screens no longer **release the tenant shell** when you save them. Instead, the options class that projects those settings is refreshed live through `IOptionsMonitor<TOptions>`, using Orchard Core's options update-notifier (`IOptionsUpdateNotifier.RequestUpdate<TOptions>()` and `services.AddSignalOptionsChangeTokenSource<TOptions>()`, introduced in `OrchardCore` `4.0.0-preview-19118`). Saving these settings now takes effect without restarting the tenant, and the "the tenant will be reloaded" warning has been removed from the affected editors.

The options classes changed this way are: `GeneralAIOptions`, `AIDataSourceOptions`, `McpServerOptions`, `AIMemoryOptions`, `ChatInteractionMemoryOptions`, `UserAvatarOptions`, and the telephony provider options `TelnyxOptions`, `DialpadOptions`, and the shared `TelephonyProviderOptions` aggregate (which the Telnyx, Dialpad, and Asterisk provider modules contribute to).

**Breaking:** `IOptions<TOptions>` resolves a process-lifetime singleton that is computed once and never observes the update signal. Any custom or external code that read one of the options above through `IOptions<TOptions>` will keep serving the value captured at first resolution and no longer pick up a settings change until the process restarts. Such code must switch to `IOptionsMonitor<TOptions>` and read `CurrentValue` (or `IOptionsSnapshot<TOptions>` in a scoped context) to observe live updates.

Settings whose consumers still read them through a singleton `IOptions<TOptions>` — currently the anonymous **AI Visitor Identity**, **Prompt Security**, and **AI Documents interaction** settings, whose readers live in the `CrestApps.Core` packages — continue to release the shell on save until those consumers are migrated to `IOptionsMonitor`.

### AI

- **The MCP Server no longer exposes tools by default.** Previously every registered AI tool was listed and callable by any connected MCP client. Tool exposure is now **opt-in**: nothing is listed or callable until you either select the tools and tool instances on the new **MCP Server** card under **Settings → Artificial Intelligence**, add their names to `McpServerOptions.Tools`, or set `McpServerOptions.ExposeAllTools` to `true`. **Expose all tools** now exposes only *selectable* tools; system tools and hidden tools are never exposed, even when it is enabled. Deployments that relied on the previous "expose everything" behavior must enable **Expose all tools** (or populate the allow-list) to keep exposing their tools. Prompts and resources are unaffected. See [MCP Server](../ai/mcp/server#tool-exposure) for details.
- **A2A host cards now use A2A 1.0 supported interfaces.** Agent cards no longer publish the endpoint through the deprecated top-level `url` field. Clients should read the endpoint from `supportedInterfaces`, and multi-agent mode still points each interface to `/a2a?agent={agentName}`. See [A2A Host](../ai/a2a/host) for details.
- **The deployment purpose is gone; deployments declare model capabilities.** `AIDeploymentPurpose` and `AIDeploymentType` were removed from the framework, along with `AIDeployment.Purpose`, `AIDeployment.Type`, `SupportsPurpose`, `SupportsType`, `CanServeTextCompletion`, and the purpose overloads on `IAIDeploymentManager`. A deployment now says what its model can do (a **capability**), and where it gets used is a **slot** resolved from site settings and the selection on the profile, template, or interaction. `GetByPurposeAsync` / `GetAllByPurposeAsync` become `GetAllBySlotAsync`, and `ResolveOrDefaultAsync(purpose, …)` becomes `ResolveSlotAsync(AIDeploymentSlotNames.X, …)`.
  - The **Purposes** checkbox group is removed from the deployment editor. **Model capabilities** is the single place a deployment describes itself, and at least one is now required. The deployment list shows capabilities in place of purposes.
  - **Stored data needs no migration.** A record that still carries a `Purpose`, `Capability`, or `Type` — in the store, in a recipe, or in `appsettings.json` — is projected onto capabilities every time it is read. The projection is permanent, not a one-time upgrade step.
  - A deployment that had never declared capabilities used to be shown an *empty* capability list when opened, and saving anything unrelated wrote `Features = []`, silently turning it from *unconstrained* to *declares nothing*. It is now offered the defaults, which is how it already behaves at run time.
- **`ChatMode.Realtime` and the separate realtime deployment field are removed.** Whether an AI profile or a chat interaction is a speech-to-speech conversation now follows from its **chat deployment** declaring the `realtime` capability, rather than from a second stored answer that could disagree with the deployment actually selected. This is how chat interactions already worked; AI profiles now match.
  - The chat deployment picker lists text-capable **and** realtime-capable deployments; the utility picker stays text-only.
  - The **Chat mode** selector and the **text-to-speech playback** switch are hidden when the selected chat deployment is realtime, and the **Voice** picker switches to that deployment's realtime voices.
  - A site can no longer force realtime globally through the chat interaction chat mode.
  - **Stored data needs no migration.** A profile that named a `RealtimeDeploymentName` folds it onto `ChatDeploymentName` when read, and its old chat deployment moves to `UtilityDeploymentName` when the profile has not named one — so background work keeps running on the model it always did. A stored `ChatMode` of `"Realtime"` reads as `TextInput` instead of failing the settings load. `ProfileTemplateMetadata.RealtimeDeploymentName` is obsolete and still applies, supplying the chat deployment.

  See [Model Capabilities](../ai/model-capabilities) and [Realtime Voice](../ai/realtime-voice) for details.
- **One chat thread now carries both typed messages and a spoken conversation.** Pointing a profile at a speech-to-speech model used to turn the whole surface voice-only: the message box was hidden and typed messages were rejected. The chat deployment goes back to meaning only "the text model this profile talks to", and a new **Conversation deployment** names the model that carries a spoken conversation. A surface in the **Conversation** chat mode offers a voice toggle *beside* a working message box, and the user decides turn by turn which to use.
  - `ChatModeProfileSettings.ConversationDeploymentName` and `ChatInteraction.ConversationDeploymentName` name that model. Left empty, the realtime slot's own chain applies — the site's default realtime deployment, then the first realtime-capable deployment. Nothing records *how* the conversation is carried: whether the resolved deployment speaks natively or chains speech-to-text, chat, and text-to-speech is read off the deployment itself.
  - The **Chat deployment** picker lists text-capable deployments only, on the profile editor, the AI Profile Template editor, and the chat interaction settings panel. A speech-to-speech model belongs in the **Conversation deployment** picker beside it.
  - The **Chat mode** selector and the **text-to-speech playback** switch no longer disappear when a realtime model is selected, because the deployment no longer decides the mode. **Conversation** is offered whenever either a realtime deployment or the speech-to-text plus text-to-speech cascade can serve it.
  - While a voice session runs, the message box and send give way to the voice settings and the **End Conversation** button takes the width they leave; they come straight back when it ends. Sending a typed message ends the session first, so the two kinds of turn take turns rather than overlapping. The dictation microphone is suppressed while a realtime session carries the conversation, which already owns the microphone.
  - A chat interaction has no chat mode of its own, so naming a conversation deployment on the interaction is itself the opt-in to speaking.
  - Because the chain falls through to the first realtime-capable deployment, a site with *any* such deployment will carry conversations with it even with no site default configured and nothing named on the profile. There is deliberately no per-profile switch back to the cascade: to keep the cascade, have no deployment declare `realtime`; to speak without a speech-to-speech model, use a cascaded realtime deployment.
  - A conversation deployment that is named but cannot run a realtime session is reported rather than quietly replaced, so a typo does not silently move the conversation to a different model.
  - **Stored data needs no migration.** A profile stored in the old shape is folded when the editor reads it: its realtime chat deployment is shown as the **Conversation deployment** with the chat mode set to **Conversation**, and saving the profile persists that shape. Nothing is rewritten behind the user's back. `ProfileTemplateMetadata.RealtimeDeploymentName` is obsolete and still applies, now supplying `ConversationDeploymentName` and putting the generated profile in **Conversation** mode.

  See [Realtime Voice](../ai/realtime-voice) for the full resolution order.

### AI

#### The AI profile and template editors group the model with how it is spoken to

The **Deployments** card on the AI Profile and AI Profile Template editors is now **Deployments &
Interactions**, and the **Chat mode**, **Voice**, and **Enable text-to-speech playback** fields move into it
from the *General* card. They sit directly under the chat deployment and its model parameters, because the
chat deployment is what decides whether they apply at all — with the fields a card away, selecting a
realtime model made three fields vanish off-screen. The card now reads in one pass: chat deployment, its
model parameters, how you converse with it, then the utility deployment and its parameters. Chat
interactions already grouped these in their settings panel and are unchanged.

#### Stored deployments are rewritten to declare their capabilities

A new migration step persists the model capabilities implied by each stored deployment's legacy purpose, so
the stored JSON says what the editors and the deployment list already show, and the dead legacy field stops
being carried around. Deployments that come from configuration are untouched, being read-only and outside
the store.

**A chat or utility deployment is migrated with `textGeneration`, `toolCalling`, and `streaming`.** The
framework's read-time projection maps those two purposes onto `textGeneration` alone, because they are the
only purposes that never named a single capability. In practice a deployment on the legacy purpose was
driven through a chat client that called tools and streamed its response, with no switch to turn either
off — so declaring text generation by itself would migrate a working site into one where tools and streamed
responses are silently disabled. The migration credits all three. Anything a particular model cannot really
do stays one checkbox away in the deployment editor.

Every other purpose still maps onto the one capability that named the same thing: `Embedding` to
`textEmbedding`, `Image` to `imageOutput`, `Vision` to `imageInput`, and so on. A deployment that already
declares `realtime` is left alone: it is a speech-to-speech model stored under the chat purpose, it answers
a text completion with an HTTP 400, and the purpose says nothing about it beyond that it is conversational.

Recipe, configuration, and API imports that still carry a legacy `Purpose`, `Capability`, or `Type` are
credited the same way, so an imported deployment and a migrated one end up declaring the same set.

### Reports

- `ReportFilter` no longer exposes `FromUtc`, `ToUtc`, or `DateRangeKey` as first-class properties, and `ReportContext` no longer exposes `FromUtc` or `ToUtc`. The date range is now contributed and stored like any other filter, so reports that do not need a date selector can omit it. Read and write the period through the new `ReportFilter` helpers (`GetDateRange()` / `SetDateRange()` — for example `context.Filter.GetDateRange()` inside a report), and read or write any filter value with the typed `TryGet<T>(string key, out T value)`, `GetOrDefault<T>(string key)`, and `Set<T>(string key, T value)` extension methods.

### SignalR

The SignalR module has now been migrated into the Orchard Core framework.

If you are currently using `CrestApps.OrchardCore.SignalR`, you should migrate to the `OrchardCore.SignalR` module instead. Similarly, if you are using `CrestApps.OrchardCore.SignalR.Redis`, you can migrate to `OrchardCore.SignalR.Redis`.

For now, the CrestApps SignalR features have been marked as deprecated. However, if you are already using the CrestApps modules, they will automatically enable the corresponding Orchard Core features for you. `HubRouteManager` has been removed; modules now map hubs with `SignalRHubRoutes.GetHubPath<T>()`, and views generate tenant-aware client URLs with `Html.SignalRHubUrl<T>()`.

:::tip
Do not remove the CrestApps SignalR module yet if you want the automatic migration to take place. Once the migration has completed, you can remove the deprecated module. Alternatively, you can remove it immediately and manually enable the SignalR features provided by the Orchard Core framework.
::: 

### Telephony

- The Dialpad module, feature id, provider technical name, namespaces, and public types now use the `Dialpad` casing consistently.

### Resource Module

- The `crestapps-bootstrap-select` style and script have been removed from the `Resource` module. Instead you should use the `bootstrap-select` style and script which are registered by Orchard Core.
- Modules that consume the `bootstrap-select` style and script (Contact Center, Enhanced Roles, Content Transfer, and Omnichannel Management) now declare a dependency on the Orchard Core `OrchardCore.Resources` feature so the `bootstrap-select` resource and the `depends-on`/`at` resource tag helpers resolve correctly.

### Telephony

The following public contracts changed in the Telephony module and its abstractions. External providers and callers that build on these types must update to the new signatures.

- The `CrestApps.OrchardCore.Telephony.Admin` feature has been removed. The provider settings screen and administration menu are now part of `CrestApps.OrchardCore.Telephony`, and provider features register their settings drivers directly. Remove the old feature ID from recipes and deployment plans.
- `TelephonyConstants.Feature.Admin` has been removed. Use `TelephonyConstants.Feature.Area` when declaring a dependency on Telephony.
- The public `TelephonyAdminStartup`, `AsteriskAdminStartup`, and `DialpadAdminStartup` classes have been removed because their registrations now live in each module's primary `Startup` class.
- `ITelephonyAuthenticationProvider.RevokeTokensAsync` now returns `Task<TelephonyResult>` instead of `Task`. Callers receive a typed confirmed-success, definitive-failure, or indeterminate result instead of relying on an exception or assuming success. External implementations of this interface must update their signature.
- `ITelephonyAuthenticationService.DisconnectAsync` now returns `Task<TelephonyResult>` instead of `Task`, for the same reason.
- `RecordingMediaWriteRequest.Content` is now a `System.IO.Stream` instead of a `byte[]`, so recording media streams to storage rather than being buffered in memory. Any code that constructs this request directly must supply a stream.
- `ITelephonyUserAccessor` exposes `ReloadCurrentUserAsync()` and `PersistCurrentUserAsync(Func<IUser, bool> mutate)`. The persist method loads the current user in an isolated unit of work, applies the mutation, and durably commits only that user document, so a serialized token refresh or a disconnect makes its write visible to other requests without flushing unrelated changes staged by the ambient request. Custom implementations of this interface must implement these members.
- The `DialpadSettings` model has been restructured so Production and Sandbox credentials are stored independently under nested `Production` and `Sandbox` environment objects. The former flat credential properties (`ApiToken`, `UserId`, `OutboundCallerId`, `ClientId`, `ClientSecret`, `Scopes`, `WebhookSigningSecret`, `ApiBaseUrl`, `AuthenticationType`) and the obsolete `UseOAuth` property have been removed from the top-level settings. Existing Dialpad credentials are not migrated and must be re-entered on the **Production** or **Sandbox** tab after upgrading. Code that reads these settings must use `DialpadSettings.GetActiveEnvironmentSettings()` or `GetEnvironmentSettings(environment)`.
- Dialpad outbound calls now resolve the connected OAuth user's numeric id through `users/me`, and API-key user ids are serialized as integers as required by Dialpad's call API.

## Change Logs

### Contact Center

Version `3.0.0` introduces the **Contact Center**, a new module family that turns the Omnichannel CRM into a full contact center. It sits between the CRM and the Telephony module: the CRM owns the business work, Telephony executes the media, and the Contact Center orchestrates routing, reservations, dialing, disposition, and supervision. Every capability ships as its own feature, so a tenant enables only what it needs.

Highlights:

- **Orchestration core** — a headless interaction lifecycle with a durable, append-only domain event log and baseline permissions, so every call and work item has a reliable, auditable history.
- **Agents, presence, and availability** — agent profiles with presence states, capacity, and skills, plus durable agent sessions with heartbeat and after-call recovery that work with or without a real-time connection.
- **Queues and reservations** — work queues with prioritized items and concurrency-safe reservations, so an activity is offered to exactly one agent at a time.
- **Policy-based routing** — capacity- and skill-aware assignment with sticky-agent, SLA-aging, business-hours, and overflow strategies that match each interaction to the right agent.
- **Inbound and outbound voice** — a provider-agnostic Voice Contact Center Call Router with inbound entry points, caller qualification, and business-hours decisions, plus an optional soft-phone incoming-call experience. Entry points now support a **Route to** target of either a queue or a **specific agent**: an agent-target entry point offers the dialed number (DID) directly to the named agent as a personal line and falls back to the target queue when that agent is unavailable. Agent profiles also define an **outbound caller id** field intended for presenting an agent's assigned number on outbound calls with providers that support per-call caller id (such as Telnyx); the field is on the model but is not yet surfaced in the agent editor or resolved on the dial path, so outbound calls currently present the tenant default (or a per-call/campaign) caller id.
- **Dialer** — Manual, Preview, Power, and Progressive dialing strategies with scheduled pacing and outbound activity batches routed through Contact Center voice providers.
- **Consolidated, less-confusing features** — the agent capability (**Contact Center Agents**, `…ContactCenter.Agents`) now owns agent profiles, presence, and canonical availability together, and the work-distribution capability (**Contact Center Work Distribution**, `…ContactCenter.Queues`) now owns queues, reservations, and routing together, so there are fewer overlapping toggles to reason about. Capability features use clear, business-oriented names — **Contact Center Outbound Dialer**, **Contact Center Paced Dialing** (Power and Progressive), **Contact Center Inbound Voice**, **Contact Center Call Recording**, and **Contact Center Supervision & Live Dashboard** — with plain-language descriptions. Contact Center capabilities include their own administration screens instead of requiring a separate Administration feature; the server-side **Contact Center Voice** orchestration and the shared **Contact Center Real-Time** hub are enabled automatically as dependencies of the capabilities that use them instead of being standalone toggles; the Contact Center soft-phone projection and the CRM-integrated **Agent Workspace** are integration glue that activate automatically once the capabilities they compose (Contact Center Voice, Contact Center Real-Time, the Telephony soft phone, and — for the workspace — Contact Center Agents) are enabled, rather than separate toggles; each provider's **contact center voice adapter** (Telnyx, Dialpad, Asterisk) likewise activates automatically once that provider module and Contact Center Voice are both enabled, so there is no per-provider toggle to match the provider you already configured; mandatory outbound compliance is part of the base Dialer; and the certified inbound-voice recipes enable Inbound Voice. Enabling Paced Dialing therefore activates a complete Dialer Profiles, compliance, and runtime surface.
- **Outbound compliance** — a mandatory eligibility gate with suppression auditing, retry limits, and calling-window enforcement, so outbound campaigns stay compliant.
- **Real-time agent and supervisor experience** — a shared SignalR hub that broadcasts presence, offers, and queue depth; a CRM-integrated agent workspace; and a live supervisor dashboard with capability-gated monitoring.
- **Docked agent bar** — a persistent bar injected into the admin chrome (the layout footer) on every admin page for signed-in agents, holding its own live Contact Center hub connection outside the soft phone. It keeps work reaching the agent — popping the matched record and driving disposition — even when the soft phone runs in its own window or the browser extension, and it self-manages with the agent's live state. It rides the same integration glue as the Agent Workspace (Contact Center Agents, Real-Time, Voice, and the Telephony soft phone), and is deliberately not injected on the standalone `/softphone` page. See [Agent Desktop & Dashboard](../contact-center/agent-desktop#the-docked-agent-bar).
- **Recording and monitoring** — provider-capability-gated recording orchestration and recording-state events for voice interactions, including an **agent secure pause** that lets an agent suppress recording while a customer reads out sensitive data (card or identity numbers) and resume it afterward. Secure pause is ownership-checked and policy-gated, blocks new supervisor monitoring while a capture is in progress and force-stops any supervisor who was already engaged, and is bounded by a background automatic-resume guard so a pause can never silently outlive its purpose. It is off by default and enabled per tenant in the Recording settings.
- **Hosted secure data capture** — an optional **Contact Center Secure Data Capture** feature that lets an agent send a live customer to a dedicated secure page to enter sensitive data (such as a card number) instead of reading it aloud. The value is tokenized at submission, so the agent, the supervisor, and the recording only ever see a masked representation and a durable token reference; values that must never be retained, such as a card security code, are validated and then discarded with no token or mask kept. Captures are ownership-checked, limited to one in-progress capture per interaction, authorized by a one-time link whose SHA-256 hash is all that is stored and served with no-store/no-referrer headers, bounded by a configurable expiry with a background safety net, and pause recording during the capture as defense in depth with a self-healing recovery pass so recording can never be left paused permanently. The built-in masking sink is registered only in Development and is for development only; outside Development secure capture fails closed until an operator supplies an `ISecureCaptureTokenSink` backed by a PCI-DSS-compliant vault. It is off by default and enabled per tenant in the Secure Data Capture settings.
- **Reports and analytics** — executive, interaction, queue and SLA, agent, transfer, recording, campaign, and subject reports contributed to the admin **Reports** area.
- **Workflows bridge** — an optional Contact Center domain-event activity, so Orchard Core Workflows can react to contact center events.
- **Recipe and workflow schema validation** — the CrestApps Recipes feature now ships JSON schemas for the Contact Center and Omnichannel configuration steps (skills, queue groups, business-hours calendars, queues, agent entitlements, agent state reason codes, entry points, dialer profiles, campaign groups, campaigns, channel endpoints, dispositions, and subject actions) and for the Contact Center workflow activities, so recipe authors and AI tooling get per-step validation and property guidance.
- **Administration** — Contact Center settings screens plus each enabled capability's own administration screens.

See [Contact Center](../contact-center/index.md) for setup and configuration.

### Telephony

- Provider HTTP clients no longer auto-replay unsafe requests. The Dialpad and phone-number-verification resilience pipelines now retry only idempotent safe methods, so a lost response can no longer place a second call or double-spend an OAuth grant, while transient failures on safe reads are still retried.
- Recording media now streams end to end through the tenant file store instead of being buffered in memory, so large recordings no longer pressure the managed heap during ingestion. See **Breaking Changes** for the related `RecordingMediaWriteRequest.Content` change.
- Token revocation and disconnect now report a typed result, so callers can tell confirmed success from a definitive or indeterminate failure. See **Breaking Changes** for the signature changes.
- The **Settings → Communication → Telephony** admin menu entry now displays a phone icon, matching the Orchard Core convention of a per-item navigation icon view.
- The soft phone keypad now uses a country-aware [intl-tel-input](https://intl-tel-input.com/) phone number field with a flag/country selector. A valid national number typed on the keypad is normalized to canonical E.164 before it is dialed, so outbound compliance screening (do-not-call and calling-window checks) can canonicalize the destination instead of rejecting a bare national number. Other non-number entries are dialed exactly as typed rather than being turned into an invalid international number. A new **Default country** soft phone setting controls the initially selected country and defaults to **Automatic**, deriving the country from the current culture and falling back to the browser's locale and then the United States when a region cannot be determined, so a country is always selected. The country selector dropdown renders above the floating widget so it is always visible, and opening it no longer scrolls the page the first time the flag is clicked. Call history and active-call numbers are still formatted for readability by the widget's own display formatter, independently of the input library.
- The soft phone can now dial internal extensions. A **Dial extension** toggle below the number field switches the keypad into extension mode, hides the country selector, accepts a free-form extension, and flags the dial request as an extension (`DialRequest.IsExtension`). Extension calls skip outbound compliance screening (do-not-call and calling-window enforcement) because an internal extension is not consumer outreach and cannot be canonicalized to E.164, while every real phone number still passes the fail-closed screening gate.
- The soft phone widget no longer briefly flashes the keypad before showing the correct state. While the provider and connection status are still resolving, the keypad, the call buttons, and every status message stay hidden until the real state (unavailable, connect, or operating) is known.
- The soft phone no longer stretches to nearly full screen height when a provider that requires a per-user connection (such as Dialpad OAuth) is enabled. The height-reserving keypad body is now collapsed behind the **Connect to provider** panel, so the widget keeps its normal height.
- The **Connect to provider** button now reliably opens the provider's authorization window in a new browser tab and surfaces an inline error inside the connect panel when the authorization URL cannot be resolved or the browser blocks the popup, instead of appearing to do nothing.
- When the default provider uses OAuth 2.0 and the current user is connected, the soft phone header now shows a **Disconnect provider** action so the user can clear that provider connection directly from the widget instead of going through provider-specific settings pages.
- OAuth connect failures are no longer silent. When the Dialpad authorization callback cannot complete the token exchange, the soft phone now shows a safe reason inline in the connect panel, and the server logs the failure category without writing provider-supplied callback text to application logs. Dialpad token exchange rejections still include sanitized provider response details for operator troubleshooting, while client secret decryption failures and missing OAuth state cookies are logged as distinct categories instead of quietly closing the window with the soft phone still showing **Not connected**. See [Dialpad](../telephony/dialpad) for the log messages and their resolutions.
- The soft phone now applies successful dial responses immediately instead of waiting for a later provider state event, so users see the new outbound call as soon as a provider accepts it. Dialpad outbound-call logging now records the selected environment, REST endpoint, and accepted call id without logging phone numbers, making it clearer when Dialpad accepted an initiate-via-ring request but no active Dialpad device answered it.
- The Dialpad webhook now accepts the current signed call-event payload shape, including numeric `call_id` values and nested `contact` and `target` objects, so live state updates no longer fail closed on those deliveries and fall back to REST polling only.
- Direct inbound Dialpad calls to an OAuth-connected user's own Dialpad line now resolve the correct Orchard soft-phone user from stored Dialpad account metadata, so a new inbound webhook can notify the right connected user even when no prior interaction record exists for that call id.
- The soft phone now refreshes active provider state while a call is active, so REST-only providers such as Dialpad can move the UI out of `Connecting` even when no real-time event arrives. Dialpad active-call display now lets the phone-number input library own country-code rendering, avoiding a duplicate `+1` in the disabled call display.
- The standalone `/softphone` page no longer shows its incoming-call modal at the same time as the notification of a desktop app that embeds it (such as the CrestApps Soft Phone for Windows). The page sends the ringing call, with its queue and matched records, to the app through the WebView2 message channel, and hides the modal only when the app confirms that its notification for that call is on screen. If the app does not confirm within 2 seconds, or its notification closes without an answer, the modal shows as before. Answer, Decline, and Voicemail in the app's notification run in the page, through the same paths as the modal buttons. A normal browser tab and the browser extension are not affected. See [Notifications from a desktop app](../telephony/index.md#notifications-from-a-desktop-app).

### Providers

#### Asterisk

Adds the new **Asterisk** provider (`CrestApps.OrchardCore.Asterisk`), which integrates the Asterisk telephony platform with the Telephony soft phone through the Asterisk REST Interface (ARI).

Highlights:

- A per-tenant Asterisk provider with its own settings, plus an optional host-configured **Default Asterisk** provider.
- The host-configured **Default Asterisk** provider is now available to every tenant where the module is enabled, not only the default shell. Each tenant resolves the shared connection under a unique per-tenant ARI application name (`<ApplicationName>-<ShellName>`) so their Stasis event streams stay isolated. Existing default-shell deployments that rely on inbound routing must update their Asterisk dialplan to target `Stasis(<ApplicationName>-Default)` for the default shell.
- The `CrestApps.OrchardCore.Cms.Web` host launch profile now injects the **Default Asterisk** environment variables, so running the CMS host directly configures the provider by default without the full Aspire host.
- Soft-phone calls placed through the host-configured **Default Asterisk** provider now update live over SignalR (connected, held, and disconnected states) without a manual page refresh. The interaction store canonicalizes the provider identity so calls recorded under the **Default Asterisk** alias correlate with the real-time voice events that the listener tags with the canonical `Asterisk` provider name.
- Contact Center voice and media features that adapt Asterisk call execution, real-time call events, and bidirectional RTP media to Contact Center orchestration.
- A local Aspire container and an **Asterisk Web** sample for end-to-end routing and agent-offer testing during development.

#### Dialpad

- Dialpad settings now support the **Production** and **Sandbox** environments independently. Each environment has its own tab with its own authentication type, API key, user id, outbound caller id, OAuth client id/secret/scopes, and webhook signing secret, and a new **Active environment** selector chooses which credential set the provider connects with. A tenant can hold production and sandbox credentials side by side and switch between them without re-entering secrets. Only the active environment is validated on save.
- Each Dialpad environment now exposes an optional **Host** setting so a tenant can target an alternate Dialpad host (for example an alternate sandbox or beta host). It defaults to `dialpad.com` for production and `sandbox.dialpad.com` for sandbox, and drives both the OAuth 2.0 endpoints and the default REST API base address.
- The Dialpad OAuth authorization request no longer force-appends the `offline_access` scope. Dialpad requires every scope to be approved per OAuth app, so forcing `offline_access` made the connect step fail with `Invalid scopes: offline_access` for apps that were not granted it. Only the scopes configured on the environment are now requested; add `offline_access` to the **OAuth scopes** to receive a refresh token when your Dialpad app has that scope approved.
- The Dialpad documentation now includes the inbound call-event webhook registration flow, including the tenant callback URL, shared signing secret, `webhooks` API request, and `subscriptions/call` request for alternate sandbox hosts such as `dialpadbeta.com`.
- The active Dialpad environment now requires webhook registration and the settings UI can register the company-level Dialpad webhook automatically. Administrators choose **Admin account** or **Admin API key** as the webhook registration method, then click **Register webhook**. For Admin account, that same button starts the Dialpad sign-in flow and the server completes registration server-side when sign-in returns; for Admin API key, it uses the saved encrypted API key. The server generates the signing secret and commits it (encrypted) first, then creates the webhook (`POST /api/v2/webhooks`) and the call-event subscription (`POST /api/v2/subscriptions/call`) from a deferred task that runs after the secret is committed, so Dialpad can read the committed secret when it verifies the webhook. The secret is never shown in the browser, and the settings page polls the registration status and refreshes when it completes. The active environment shows a danger alert until registration is complete, a success alert when the saved secret and Dialpad ids are present, and a confirmed **Disconnect webhook** action that deletes the saved Dialpad subscription/webhook before clearing local registration state. Dialpad call-event delivery is treated as required configuration for synchronized soft-phone state and inbound routing; REST call-state polling remains only a fallback.
- The Dialpad webhook callback endpoint (`/api/dialpad/webhook/call`) now ships with the base **Dialpad** feature instead of only its contact center voice adapter, so signed Dialpad call-event deliveries update soft-phone state even when Contact Center Voice is not enabled. When Contact Center Voice is enabled, the same deliveries still flow into Contact Center routing and projection.

#### Telnyx

Adds the new **Telnyx** provider (`CrestApps.OrchardCore.Telnyx`), which integrates the Telnyx voice platform with the Telephony soft phone and the Contact Center. Unlike a click-to-call provider, Telnyx exposes a SIP-over-WebSocket registrar and a server-side Call Control API, so the browser soft phone carries the call audio itself (WebRTC) and the Contact Center can bridge live calls to agents server-side (`ServerSideAcd`) — the basis for true power dialing.

Highlights:

- A single-API-key Telnyx provider that places and controls calls through the Telnyx Call Control (Voice API), advertising dialing, hang up, hold, resume, mute, blind and attended transfer, merge, DTMF, and inbound calls.
- A browser **WebRTC soft phone**: the server mints a short-lived Telnyx telephony credential per session and the browser logs in to Telnyx's WebRTC gateway through the **Telnyx WebRTC SDK** (`@telnyx/webrtc`, the vendored `telnyx-webrtc` media adapter), which owns the peer connection, media, and SDP/codec negotiation end to end — replacing the earlier shared SIP.js adapter and its browser-side SDP workarounds. Outbound calls use a **server-side originate-and-bridge**: the platform rings the agent's registered browser leg (which the soft phone auto-answers) and bridges it to the destination, so the agent hears the call in the browser. Credentials are per-user capped, expire on their own, and are revoked at Telnyx on sign-out.
- **Ed25519-signed webhooks** at `/api/telnyx/webhook/call`. Telnyx signs each delivery over `{timestamp}|{body}` and this module verifies it against the account public key configured in settings (no shared secret is generated); the endpoint rejects unsigned, stale, or oversized deliveries and processes accepted events through the durable provider webhook inbox.
- A **Telnyx contact center voice adapter** that advertises the `ServerSideAcd` delivery model and supports dialer dialing, agent connect (originate the agent's browser SIP leg and bridge it to the caller), call transfer, and — with the **Contact Center Call Recording** feature — recording. Recording is driven by Contact Center governance (`record_start` / `record_pause` / `record_resume` / `record_stop`); the `call.recording.saved` webhook is ingested into the encrypted media store and the Telnyx-hosted copy is deleted afterward, so no plaintext recording lingers off-platform. It is integration glue rather than a separate feature: it activates automatically whenever the **Telnyx** module and **Contact Center Voice** are both enabled.
- **Bidirectional media streaming** over the `api/telnyx/media/stream` WebSocket (G.711 mu-law) — the Telnyx equivalent of Asterisk ARI External Media — giving the Contact Center a live server-side media leg.
- **Extension dialing** (`CrestApps.OrchardCore.Telnyx` advertises `ExtensionDial | ExtensionConference`): call another on-platform user by extension, or add an extension into a call as a conference participant, by originating and bridging two Telnyx SIP-over-WebSocket registrations. See [Extension Dialing](../telephony/extension-dialing).
- A new **Telnyx AI Voice Agent** feature (`CrestApps.OrchardCore.Telnyx.AiVoice`): the Phone-channel omnichannel processor dials a contact over Telnyx and runs an automated conversation using Telnyx text-to-speech and real-time transcription driven by an AI chat profile, then settles the omnichannel activity with a summary and disposition — the voice counterpart to automated SMS.
- A new **Telnyx SMS** feature (`CrestApps.OrchardCore.Telnyx.Sms`): a Telnyx SMS/MMS provider (configured from the `OrchardCore_Sms_Telnyx` appsettings section or the SMS settings screen) with an Ed25519-signed messaging webhook at `/api/telnyx/webhook/sms` for inbound `message.received` events and `message.finalized` delivery receipts, so Telnyx numbers can send and receive text through the SMS Portal and SMS Automation.
- See [Telnyx](../telephony/telnyx) for setup and troubleshooting.

### Omnichannel Messaging Workspace

Version `3.0.0` adds the **Omnichannel Messaging Workspace** (`CrestApps.OrchardCore.Omnichannel.Messaging`, category **Contact Center**), a **human-operated**, channel-agnostic messaging inbox: one customer list and one conversation view for every non-voice channel, with a tab per channel above each customer's conversation and a live unread badge on each tab. Channels are separate features; the first is the **SMS Messaging Channel** (`CrestApps.OrchardCore.Omnichannel.Messaging.Sms`), and email, WhatsApp, Messenger and others can be added by implementing `IMessagingChannel`. The workspace provides a shared team inbox, threaded conversations (one per customer address on each channel), a composer with canned-response templates, live contact search, claim/assign/transfer, close/spam/reopen, and 1:1 broadcasts processed by a durable background task, with real-time inbound and delivery-receipt updates over its own SignalR hub. It is the human counterpart to the AI-driven [SMS Automation](../omnichannel/sms) and shares the same Omnichannel message store, so an AI conversation can hand off to a human on the same number.

It deliberately reuses existing building blocks: each address it sends from (an SMS number, for the SMS channel) is an **Omnichannel channel endpoint** that carries its provider and inbound routing (target agent/queue, distribution mode, auto-reply), so the earlier separate `SmsNumberRoute` concept was retired. Operators are Contact Center **agent profiles** resolved through a dependency-only **Agent Services** feature (a bare profile is provisioned automatically on first access, with no Contact Center administration required), and SMS sending goes through a per-number `ISmsDispatcher` so different numbers can send through different carriers. The workspace depends only on Omnichannel Channel Endpoints, Contact Center Agent Services and `OrchardCore.SignalR`; the SMS channel adds `OrchardCore.Sms`. See [Messaging Workspace](../omnichannel/messaging-workspace).

#### Contact index migration no longer stalls on PostgreSQL

The `OmnichannelContactsMigrations` upgrade steps rebuild the default contact index by re-issuing `CREATE TABLE`, `ADD COLUMN`, and `CREATE INDEX` statements and swallowing the "already exists" errors with `try`/`catch`. Orchard Core runs every migration step through a single `SchemaBuilder` that shares the migration's database transaction. On PostgreSQL, the first failing DDL statement aborts that whole transaction, so even though the .NET exception is caught, the shared transaction stays poisoned and the final version bump can never commit — leaving the migration permanently stuck on an old version (most often version 6). Each idempotent schema change now runs behind its own savepoint inside the migration transaction, so an "already exists" failure only rolls back that one statement and can no longer poison the migration transaction. The isolation deliberately stays inside that transaction: a change moved onto a second connection waits for locks the migration transaction already holds (on SQLite, the database's only write lock), times out, and is skipped as if it already existed. MySQL, which commits DDL implicitly and so discards savepoints, runs each change on its own connection instead. The migration now advances correctly on PostgreSQL, SQL Server, MySQL, and SQLite.

-----

#### Activity batch index migration no longer loses the `CreatedUtc` column

The activity batches admin screen orders batches by a `CreatedUtc` column added to `OmnichannelActivityBatchIndex` by an upgrade step. That step ran through the feature's shared migration `SchemaBuilder`, so when any sibling migration in the same feature threw, Orchard Core cancelled the shared session and rolled back the column addition together with the migration's version record. On databases with transactional DDL (PostgreSQL and SQL Server), the tenant was left with the migration record still pointing at the old version and the physical `CreatedUtc` column missing, so the screen failed with `Invalid column name 'CreatedUtc'`. The column additions now run as isolated, idempotent schema changes, shared with the contact index migration through the new `OmnichannelIndexMigration` base class, so a change that cannot be applied no longer takes its sibling steps down with it. A follow-up repair step now also verifies the `Source` and `CreatedUtc` columns and adds only the ones that are missing, so tenants whose migration record was already advanced past the original upgrade steps while the physical columns were rolled back are healed on the next start.

### DNC Registry

#### Local registry migration no longer blocks other feature migrations

The **Local** DNC registry repair migration checked whether its index tables already existed by comparing the database schema against an **unprefixed** table name. On installations that use a table prefix (for example multi-tenant deployments), the check always reported the tables as missing, so the migration tried to recreate them and threw a duplicate-object error. Because Orchard Core runs every feature's automatic migration on a shared session, that uncaught error cancelled the session and silently rolled back every other feature's migration in the same run — most visibly leaving the Omnichannel contact migration stuck on an old version. The existence check now resolves the physical (prefixed) table name, and the repair step no longer rethrows if the table is already present, so a single feature can no longer stall the rest of the migration batch.

### AI

- **AI Usage Analytics reports automated voice calls, and breaks completions down further.** Every automated AI voice call — realtime or turn-based — now leaves one voice session summary when the assistant's part of it ends, and the **AI Usage Analytics** page gains a **Voice** section built from them: calls, AI, caller and silence minutes, average call, handoff rate and barge-ins per call, grouped by deployment and model, AI profile, campaign, channel, engine or day. Talk time is measured from the call audio rather than the transcript. The completion table can now be grouped by model, deployment, AI profile or connection, and the whole page filtered to one AI profile. The review that concludes a call now runs on the call's chat session, so its tokens are counted with the call. Realtime token usage appears once CrestApps.Core reports it. See [AI Usage Analytics](../ai/usage-analytics).
- **A tool instance can vector-search an existing AI data source.** With the **AI Data Sources** feature enabled, the **AI Tool Instances** feature registers a **Data source search (vector)** source (`data-source-search`). Each instance binds one existing AI data source plus its own retrieval parameters — retrieval mode (matching chunks, or the full source documents they belong to), strictness, retrieved document count, and an OData filter — and is exposed to the model as its own callable function, so several knowledge bases can sit side by side under their own names. The model supplies only the search phrases, embedded with the same embedding deployment the knowledge base index was built with; results carry `[doc:N]` citations. Unlike a data source attached to a profile, retrieval runs when the model asks for it instead of on every turn. Importable through the `AIToolInstances` recipe step via `DataSourceSearchToolSettings`. See [AI Tool Instances](../ai/tool-instances#the-data-source-search-source).
- **Realtime TURN credentials can be minted by Cloudflare, per tenant.** Realtime voice can now source its TURN servers from Cloudflare Realtime, which issues short-lived credentials through an API instead of exposing a shared secret that could be signed locally. Configure the TURN Token ID and API token under `OrchardCore:CrestApps:AI:RealtimeTransport:Cloudflare`. Like the rest of the realtime transport section, it is read through `IShellConfiguration`, so each tenant can mint credentials from its own Cloudflare account rather than sharing the host's. A tenant that configures no token keeps using the `StunUrls` and `TurnUrls` it already had, and that same path also covers a Cloudflare outage. See [Realtime Voice](../ai/realtime-voice#cloudflare-realtime-turn).
- **Cascaded realtime deployments.** Realtime voice no longer requires a provider that ships a speech-to-speech model. Create a deployment under the new **Cascaded Realtime** provider and pick the three deployments it chains — one that transcribes, one that generates the reply, and one that speaks it. The three may come from different providers, and the profile, chat UI, transcripts, and turn persistence all behave exactly as they do with a native realtime model. Tools, data sources, and the profile's instructions are applied to the chat deployment, so a voice profile keeps everything a text profile has. The deployment declares the **Realtime** feature itself, and its **Voice** picker lists the text-to-speech deployment's voices. Importable through the `aideployment` recipe step via `CascadedRealtimeMetadata`. See [Realtime Voice](../ai/realtime-voice#cascaded-realtime-when-no-provider-speaks).
- **The anonymous visitor cookie can be configured to survive inside a frame on another site.** The **Visitor Identity** card under **Settings → Artificial Intelligence** gains **Allow cross-site embedding** and **Partition the cookie per embedding site**, alongside the cookie name and lifetime it already had. The visitor cookie is written `SameSite=Lax` by default, which a browser refuses in a third-party context, so a chat embedded in a frame on a customer's site looked like a brand new visitor on every request: the conversation did not survive a page load, and the visitor rate-limit partition never accumulated. Turning cross-site embedding on writes the cookie `SameSite=None; Secure` instead, which is the only combination a browser keeps in a frame; a request that did not arrive over HTTPS keeps the `SameSite=Lax` cookie rather than losing it altogether. Partitioning is on by default and keeps that cookie apart from the first-party one of the same name. Cross-site embedding is off by default, so nothing changes for a chat served from its own site. Importable through the `Settings` recipe step via `AIVisitorIdentityOptions`. See [Chat](../ai/chat#anonymous-visitor-identity).
- **An anonymous visitor sees their own chat history.** `DefaultAIChatSessionManager.PageAsync` answered an empty list for anyone who was not signed in, so a chat serving anonymous visitors — an embedded widget, most of all — showed them no history at all, even though `FindAsync` would happily open any one of those sessions by id. It now lists the sessions the caller's visitor identity owns, the same `ClientId` the session was created with, and still answers nothing when no visitor identity has been issued. A signed-in user is unaffected.

#### Opt-in tool exposure for the MCP server

The **MCP Server** feature now exposes tools on an opt-in basis (see [Breaking Changes](#ai)). The server exposes only the AI tools and configured tool instances you explicitly allow, and the allow-list is enforced by both the list and the call handlers, so a tool that is not exposed can neither be discovered nor invoked.

Highlights:

- A new **MCP Server** card on the **Settings → Artificial Intelligence** page configures the authentication mode and selects which tools and tool instances are exposed, using the same selector as the AI Profile editor.

It exposes only *selectable* tools, so system and hidden tools are never listed or callable even in this mode. Enabling it hides the **Tools** and **Tool instances** selectors, because the selection no longer applies.

- The **AI Tool Instances** feature now registers the built-in documentation search sources (sitemap crawl, prebuilt search index, and Algolia DocSearch), so a public documentation site can be declared as a tool instance and exposed to MCP clients on demand. The Algolia search-only API key is now encrypted with ASP.NET Core data protection at rest.

See [MCP Server](../ai/mcp/server#tool-exposure) and [AI Tool Instances](../ai/tool-instances#the-documentation-search-sources) for details.

#### Tiered anonymous chat rate limits

The **Prompt Security** section under **Settings → Artificial Intelligence** now exposes the tiered anonymous rate limits added in `CrestApps.Core`:

- **Anonymous message rate-limit tiers** and **Anonymous session-start rate-limit tiers** accept one tier per line as `limit, window` (the window is a .NET `TimeSpan`, for example `00:00:30` or `1.00:00:00` for a day). A request is throttled when it would exceed any tier, so a short burst tier can sit alongside longer sustained tiers. Both default to the same tiers as `CrestApps.Core`, and clearing a field falls back to the matching single-window limit.
- Tiers apply to **anonymous** callers only. **Maximum messages per window** and **Message rate-limit window** now govern authenticated callers, and anonymous callers only when no message tiers are configured; **Maximum anonymous sessions per window** and **Anonymous session window** are likewise the fallback for the session-start tiers.
- The default for **Maximum anonymous sessions per window** changed from `5` to `20` to match `CrestApps.Core`. Sites that already saved this setting keep their stored value.
- Both tier lists can be set from a recipe through the `PromptSecurityOptions` site settings step.
- Individual AI profiles (and profile-source AI profile templates) can override both tier lists from their **Prompt Security** tab. A blank field inherits the site tiers; entering tiers replaces them for that profile; and a **Do not use tiered ... limits for this profile** checkbox opts the profile out of tiered limits entirely so it falls back to its own single-window values.
- The message shown when a visitor is throttled while starting a new chat no longer discloses the configured limit, the current count, or the retry delay, and is now localizable. Those values would let an abuser tune their traffic to sit just under the throttle.
- A throttled session start is now signalled to the client as a dedicated rejection (`ReceiveSessionStartRejected`) rather than a generic error, so the embedded chat widget shows the message instead of treating it as recoverable, clearing the visitor's state, and silently retrying. This also covers the OrchardCore-specific TemplatePrompt path, which replaces the framework's generated-prompt handler outright.
- The chat UI no longer leaves a throttled visitor waiting on a hung request. The chat scripts were updated to `@crestapps/ai-chat-ui` `2.0.0-preview.154`, which rejects the pending new-session request, clears the typing indicator, and shows the message instead of failing silently. The `AIChatApp`, `AIChatWidgetApp`, `ChatInteractionApp`, `document-drop-zone`, and `technical-name-generator` resources moved to version `2.0.0`, so cached copies of the old scripts are replaced.
- Documented that the tier lists take precedence over the single-window settings, so lowering **Maximum anonymous sessions per window** has no effect while the default tiers are still in place.

See [Prompt Security](../ai/chat#prompt-security) for details.
