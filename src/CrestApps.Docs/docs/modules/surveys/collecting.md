## Collectors

A collector (`SurveyCollector`) is a way in: a **web link**, a **kiosk**, an **invitation** list, or a kind of a consumer's own. Each has its own token (the public URL `/s/{token}`), opening and closing times, most responses, password (stored as a hash), hidden variable values and culture. The first publish creates the survey's default web link. A collector's QR code is served as SVG at `admin/surveys/collectors/{id}/qr.svg`.

A **kiosk** shows the ending for a few seconds, then returns to the start for the next person; it clears the resume cookie (before an ending that redirects, too) and never resumes a response. Every kiosk response is a guest response that no per-person limit counts, so the next person can't resume it; give a kiosk's survey an audience that lets guests answer. A kiosk refuses to start while the visitor is signed in, and says to sign out: someone who opens the kiosk address at home, signed in, would otherwise answer as an uncounted guest and bypass the survey's limits. Keep the kiosk device signed out. A kiosk response can't be reviewed or reopened.

## Respondent routes

A GET never starts a response or uses up an invitation, so link previews (chat apps) and mail scanners that follow a link create nothing. Pages that start something post a form: the page submits it at once with script, and shows a button without script.

| Route | Does |
| --- | --- |
| `GET /s/{token}` | The start page (password or CAPTCHA when needed). When the survey skips it, or the address asks for it with `?autostart=1` on a navigation from a page of the same site (the Start button of an embedded survey, told by the browser's `Sec-Fetch-Site: same-origin`), the page posts its start form at once. `?autostart=1` from another site, an e-mail, a bookmark or a typed address shows the start page, its introduction and its Start button |
| `POST /s/{token}/start` | Starts a response, or resumes the browser's response in progress |
| `GET`/`POST /s/r/{responseId}` | The current page; posts Next, Back or Finish |
| `POST /s/r/{responseId}/save` | Autosave without checks |
| `POST /s/r/{responseId}/evaluate` | Visibility and piping for answers not yet posted |
| `POST /s/r/{responseId}/check/{questionId}` | Immediate feedback |
| `GET /s/r/{responseId}/done` | The ending |
| `GET /s/r/{responseId}/review` | The review, as the review settings allow. Hidden questions (values from the link, a consumer or a workflow) are left out; the admin Details page shows them |
| `POST /s/r/{responseId}/reopen` | Reopens a finished response when changes are allowed |
| `GET /s/i/{token}` | A personal invitation link: marks the invitation opened and shows a page that posts the start |
| `POST /s/i/{token}` | Starts the invited person's response, or resumes it from any browser |
| `GET /s/i/{token}/unsubscribe` | The unsubscribe page of an invitation e-mail; changes nothing |
| `POST /s/i/{token}/unsubscribe` | Unsubscribes the invitation's address from survey invitations (no form token, for one-click unsubscribe) |
| `GET /s/{token}/results` | Totals of all responses, when the survey shows them |
| `GET /s/r/{responseId}/results` | The same totals for the respondent of that response, for a survey reached without a public link (a course item's survey) |
| `GET /surveys/my` | The signed-in user's own responses |

Posts check the antiforgery token. When the Orchard Core **Rate Limits** feature is on, every route in the table is in the rate-limit group `Surveys.Respond`: **120 requests a minute per IP address** (a fixed one-minute window, `RespondRateLimitsStartup.RequestsPerMinute`). Admin **Preview** works the same way: opening its link shows a page that posts the start of the test response.

Every response under `/s` carries `Referrer-Policy: no-referrer`, so the tokens in collector and invitation links never reach another site in a `Referer` header. Every response under `/s`, and `/surveys/my`, also carries `Cache-Control: no-store`, because the ending, the review and the totals show answers, piped texts and scores: no browser cache, back-forward cache or shared proxy keeps them for the next person at a kiosk or a shared computer. Every response under `/s`, and `/surveys/my`, carries `X-Robots-Tag: noindex, nofollow` too, and the links of `SurveyPart` and the `[survey]` shortcode carry `rel="nofollow"`, so search engines don't index respondent pages.

:::warning[Tokens in addresses]
Collector tokens (`/s/{token}`), personal invitation tokens (`/s/i/{token}` and `/s/i/{token}/unsubscribe`) and response ids (`/s/r/{responseId}`) are in the URL path, so they are written to web server and proxy access logs and to OpenTelemetry's `url.path` attribute, next to the client IP address. A response id alone opens nothing (a response opens only for its signed-in user or the browser holding its resume cookie), but an invitation token is the invitee's key, and on an anonymous survey a log line links a response id to an IP address. Surveys doesn't wrap the host's request logging or ASP.NET Core instrumentation, so treat these logs as personal data: keep them short, limit who can read them, and filter or redact `/s/` paths in your log pipeline or OpenTelemetry collector (for example a collector processor that replaces the path segment after `/s/i/` and `/s/r/`).
:::

### Resume tokens and cookies

A response is owned by the signed-in user who started it, or by whoever holds its resume token. A response started by a signed-in user on an identified survey has no resume token. The token is `{responseId}.{secret}` with a 256-bit secret, and only its SHA-256 hash is stored (the start lock key holds the hash too, never the token).

The browser holds the token in an HttpOnly, SameSite Lax cookie `sr_{surveyId}` on the tenant's `/s` path (`{PathBase}/s`), for 30 days. When the ending of the response shows, the cookie keeps (and renews) its 30 days while the guest may still come back to the response: the survey allows changes after finishing (`Navigation.AllowEditAfterSubmit`) and is open, or the review shown later (`Review.LaterWhileOpen` while the survey is open, `Review.AfterClose` once it closed) includes the respondent's answers. Otherwise it is kept one more day, for the review shown right after the ending, so cookies don't pile up; a reopen gives it its 30 days back. A guest's only proof that a response is theirs is this cookie, so once it ends the response can't be reviewed or reopened from that browser. Writing a resume cookie also removes the browser's resume cookies of an older generation, so they don't pile up. Each resume cookie is bound to a generation cookie `sr_g_{hash}` on the tenant's root path (`{PathBase}`, or `/`), where `{hash}` is the first eight hexadecimal digits of the SHA-256 of the tenant name (`SurveyResumeCookies.GenerationCookieName`): a tenant without a prefix writes it on `/`, which requests to prefixed tenants on the same host carry too, so each tenant has its own. A page outside `/s` that writes a resume cookie (a course item, admin Preview) joins the browser's current generation and leaves its other open responses alone. Signing in or out (Orchard Core `ILoginFormEvent` and `ILogoutFormEvent`) writes a new generation, so every resume cookie written before stops counting and is removed on the next respondent page. On a shared computer, the next person never resumes the previous person's response. Code that starts a response for someone (a course, for example) calls `SurveyResumeCookies.Write(surveyId, token)` from `CrestApps.OrchardCore.Surveys.Core`, and never puts the token in a URL.

There are no resume links: no address carries a resume token, so a response can't be handed to another browser by sharing a link, and a guest never lands in someone else's response with their answers filled in. A response resumes only for its signed-in user, or in the browser holding its resume cookie.

A personal invitation link is the invitee's key: on an identified survey, posting it resumes the invitation's response in progress from any browser (with a new resume token there), so a scanner that opened the link first does not lock the invitee out. A response that belongs to a user account resumes only for that user. An anonymous response does not name its invitation, so it resumes only in the browser that started it.

## Access rules

`ISurveyAccessRule`s decide whether a response may start, run again when it completes (under a lock, so two tabs cannot pass a limit), and are asked through `CheckResumeAsync` before a response in progress is handed back to a returning respondent (the built-in rules allow it; a rule about who the respondent is, such as the Learning enrollment rule, checks again). The first refusal wins.

| Order | Rule | Checks |
| --- | --- | --- |
| 100 | `Status` | The survey is open |
| 200 | `AvailabilityWindow` | The survey's and the collector's opening and closing times, and accommodations' windows |
| 300 | `WeeklySchedule` | The days and hours of the weekly schedule, in the site time zone |
| 400 | `Audience` | Anyone, signed-in users with Respond to surveys, members of user audiences, or invited people only |
| 500 | `Password` | The collector's password |
| 600 | `Captcha` | A CAPTCHA for respondents who are not signed in and not invited (reCAPTCHA feature). Only an invitation sent to someone (a user, party, e-mail address or phone number) skips it; a bare personal link made for no one asks for it on its start page. It fails closed: with the reCAPTCHA feature off, a survey that requires a CAPTCHA refuses such respondents with a message, and the access page refuses to turn the requirement on |
| 700 | `Invitation` | One response per invitation |
| 800 | `RespondentLimits` | Total, per day, per week (from the site's first day of the week), per month, and the wait between responses; accommodations add attempts |
| 900 | `MaxResponses` | The survey's and the collector's most completed responses |
| 1000 | `Quota` | Full quotas (on completion) |

Limits count completed or started responses per respondent, recognized by the user account, the invitation, a browser cookie (weak: it can be cleared) or not at all. Test responses (preview) skip limits and windows.

## Anonymity

**Identified** responses store the user and party (and the IP address when the survey collects it). **Anonymous** responses store none of these, no invitation, and nothing else the caller sends that could name the person:

- No properties (`StartResponseRequest.Properties` are dropped), except the link back that the ending shows: `SurveyResponseProperties.ReturnText`, and the local path of `SurveyResponseProperties.ReturnUrl` without its query string or fragment. They name a page (a course item), not a person.
- A context keeps its id only when its kind is registered as shared (`AddSurveyContextKind(kind, name, identifiesRespondent: false)`, such as a Learning course); any other context keeps its kind with the id `anonymous`. Hidden variables are the author's choice and are kept, so don't collect identifying values in them on an anonymous survey.
- Limits use an HMAC of the respondent under the survey's **anonymity secret**, in a participation record (`SurveyParticipation`, per day) that holds no response id, no time finer than the day (the cooldown of an anonymous survey counts from the end of the day of the last completion) and only a hash of the context.

The anonymity secret is kept in the survey document only as ASP.NET Data Protection ciphertext (purpose `CrestApps.OrchardCore.Surveys.AnonymitySecret.v1`), whose keys live outside the database, so reading the database is not enough to recompute a respondent's key. There is no fallback to the survey id. `SurveyAnonymitySecrets` reveals it, makes respondent keys and signs invitation links. The `SurveyAnonymityMigrations` migration asks for the `Surveys.AnonymityUpgrade` resumable step, which runs in the background a page at a time, protects the secrets of existing surveys in place (keeping their values, so limits and links keep working) and clears the exact times of existing anonymous participation records. If the Data Protection keys are missing (a key ring that isn't persisted, web-farm nodes that don't share keys, a database restored on another host), the secret is never replaced on its own: the survey fails closed (starting, completing and sending invitations stop, and the error is logged) until the keys are restored. When they can't be, the survey's **Access and settings** page shows the problem and a **Reset the anonymity secret** button (Manage the survey, with a confirmation). Resetting starts the limits over, re-issues every invitation's stored token hash so sending the invitations again sends working links, and leaves links sent before unusable. On a web farm whose servers don't share their Data Protection keys, a reset only moves the failure: the new secret is protected with the resetting server's keys, so the other servers can't read it. Share the key ring first (for example the Orchard Core Azure Data Protection feature, or Redis). While the secret can't be read, respondent pages and personal invitation links show a "not available right now" page (503), the Surveys API answers 503 with a problem result, course quizzes and surveys go back with a message, admin invitation sends show the reason instead of an error page, and the hourly reminder task logs and skips that list and goes on with the others. The token hash is also re-issued whenever an invitation is sent or reminded again.

Anonymity can't change once a survey has responses (test responses aside): the access editor refuses the change, so responses given under one promise are never shown under the other. Delete the responses or copy the survey to change it. Outputs of anonymous surveys honor the minimum group size, never below the site's floor ([Results and reports](./results-and-reports.md#anonymous-surveys)).

## Invitations

With **Survey Invitations** on, an invitation collector invites users of the site (by user name), a user audience, a cohort, or e-mail addresses. One **Invite** reads **at most 5,000 recipients** (the audience or cohort members past that number, and the addresses past it, are not invited; invite the rest in another batch). Each invitation (`SurveyInvitation`) has a personal link `/s/i/{token}`; the token is an HMAC of the invitation id under the survey's secret, and only its hash is stored. Users get a notification (type `SurveyInvitation`), which follows the user's own notification preferences; other people get an e-mail rendered from the collector's Liquid template. The template runs in a sandbox: Fluid's own filters and only `Survey.Name`, `Survey.Title`, `Invitation.DisplayName`, `Invitation.Email`, `Invitation.ExpiresUtc`, `Link` and `UnsubscribeLink`, with a step limit; the site's Liquid objects and filters (users, content, queries) are not available. An e-mail invitation is for exactly one address: a list or a malformed address is refused by the invitation service, whoever calls it. The site sends at most **Settings > Surveys > Invitation e-mails a day** (2,000 by default) invitation and reminder e-mails a day, counted from midnight in the site's time zone. Each first send and each reminder is one e-mail (only an invitation's last reminder time is kept, so two manual resends of one invitation in a day count once). User invitations go to the notification inbox and don't count. An invitation over the limit stays **Pending** with a hold mark (`SurveyInvitationHold`, indexed as `SurveyInvitationIndex.Held`), and the hourly reminder task reads held invitations by that mark (however many invitations were created and never sent) and sends them once the limit allows, before any reminders; invitations created without sending are never sent by the task. On a site upgraded from a version without the hold column, the `Surveys.InvitationHolds` resumable step marks the invitations held before: it reads only pending invitations, 1,000 a minute, and saves only the held ones, so they are marked within its first runs. A reminder over the limit simply stays due. The limit is exact, also on a web farm and when several sends run at once. Before its first e-mail of a day, a send takes the tenant's lock for that day of the site (`SurveyInvitationEmailLimit`, through Orchard Core's `IDistributedLock`, key `Surveys:InvitationEmails:{yyyy-MM-dd}`) and keeps it until its changes are saved, so the next send counts every e-mail sent before it. A send is everything one scope sends (one request, such as one **Invite** of up to 5,000 recipients or one **Send**, a workflow run however many **Send Survey Invitation** tasks it runs, or one invitation list of the reminder task): it reads the limit and counts the day's e-mails once under the lock, then adds its own e-mails as they go out, so a send of thousands of invitations doesn't run a count for each. **Invite** creates every invitation first and then sends them (`SurveyInvitationService.InviteManyAsync`). A send asks for the lock at most once: when it can't get it within 10 seconds, it sends no e-mail and waits no more; its first sends are held and its reminders stay due, for the next run of the reminder task. Once one invitation list of a reminder run finds the lock busy, the run's later lists hold their e-mails without asking for it (their notifications to users still go out). A send sends e-mails only during the 5 minutes after it took the lock (`SurveyInvitationEmailLimit.SendingWindow`); the e-mails it would send later are held the same way. The lock expires on its own after 30 minutes (`LockExpiration`, so a stopped server doesn't block the day), which leaves a send 25 minutes after its last e-mail to save, so the lock does not expire while sent e-mails are still unsaved and let another sender count without them. Once a send stops sending, every later e-mail of it is held at once, without the opt-out checks (they run when it is sent), so only the save is left. Code that sends invitations in its own long-running scope must save within that time. The lock is in-process by default; on a web farm enable Orchard Core's **Redis Lock** feature (`OrchardCore.Redis.Lock`) so the servers share it. A send the mail server fails or refuses (`SurveyInvitationDelivery.RetryLater`) isn't a bounce: a first send stays **Pending**, held, and the reminder task tries it again each hour, up to 5 times (`SurveyInvitationHold.MaxSendAttempts`), before it is marked **Bounced**; a reminder simply stays due. Only an invitation that can never be delivered (its user no longer exists, or it has no address) is marked **Bounced** at once. With no e-mail service (the Email feature off), e-mail invitations are held the same way without taking the lock, and **Invite** with **Send the invitations now** refuses e-mail recipients with a message. Inviting a **Bounced** or **Opted out** invitation's recipient again makes it **Pending** again, and the opt-out checks decide again when it is sent. An existing invitation is found by the index (the user, the recipient or the lowercased address), never by reading the whole list. Each reminder run visits every open invitation of a list, a page of 500 at a time, so invitations that used up their reminders never hide the ones after them, and an expired invitation is marked **Expired** even when no reminder is due. Links may expire.

Reminders (type `SurveyReminder`) go every N days, up to a set number, to people who have not completed the survey; they stop on completion. An anonymous response never names its invitation: it keeps an `InvitationSeal`, an HMAC of the invitation id under the survey's protected secret that nothing stored links back to the invitation. Each invitation's index keeps a second HMAC of its seal under the same secret, so completing the response finds the invitation with one indexed query (invitations made before that value was kept are still matched by recomputing their seals), marks it **Completed** (so its link can't start another response) and clears the seal. Someone who reads the database sees the seal and the lookup value but can't link them without the secret.

Sending invitations needs **Manage survey invitations**, or **Manage invitations of own surveys** on the surveys the user owns. **Manage own surveys** alone does not allow it, because invitations send site e-mail.

`ISurveyInvitationService` creates and sends invitations from code, and `ISurveyLinkService.CreateLinkAsync` makes a personal link for a respondent and a context (used by the **Create Survey Link** workflow task).

### Opt-outs and unsubscribes

Survey Invitations depends on **Outreach**, so turning it on turns Outreach on. Invitations are sent by the invitation service and its hourly task rather than as Outreach runs, but every e-mail invitation and reminder honors the same opt-outs as an Outreach run:

1. Just before an e-mail invitation or reminder is sent, every `ISurveyInvitationRecipientPolicy` is asked (`AddSurveyInvitationRecipientPolicy<T>()`). The Invitations feature registers one that asks Outreach's `IOutreachRecipientPolicy` checks for the address on the `Email` consent channel. Outreach's consent policy asks the consent service, so contact preferences and address opt-outs (Omnichannel contacts), customer marketing preferences and survey unsubscribes all apply.
2. An invitation whose address opted out is not sent and gets the status **Opted out**; it gets no reminders.
3. Every invitation e-mail ends with an unsubscribe link, `/s/i/{token}/unsubscribe`, whatever the collector's message says. Opening it changes nothing; confirming it (a post, which mail apps' one-click unsubscribe may send without a form token) marks the invitation **Opted out** and records the address through `IConsentService` with the source `survey-invitations`. The Invitations feature registers that consent source; it keeps only an HMAC of the address, keyed by a site key protected with Data Protection (hashes stored before the key existed are still honored), so no survey invites the address again and every other send that asks the consent service skips it. The list is saved with a concurrency check, and the unsubscribe page retries a conflicting save in a fresh scope, so two unsubscribes at once never lose one and never fail the page; two first-ever unsubscribes can each create a list, and every list is read. If the list's key can't be read (missing Data Protection keys), the consent source answers `ConsentAnswer.Unknown` for an address rather than saying the person opted out or not (see [Consent](../../omnichannel/management.md#consent-may-we-reach-them)). Survey invitations ask the consent service themselves and hold an e-mail invitation on an unknown answer, without changing its status (a first send gets the hold mark and goes out once the key is back). Other sends decide for themselves: an Outreach campaign lets the other consent sources decide, so a Surveys key problem neither fails nor empties a campaign that has nothing to do with surveys.

Invitations to users of the site go to their notification inbox and are not checked against e-mail opt-outs.

## Embedding

With **Survey Embedding** on:

- `SurveyPart` (attachable) picks an open survey and one of its links, and shows the survey in the page, as a button or as a link. The `SurveyWidget` content type holds the part. The card holds no form or form token, so a page or zone that Orchard Core caches for every visitor stays safe: its **Start** button opens `/s/{token}?autostart=1`, whose page posts the start form at once with a token of its own. The page honors `autostart` only on a navigation from the same site (`Sec-Fetch-Site: same-origin`), so a copy of the link on another site, in an e-mail or in a search result opens the start page instead, introduction included.
- The shortcode `[survey name="customer-satisfaction" collector="..." display="link"]` renders a button (or a link) that opens the survey (with Shortcodes on). Its link starts with the tenant's path base, so it works on a tenant served under a prefix.

## Quotas

A quota counts completed responses that match its rule. When the count reaches the limit, new matching respondents are screened out with the quota's ending, or the survey closes, or nothing happens (count only). Counters change only under the survey lock, and the **Survey Quota Reached** workflow event fires.

## Responses

A response moves through `InProgress`, `Completed`, `ScreenedOut`, `Abandoned` and `Voided`. A completed response can be reopened only when the survey allows changes after finishing, and keeps its version. Unfinished responses idle longer than the survey's limit (168 hours by default) are abandoned by the maintenance task.

Consumers start responses for their own records through `ISurveyResponseService.StartAsync` with a `Context` (a `RecordRef`), their own variables and properties.
