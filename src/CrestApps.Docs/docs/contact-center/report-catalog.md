# Enterprise Contact Center Report Catalog

<YouTube video="reports-run-and-export" title="Video overview of finding, running, filtering and exporting reports" />

Contact Center reporting and Omnichannel Management contribute immediately runnable reports to the shared **Reports** area (Contact Center reports activate automatically once `CrestApps.OrchardCore.ContactCenter.Queues` and `CrestApps.OrchardCore.Reports` are both enabled). The admin menu organizes them into **Executive**, **Operations**, **Queue & Routing**, **Agent Performance**, **Workforce & Payroll**, **Billing & Usage**, **CRM & Campaigns**, **Compliance & Audit**, and **Technical & IT** groups. The catalog intentionally reports only facts represented by durable Contact Center or CRM data. It does not infer schedules, pay rates, quality scores, survey responses, or customer-resolution outcomes that have not been collected.

## Shared report behavior

| Capability | Behavior |
| --- | --- |
| Reporting population | Unless a report says otherwise, one interaction or CRM activity enters the report when its `CreatedUtc` is within the inclusive UTC bounds resolved from the selected tenant-local date and time range. This cohort rule prevents the same item from moving between periods when it later ends or completes. Backlog and aging are exceptions: they include currently nonterminal activities created on or before **To**, including older open work. |
| Default filters | Every report has tenant-local **From** and **To** date/time controls. Each report declares its supported dimensions, and the filter editor renders only those controls. Interaction reports commonly add queue group, queue, agent, channel, and direction. Workforce reports add agent. Contact Center campaign/subject reports add campaign group, campaign, channel, source, and activity status. Omnichannel reports add campaign group, campaign, channel, source, and activity status. The same filter values are applied to browser results and exports. |
| Time grouping | Durable source timestamps are stored and compared in UTC. Date/time controls are displayed in the tenant time zone and converted to UTC before the query runs, including daylight-saving transitions. Daily rows use UTC dates, except the daily agent timecard and the reconciled payroll timecard, which use the tenant's time zone. No percentage or average is averaged across displayed rows; totals are recalculated from raw counts and durations. |
| Sorting | Summary tables default to descending population. Daily tables sort chronologically. Interaction detail sorts newest first. Dialer call detail sorts newest first and shows 100 rows per page on screen; its export carries every matching row. Aging and attempt reports sort by ascending bucket. |
| Visualizations | The shared renderer supports KPI cards, tables, horizontal bars, and responsive Chart.js line, bar, stacked-bar, and doughnut charts. The **Executive performance dashboard** currently provides the interactive Chart.js visualizations. Other chart types described in the catalog are planned unless their report output explicitly includes a chart section. Heat-map, gauge, funnel, Sankey, and timeline renderers remain recommended extensions where noted below. |
| Aggregate rows | Every Contact Center aggregate table appends a semantic grand-total row recalculated from the filtered raw counts and durations. Layered tables add semantic subtotals: Queue Usage identifies queue-group subtotals, Campaign Summary identifies campaign-group subtotals, and Daily Agent Timecard identifies each tenant-local day's subtotal. Interaction detail, presence audit, and exception-detail tables remain raw lists and do not receive artificial totals. The browser renderer uses distinct background colors for subtotal and grand-total rows. |
| Queue-group membership | Queue groups are reporting/catalog metadata and use current-membership semantics. Reports resolve an interaction's stored queue identifier against the queue's current `QueueGroupId`; moving a queue changes historical group attribution without changing the interaction or any routing/SLA/entitlement behavior. Deleting a group makes its assigned queues ungrouped. |
| Export | CSV is built in. Excel is available when `CrestApps.OrchardCore.Reports.OpenXml` is enabled. Export actions appear in a report toolbar at the right edge of the first visible section heading and retain the active filter values. Table exports retain detail, subtotal, and grand-total rows in display order; the semantic row kind controls browser color only and does not remove rows from CSV or Excel. The toolbar and visible report heading are not exported; CSV starts with the data headings, and Excel uses the report title for worksheet tab names. PDF and JSON are not currently provided. |
| Scheduling | Reports are currently interactive and exportable. Scheduled delivery by email, collaboration channel, or SFTP is not yet implemented; daily, weekly, and monthly schedules are the recommended baseline when scheduling is added. |
| Permissions | Contact Center reports require **View Contact Center reports** and are granted to supervisors and administrators by default. CRM reports require **View Omnichannel reports** and are granted to administrators by default. Tenant isolation is enforced by Orchard shell scope and tenant-local YesSql collections. |
| Capability requirements | A report only measures data some capability writes. Reporting deliberately does not depend on the capabilities it measures, so that a tenant running chat and CRM only is never made to run, secure and upgrade voice call handling to read a queue report. Degradation happens at two levels. A report whose whole subject belongs to an absent capability renders a single notice naming the missing feature and shows no figures: transfer analysis, queue and agent transfer performance, provider performance, provider usage for billing, and call leg performance require **Voice**, and recording coverage and agent recording coverage require **Recording**. A report whose primary figures are real still runs, but drops the columns and metrics the absent capability feeds rather than rendering them as zeroes - the executive dashboard omits **Transfer rate** and **Recording coverage**, interaction and exception detail omit **Provider** and **Transfers**, agent volume and outcome reports omit **Transfers**, **Recorded** and **Recording coverage**, and the queue, agent, channel and daily usage reports omit **Transfers** and **Recordings**. In both cases the reason is the same: zero is a measurement, and an absent capability took none. |
| Drill-down | The current renderer presents report sections on one page. The drill paths below define the stable implementation target for linked drill-down navigation. |

Campaign, campaign-group, and disposition dimensions render their configured display names. Campaign reports retain campaign-level rows and add campaign-group aggregate sections where applicable. Because activities store a campaign rather than a campaign-group snapshot, reports resolve the campaign's current group at execution time; moving a campaign changes historical group aggregation. If a referenced catalog entry has been deleted, the report shows an unknown label instead of exposing the stored identifier. User table cells render through Orchard Core's cached `UserDisplayName` shape: the account username is the default text, and the **User Display Name** feature replaces it through the configured `IDisplayNameProvider`. Browser rendering preserves the enclosing admin layout, while the export resolver suppresses layout rendering so CSV and Excel contain only the resolved text value and never the surrounding admin-page HTML. Usernames are resolved from stable user identifiers when a report runs and are not duplicated in activity indexes. Deleted or unavailable users are shown as **Unknown user** or **Unknown agent**.

## Canonical KPI definitions

These definitions are authoritative across the catalog.

| KPI | Exact definition and edge cases |
| --- | --- |
| Interactions | Count of interaction records in the report cohort. Every transfer, consult, conference, callback, or requeue remains part of the same interaction unless it creates a separate communication attempt and therefore a separate interaction record. |
| Inbound offered | Count of inbound interaction records. Queue overflows and requeues do not create another offered interaction. An inbound callback promoted into an outbound attempt is counted as an outbound interaction, not another inbound offered interaction. |
| Outcome | Every interaction has exactly one outcome, decided the same way by every report (see [Interaction outcomes](#interaction-outcomes) below): answered, abandoned, voicemail, callback requested, failed, not connected, or in progress. |
| Answered | Interactions whose outcome is answered: an agent took the call. `Inbound answered` restricts the numerator to inbound interactions. A caller the platform answered only to play the queue or to record a voicemail is not answered. |
| Answer rate | `Answered interactions / all interactions` in all-direction reports. Inbound answer rate is `Inbound answered / Inbound offered`. A zero denominator produces zero. |
| Abandoned | Inbound interactions whose outcome is abandoned: the caller hung up while waiting in a queue or while an agent was being offered the call, before anybody answered. A caller who hangs up while ringing an agent is an abandon, never a failure. All abandons are included because the platform has no short-abandon threshold setting. Transfers, consults, and conferences after answer cannot be abandoned. |
| Voicemail | Inbound interactions the platform sent to voicemail instead of connecting them: an unanswered offer, the queue's maximum wait, an entry point outside business hours, or a full queue. They are neither answered nor abandoned, are shown in their own column, and are left out of the abandonment rate's numerator and the service level. |
| Callback requested | Inbound interactions whose caller accepted the queue's callback offer instead of waiting. Nobody answered the call and the caller did not give up on it: the contact continues as the scheduled callback, which is its own outbound interaction. They are neither answered nor abandoned, are shown in their own column, and are left out of the abandonment rate's numerator and the service level. |
| Failed | Interactions that failed for a technical reason: the provider reported an error, or the call could not be placed or bridged. An answered call that later failed is answered. |
| Abandonment rate | `Abandoned / Inbound offered`. Voicemail and callback-requested calls count toward inbound offered but not toward abandoned. Percentages are recalculated from counts at every aggregation level. |
| Wait before abandon | From the moment the caller joined the queue to the moment they hung up, as the routing engine measured it when it recorded the abandon. |
| Wait before voicemail | From the moment the caller joined the queue to the moment routing took them out of it to send them to voicemail. The greeting and the message are not part of the wait. |
| Wait before callback | From the moment the caller joined the queue to the moment they accepted the callback offer. The confirmation they hear afterwards is not part of the wait. |
| Average speed of answer (ASA) | `Sum(AnsweredUtc - CreatedUtc for inbound answered interactions) / Inbound answered`. Negative durations are clamped to zero. Abandoned, failed, and outbound interactions are excluded. |
| Wait | The wait shown per interaction (interaction detail, high-wait detail, queue wait time, usage and lifecycle reports) runs to what became of the call: to the agent's answer for an answered call, to leaving the queue for voicemail for a voicemail, to accepting the offer for a callback request, and to hanging up for an abandon. In-progress, failed and not-connected interactions show no wait. |
| Connected duration | For a completed interaction whose outcome is answered, `EndedUtc - AnsweredUtc`. This interval includes hold because interaction history does not yet persist separate channel-neutral hold segments. Every other outcome has no connected duration: the platform answers a caller itself to record a voicemail or to play the queue, and the provider reports that as an answer, but nobody talked to the caller. |
| Wrap-up duration | `WrapUpCompletedUtc - WrapUpStartedUtc` when both values exist and completion is not before start. Incomplete or invalid intervals contribute zero seconds and remain visible in the wrap-up completion counts. |
| Average handle time (AHT) | `Sum(connected duration + completed wrap-up duration) / handled interactions`, where handled means answered with a valid end time. This is operationally equivalent to talk + hold + after-contact work with the current channel-neutral timestamps. Abandoned, voicemail and failed interactions are excluded, and are not counted as handled by any agent. |
| Transfer rate | `Answered interactions with at least one transfer history entry / Answered interactions`. Multiple transfers increase transfer volume but not the interaction-level transfer-rate numerator. Consultative and blind transfers are included when recorded; conferences are not transfers unless a transfer history entry also exists. |
| Recording coverage | `Answered voice interactions with a non-empty recording reference / Answered voice interactions`. Paused or stopped recordings count as covered when a recording reference exists. |
| Service level | Per queue: `Inbound interactions answered within the queue SLA threshold / (Inbound answered + abandoned)`. Failed, voicemail and callback-requested interactions are excluded. All abandons remain in the denominator because no short-abandon threshold is stored. The original interaction is counted once after overflow or requeue. A queue without a positive threshold displays no service-level percentage. |
| Completion rate | `Completed CRM activities / Activities in the group`. Failed, cancelled, purged, pending, and in-progress activities remain in the denominator. Reopened work is represented by a new or nonterminal activity and is not treated as completed. |
| Average attempts | `Sum(max(Attempts, 0)) / Activities in the group`. |
| Overdue | A nonterminal activity whose `ScheduledUtc` is before the report's `ToUtc` as-of boundary. |
| Observed signed-in time | Sum of clipped agent-presence intervals whose current status is not `Offline`. The interval begins at the durable presence transition time, ends at the next transition, and is clipped to the selected report boundaries. Time before the first known transition is unknown and excluded. |
| Productive presence | `Available + Reserved + Busy + WrapUp` observed presence duration. This is a presence classification, not proof of payroll eligibility or schedule adherence. |
| Agent utilization | `(Busy + WrapUp) / Observed signed-in time`. Break, away, meeting, training, do-not-disturb, and other signed-in not-ready states remain in the denominator. |
| Agent occupancy | `(Busy + WrapUp) / (Available + Reserved + Busy + WrapUp)`. Offline and explicitly not-ready states are excluded. This is a presence-derived operational occupancy measure and does not use workforce schedules. |
| Activity cycle time | For completed CRM activities, `CompletedUtc - CreatedUtc`, clamped to zero. Median is recalculated from the sorted raw duration population. |
| Usage for billing | Raw interaction count and measured connected, wrap-up, queue-wait, transfer, and recording usage. The platform does not apply prices, contracts, taxes, minimum billing increments, or currency conversion. |

## Interaction outcomes

An interaction's status says where its communication session stopped; its outcome says what happened to the contact. The two differ: a caller who gave up and a caller sent to voicemail both leave an ended session. Every report takes the outcome from one classifier, `InteractionOutcomeClassifier`, which reads the interaction and the call events the routing engine records against it, and applies these rules in order:

1. A caller who accepted the queue's callback offer is **callback requested**: a `CallbackRequested` event, recorded when the callback is arranged, or the `queued_callback` terminal reason set on the interaction at the same time. They left the queue to be called back, which is neither an agent answering nor the caller giving up.
2. A recorded `CallAbandoned` event makes the interaction **abandoned**. Routing records it only for a caller who hung up while waiting, in a queue or while ringing an agent, before any agent answered, so it holds even when the platform had answered the caller itself to play the queue.
3. A call the platform sent to voicemail is **voicemail**: a `CallSentToVoicemail` event, or the voicemail flag set on the interaction when it was sent. The platform answers the leg to record the message, and that answer does not make it an answered call.
4. Any other call with an answer time is **answered**.
5. A call that has not ended is **in progress**.
6. A call whose session failed is **failed**.
7. Any other inbound call that ended unanswered is **abandoned** (a caller who hung up before reaching a queue has no abandon on record); an outbound one is **not connected**.

A call sent to voicemail stays on the line while the caller listens to the greeting and leaves a message, so it ends when the caller hangs up. Sending it to voicemail ends routing's part in it (the caller leaves the queue and the agent is released) and records `CallSentToVoicemail`; the call's single `CallEnded` event and the interaction's `EndedUtc` come from the hangup. End-to-end duration therefore includes the greeting and the message, while wait stops when the call left the queue for voicemail and connected duration is zero.

A caller who hangs up before anybody answers cancels the call, and the interaction's status is `Ended`, not `Failed`. `Failed` is kept for a provider that could not carry the call, a dial that could not be placed, or an agent leg that could not be bridged.

Because the outcome is derived from the event log rather than stored, history reports correctly without a data migration. Interactions written before a caller's cancel stopped settling as `Failed` are still reported as abandoned, because the abandon was recorded alongside them.

## Report catalog

Each report uses the shared date/time filter, export, permission, scheduling, and aggregation behavior above. “Columns/KPIs” names the complete default output.

## Running and filtering a report

How to pick a report, set the date range and filters, and export it is described step by step in [Reports](../user-manual/reports.md) in the User Manual. The technical rules behind those screens:

- **Features.** Enable **Reports** (`CrestApps.OrchardCore.Reports`) and the feature that contributes the report. There is no separate Contact Center reports feature: the Contact Center reports switch on when **Contact Center Work Distribution** (`CrestApps.OrchardCore.ContactCenter.Queues`) and **Reports** are both enabled. The CRM reports come with **Omnichannel Management** (`CrestApps.OrchardCore.Omnichannel.Managements`), and the lead and opportunity reports with **Omnichannel CRM** (`CrestApps.OrchardCore.Omnichannel.Crm`). Excel export needs **Reports (OpenXml)** (`CrestApps.OrchardCore.Reports.OpenXml`).
- **Range.** **From** and **To** are entered in the tenant's local time zone and converted to UTC. The default is today, from the start to the end of the current tenant-local day. A Contact Center report refuses a range wider than 400 days; raise or lower it with `CrestApps:ContactCenter:Reporting:MaximumReportRange` (a `TimeSpan`, default `400.00:00:00`). The agent workforce reports, which read the agent state log, have a tighter limit of 31 days by default, described in [Agent workforce reports over long periods](#agent-workforce-reports-over-long-periods). If **From** is later than **To**, the report swaps the resolved UTC boundaries before querying.
- **Dimensions.** Interaction reports offer queue group, queue, agent, channel, and direction (queue usage has no agent filter); workforce, call-quality and call-handling reports offer agent, and the last two also queue; campaign, subject and CRM reports offer campaign group, campaign, channel, source, and status, and the Omnichannel CRM reports also disposition, which takes several dispositions at once. The enterprise interaction reports have no grouping choice: each has the fixed layout described below. An empty dimension means **All**, and filters combine with logical AND; for example, selecting Queue A, Agent B, Voice, and Inbound returns only interactions matching all four dimensions.
- **Recalculation.** Every metric, table row, total, percentage, and duration is recalculated from the filtered raw population.
- **Export.** With only CSV available the toolbar shows a single **Export CSV** button; with Excel too, an **Export** dropdown. Export actions submit the same filter form, so downloaded data matches the visible report.

### Agent workforce reports over long periods

Every report in the table above (the **Agent presence audit** among them), the **Agent activity timeline** and the **Reconciled payroll timecard** read agent state changes from the durable event log. Their cost grows with the number of changes in the period, so a wide period on a busy tenant used to outlast the database command timeout. The following bounds apply.

| Bound | Behavior |
| --- | --- |
| Period limit | A period longer than `CrestApps:ContactCenter:Reporting:MaximumWorkforceReportRange` (default 31 days) is refused before any event is read. The report shows one section, *This period is too long for this report*, which names the limit and the number of days chosen and shows no figures. The period is measured in the tenant's time zone, so a calendar month that crosses a daylight-saving change is still accepted. The period is refused rather than clamped, because a payroll or utilization figure for a shorter period than the one asked for would read as an answer to the question asked. |
| Export limit | An export is refused the same way above `MaximumWorkforceExportRange` (default 31 days). The exported file then holds only the message section. |
| Row caps | In the browser, the **Agent presence audit** lists the most recent 5,000 changes and the **Agent activity timeline** the first 5,000 entries, each with a note that gives the total and says to choose an agent or a shorter period. The cap is applied before rows are built: the timeline places and counts every entry but builds only the ones it lists, and its summary metrics still count every entry. An export of the presence audit lists every change; the timeline lists, and exports, its first 5,000 entries. |
| Timeout | When the database still does not finish reading a period within its command timeout, the report shows *This period is too large to report* and asks for an agent or a shorter period, instead of an error page. A cancelled request is not reported as a timeout. |
| Paged reads | The period is read in pages of 1,000 events, each continuing after the last event read by occurrence time and document id (keyset paging on the `IDX_InteractionEventIndex_Window` index), so no single statement holds a connection for the whole period. The state each agent was in when the period opened is found with one statement per 100 agents, each a `UNION ALL` of one newest-first seek per agent on the aggregate index, instead of one query per agent. |

#### Daily agent time summaries

The time-based kinds, **Agent time summary**, **Presence status duration**, **Ready versus not-ready time**, **Agent utilization**, **Agent occupancy**, **Presence reason breakdown**, **Queue signed-in hours**, **Campaign signed-in hours** and **Payroll timecard inputs**, read whole UTC days from a daily summary instead of from the day's state changes when they report on every agent. A summary holds, per agent, the time and the number of intervals in each combination of state, reason, queues and campaigns, and the time of the interval already running at midnight, which is counted on the day it started. The figures are the same as a report over the log: the summary of a day is computed by the same code a report runs, over the day and the hour before it.

- **Which days.** A summary is used for a UTC day that starts after the period starts and ends by the time the period ends. The first day of a period is always read from the log, so the period opens exactly as a report over the log opens it; so are the last, partial day, any day without a summary, and, for a tenant whose time zone is not UTC, the partial UTC days at either end. A report filtered to one agent always reads the log, which is one seek on the aggregate index.
- **Which reports read the log.** The **Daily agent timecard** (local days and the first and last observed time of each), the **Agent break and away analysis** (the longest single break), the **Agent presence audit**, the **Agent activity timeline** and the **Reconciled payroll timecard** need individual changes and always read the log, bounded by the period limit.
- **Staleness.** Each summary records how many state changes the log held for its day. Before using a run of consecutive summaries, the report counts the day's changes on the event index (the count reads only the index); a day whose count changed, a late change recorded for it or a purge, is read from the log instead, together with every later day of the run, because a change late in one day is the state the next day opens in. The summary of the day before the first used day is checked too, when it exists.
- **Roller.** The **Contact Center Agent Time Summaries** background task runs every five minutes under the background task lock. It computes each UTC day 30 minutes after it ends, so a sign-off dated by an agent's last heartbeat before midnight is in the log first; backfills earlier days, newest first, ten days per run, back to `AgentTimeSummaryBackfill` (default 92 days) or the first agent state change, whichever is later; re-checks the counts of the seven most recent days and of seven older days in rotation, deleting a day whose log changed and the days after it so they are recomputed; and deletes summaries older than the backfill window. A new or upgraded tenant therefore backfills its existing log automatically. Deleting summaries is always safe: those days are read from the log until they are computed again, and changing the computation's version makes every summary of the old version unread and recomputed.
- **Storage.** One `AgentDailyTimeSummary` document per UTC day in the Contact Center collection, found through `AgentDailyTimeSummaryIndex` (`Date`, `Version`, `EventCount`), created by `AgentDailyTimeSummaryIndexMigrations`.
- **Turning it off.** Set `AgentTimeSummaryBackfill` to `00:00:00`. Every report then reads the log, and the roller deletes the summaries it kept.

Known limits of the summaries: a sign-off recorded more than an hour after the time it is dated by, across midnight, can supersede changes the next day's summary counted; and an agent whose profile was deleted before a day was summarized, and who has a state change elsewhere in the period, is missing from that day's summary. Both differ from a report over the log only in those cases, and both are corrected for a day by deleting its summary.

## Report Builder data sets

The Contact Center also exposes its records to the Report Builder and to Orchard Core data pipelines as the `ContactCenter` data source, so a report the catalog does not have can be built without code. The data source is registered when Data Pipelines Core (`OrchardCore.DataPipelines.Core`) is enabled, and each data set is registered by the feature that stores its records, so a data set whose feature is off is never listed. Every data set needs **View Contact Center reports** (`ViewContactCenterReports`). A principal without it, or no principal, sees no data set and reads no row.

Each data set reads its newest records first, a page at a time, by its main date, and pushes the date range of a report, the keys of a join and the values a filter allows on the columns its index holds down to the database. Identifier fields reference the data sets they point to, so related data sets join on their own: `AgentId` joins **Agent profiles**, `QueueId` joins **Queues**, `InteractionId` joins **Interactions**, `ActivityItemId` joins the Omnichannel **Activities**, `CampaignId` joins the Omnichannel **Campaigns**, and user IDs join Orchard Core's **Users**.

Notes on what the data sets hold:

- **Agent state changes** are the changes as they were recorded. The **Agent activity timeline** and the workforce reports also mark a change that a later sign-off superseded, and a transition that is missing from the record; the data set does not, because that is a reading of the log, not a value stored in it. The payload of an event written by a newer release than the one that reads it is not read, so its row has only the event's own values. The data set reads each row from its event's payload, so it does not group itself in the database.
- **Dispositions** and **campaigns** are Omnichannel records: join `ActivityItemId` to the Omnichannel **Activities**, which carries the disposition, and `CampaignId` to **Campaigns**. See [Omnichannel Management](../omnichannel/management.md#report-builder-data-sets).
- **Business-hours decisions** are not stored. Routing and the automated conversations check a queue's business-hours calendar when they act, and keep no record of the check: routing skips a closed queue without a **Dialer decisions** row. Some of what they do because of it is stored: a queue that sends its callers on after hours records each move as an overflow (`OverflowedFromQueueId` and `OverflowCount` on **Queue items**, without the cause), and an automated conversation that could not reach an agent after hours ends with the terminal reason `handed_off_after_hours_callback` on its activity. A dial held back because the contact's local time is outside the dialer profile's calling window is a **Dialer decisions** row with the reason `OutsideCallingWindow`.
- **Handoffs** from an automated voice agent are recorded on the interaction (`HandoffReason`, `HandoffAiSessionId`) and as an `AiHandoffRequested` row of **Interaction events**.
- The daily agent time summaries are derived data that can be deleted and computed again at any time, so they are not a data set: read **Agent state changes** instead.

## Known data limitations

The following common report families are intentionally not emitted until their source data exists:

- **Workforce planning:** forecast accuracy, staffing requirement, schedule adherence, conformance, shrinkage, overtime, and paid-hours compliance require forecasts, schedules, employment calendars, and pay policies. The included occupancy, utilization, and timecard reports use durable observed presence only.
- **Quality management:** evaluation scorecards, calibration, coaching completion, compliance failures, and evaluator productivity require the planned quality module.
- **Customer experience:** CSAT, NPS, customer effort, and first-contact resolution require survey responses and a durable case/resolution-reopen correlation model. Disposition alone is not a valid substitute for FCR.
- **Advanced interaction analytics:** sentiment, topic, silence, interruption, script adherence, and AI summaries require transcript analytics and an enabled provider.
- **IVR journey analytics:** menu path, containment, self-service completion, and opt-out require multi-step IVR event capture.
- **Historical backlog reconstruction:** activity reports use the current persisted activity status. Backlog and aging include all currently nonterminal work created by the selected **To** boundary, but they cannot reconstruct whether an activity that is completed today was still open at a past boundary without a dedicated activity-state history projection.
- **Payroll and billing money:** reports provide measured durations and counts, but wages, premiums, contracted rates, billing increments, taxes, discounts, currency, and invoice totals require organization-specific rate and policy data that is not persisted by these modules.

These exclusions prevent plausible-looking but operationally false enterprise KPIs.
