The versioned machine-readable contract is `.github/contact-center/pr-test-control-matrix.v1.json`. It maps every P0 and P1 finding from the repository-tracked Contact Center plan's independent production-readiness review to one accountable gate. Release remains blocked until every P0 gate, and every P1 gate in scope for the release profile, passes with retained CI evidence.

Each gate resolves:

- A **category** with an owning DRI role and approver roles.
- A stable **test id** and a **CI job** (`implemented`, `partial`, or `planned`).
- The **provider, database, and topology** context the gate must be proven under.
- A **falsifiable invariant** - a concrete behavior that a test can prove true or false.
- A **retained evidence location** - an existing test/CI artifact path, or a `planned:` path that the owning remediation phase (R1-R8) must populate.

It is expected and acceptable for most CI jobs and evidence paths to be `planned` this early in the remediation program; every P0/P1 finding must still be represented so no gate can be silently dropped.

## Every status claim is bound to a real CI job

A gate status is only meaningful if the CI job it names actually exists. `LedgerEvidenceTests` parses the top-level `jobs:` mapping of every workflow in `.github/workflows` and enforces the binding in both directions:

- A gate marked `implemented` or `partial` must name a workflow and job that resolve, and its `additionalJobs` must resolve too.
- A gate marked `planned` must carry the `planned:` prefix on its workflow and must **not** resolve.

The second rule is what keeps the matrix honest over time. When an anticipated job finally lands, the `planned` gate that named it starts resolving, the test fails, and the matrix cannot stay stale - the status has to be upgraded to match reality.

Evidence is checked as well, not just status:

- With the default `"evidenceKind": "tests"`, the gate's `evidenceLocation` must cite at least one test class that exists in the repository, and every cited class that exists must live in a test project one of the gate's own CI jobs actually runs. A gate cannot borrow credibility from tests that never execute in it.
- With `"evidenceKind": "workflow"`, the cited workflow files must exist and one of them must declare the job the gate names.

The workflow parser is itself pinned against the known job set of eleven workflows, so a parser that silently returned nothing (making every `planned` gate trivially "unresolved") or returned every YAML key (making every enforced gate trivially "resolved") fails the build instead of passing vacuously.

## The gates themselves are gated

A control matrix can only describe gates that run. Four further checks in `LedgerEvidenceTests` keep the workflows behind the matrix trustworthy:

- **No orphaned suites.** Every project marked `<IsTestProject>true</IsTestProject>` under `tests/` must be executed by at least one workflow. The Telephony browser suite was orphaned in exactly this way and silently carried a failing test until it was adopted by `contact_center_browser_gates.yml`.
- **Nothing ships untested.** Every test project must also run in `release_ci.yml`, which is the last gate before packages are published.
- **Gates watch the whole tree.** The Contact Center gate workflows must filter on `src/**` and `tests/**`. They previously listed individual module folders, so a change to a shared Core project skipped the very gate that proved it.
- **Failures cannot be swallowed.** Any workflow step piping a command into `tee` must set `pipefail` or inspect `PIPESTATUS`; otherwise the step reports the exit status of `tee` and a failing build passes. Comment lines are stripped before this check, so a comment mentioning `pipefail` cannot satisfy it.

A gate is also only as good as the tests it runs. A test that reads production source as text, or that asserts a value it stubbed itself, satisfies a gate without proving anything, so the Contact Center suites that behaved that way were rebuilt to invoke the code they describe:

- `ContactCenterHubSecurityTests` constructs the real `ContactCenterHub` and invokes `OnConnectedAsync`, rather than searching `ContactCenterHub.cs` for substrings in the expected order.
- `ContactCenterMigrationSqlTests` runs the migration SQL builder against the four real YesSql dialects and executes the generated statement on a live SQLite database, rather than asserting a string shaped by its own `Mock<ISqlDialect>`. The mock had encoded quoting and index-prefix rules that no supported engine actually uses.
- `ActivityQueueServiceConcurrencyTests` races eight workers against one activity on a real store and proves a single queue claim survives, rather than making one call against one stub.
- `ContactCenterOperationalLogPrivacyTests` parses every logging call in the guarded trees with Roslyn instead of pinning twenty exact source strings, so the redaction rule applies to code written after the audit.

Governance suites that validate the shape of a JSON document are retained as schema guards, but they are not counted as behavioural coverage for any control.

## Ledger authority

Exactly one Contact Center plan document may be release-authoritative. Each Markdown ledger in `.github/contact-center` declares itself with a machine-readable marker:

- `<!-- ledger-authority: release-authoritative -->` - the current release ledger. Every item it marks `[x]` or `[~]` must carry a `` `gate:<workflow>.yml#<job>` `` annotation naming a CI job that resolves, and every item still open must **not** claim an enforcing job.
- `<!-- ledger-authority: historical -->` - retained for architecture and completed history, but not used for release scoping.

`LedgerEvidenceTests` fails the build if no document claims authority, if more than one does, or if any document declares both or neither.

## Contract tests

`ContactCenterPrTestControlMatrixTests` in `tests/CrestApps.OrchardCore.Tests/Modules/ContactCenter` fails the build if:

- The matrix does not contain exactly 53 gates, or the per-category gate counts drift from the table above.
- Any gate id is duplicated, or any of the 41 current P0/P1 gate ids is missing, has the wrong severity, or has drifted from its authoritative title in the production-readiness review.
- A gate's category has no DRI role or no approver roles.
- A gate's execution context omits providers, databases, or topologies.
- A gate has no plan-finding citation, title, falsifiable invariant, test id, CI job id/workflow, or retained evidence location.
- No P0 gate has at least `partial` CI enforcement, which would indicate the remediation program has not started closing any commercial release blocker.

`ContactCenterFeatureDependencyArchitectureTests` in the same folder fails the build if:

- A Contact Center feature's manifest declares a new, unrecorded dependency on a feature outside the Contact Center family, or the ledger records a manifest dependency that no longer exists.
- A recognized Contact Center `StartupBase` registration requires a service not guaranteed by its manifest or `[RequireFeatures]` transitive closure, and that finding is not already recorded in the ledger, or the ledger records a finding that no longer reproduces.
- A ledger violation references a control-matrix gate id that does not exist.
- A Contact Center feature's transitive manifest-dependency closure reaches an unresolvable dependency, cycles back to the feature itself, or drifts from the pinned closure recorded in the ledger.

The W5.4 gate `V005` is `implemented`. Before it, every Asterisk test asserted against a `TestAriClient` stub declared in the same file, so the suite could only prove the code agreed with itself; nothing tied it to the protocol Asterisk actually speaks. The Asterisk project publishes its REST Interface as machine-readable Swagger declarations per release, so those declarations are now vendored verbatim under `tests/CrestApps.OrchardCore.Tests/Telephony/Cassettes/Asterisk`, in a directory named for the release, behind a provenance manifest that records the upstream repository, ref, URL, and SHA-256 of every file, plus the container image tag and digest the single-node profile is pinned to. `AsteriskAriContractProvenanceTests` recomputes those hashes and requires the vendored release to equal the release parsed out of the Asterisk `Dockerfile`, and requires exactly one vendored release directory to exist, so bumping Asterisk fails the build until the declarations are refreshed. `AsteriskAriEventContractTests` scans the production mapper for the event types it interprets and requires the contract manifest and the recorded event payloads to cover exactly that set, requires every property path the mapper depends on to resolve against the vendored declarations, requires every recorded payload to contain only fields those declarations permit, and requires each compatibility fallback the mapper merely tolerates to stay absent from them, so a field Asterisk later adopts must be promoted rather than left as a guess. `AsteriskAriRestContractTests` drives the real `AsteriskAriClient` over recorded responses, exercises every method the interface publishes, and requires every issued request to match an operation the vendored declarations declare with only query parameters that release accepts. DialPad publishes no vendorable schema, so `DialPadWebhookContractTests` binds that provider to recorded deliveries instead: it scans the normalizer's own token switches and requires the recorded state tables to name exactly the call-state, recording-state, and answer-classification tokens the production code interprets, then replays every recorded delivery through the signed JWT ingress, the production deserializer, and the production normalizer. These gates found and forced the correction of two real defects. The mapper read channel variables from four locations, none of which was `Channel.channelvars`, the only location a conforming Asterisk release populates, so the interaction correlation identifier could never be recovered from a channel object. Recording duration was read from `StoredRecording`, which Asterisk declares with only a name and a format, so every completed recording reported no duration; the client now reads the live recording, where the duration is declared, before stopping it.

The W5.6 gate `V006` is `implemented`. `V005` binds the providers to the protocol they speak, but a conforming payload still has to survive the way a provider actually delivers it. Provider nodes do not share a clock, do not sequence every event type, retry aggressively, and can report a call terminated more than once, so the example-based tests that preceded this gate only ever proved the state machine handled the orderly case. `CallStateMachinePropertyTests` replaces that with eight properties, each run over 400 seeded adversarial delivery sequences, driving the production `ProviderVoiceEventService` and the production `DefaultContactCenterEventPublisher`. A generator emits a real call lifecycle, then corrupts its delivery with duplicates, whole-stream replays, arbitrary reordering, clock skew wider than the spacing between events, streams where most events carry no sequence number, late backward state regressions stamped with the freshest timestamp and highest sequence, and competing terminal reports that disagree about how the call ended. The properties require the session to converge to one terminal state regardless of delivery order, never to regress its lifecycle rank, never to resurrect a terminated call, never to strand a call the provider reported terminated, never to publish a lifecycle domain event twice, and never to leave live-only flags such as mute set on a terminated call; a companion property asserts anti-vacuity floors so the generator cannot silently stop producing the hard cases. These properties found and forced the correction of two real defects. A terminal delivery carrying a stale mute flag re-applied it after the terminal normalization had cleared it, publishing a mute event for a call that had already ended. More seriously, the staleness guards were applied to terminal deliveries, so a hangup stamped fractionally behind the preceding state change, or arriving without a sequence number, was silently discarded: the session stayed live forever, `CallEnded` was never published, wrap-up never started, and the agent and their reservation were never released. Sabotage probing also established that the service-level and publisher-level duplicate suppression are individually redundant and only observable when both are removed, which is recorded rather than papered over.

The W1.3 gate `V007` is `implemented`. Contact Center and the soft phone spoke two call vocabularies — twelve states and seven — and every call site translated between them with its own switch. The switches disagreed with one another, and in the widening direction they all discarded the outcome, so a busy number, an unanswered dial, an abandoned call, and a completed conversation became the same `Ended` state the moment a provider event crossed into Contact Center. Asterisk reports the release reason as a Q.850 cause code on every hangup event, and that code was captured only as an uninterpreted metadata string, so outbound compliance reporting and abandon analytics had nothing to count. There is now one provider-neutral `HangupCause` vocabulary, one projection type that is the only place either translation may be written, and a source scan over every production file that fails the build if a second translation reappears. `AsteriskHangupCauseMapperTests` pins every Q.850 cause an Asterisk release can report to the outcome it represents, and additionally requires the causes reachable across the whole Q.850 range to cover the entire provider-neutral vocabulary except the answer-detection outcome, which no release cause can express and which is proven separately through the AMD channel variable. Q.850 has no distinct abandoned cause — a caller who hangs up while the far end is still alerting releases the channel normally — so that one distinction is resolved by the state machine, which is the only component that knows whether the call was ever answered. `CallStateMachinePropertyTests` then requires, over the same adversarial delivery sequences that prove the state machine converges, that no session ever reaches a terminal state without a recorded cause; a provider that reports a terminal state without a cause has it derived from the state, and a provider that reports nothing records that honestly as unknown rather than as a normal clearing.

See [Production support](production-support.md) and [Service objectives](service-objectives.md) for the related finite support matrix and measurable service-level contracts.

The W1.5 gate `D010` is `implemented`. The Contact Center stores were hardened against lost updates long before this, but the surviving Telephony interaction store was not: it saved without an optimistic-concurrency check, so the last writer to commit simply overwrote whatever the previous one had persisted. That store is written from three directions at once — real-time provider events, the periodic reconciliation pass that asks the provider for authoritative call state, and inbound-call dispatch — and all three read the interaction, mutated the copy they were holding, and saved it, which is precisely the shape that loses work. A reconciliation pass carrying a provider snapshot taken seconds earlier could reinstate a live call over a hangup that a real-time event had already committed. Every write is now concurrency-checked, and every read-modify-write path routes through a store method that owns a dedicated session, re-reads the interaction, and reapplies the caller's mutation against the version that actually won, retrying until it commits or a bounded attempt budget is exhausted. The mutation may also decline after the re-read, which is what lets the real-time dispatcher re-evaluate its terminal guard against the winning version rather than against the copy it read before the race. `TelephonyInteractionStoreConcurrencyTests` proves this against a real SQLite database: a stale writer is rejected instead of overwriting the winner, a competing writer's field survives the retry rather than being reverted by the mutation that lost the first attempt, and a hangup committed between the read and the write causes the in-flight mutation to decline instead of resurrecting a call that had already ended.

The W1.4 gate `V008` is `implemented`. `ITelephonyProvider` declared thirteen call operations alongside the provider's identity, so every provider had to supply an implementation for every operation whether or not it could perform it. The shipped Asterisk adapter had exactly that hole: it implemented `TransferAsync` and immediately returned a failure string for the warm-transfer branch, because attended transfer was folded into the same capability flag as blind transfer and the interface gave it no way to decline the operation rather than accept and refuse it. The interface now declares only `Name` and `Capabilities`, and each operation lives on its own contract — call control, inbound call handling, hold, mute, blind transfer, attended transfer, conference, DTMF, voicemail, and soft-phone credentials — with `TelephonyCapabilityContracts` recording, in one place, the contract each capability flag requires. Attended transfer became a capability in its own right, so a provider that can release a call without consulting the destination is no longer forced to claim it can consult it. Dispatch is now doubly gated: an operation runs only when the resolved provider both advertises the capability and is assignable to its declared contract, so a provider that advertises a capability it cannot execute is refused instead of being dispatched into a missing implementation, and a provider that implements a contract it never advertised is refused as well. The two Contact Center call sites that resolve a telephony provider by name rather than through the shared service repeat the same check before dialing. `TelephonyProviderCapabilityContractTests` proves the split is real rather than cosmetic: a provider implementing only `ITelephonyCallControlProvider` compiles, resolves, dials, and hangs up while every other operation fails closed; a provider advertising all twelve capabilities while implementing only call control fails closed on all ten it cannot execute; warm and blind transfer route to different contracts and neither satisfies the other; every capability flag declares a contract that is an interface in the telephony abstractions; the provider interface is asserted to declare no call operations, so re-fattening it fails the build; and each shipped provider is checked against the widest capability set its own capability source can ever advertise, read out of the Asterisk capability function across its whole input space and out of the DialPad capability property directly, so a provider that starts advertising a capability without implementing its contract fails the build rather than failing a call.

The W1.6 gate `V009` is `implemented`. The shared Contact Center contracts published one vendor's implementation as if it were the platform's: `MonitoringMetadata` declared a snoop channel identifier and a supervisor bridge identifier, and the transfer, conference, and attended-transfer metadata classes each declared a bridge identifier and a provider channel identifier. None of those keys were read by any provider-neutral consumer — the Asterisk adapter was the only code in the product that wrote them — so every future provider inherited a documented obligation to populate concepts that only exist in one vendor's media engine. Those ten result keys now live in `AsteriskVoiceResultMetadata` inside the Asterisk module, keeping their exact wire values so no stored metadata changes meaning, while the three `AgentUserId` request keys stay in the shared contracts because they genuinely are the platform's input to every provider. `RecordingMetadata.RecordingName` became `ProviderRecordingId`, which says what the value is rather than borrowing the vendor's noun for it, and `CallSession.BridgeId` became `MediaTopologyId`. `MergeRequest` no longer carries the legacy `PrimaryCallId`/`SecondaryCallId` pair that predated the `CallIds` collection; removing it also fixed a real defect, because the hub's diagnostic log described a merge using only the two legacy fields and therefore logged nothing at all for requests sent by the current client. `ProviderNeutralContractArchitectureTests` holds the boundary: the neutral telephony and Contact Center projects are scanned for vendor product names and single-provider topology vocabulary with comments stripped, so explanatory prose may still name a provider as an example while declared contract vocabulary may not; the relocated metadata keys are proven to appear nowhere outside the Asterisk module; they are also proven to still be in real use inside it, so deleting the keys rather than relocating them cannot make the boundary pass vacuously; the scan is floored at more than two hundred files so narrowing it to a token subset fails; and the forbidden vocabulary is proven to match at least four distinct terms in real provider source, so the boundary cannot degrade into guarding words nobody was going to write.

The W1.2 gate `V010` is `implemented`. One Asterisk ARI stream fed two consumers, and they were wired as alternatives rather than peers: `AsteriskRealtimeVoiceEventDispatcher` walked a first-wins bridge chain and returned the moment any bridge claimed the delivery. The Contact Center bridge sat on that chain, so on a tenant with Contact Center voice enabled the telephony call-history projection never ran — `TelephonyInteraction` stayed `InProgress` forever for every call Contact Center owned, and the soft phone never received the hangup. With Contact Center disabled the surviving projection ran on the fall-through path with no lock, no ordering and no de-duplication at all, which is the same stream the Contact Center path guarded with a distributed lock, an idempotency claim and a monotonic watermark. Only one half of the product was hardened, and which half depended on a feature toggle. The provider-neutral `NormalizedVoiceEventIngestor` in `Telephony.Core` now canonicalizes the provider identity, takes the ingestion lease exactly once through `VoiceIngressGate`, and fans the delivery out to every registered `INormalizedVoiceEventHandler`; `TelephonyCallHistoryVoiceEventHandler` and `ContactCenterVoiceProjection` are peers on that stream. The gate is the single lock authority: `ProviderVoiceEventService` no longer takes its own distributed lock, and a projection that re-enters ingestion — including from the fresh shell scope opened by the `ConcurrencyException` retry — is satisfied re-entrantly instead of contending with the lease its own caller holds. The re-entrancy registry is deliberately established from a synchronous frame, because assigning an asynchronous-local value from inside an `async` method confines it to that method and reverts it on return, which made an earlier revision of this gate dead-lock against itself; `VoiceEventFanOutIntegrationTests` caught that and still fails if the assignment moves back into asynchronous code. The bridge chain survives, but narrowed to what it was always for: only internal call-control orchestration — answering and parking a first-seen inbound channel, or releasing a module-originated agent leg — may absorb an event before it reaches the normalized stream, and `ContactCenterFeatureDependencyArchitectureTests` now proves the Contact Center projection is owned by the Contact Center voice feature rather than by any single provider module, so no provider can reintroduce a consumer that starves its peers.

The W2.1 gate `D011` is `implemented`. Routing state — assignment status, reservation identity and expiry, assignee, and the dialer's attempt count — lived on the CRM `OmnichannelActivity` document, which meant the reservation loop had to write the same optimistic-concurrency document a person could be editing in the admin UI at the same moment. Two writers on one document produce a lost update, or a `ConcurrencyException` thrown at the routing commit; losing a reservation commit strands live work with a caller on the line. Those fields are now owned by a `ContactCenterWorkState` document keyed one-to-one to the activity by a unique index, every Contact Center writer mutates it through `IContactCenterWorkStateService`, and the CRM activity keeps the same fields only as a read model that `ContactCenterWorkStateActivityProjection` reconciles after the routing transaction has committed. The read model was retained rather than deleted because it is load-bearing outside routing: `OmnichannelActivityAuthorizationHandler` decides activity ownership from `AssignedToId`, and the CRM admin list, bulk-manage filters, and enterprise reports all query the same columns through `OmnichannelActivityIndex`; deleting them would either remove CRM function or invert the layering by making the CRM query a Contact Center store. The consequence is that the read model can lag, so the gate pins which of the two a routing decision must read. `ContactCenterWorkStateAuthorityTests` scans every Contact Center, Telephony, and provider source file for a write of any of the ten routing-owned fields onto a CRM activity, classifying the receiver rather than the member name — a queue item and a provider command both carry a `ReservationId` they legitimately own — and it self-tests that scan against the projector as a known-positive control, requiring all ten writes to be seen there, so a change that made the scan stop recognizing activities would fail rather than silently pass everything. Alongside the scan it proves the behaviour: a reservation running against a real SQLite database while the CRM holds an earlier read of the same activity commits without either writer conflicting and without either write being lost; a routing read returns the authoritative work state while the read model is deliberately stale; and work that predates the work state document adopts the projection instead of being reported as unassigned with no attempts, which is what stops an upgrade from re-offering work an agent already holds and resetting the dialer's attempt cap. Sabotage probing falsified each of these: dropping one field from the projector, making the read fall back to the activity, removing first-touch adoption, running the reconciliation inside the routing transaction rather than after it, blinding the scan's receiver classification, and reintroducing a routing-state write on the activity in both the reserve and the inbound-terminal path were each detected. Two deviations are recorded rather than hidden: `ActivityStatus` remains CRM-owned and is not extracted, and `AgentWorkspaceEndpoints` and `ContactCenterReportingService` still read the projected columns — the former only as a fallback beside the authoritative interaction agent, the latter in bulk reporting queries where reading per-activity work state would be a query-per-row.

The W2.2 gate `D012` is `implemented`. A live call was summarized by six scalars on `CallSession` — `MediaTopologyId`, `ConferenceId`, `SupervisorAgentId`, `SupervisorLegId`, a `ParticipantCount`, and an `IsConference` flag — none of which could answer who was on the call at a given moment, which party left and when, or whether an agent was consulting a third party while the customer waited. Four of those six were never written by any code path in the product; only the store's validation read them. The practical consequence was that supervisor monitoring had no durable state at all: an engagement fired a provider command, published an event, and left nothing behind, so nothing could tell a supervisor was listening, refuse a second engagement by the same supervisor, or release the right leg when one of two engagements stopped. The session now carries `Legs` with a role and a normalized lifecycle per leg, a `Bridge` whose participant list records a join and a leave time rather than being edited in place, `Consults`, `MonitorSessions`, and typed `Relationships` to other calls, and `CallTopologyProjector` is the only writer of any of it. Because the membership list is append-only, `Bridge.ParticipantsAt` reconstructs who was on the bridge at any past instant, which is what makes conference reporting and after-the-fact dispute review possible. A provider-reported participant count is carried separately from observed membership on purpose: a provider that publishes only a count cannot say who those parties are, and fabricating members to match the count would turn the membership history into fiction, so the count wins for display while membership stays factual. `EndLeg` distinguishes a leg that never answered from one that hung up, which is what lets abandon and no-answer reporting separate without borrowing provider vocabulary. `CallTopologyAuthorityTests` scans every Contact Center, Telephony, and provider source for a topology mutation outside the projector; it deliberately matches on member name rather than on an inferred receiver type, because an earlier receiver-typed version of this scan passed a sabotage probe that added `callSession.Legs.Add(...)` to a service whose session came from `var callSession = await manager.FindByInteractionIdAsync(...)` and therefore had no written type to recognize. Matching on the name is sound only while these names belong to one type, so a companion test pins that each is declared exactly once across the scanned projects and fails loudly if that stops being true. Alongside the scan the gate proves behaviour: membership is reconstructible at a past instant, leaving does not erase a participant, a consultative transfer is representable with no provider metadata strings, an ended consult ends its leg so none is left dangling, a relationship with no identifier is refused rather than recorded as an unwalkable edge, and monitor, whisper, and barge each have a live representation with barge alone joining the supervisor to the bridge. Sabotage probing falsified all of it: erasing the participant on leave, collapsing the leg end status, allowing duplicate relationship edges, accepting a relationship with no identifier, leaving a consult's leg open, reintroducing a `ConferenceId` scalar, blinding the scan's member matching, adding a topology write to a service outside the projector, and making a topology member name ambiguous by declaring it on a second type were each detected. One deviation is recorded rather than hidden: a provider that reports no leg identifier for a supervisor engagement still produces a `MonitorSession` with a null `ProviderLegId`, which records that the engagement exists but cannot place the supervisor on the bridge for a barge. A second review pass found that the first implementation ended only the leg the provider named on a hangup, which on the ordinary inbound path left the agent joined to the bridge of every completed call forever, because a terminal session accepts no further deliveries and nothing could repair it afterwards; every remaining leg is now ended and the bridge destroyed. It also found that a leg could be stamped with an end time behind its own start, because the two writers use different clock domains and terminal deliveries are deliberately exempt from the stream's timestamp guard, which made the store reject the session and fail the whole webhook delivery permanently, leaving the call connected and its agent occupied; the end time is now clamped as leaving and destroying already were. A monitor session now records the supervisor's user identifier and agent identifier separately, because only the user identifier is always present and mixing the two made the rule that a supervisor cannot monitor their own agent leg compare two different identity spaces and therefore never fire. A media move to a new provider bridge identifier retains the previous bridge rather than discarding it, so membership before the move is still reconstructible. The scan itself was hardened after the review demonstrated four ways past it — aliasing a topology member into a local, mutating an object reached through a member, seeding topology inside an object initializer, and calling a mutator absent from the listed set — so it now treats any expression rooted in a topology member as topology, flags aliasing and hand-off, and recognizes reads through an allow list, meaning an unfamiliar method counts as a mutation instead of being ignored. The scan also reports aliasing — iterating the collection, taking an element out of it, or assigning it to a local — but only when the alias is then written through, called with an unlisted member, or handed somewhere that could mutate it, following a hand-off one call deep into a same-file helper. Reads are deliberately not reported: the store's own validation iterates topology purely to check it, and a gate that flags read-only code is a gate that gets weakened. A companion case fails if a project that can reach the call session is missing from the scanned list, walking the whole project-reference closure rather than direct references, which is what caught the three host projects that reach the call session through the Contact Center module rather than through its core. One deviation is recorded: retaining the previous bridge when the parties are moved to different media is correct and tested but unreachable today, because no contract carries a provider media-topology identifier, so the retained-bridge list is always empty outside tests.

The W2.2 gate `D013` is `implemented`. Copying a provider voice event dropped the provider's `HangupCause`, and the loss was invisible because the call session infers a cause from its own state when none is supplied, so a plausible substitute always appeared in place of the value the provider actually reported. That copy is taken on the fan-out path, so the consumers that recorded a call's outcome saw an inferred cause and every downstream report of why calls ended was quietly wrong, with nothing anywhere to indicate a real cause had been discarded. The defect was not found by reading the copy, which looks complete: it was found because a test asserted a leg's hangup cause and got the inferred one. `ProviderVoiceEventCloneCompletenessTests` therefore does not check for `HangupCause` specifically. It reflects over every settable property the event type declares and parses the copy's object initializer, so the copy is proved complete against the type itself and any field added later fails the build until the copy carries it. Sabotage probing confirmed it detects a dropped field.
