The versioned machine-readable contract is `.github/contact-center/pr-test-control-matrix.v1.json`. It maps every P0 and P1 finding from the repository-tracked Contact Center plan's independent production-readiness review to one accountable gate. Release remains blocked until every P0 gate, and every P1 gate in scope for the release profile, passes with retained CI evidence.

Each gate resolves:

- A **category** with an owning DRI role and approver roles.
- A stable **test id** and a **CI job** (`implemented`, `partial`, or `planned`).
- The **provider, database, and topology** context the gate must be proven under.
- A **falsifiable invariant** - a concrete behavior that a test can prove true or false.
- A **retained evidence location** - an existing test/CI artifact path, or a `planned:` path that the owning remediation phase (R1-R8) must populate.

It is expected and acceptable for most CI jobs and evidence paths to be `planned` this early in the remediation program; every P0/P1 finding must still be represented so no gate can be silently dropped.

## Every status claim is bound to a real CI job

A gate status is only meaningful if the CI job it names actually exists. `LedgerEvidenceTests` parses the top-level `jobs:` mapping of every workflow in `.github/workflows` and enforces the binding in both directions:

- A gate marked `implemented` or `partial` must name a workflow and job that resolve, and its `additionalJobs` must resolve too.
- A gate marked `planned` must carry the `planned:` prefix on its workflow and must **not** resolve.

The second rule is what keeps the matrix honest over time. When an anticipated job finally lands, the `planned` gate that named it starts resolving, the test fails, and the matrix cannot stay stale - the status has to be upgraded to match reality.

Evidence is checked as well, not just status:

- With the default `"evidenceKind": "tests"`, the gate's `evidenceLocation` must cite at least one test class that exists in the repository, and every cited class that exists must live in a test project one of the gate's own CI jobs actually runs. A gate cannot borrow credibility from tests that never execute in it.
- With `"evidenceKind": "workflow"`, the cited workflow files must exist and one of them must declare the job the gate names.

The workflow parser is itself pinned against the known job set of eleven workflows, so a parser that silently returned nothing (making every `planned` gate trivially "unresolved") or returned every YAML key (making every enforced gate trivially "resolved") fails the build instead of passing vacuously.

## The gates themselves are gated

A control matrix can only describe gates that run. Four further checks in `LedgerEvidenceTests` keep the workflows behind the matrix trustworthy:

- **No orphaned suites.** Every project marked `<IsTestProject>true</IsTestProject>` under `tests/` must be executed by at least one workflow. The Telephony browser suite was orphaned in exactly this way and silently carried a failing test until it was adopted by `contact_center_browser_gates.yml`.
- **Nothing ships untested.** Every test project must also run in `release_ci.yml`, which is the last gate before packages are published.
- **Gates watch the whole tree.** The Contact Center gate workflows must filter on `src/**` and `tests/**`. They previously listed individual module folders, so a change to a shared Core project skipped the very gate that proved it.
- **Failures cannot be swallowed.** Any workflow step piping a command into `tee` must set `pipefail` or inspect `PIPESTATUS`; otherwise the step reports the exit status of `tee` and a failing build passes. Comment lines are stripped before this check, so a comment mentioning `pipefail` cannot satisfy it.

A gate is also only as good as the tests it runs. A test that reads production source as text, or that asserts a value it stubbed itself, satisfies a gate without proving anything, so the Contact Center suites that behaved that way were rebuilt to invoke the code they describe:

- `ContactCenterHubSecurityTests` constructs the real `ContactCenterHub` and invokes `OnConnectedAsync`, rather than searching `ContactCenterHub.cs` for substrings in the expected order.
- `ContactCenterMigrationSqlTests` runs the migration SQL builder against the four real YesSql dialects and executes the generated statement on a live SQLite database, rather than asserting a string shaped by its own `Mock<ISqlDialect>`. The mock had encoded quoting and index-prefix rules that no supported engine actually uses.
- `ActivityQueueServiceConcurrencyTests` races eight workers against one activity on a real store and proves a single queue claim survives, rather than making one call against one stub.
- `ContactCenterOperationalLogPrivacyTests` parses every logging call in the guarded trees with Roslyn instead of pinning twenty exact source strings, so the redaction rule applies to code written after the audit.

Governance suites that validate the shape of a JSON document are retained as schema guards, but they are not counted as behavioural coverage for any control.

## Ledger authority

Exactly one Contact Center plan document may be release-authoritative. Each Markdown ledger in `.github/contact-center` declares itself with a machine-readable marker:

- `<!-- ledger-authority: release-authoritative -->` - the current release ledger. Every item it marks `[x]` or `[~]` must carry a `` `gate:<workflow>.yml#<job>` `` annotation naming a CI job that resolves, and every item still open must **not** claim an enforcing job.
- `<!-- ledger-authority: historical -->` - retained for architecture and completed history, but not used for release scoping.

`LedgerEvidenceTests` fails the build if no document claims authority, if more than one does, or if any document declares both or neither.

## Current gate count

The matrix currently tracks 64 gates across every P0/P1 finding in the 2026-07-13 independent production-readiness review, plus the gates added by later accepted amendments: `C001`-`C008` (correctness), `D001`-`D018` (data), `F001`-`F010` (feature/package graph), `O001`-`O009` (operations), `S001`-`S006` (security), `T001`-`T003` (test/topology), and `V001`-`V010` (voice/provider).

A handful of gates already have `implemented` or `partial` evidence because the underlying remediation shipped ahead of this matrix (tenant-qualified real-time identity, manager-owned queue/campaign entitlements, development-host containment, Asterisk credential-log redaction, centralized operational PII redaction, webhook body limits, the declared recording/monitoring prohibitions in the support matrix, and the static feature-dependency architecture ledger). Every other gate remains `planned` until its owning remediation phase (R1-R8) lands the behavior and its automated evidence.

The S001 in-process R0a proof now runs two active shell identities through the same hub context and verifies that user and supervisor notifications resolve to different tenant-qualified destinations. A separate R0b production-backplane run is still required before multi-node isolation is approved.

The F001, F002, and T001 in-process proof, `ContactCenterFeatureDependencyArchitectureTests`, statically parses the Contact Center, SignalR, Telephony, and Omnichannel Managements manifests plus every Contact Center `StartupBase` class and checks them against the machine-readable ledger `.github/contact-center/feature-dependency-violations.v1.json`. R2 has removed FDV001 through FDV003: the base feature now depends only on headless Omnichannel infrastructure with a separate Administration feature; server-side Voice depends on provider-agnostic Telephony; and `Voice.SoftPhone` exclusively owns the soft-phone display driver, resources, endpoints, and call-state projection under declared RealTime, Voice, and Telephony Soft Phone dependencies. For recognized generic registrations the proof resolves constructor dependencies against both manifest and `[RequireFeatures]` closures and now enforces zero known feature-dependency violations. This is a static dependency-closure characterization only; factory/non-generic registrations and the runtime proof that every legal feature combination actually enables, migrates, and resolves every service on a live Orchard tenant remain `planned:contact-center-feature-activation-matrix` dependencies.

The F008 proof, `ContactCenterHeadlessClosureTests`, is the runtime half of that argument and closes the gap the F001 narrative above records as planned. Screens are no longer part of a capability: each capability feature registers services only, and the screens it used to register live in a separate `.Admin` feature that depends on the capability rather than the other way round, so enabling a capability can never pull a user interface in. The split crosses module boundaries for the same reason - the Omnichannel management module is now a headless `CrestApps.OrchardCore.Omnichannel.Activities` feature that the Contact Center base depends on plus the administration experience on top of it, and the Telephony provider settings screen is separated from the telephony services - because a capability that transitively drags an administration module in is no more headless than one that registers the screens itself. Routes are surface as much as services are - moving a screen's driver without the controller that consumes it leaves the route registered and authorized while the display pipeline that binds and validates its form no longer resolves, so the write path silently persists whatever the empty editor produced - and the sweep covers both. The oracle is structural: one tenant boots the whole headless closure and every navigation provider, display driver, and routed administration controller the tenant can resolve is enumerated by reflection, so a screen added to a capability feature later fails the gate without anyone remembering to extend the test. The features excluded from that closure are the ones that exist to serve a user interface, and each must prove it serves one, so the closure cannot be weakened by moving a headless feature onto the exclusion list. A feature must contribute surface of its own rather than inherit it: its declared dependency closure is booted with the feature withheld and that surface subtracted, because every administration feature depends on the administration root and would otherwise satisfy the requirement on the root's screens alone. That is what keeps `CrestApps.OrchardCore.ContactCenter.Admin` from being an empty marker that silently does nothing when enabled.

The F009 proof extends that separation from screens to figures. A report only measures data some capability writes, so a reporting feature that pulled its producing capabilities in would recreate the coupling F008 removed - a tenant running chat and CRM only would have to run, secure and upgrade voice call handling to read a queue report. Analytics therefore depends on neither `Voice` nor `Recording`, and the reports those capabilities feed state the requirement instead of publishing a number. Zero is a measurement; an absent capability took none, and "recording coverage: 0%" read by a compliance officer on a tenant that never had recording is a false operational statement rather than an empty result. Degradation is at the granularity of the claim, not the report. A report whose whole subject belongs to an absent capability returns the notice; a report whose primary figures are real - the executive dashboard, interaction and exception detail, agent volume and outcome, and the queue, agent, channel and daily usage reports - keeps running and drops only the columns and metrics that capability could fill, because withholding a queue usage report over a "Recordings" column would hide real work, while rendering that column as a structural zero states that no calls were recorded. Every Contact Center report is required to declare which capabilities produce its data, not only the ones that currently need to, so a new report cannot be added without that decision being made. `ContactCenterReportCapabilityDegradationTests` proves both halves in a live analytics-only tenant, because a report registered without the guard or a guard registered in the wrong feature still compiles and still returns zeroes; a fourth assertion runs every report and fails if any column, metric or bar heading belongs to an absent capability, which is what covers the mixed reports the whole-report guard deliberately does not withhold. Each assertion fails as vacuous if no report was degraded or every capability was present, so emptying the requirement map or re-coupling analytics to telephony cannot make it pass quietly. `ContactCenterReportDataProvenanceArchitectureTests` proves the converse: for every persisted field a report reads, some production source outside the reports must write it. That is the only oracle that separates an empty measurement from a field nothing has ever populated, and it is what identified two reports - call-leg performance reading `Interaction.CallLegs`, and transcript coverage reading `Interaction.TranscriptReference` - that rendered a confident empty table and a confident 0% on every tenant because no code path had ever assigned either member. Call-leg performance now reads the legs the voice topology projector maintains on the call session, and transcript coverage was withdrawn with the field it invented.

The F010 proof asks a different question of the same feature graph: not whether a tenant can run a capability, but whether a tenant can be reproduced. Every entity an operator configures - skills, queue groups, business hours calendars, queues, entry points, dialer profiles and agent state reason codes, together with the CRM dispositions, channel endpoints, campaign groups, campaigns, subject flows and subject actions the contact centre routes and reports on - is exported by a deployment step and imported by a recipe step, so a contact centre can be built in a staging tenant, reviewed as a diff in source control, and replayed into production instead of being rebuilt by hand under a cutover window. The failure being guarded against is silent rather than loud. A step that hand-lists the properties it carries keeps compiling and keeps succeeding after a property is added to the entity it exports; the import reports no error and the missing settings simply read as their defaults, so the loss surfaces as a misrouted call in production rather than as a red build. Export and import are therefore driven by reflection over the entry type, and the oracle is anchored to the stored entities rather than to a second export - comparing one export against another is satisfied by a step that drops the same property on both sides, which is exactly the defect in question. What a plan must not carry matters as much as what it must. Agent profiles were withdrawn from configuration during review: a profile names the person who holds it, carries their contact details, and records the state that person is in right now, so exporting one moves a person and their live presence between environments. It is declared runtime state instead, and the coverage gate holds that declaration to the same standard as any other. `ContactCenterConfigurationPortabilityTests` seeds a live tenant with an entry per catalog whose every writable member is set away from its default, exports a plan, replays it into a second live tenant, and then reads both tenants through the managers that own the entries and compares them member by member. It also proves the properties that make a plan usable more than once: entries are exported in dependency order, because a queue that references a skill cannot be imported before it, and they are reconciled by identifier and then by the name or display text that identifies them, so replaying a plan into a tenant whose own migrations already seeded the same reason codes updates them rather than duplicating them. A plan is only reproducible if identity survives it. Configuration refers to configuration by identifier - a queue names its queue group, an entry point names its queue, a subject action names the disposition that triggers it - so an import that minted fresh identifiers would land every cross-reference on the destination pointing at an entry that does not exist, and the test asserts that every identifier the plan exports is present afterwards. Reconciling by name reopens the same wound from the other side: when both environments created the same queue group independently the destination keeps the identifier it had already published, and the rest of the plan still names the source's. The import therefore records every substitution it makes and carries it into the steps that follow, and a live-tenant case proves it by importing into a tenant that already owns the group and asserting the imported queues point at the identifier that tenant holds. Further cases cover the rest of what an operator would call synchronised: an entry identified by display text rather than a name is reconciled with the copy the tenant already had, configuration that carries neither a name nor a display text anything ever fills in - subject flow settings, identified by the subject they configure - is reconciled rather than duplicated, and a setting cleared at the source is cleared at the destination rather than omitted from the plan and silently retained. Configuration is a graph and a plan is a sequence, so ordering alone cannot make every reference resolvable when it is written: a queue overflows into another queue in its own step and references a channel endpoint that a different deployment step carries. Substitutions are therefore applied to the entries already stored as well as to the entries still to come, and two cases prove it by importing a plan whose Contact Center step is placed first and asserting that both references land on the entries the destination holds. `ConfigurationCatalogTests` drives the shared catalog directly for the rules a live tenant cannot easily stage - a value the owning manager derives is not overwritten by the plan's raw value, an entry the manager rejects is reported without being stored, an entry that cannot be built is reported without stopping the entries around it, and a hand-written plan that invents its own identifiers - `"support-queue"` rather than a store-issued one - has them translated wherever it used them. Reconciling by name is only safe if each entry the destination already owned is claimed once, because nothing in the product stops an operator from keeping two queues named "Support" or several subject actions on one disposition; a case proves that two entries sharing a name both arrive rather than the second overwriting the first. A step that names no collection the tenant recognises - a hand-written plan with a mistyped collection - is reported rather than passed over as a success, and a step that spells its collection in another case is still imported, because the recipe engine binds its own steps without regard to case. `ContactCenterConfigurationCoverageTests` and `OmnichannelConfigurationCoverageTests` close the set: every stored entity in the Contact Center and Omnichannel core assemblies is either declared as configuration carried by a named step or declared in writing as runtime state that must not travel between environments, with a discovery floor so reflection returning nothing cannot pass quietly.

R4 splits `IContactCenterVoiceProvider` metadata from executable call-control, queue/assignment, transfer, conference, recording, monitoring, and media contracts. Asterisk and DialPad advertise only dialer dialing on their base adapters, outbound routing and server-side bridge staging require the call-control contract, and separately feature-gated media is discovered from its executable registration rather than a capability owned by the base adapter. The last disconnect and a stale heartbeat are immediately ineligible even when the administrative profile still says `Available`. The D004 R0a shared-database characterization runs two independent service providers and YesSql sessions against one SQLite database. The W8.5 gate `O008` is `implemented`. A tenant that piloted the preview can export every Contact Center document, quiesce all enabled features, reset either operational data or all data, and verify the result, and the destructive step is coupled to the recoverable one rather than merely documented after it: the export returns a receipt derived from live per-data-set counts, and reset recomputes that receipt and refuses a stale one, so a tenant still admitting work invalidates its own receipt and can never satisfy the guard. Reset additionally refuses by default, outside development, on a confirmation token that does not match the tenant, and while any enabled feature is still admitting work. `ContactCenterPreviewMaintenanceCompletenessTests` compares the data-set registry against the persisted document types discovered by reflection, with a floor so it cannot pass vacuously, so a new entity cannot escape both export and reset. `ContactCenterPreviewMaintenanceTests` exercises the cycle against a real YesSql SQLite store and pins every refusal path, the configuration-preserving operational scope, and staleness after a late write. `ContactCenterPreviewMaintenanceActivationTests` repeats the cycle inside a real Orchard tenant so the container registration, options binding, and lifecycle participants are proven rather than assumed.

The W15.3 gate `O009` is `implemented`. The additive-migration gate reads migrations statically and rejects a destructive operation, which is necessary but not sufficient: adding a non-nullable column with no default is entirely additive, passes that gate, and still breaks every write a still-running previous version performs. `ContactCenterRollingUpgradeTests` therefore builds two real SQLite databases from the shipped migrations. One takes the fresh-installation path, which is the create step followed by every update step Orchard still applies afterwards. The other is installed at the previous schema version and then upgraded. A previous-version writer and a current-version writer both insert into the upgraded tables and the previous version's projection is read back, so a column that a previous-version node cannot supply is caught as a failed write rather than as a passing static check. A further assertion compares every column definition and every unique constraint between the two databases, because a fresh installation and an upgraded installation of the same version must not be distinguishable. Discovery floors and a strict-subset assertion stop the suite passing vacuously. This gate found and forced the correction of a real divergence: the reservation and queue-item claim keys were declared with an inline unique constraint and no default on the create path but with a named unique index and an empty-string default on the upgrade path, so the same release produced two different schemas.

## Contract tests

`ContactCenterPrTestControlMatrixTests` in `tests/CrestApps.OrchardCore.Tests/Modules/ContactCenter` fails the build if:

- The matrix does not contain exactly 53 gates, or the per-category gate counts drift from the table above.
- Any gate id is duplicated, or any of the 41 current P0/P1 gate ids is missing, has the wrong severity, or has drifted from its authoritative title in the production-readiness review.
- A gate's category has no DRI role or no approver roles.
- A gate's execution context omits providers, databases, or topologies.
- A gate has no plan-finding citation, title, falsifiable invariant, test id, CI job id/workflow, or retained evidence location.
- No P0 gate has at least `partial` CI enforcement, which would indicate the remediation program has not started closing any commercial release blocker.

`ContactCenterFeatureDependencyArchitectureTests` in the same folder fails the build if:

- A Contact Center feature's manifest declares a new, unrecorded dependency on a feature outside the Contact Center family, or the ledger records a manifest dependency that no longer exists.
- A recognized Contact Center `StartupBase` registration requires a service not guaranteed by its manifest or `[RequireFeatures]` transitive closure, and that finding is not already recorded in the ledger, or the ledger records a finding that no longer reproduces.
- A ledger violation references a control-matrix gate id that does not exist.
- A Contact Center feature's transitive manifest-dependency closure reaches an unresolvable dependency, cycles back to the feature itself, or drifts from the pinned closure recorded in the ledger.

The W5.4 gate `V005` is `implemented`. Before it, every Asterisk test asserted against a `TestAriClient` stub declared in the same file, so the suite could only prove the code agreed with itself; nothing tied it to the protocol Asterisk actually speaks. The Asterisk project publishes its REST Interface as machine-readable Swagger declarations per release, so those declarations are now vendored verbatim under `tests/CrestApps.OrchardCore.Tests/Telephony/Cassettes/Asterisk`, in a directory named for the release, behind a provenance manifest that records the upstream repository, ref, URL, and SHA-256 of every file, plus the container image tag and digest the single-node profile is pinned to. `AsteriskAriContractProvenanceTests` recomputes those hashes and requires the vendored release to equal the release parsed out of the Asterisk `Dockerfile`, and requires exactly one vendored release directory to exist, so bumping Asterisk fails the build until the declarations are refreshed. `AsteriskAriEventContractTests` scans the production mapper for the event types it interprets and requires the contract manifest and the recorded event payloads to cover exactly that set, requires every property path the mapper depends on to resolve against the vendored declarations, requires every recorded payload to contain only fields those declarations permit, and requires each compatibility fallback the mapper merely tolerates to stay absent from them, so a field Asterisk later adopts must be promoted rather than left as a guess. `AsteriskAriRestContractTests` drives the real `AsteriskAriClient` over recorded responses, exercises every method the interface publishes, and requires every issued request to match an operation the vendored declarations declare with only query parameters that release accepts. DialPad publishes no vendorable schema, so `DialPadWebhookContractTests` binds that provider to recorded deliveries instead: it scans the normalizer's own token switches and requires the recorded state tables to name exactly the call-state, recording-state, and answer-classification tokens the production code interprets, then replays every recorded delivery through the signed JWT ingress, the production deserializer, and the production normalizer. These gates found and forced the correction of two real defects. The mapper read channel variables from four locations, none of which was `Channel.channelvars`, the only location a conforming Asterisk release populates, so the interaction correlation identifier could never be recovered from a channel object. Recording duration was read from `StoredRecording`, which Asterisk declares with only a name and a format, so every completed recording reported no duration; the client now reads the live recording, where the duration is declared, before stopping it.

The W5.6 gate `V006` is `implemented`. `V005` binds the providers to the protocol they speak, but a conforming payload still has to survive the way a provider actually delivers it. Provider nodes do not share a clock, do not sequence every event type, retry aggressively, and can report a call terminated more than once, so the example-based tests that preceded this gate only ever proved the state machine handled the orderly case. `CallStateMachinePropertyTests` replaces that with eight properties, each run over 400 seeded adversarial delivery sequences, driving the production `ProviderVoiceEventService` and the production `DefaultContactCenterEventPublisher`. A generator emits a real call lifecycle, then corrupts its delivery with duplicates, whole-stream replays, arbitrary reordering, clock skew wider than the spacing between events, streams where most events carry no sequence number, late backward state regressions stamped with the freshest timestamp and highest sequence, and competing terminal reports that disagree about how the call ended. The properties require the session to converge to one terminal state regardless of delivery order, never to regress its lifecycle rank, never to resurrect a terminated call, never to strand a call the provider reported terminated, never to publish a lifecycle domain event twice, and never to leave live-only flags such as mute set on a terminated call; a companion property asserts anti-vacuity floors so the generator cannot silently stop producing the hard cases. These properties found and forced the correction of two real defects. A terminal delivery carrying a stale mute flag re-applied it after the terminal normalization had cleared it, publishing a mute event for a call that had already ended. More seriously, the staleness guards were applied to terminal deliveries, so a hangup stamped fractionally behind the preceding state change, or arriving without a sequence number, was silently discarded: the session stayed live forever, `CallEnded` was never published, wrap-up never started, and the agent and their reservation were never released. Sabotage probing also established that the service-level and publisher-level duplicate suppression are individually redundant and only observable when both are removed, which is recorded rather than papered over.

The W1.5 gate `D010` is `implemented`. The Contact Center stores were hardened against lost updates long before this, but the surviving Telephony interaction store was not: it saved without an optimistic-concurrency check, so the last writer to commit simply overwrote whatever the previous one had persisted. That store is written from three directions at once — real-time provider events, the periodic reconciliation pass that asks the provider for authoritative call state, and inbound-call dispatch — and all three read the interaction, mutated the copy they were holding, and saved it, which is precisely the shape that loses work. The W2.1 gate `D011` is `implemented`. Routing state — assignment status, reservation identity and expiry, assignee, and the dialer's attempt count — lived on the CRM `OmnichannelActivity` document, which meant the reservation loop had to write the same optimistic-concurrency document a person could be editing in the admin UI at the same moment. A live call was summarized by six scalars on `CallSession` — `MediaTopologyId`, `ConferenceId`, `SupervisorAgentId`, `SupervisorLegId`, a `ParticipantCount`, and an `IsConference` flag — none of which could answer who was on the call at a given moment, which party left and when, or whether an agent was consulting a third party while the customer waited. The W10.2 gate `D017` is `implemented`. The W10.1 gate `D018` is `implemented`. The five aggregates that carry Contact Center state - the interaction, the call session, the queue item, the reservation, and the routing work state - were plain property bags. Every status was publicly settable, so the question "can this call move from planned to held" was answered separately by the ingestion service, the command executors, the healing service, and the router, and nothing required those answers to agree. The one ordering rule that did exist grouped call states into five lifecycle phases, which cannot tell an illegal edge from a legal one inside a phase: a call moving from planned to held does not regress, so the phase check admitted it, and the record then said the call was on hold without ever having been answered. Every talk time, hold time, and wallboard figure computed from that record reported the fiction as real, and no error was raised anywhere, because from each writer's point of view it had simply set a property.

The fix moves the answer into the aggregate, where there is one of it. Each aggregate's status has a private setter and a `TransitionTo` that consults a single declared edge table; a move no edge admits throws with the aggregate, the status it is in, and the status it was asked to reach, rather than being recorded. Settled statuses have no outgoing edge, because an ended call that starts ringing again is two calls merged into one history and a completed queue item that re-enters the queue is work handed to a second agent after the first already did it. Re-applying the status a record already holds is admitted, so at-least-once redelivery is not turned into an error. The operations that used to be spelled out at each call site now say what they mean: `Requeue` returns an interaction to routing and drops the agent it was offered to, and `Reoffer` moves it back to alerting for the next agent. Both move along declared backwards edges rather than around the table, so both are refused once the session has settled for the same reason everything else is - a settled status has nowhere to go. Declaring those edges also fixed a real break: a queue transfer keeps the customer connected while the agent leg alerts the next agent, so an interaction has to be able to reach alerting again from every live status, and a call session has to be able to alert again while connected or held.

Three operations deliberately report rather than decide, and they say so in the name of the operation they use. A provider-backed call session mirrors what the provider says the call is doing, and the interaction projected from that session mirrors the session, because the provider owns those facts and ordering for the stream is already enforced upstream; applying a second, narrower rule there made the session and the interaction disagree, which the pre-existing property test caught immediately. A work state seeded from the activity it projects adopts that activity's routing status, because seeding has no previous status to move from. These three do not consult the table, so the honest statement of what this gate enforces is: the table governs every path where this system decides the next status, and does not govern the three that report a fact decided elsewhere. Two things keep that exception from becoming a hole. Mirroring refuses to bring a settled record back to life, because a record can settle on a path the provider stream never sees - an offer released after the customer abandoned - and a late frame that reopened it would put a finished conversation back into an agent's live work. And a structural scan pins the two files and four call sites allowed to use these operations, so a fourth caller reaching for one to skip a refusal fails the build.

The gate is structural as well as behavioural. The complete N x N matrix of all five lifecycles is walked against a transliteration of each table written in a different shape. That is a drift alarm, not a proof of correctness: it catches an edge changed in one place and not the other, but an edge that is wrong in both would satisfy it. The claims that do not depend on the transliteration are asserted separately, derived from the enums and the settled predicates rather than from the edge lists - that no settled interaction status and no terminal call state has any outgoing edge, that every unsettled interaction status can still reach an ending so nothing can be stranded alive, and that a planned call is refused the established and unanswered outcomes that imply it was answered, which is the specific reading this gate exists to reject. Reflection asserts that no guarded status carries a public setter, and every aggregate is round-tripped through `System.Text.Json`, because a private setter without an explicit include is dropped silently on deserialize and every persisted aggregate would come back holding the enum's default - which reads as a created interaction, a planned call, and a waiting queue item, so live work would look like new work. The test-only seam that arranges a state directly is refused to production code by a scan that fails closed if a guarded root or a named file it claims to cover no longer exists. Sabotage probing introduced seventeen mutations across two rounds - reopening a setter, dropping the serialization include, widening a table, giving a settled status a way out, making the transition check return true unconditionally, calling the restore seam from production code, silently narrowing the guarded roots, dropping the settled guard from the expiry sweep and from the failure projections, removing the mirror resurrection guards, re-admitting planned to held, removing the re-offer edge, stranding a status with no ending, and adding a fifth bypass call site - and all seventeen were caught.

A refusal is only correct where the caller can act on it, and two paths could not. The expiry sweep releases every due reservation in the tenant from a background task whose per-queue `try`/`catch` does not cover the sweep, so a refusal raised because the customer hung up while the offer was ringing - an ordinary race - would abandon every later reservation in the batch and do so again on every tick. The failure projections in the provider-command executors are what let a compensating command finish, and a refusal there would leave the command compensating forever with the exception swallowed by the dispatcher. Both now skip the status change on an already-settled record and complete the rest of their work, and both are covered by tests that drive the real path.

Two limits are worth stating plainly. `AgentSession` was surveyed and left alone: it records connections and heartbeats and carries no status enum, so there is no lifecycle to declare, and inventing one would have added ceremony without a rule. And closing the status setters is not the same as closing every setter; the remaining properties on these aggregates are still publicly settable, so this gate constrains what a status may become, not who may write the rest of the record.
