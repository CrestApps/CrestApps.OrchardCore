# 10 - Backward review: from the complete framework to the Orchard Core implementation

This review starts from the finished framework and asks, for every contract, default, and registration the framework exposes: what does Orchard Core bind, where, and which test proves the binding behaves like today. It is the counterpart of [08](08-mvc-consumer-walkthrough.md) (which starts from an MVC consumer). Anything with an empty "Orchard binding" cell is a plan gap; there are none left after this pass, but the table must be re-checked at the end of Phase 0 and Phase 1.

## 2. Framework services Orchard must never register

`AddYesSqlDataStore`/`AddCoreYesSqlDataStore`, `AddBackgroundWorkers()` (hosted runners), `AfterCommitStoreCommitter`, the store-committer MVC/endpoint/hub filters, `AddContacts()`/`AddSubjects()` (default CRM model), `ContactPreferenceDoNotCallRegistry`, `PhoneNumberContactTimeZoneResolver`, `SingleTenantAccessor`, `LocalDistributedLockProvider`, `ClaimsUserDirectory`, `DefaultContactCenterScopeExecutor`, `StartupCheckHostedService`, `SchemaMigrationRunner`, `MapSoftPhoneExtensionPage` (Orchard has its own page). An architecture test in `tests/CrestApps.OrchardCore.Tests/Architecture` asserts none of these types appear in a tenant container for any feature profile.

## 3. Orchard-only concerns the framework must never know

Feature ids and manifests, `Permission` objects and providers, admin menus, display drivers and shapes, `ISiteService` documents, `ShellScope`/`ShellSettings`, `IBackgroundTask`, `DataMigration`, recipes/deployment/workflows/audit trail, content types/parts/items, Orchard resource manifests, `OrchardCore.Sms`/`OrchardCore.Redis`/`OrchardCore.FileStorage`, `IModularTenantEvents`, `CrestApps.OrchardCore.Users` pickers, the TimeZones map module, Content Transfer.

## 4. Cross-cutting compatibility checks (verify in Phase 0, re-verify in Phase 1)

1. **Hub paths and group names are byte-identical** (`SignalRHubRoutes.GetHubPath<T>()` and `TenantSignalRGroupName`), because the shipped scripts and the browser extension hard-code them.
2. **Endpoint routes are identical**, including antiforgery behaviour and authorization filters.
3. **`IIndexProvider` registration style** matches Orchard's `AddIndexProvider<T>()` (singleton, non-`TryAddEnumerable` duplicates are harmless but ordering-sensitive registrations must not change).
4. **YesSql collections and index table names** unchanged; framework default-model indexes use distinct table names so they never collide with the Orchard content indexes.
5. **JSON shapes** of every stored document identical (serialization snapshot tests for `Interaction`, `TelephonyInteraction`, `OmnichannelMessage`, `OmnichannelActivity`, `SmsConversation`, `AgentProfile`, `QueueItem`, `CallSession`, `TelnyxAgentCredential`).
6. **Data protection purposes** (recording encryption, Telnyx credential protection, Twilio token, secure capture tokens) unchanged.
7. **Options section names** unchanged (`CrestApps:ContactCenter:*`, `CrestApps:Sms:Workspace`, `CrestApps:Sms:Portal:KeywordReplies`, `CrestApps:Omnichannel:Automation`, `OrchardCore_Sms_Telnyx`).
8. **Background schedules** unchanged (`[BackgroundTask(Schedule = ...)]` on wrappers).
9. **Service lifetimes** unchanged (DI snapshot, P0.13).
10. **Localization**: framework strings use `IStringLocalizer<T>`; Orchard's `.po` files key on the string, not the type, so moving types does not break translations; verify one localized string end to end.
11. **`ExtensibleEntityJsonOptionsInitializer`** (hosted service registered by `AddCrestAppsCore`) already runs in Orchard through the AI module; the suite must not register it twice (`TryAddEnumerable`).
12. **Assembly-scanning behaviours** (`AddTemplatesFromAssembly`, embedded prompt templates in `Omnichannel.Sms`) keep working after the assembly changes name; test by resolving the template by id.
