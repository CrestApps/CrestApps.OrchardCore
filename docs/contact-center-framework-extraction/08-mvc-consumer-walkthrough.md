# 08 - Backward walkthrough: can a plain MVC application run the whole contact center?

This document walks the plan backward from the consumer that matters most: an ASP.NET Core MVC application that references only `CrestApps.Core.*` packages, knows nothing about Orchard Core, and must be able to install, configure, operate, and upgrade a full contact center. Every step names the framework piece that serves it, its status in the plan, and what the host itself must supply. Gaps found by this walk were folded back into the other documents; the "Plan change" column says where.

Reading rule: the Orchard Core modules are one implementation of the framework. Anything the MVC host needs that Orchard gets "for free" from Orchard services must exist in the framework as a default (or an explicit opt-in package), and Orchard overrides it.

## 2. Gaps found and how the plan was changed

| Gap | Finding | Plan change |
| --- | --- | --- |
| G1 | The AI sample initializes schema with a hand-written list of `Create*IndexSchemaAsync` calls and has no versioned upgrade path; Orchard has versioned `DataMigration`s. A standalone contact center cannot be upgraded that way | Store package gains `Migrations/ISchemaMigration` (versioned steps `Create`, `UpdateFrom1..N`) per feature, a `SchemaMigrationRunner` with a `SchemaVersion` document, and `RunContactCenterSuiteSchemaMigrationsAsync(IServiceProvider)`. Existing Orchard `*Migrations` bodies become the framework steps (same version numbers); the Orchard classes delegate to them. W0 scaffolds the runner, W3 is the first user |
| G3 | Dialer compliance requires `INationalDoNotCallRegistry`; only Orchard modules implement it | Framework default registry over contact preferences with a fail-closed option; optional `CrestApps.Core.Omnichannel.Compliance.DncRegistry` package (local list + national importers) as a Phase 2 follow-up; Orchard keeps its modules |
| G4 | Contact time-zone detection depends on the Orchard TimeZones module and a content handler | `IContactTimeZoneResolver` (S22) with a libphonenumber-based default and an optional `TimeZoneMap` catalog; the framework contact handler calls it when `AutoDetectTimeZone` is on; Orchard's handler keeps using its map |
| G5 | Scripts get hub/endpoint URLs from Orchard resource configurations and view models | Framework client-configuration models and providers (S23) |
| G6 | The Telnyx browser SDK bundle is vendored in `CrestApps.OrchardCore.Resources`, not in the Telephony assets | `CrestApps.ContactCenter.Resources` vendors the same esbuild bundle (`vendors/telnyx-webrtc`), W10 |
| G7 | Recording playback and voicemail greeting upload are controller-only in Orchard | `MapContactCenterVoiceMediaEndpoints` added to the endpoint list |
| G9 | Multi-node hosting relies on `OrchardCore.Redis` | documented; `CrestApps.Core.Redis` follow-up (lock provider, rendezvous owner store) after Phase 2 |
| G11 | No contact import outside Orchard Content Transfer | optional Phase 3 sample import; framework importer later |
| G14 | Agent sign-out on logout is an Orchard cookie configuration | `IAgentSignOutHandler` (S21) |
| S9 | `UserManager<IUser>` is used 31 times; the first `IUserDirectory` draft was too small | W1 derives the contract from those usages (lookup by id/name, batch get, search, roles, enabled flag) before any code moves |

## 3. Verdict

With G1, G3, G4, G5, G6, G7, and G14 folded in, an MVC application can install, configure, run, and upgrade the contact center (voice, routing, dialer, recording, supervision, SMS portal with Telnyx or Twilio, CRM data, automation) with no Orchard Core dependency. Phase 3 delivers the sample screens including provider configuration; Phase 4 delivers reports, national DNC registries, Redis infrastructure, Azure integrations, the time-zone map, and contact import. Workflows, recipes, deployments, audit trail, content transfer, widgets, email/other channels, and phone verification stay Orchard-only (D-18). Orchard Core remains a full implementation of the framework: it never registers the framework's default CRM model, DNC registry, time-zone resolver, user directory, lock provider, tenant accessor, scope executor, or SMS provider resolver, and binds each contract to its own services instead.
