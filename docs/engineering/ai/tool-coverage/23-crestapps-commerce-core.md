# CrestApps: commerce core

Part of the [AI tool coverage plan](README.md). Nothing in this file is built yet. The design rules, the permission and approval model and the test plan that apply to every tool below are in [01-foundation.md](01-foundation.md) and [03-testing.md](03-testing.md); the final agent roster is in [02-agents.md](02-agents.md) and wins over the agent notes in this file.

Scope: the 21 back-office commerce modules under `src/Modules/` — Products (+ Products.AzureAI, Products.Elasticsearch, Products.Lucene), Inventory, Carts, Checkout, Orders, Commerce, Commerce.StoreProfile, Commerce.Webhooks, Markets, Taxation, Shipping, Fulfillment, Fulfillment.Printify, Stripe, PayLater, Transactions, Receipts, PointOfSale — with their shared code in `src/Core/*` and `src/Abstractions/*`. Everything below was read from code (manifests, admin menus, controllers, settings drivers, permission classes, recipe steps, core services); the user manual under `src/CrestApps.Docs/docs/user-manual/commerce/` was used only to cross-check. The two plans (`docs/ecommerce-plan.md`, `docs/commerce-suite-review-and-plan.md`) say nothing about admin AI tools.

Findings that apply to the whole group:

- **No AI tools exist in any of these modules today.** `AddCoreAITool` is not called in any of them. The five customer-facing shopping tools in `CrestApps.OrchardCore.AgenticCommerce` (`searchStoreProducts`, `getStoreProduct`, `startStoreCheckout`, `addToStoreCart`, `getStoreCart`) are a different audience and are left alone; every tool below is a merchant tool and is new.
- **What is a content item and what is its own store.** Content items (reachable through the generic content tools): products and product listing pages (any content type carrying `ProductPart` / `ProductListingPart`, with `ProductPricePart`, `ProductVariantsPart`, `ProductBundlePart`, `ProductGroupPart`, `ProductRecommendationsPart`, `ProductFeedPart`, `InventoryPart`, `ShippingPart`, `TaxationPart`, `ProductMarketsPart`, `GiftCardPart`). Own stores (not reachable through content tools): orders (`IOrderStore`), order returns (`IOrderReturnStore`), gift cards (`IGiftCardStore`), coupons and generated codes (`ICouponStore`), stock items / movements / reservations / locations (`IStockItemStore`, `IStockMovementStore`, `ICatalog<StockLocation>`), purchase orders (`IPurchaseOrderStore`), shipments (`IShipmentStore`), shipping zones with their methods (`INamedCatalog<ShippingZone>`), currencies (`INamedCatalog<CurrencyEntry>`), markets (`IMarketStore`), tax categories / types / jurisdictions / rules / tables (named catalogs), transactions (`ITransactionManager`), payment attempts, refunds and payment issues (`IPaymentAttemptStore`, `IPaymentRefundStore`, `IPaymentIssueStore`), registers, POS departments and shifts (Point of Sale stores).
- **The generic content write tool bypasses the product editor's rules.** `createOrUpdateContentItem` writes the JSON and calls `IContentManager.ValidateAsync`; it does not run display drivers. The product rules live only in drivers: `ProductPartDisplayDriver.UpdateAsync` (price not negative, sale price below price, sale ends after it starts, the currency must exist, site-time to UTC conversion) and `ProductVariantsPartDisplayDriver.UpdateAsync` (variants generated by `ProductVariants.Combine`, duplicate variant SKU check). Content handlers still run (stock items sync, search records refresh). This is why two narrow product write tools are proposed.
- **Money.** Refund is the only money-moving action the admin UI has (no capture, void, payout or admin "charge": payments are captured at checkout; `ITransactionCommandService.ChargeSavedPaymentMethodAsync` exists but its own remarks say only server code may call it and no admin action calls it, so no tool is proposed for it). Refunds run through `ICheckoutRefundService.RequestRefundAsync` (`DefaultCheckoutRefundService` in Checkout.Core), which calls the payment provider's `ICheckoutPaymentRefundProvider` (Stripe: `StripeCheckoutPaymentProvider`); a provider that cannot refund records the refund as `PendingManualReview`. Other actions that cost or create money and are marked `External`: buying a carrier label (`ICarrierProvider.BuyLabelAsync`, EasyPost), issuing a gift card or changing its balance (stored value).
- **Where the tools live and how they are gated.** Each tool belongs in its own module's `AIToolsStartup` gated by `[RequireFeatures("CrestApps.OrchardCore.AI")]` and additionally by the feature that owns the screen (for example Returns tools by `CrestApps.OrchardCore.Orders.Returns`). This also matters technically: several services the tools need are module classes, not Core contracts (`DraftOrderService`, `OrderReturnService`, `GiftCardEmailSender`, `CouponEditor`, `InventorySyncService`, `CurrencyUsageService`, `IMarketStore`, `IStripeConnectService`, `PosShiftService`, the POS stores).
- **Logic that today exists only inside controllers or settings drivers** and must be extracted before a tool can reuse it is called out per module (purchase orders, markets, registers, departments, stock locations, product feed key, store setup progress, manual refund settlement, the commit-and-retry handling of stock changes).
- **Dates.** The repository rule is never to show UTC: every tool takes and returns dates in the site or user time zone through `ILocalClock`, as the controllers do.

## Commerce — `CrestApps.OrchardCore.Commerce`

**What an admin can do in the UI:**

- Commerce → Set up your store (`StoreSetupController.Index`, permission `SetUpStore`): see the ordered steps contributed by every enabled module's `IStoreSetupStep`, which are done, skipped or optional, what is set up now, and a link to the page that does each in full.
- Run a step's quick action (`Run`, POST) with the step's own fields. Quick actions verified in code: add the Product content type (Products), choose the store currency (Checkout `CurrencySetupStep`, field `currency`), store name / email / phone / address (Receipts `StoreDetailsSetupStep`), a flat shipping amount per order (Shipping `ShippingSetupStep`), bank-transfer instructions (Pay Later `OfflinePaymentsSetupStep`), add the staff roles Store manager, Warehouse, Customer support and Marketing (Commerce `StaffRolesSetupStep`, step name `staff-roles`). The Stripe, tax and test-order steps have no quick action, only a link.
- Skip a step, or undo the skip (`Skip`, POST).
- Registers the shared Commerce admin menu. The shopper account overview (`AccountController`) is storefront only.

**Already covered:** nothing.

Progress is `StoreSetupSettings` (`Completed`, `Skipped`) in site settings. The bookkeeping (`UpdateProgressAsync`, the "current step" rule, the `setup.` form-field prefix) is private to `StoreSetupController` and must move to a small service first. `runStoreSetupStep` is `Security` because the `staff-roles` step creates roles that receive permissions through stereotypes and the Products step creates a content type; `SetUpStore` is declared `isSecurityCritical`.

**What an admin can do in the UI:**

The editor carries: `ProductPart` (price, currency, SKU, compare-at price, sale price with start and end, min / max / step quantity, volume tiers, role discounts, add-ons, external URL and button text, purchasable, featured, position, price display), `ProductPricePart` (several named prices, one-time or recurring with interval, trial, setup fee, custom amount), `ProductVariantsPart` (options such as Size and Color, and the variants generated from them, each with SKU, price, compare-at, sale price, image, enabled), `ProductBundlePart` (up to 10 parts with quantities), `ProductGroupPart` (up to 20 products), `ProductRecommendationsPart` (upsells and cross-sells), `ProductFeedPart` (brand, GTIN, MPN, condition, Google category, exclude from feeds, agent visibility).
- Commerce → Product Listings (Contents list of types with `ProductListingPart`): listing pages with their filters, sorting, layout and paging.

- Settings → Commerce → Product feeds (`ProductFeedSettingsDisplayDriver`, `ManageProductFeeds`): default brand / condition / Google category, include out-of-stock, agent defaults, the feed URLs (`/feeds/products.xml`, `/feeds/products.csv`), make a new access key or remove it, and the list of what Merchant Center would refuse.
- Content type editor: Product part options, variant option settings (filterable), product page layout, and per-field product attribute settings (`ProductPartSettingsDisplayDriver`, `ProductVariantsPartSettingsDisplayDriver`, `ProductPageSettingsDisplayDriver`, `ProductAttributeSettingsDisplayDriver`).
- Import and export products as CSV through Content Transfer handlers (`ContentTransfer/*`, another group's module).
- Storefront only: listing pages, compare (`products/compare`), cards, the feed URLs, the Catalog API (`CatalogApiEndpoints`).

**Already covered:** content tools cover creating, reading, editing, cloning, publishing and deleting products, bundles, grouped products, recommendations, feed fields and listing pages — but see the validation gap above, and `searchForContentItems` takes only a text term (no content type, SKU, price or stock filter). `applyContentTypeDefinitionFromRecipe` covers the part and field settings. Recipe step `Currencies` (through `importOrchardCoreRecipe`) creates or updates currencies. `ProductFeedSettings` goes through the generic settings tools. Background tasks "Product Sales" and "Product Search Indexing" need no tool.

**Settings groups:** `ProductFeedSettings` / group `product-feeds` / permission `ManageProductFeeds` / secrets: `Key` (the feed access key; it is generated, never typed — the form posts `KeyAction` = `new` or `remove`, so exclude it from `updateSiteSettings` and use `regenerateProductFeedKey`).

**Implementation notes:**

- `listProducts`: product types come from `ProductContentTypes.GetProductTypesAsync` (module class). SKU lookup through `ProductSkuIndex` (`ContentItemId`, `ContentType`, `Sku`, `VariantId`, `Published`, `Latest`); authorize each item with `ViewContent` as `CatalogApiEndpoints` does. Stock is optional: resolve `IStockItemStore` and call `ListByProductAsync` only when Inventory is enabled (the Products module must not reference Inventory types beyond its `.Core`).

- `IProductSearchIndexRefresher.RequestRebuildAsync()` exists but no admin action calls it, so no tool is proposed.

## Inventory — `CrestApps.OrchardCore.Inventory`, `CrestApps.OrchardCore.Inventory.StockAlerts`, `CrestApps.OrchardCore.Inventory.Api`

**What an admin can do in the UI:**

- Commerce → Inventory (`InventoryAdminController.Index`, `ViewInventory`): list and search stock items, filter All / Low stock / Out of stock / Backordered.
- "Sync" (`Sync`, POST, `ManageInventory`): start counting products whose type gained the Inventory part and refresh titles, SKUs and thresholds.
- Export every counted product and variant as CSV (`Export`, `ViewInventory`); import counts from CSV, all or nothing, at most 10,000 rows and 2 MB (`Import`, `ManageInventory`).
- A stock item's page (`Item`, `ViewInventory`): levels at each location, units held for orders, movement history, how many shoppers wait for a back-in-stock email.
- On that page (`ManageInventory`): Receive or Adjust (`Adjust`), Count (`Count`), Transfer between locations (`Transfer`), Recount from the history (`Rebuild`).
- Settings → Commerce → Inventory (`InventorySettingsDisplayDriver`, `ManageInventory`): default low-stock threshold, hold minutes, roles notified of low stock, and the list of stock locations (add, rename, reorder, remove; the default location cannot be removed).
- On each product: the Inventory part (`TrackInventory`, `AllowBackorder`, `LowStockThreshold`, `ReleaseDateUtc`).
- Workflow event "Low stock" (`LowStockEvent`); low-stock notifications to the configured roles; background task "Expired stock holds".
- Storefront only: back-in-stock subscribe (`StockAlertsController`), availability API.

**Already covered:** content tools cover the Inventory part on a product. Recipe steps `Stock` (set counts by SKU or content item id) and `StockLocations` (add or update locations) through `importOrchardCoreRecipe`. `InventorySettings` through the generic settings tools, except the locations (see below). The workflow tools cover the Low stock event. Reports "Stock on hand" and "Stock movements" are registered with the Reports module (`AddReport<StockOnHandReport>`, `AddReport<StockMovementsReport>`) and belong to whatever generic report tool that group proposes.

**Settings groups:** `InventorySettings` / group `inventory` / permission `ManageInventory` / secrets: none. Two cautions for the generic settings tools: the same page edits the stock locations, which are saved to `ICatalog<StockLocation>` and not to the settings object (`settings.Locations` is emptied on every save), so `Locations` must not be offered as a settings field; and changing `DefaultLowStockThreshold` queues `InventorySyncService.SyncAllAsync` as deferred work.

**Implementation notes:**

- Reads: `IStockItemStore.PageAsync(new StockItemQuery { Search, Filter }, skip, take)`, `FindByIdAsync`, `FindBySkuAsync`, `FindAsync(contentItemId, variantId)`; `IStockMovementStore.PageAsync(stockItemId, …)`; holds are queried by the controller straight from `ISession` on `StockReservationIndex` (collection `InventoryConstants.CollectionName`) — move that query into a store method; waiting alerts from `StockAlertService.CountWaitingAsync` (only when the StockAlerts feature is on).
- Writes: `IInventoryService.AdjustAsync(stockItemId, locationId, StockMovementKind.Received or Adjusted, quantity, reason, StockActor.ForUser(user))`, `SetCountAsync`, `TransferAsync`, `RebuildAsync`; `InventorySyncService.SyncAllAsync`; `StockCountImporter.ImportAsync(rows, reason, actor)`. `IInventoryService` works in the caller's unit of work: the controller commits with `ISession.SaveChangesAsync`, turns `ConcurrencyException` into "busy, try again" and cancels the session on import problems (`CommitAsync`, private). Each write tool must do the same; put that wrapper in one shared helper rather than copying it.
- Locations: `IInventoryLocationService.GetLocationsAsync()` for reads. The add / rename / reorder / remove logic (`ParseLocations`, `SaveLocationsAsync`, maximum count, default-location guard, ignoring locations owned by other records such as a technician's van, `OwnerKind` not null) lives only in `InventorySettingsDisplayDriver` — extract it to a location management service the tool, the driver and the `StockLocations` recipe step share.
- `importStockCounts` rewrites many counts in one call. It is `Write` by the rules (each change is a movement and can be corrected by another count), but it is the one inventory tool where approval may still be wanted; see Open questions.
- The Inventory API feature already exposes list / get / receive / adjust / count / transfer with the same permissions (`InventoryAdminApiEndpoints`); its mapper `StockItemApiMapper` is a ready model for the tool output.

- On an order's page (`OrderShipmentsDisplayDriver`): what is left to ship and the shipments so far with status, carrier, tracking and tracking events.
- Create a shipment of some or all remaining lines, shipped now or kept to pack (`ShipmentsAdminController.Create`); mark a pending shipment shipped with carrier, tracking number and link (`Ship`); mark delivered (`Deliver`); mark returned so its items can ship again (`Return`); remove a shipment that has not left (`Delete`).
- Buy a carrier label for a pending shipment (`ShipmentLabelsAdminController`): weigh the parcel (pre-filled from the items and packaging weight), get the carriers' rates (`Rates`), buy one (`Buy`) — the shipment is then shipped with the label's carrier and tracking number and the label can be printed.
- Print a packing slip for a shipment (Orders `PackingSlip`).
- Automatic: the shipped email when "send shipped emails" is on (`ShippedEmailShipmentHandler`), EasyPost tracking updates by webhook, workflow shipment events, commerce webhooks.

**Already covered:** nothing. The workflow tools cover the shipment events.

| `createShipment` | Write | no | `FulfillOrders` | Creates a shipment to pack for a paid order from some or all of the lines still to ship, with an optional note, and leaves it pending. Use `shipShipment` when it leaves. | OrdersAgent |
| `shipShipment` | External | yes | `FulfillOrders` | Marks a pending shipment as shipped with its carrier, tracking number and optional tracking link; it can also create and ship in one step everything still to ship on an order. ## Stripe — `CrestApps.OrchardCore.Stripe`

**What an admin can do in the UI (`ManageStripeSettings`):**

- Settings → Payments → Stripe (`StripeSettingsDisplayDriver`): live or test mode, publishable keys, whether each secret key and webhook secret is set (values supplied by application configuration are shown as coming from configuration), the connected account ids.
- "Connect" (`StripeConnectController.Connect`, POST): verifies the submitted or stored secret key for the live or test environment and creates the webhook at Stripe, saving the account id and the webhook signing secret. "Disconnect" (`Disconnect`, POST): removes the webhook at Stripe and clears the stored credentials for that environment.
- Workflow events for Stripe (payment succeeded, failed, canceled, refunded, dispute created, subscription created, request failed).
- Storefront only: saved payment methods in the buyer's account. API only: Stripe Terminal readers for the till (`StripeTerminalApiEndpoints`: list, pair, present a test card), with no admin screen.

**Already covered:** recipe step `StripeSettings` (through `importOrchardCoreRecipe`) imports keys in clear text and protects them; the workflow tools cover the events. Refunds through Stripe are made by `refundOrder` and `refundPayment`, not by a Stripe tool.

**Settings groups:** `StripeSettings` / group `stripe` / permission `ManageStripeSettings` / secrets: `LivePrivateSecret`, `LiveWebhookSecret`, `TestPrivateSecret`, `TestWebhookSecret` (data-protected, purpose `StripeSettings`); `LiveAccountId`, `LiveWebhookId`, `TestAccountId`, `TestWebhookId` are set by Connect, not typed. Values present in application configuration (`StripeConfigurationOptions`) override the stored ones and cannot be changed from the site.

| Tool | Kind | Approval | Permission | Description | Agent |
| --- | --- | --- | --- | --- | --- |
| `getStripeConnectionStatus` | Read | no | `ManageStripeSettings` | Reports whether Stripe is in live or test mode, whether an account is connected for each, the connected account id, and which keys are set and whether they come from the site or from application configuration. No key or secret is ever returned. | PaymentsAgent |
| `disconnectStripe` | Security | yes | `ManageStripeSettings` | Disconnects the Stripe account of the live or the test environment: removes the webhook at Stripe and clears the stored keys for it. **Implementation notes:** `IStripeConnectService.IsConnectedAsync(isLive)` and `DisconnectAsync(isLive)` (Stripe module), `StripeSettings` and `StripeConfigurationOptions.GetKeys(isLive)` for the status. **What an admin can do in the UI:**

- Commerce → Transactions (`AdminController.Index`, `ManageTransactions`): the report of what is owed and paid; search, filter by status and by source.

**Already covered:** nothing for transactions (no recipe step). `TransactionReminderSettings` goes through the generic settings tools.

## Point of Sale — `CrestApps.OrchardCore.PointOfSale`, `CrestApps.OrchardCore.PointOfSale.WebRegister`

**What an admin can do in the UI:**

- Commerce → Point of sale → Registers (`RegistersAdminController`, `ManageRegisters`): list; create and edit a register (name, the stock location it sells from, the store's address that taxes its sales, currency, the roles that may sell at it, enabled, its department keys with label and preset amount). There is no delete action; a register is disabled instead.
- Commerce → Point of sale → Shifts (`Shifts`, `Shift`): list shifts, filter by register, open one to see its float, cash movements, sales by tender and department, expected against counted cash, and the closing note.

**Already covered:** recipe steps `Registers` and `PosDepartments` (through `importOrchardCoreRecipe`). A register's sales are orders with channel Point of sale, so `listOrders` (filter by channel; `OrderQuery` also has `LocationId` and `ShiftId`) and `getOrder` cover them, and `refundOrder` refunds them.

## Open questions

- **Recipe steps against dedicated save tools.** Thirteen of the proposed write tools duplicate what a recipe step already does through `importOrchardCoreRecipe`: `saveCurrency` (`Currencies`), `saveMarket` (`Markets`), `saveStockLocation` (`StockLocations`), `importStockCounts` (`Stock`), `saveCoupon` (`Coupons`), `saveShippingZone` and `saveShippingMethod` (`ShippingZones`), `saveTaxCategory`, `saveTaxJurisdiction`, `saveTaxTable`, `saveTaxRule` (`TaxCategory`, `TaxJurisdiction`, `TaxTable`, `TaxRule`), `saveRegister` (`Registers`), `savePosDepartment` (`PosDepartments`). They are proposed because the recipe tool checks the recipe import permission rather than the domain permission (a Store manager or Marketing user has `ManageCoupons` but not recipe import), gives no typed schema, and several steps replace nested lists wholesale. If the admin widget is only ever used by administrators, dropping these thirteen brings the group to 84 tools. Which is it?
- **Secrets through the recipe tool.** `importOrchardCoreRecipe` can run the `StripeSettings` step, which accepts secret keys in clear text, and site-settings steps for `TaxJarSettings`, `EasyPostSettings` and `PrintifySettings`. Should the recipe tool refuse steps that carry secret fields, the way the generic settings tools will mask them? The same question decides whether a `connectStripe` tool can ever exist; it is not proposed here because the secret key would pass through the model.
- **Irreversible financial records.** `recordTransactionPayment`, `adjustTransaction`, `cancelTransaction` and `resolveRefund` move no money but cannot be undone, so they are marked `Destructive` with approval. Is that the intended reading of the kinds, or should there be a separate `Financial` kind? Conversely `importStockCounts`, `saveTaxRule` and `saveMarket` are plain `Write` by the rules although one call can change many counts or what every later checkout charges; should they require approval?
- **Read-only calls to outside services.** `testFulfillmentPartnerConnection` and `getShipmentLabelRates` are `External` with approval by the rules, but they only read from the partner or carrier. May read-only external calls skip approval?
- **Validation that lives in display drivers.** `createOrUpdateContentItem` bypasses the product editor's rules (negative prices, sale above price, unknown currency, variant generation, duplicate variant SKUs). Should the product rules move into content handlers so every writer is covered, which would also make `updateProductPricing` optional, or are the two narrow product tools the fix?
- **Refactoring before tools.** Purchase orders, markets, registers, departments, stock locations, the product feed key, the store setup progress, manual refund settlement and the commit-and-retry wrapper around stock changes have their logic inside controllers or a settings driver. Is extracting these into services in scope of the tools work, or should those tools wait?
- **Gift card codes and generated coupon codes** are bearer values worth money. The tools mask gift card codes by default and return generated coupon codes only on request; should they ever return full gift card codes to the model, given that chat transcripts are stored?
- **Reports.** Orders registers thirteen reports (`ManageOrders`), Inventory two (`ViewInventory`) and Shipping one (`FulfillOrders`) with the Reports module. This inventory assumes the Reports group proposes a generic `listReports` / `runReport`; if it does not, a `getSalesSummary` read (sales, orders, average order value, refunds for a date range, from `OrderReportAggregator`) should be added to OrdersAgent, because "how were sales last week?" is the most likely commerce question.
- **Records with no admin screen.** Merchant tax registrations and exemption certificates exist only as recipe and deployment steps in this group (`MerchantTaxRegistration`, `ExemptionCertificate`), and Stripe Terminal readers only as API endpoints. They are left out because the goal is parity with the admin UI; say if they should be covered.
- **Checkout settings without an editor.** `CheckoutSettings.DefaultPaymentMethod` and `SessionLifetimeHours` have no editor in this group and `Currency` is only set by the setup guide. Should the generic settings tools expose fields the settings page does not?
- **Direct tools.** `listOrders` and `getOrder` are the two tools here that every merchant conversation is likely to need; should they also be ticked on the main assistant, or stay behind OrdersAgent only?
