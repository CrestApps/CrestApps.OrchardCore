# Build status: AI tools (phase 1, tools only)

Part of the [AI tool coverage plan](README.md). This file records what was actually built, batch by batch, against the catalog. Where it and a catalog file disagree about a built tool, this file describes the code.

Phase 1 builds tools only; no agent templates are added or changed. Existing tools are not renamed, replaced or changed. Nothing in this file was run against a live site: every tool is covered by unit tests with service doubles or in-memory stores.

## How tools find the caller

Every new tool checks its Orchard Core permission for the signed-in caller through `AgentToolAuthorization` in `CrestApps.OrchardCore.AI.Agent`. It reads the caller from `IUserAccessor`, which the chat hubs set for the whole invocation on every transport, and falls back to `HttpContext.User`. A call with no signed-in caller is refused. `AIToolCallerAuthorization` in `CrestApps.OrchardCore.AI.Core` is the same file as in pull request 1319 and still reads `HttpContext` only; it is kept unchanged so the two branches merge cleanly, and should move to `IUserAccessor` too.

Tools that run Orchard Core's settings display drivers (`getSiteSettings`, `updateSiteSettings`, `listSiteSettingsGroups`) and tools that build links need `HttpContext` itself. CrestApps.Core sets it from the connection's request during every hub invocation from commit 8b74c121 (#324) on; the package in use today (`2.0.0-preview.375`) does not, so on a long-polling connection those tools see no request. WebSockets, the default, is not affected.

Each such tool can be built once the contract moves to an Orchard Core abstractions package, or once a bridge module references the module package (decision D5 in the README).

## F22: generic record tools

Built from section 3 of the maintainer's review of pull request 1334 ("generic record tools instead of 500 CRUD tools"). Not built yet: nothing here was compiled or run.

**Contract.** `AddAIRecordKind<T>(name, configure)`, `AIRecordKind`/`AIRecordKind<T>`, `AIRecordKindBuilder<T>`, `AIRecordKindOptions`, `AIRecordQuery` and `IAIRecordKindVisitor<TResult>` live in `src/Abstractions/CrestApps.OrchardCore.Abstractions/AI/Records/` (namespace `CrestApps.OrchardCore.AI.Records`). It is the smallest place every module already references: the project depends only on `CrestApps.Core.Abstractions` (catalog managers, `CatalogItem`, `ValidationResultDetails`) and the Orchard Core abstractions (`Permission`), already holds `AIFeatureIds`, and a module must not reference `AI.Core` only to register tools. It names no display management type, so the editor replay stays in `AI.Agent`: the typed kind hands itself to a visitor (`Accept`), which gives the tools the record type without reflection. `T` must be a `CatalogItem` with a parameterless constructor.

**A kind** has a camelCase name, a description for the model, a write permission and an optional read permission, an allow-list projection (required; the tools never serialize the record or its `Properties`), editor fields that hold a secret (besides the names `EditorReplay` already treats as secret), an optional in-use check, and find, new, list (text filter and paging), validate, save, delete and copy operations that default to the record's `ICatalogManager<T>` and can each be replaced; `UseCatalogManager<TManager>()` switches them all to another manager service. Registration validates the name and the required parts at startup.

**Tools** (`src/Modules/CrestApps.OrchardCore.AI.Agent/RecordTools/`, `RecordToolsStartup` with `[RequireFeatures(AIConstants.Feature.Area)]`, category "Records"): `listRecords`, `getRecord`, `saveRecord` and `deleteRecord` (asks for approval). The tools are singletons, so the `kind` enum lists every registered kind; the read permission (and for writes the write permission) is checked per call for the signed-in caller, and an unknown kind returns the kinds the caller may read. Nobody signed in means refuse.

**Writes** replay the admin editor as the record's controller does: `IDisplayManager<T>.BuildEditorAsync` on a copy, read the view models (`EditorReplay.Capture`), check the values against the fields, merge them over the built values and post them through `UpdateEditorAsync` with `FormValuesModelUpdater`, then the kind's validation (the catalog handlers' rules, which the admin pages check through `CatalogEntryValidation`) is added to the model state, and only a valid record is saved through the manager. The post is replayed twice: first on a copy of the record the store returned (so a dry run or a refused save never changes a cached instance), then, when it is valid and not a dry run, on that record itself, which is validated again and saved, as the admin controller changes and saves the instance `FindByIdAsync` handed it (a session-tracked store such as a YesSql `DocumentCatalog` could insert a copy as a new document). Catalog drivers only bind values, so the second replay does nothing the first did not. A save and a dry run return `changed` (fields whose editor value changed) and `unchanged` (requested fields that kept their value: the Taxation editors, like most catalog editors, set the name only on create). `IsNew` is posted back as built and never shown or accepted. Every validation error returns the JSON schema of the editor's fields; empty `values` returns the schema alone. Values may be flat for an editor with one section, keyed by section otherwise. When the request is missing, the editor is built with a request made for the caller; that request is not in `IHttpContextAccessor`, so a driver or handler that reads the accessor (`AuditedCatalogEntryHandlerBase` stamps the author that way) still sees none in such a hub call.

**Extraction.** The editor replay of `updateSiteSettings` moved from `Settings/SiteSettingsEditor.cs` to `Editors/EditorReplay.cs` (with `EditorModel`, `EditorSection`, `EditorField`, `EditorFieldKind`, `EditorCaptureOptions`), and `FormValuesModelUpdater` moved to `Editors/`. `SiteSettingsEditor` keeps what is site-specific (custom settings groups, the reload wrapper) and forwards the rest; the settings tools behave as before, except that two error texts say "this editor" and "the admin page" instead of "this settings page"/"group" and "the settings page". Two capture options were added and the settings tools do not use them: a kind's extra secret field names, and fixed fields.

**Same-scope reads.** Catalog stores read a cached document until the scope commits, and all tool calls of one chat message share the scope. `AIRecordScopeChanges` (scoped) keeps the records saved or deleted in the scope, so a second save starts from the first and `getRecord`, `listRecords` and `deleteRecord` see the change. A record created in the scope is not added to `listRecords` until the next message.

**Example kinds** (Taxation `AIToolsStartup`, `[Feature(TaxationConstants.Feature.Taxation)]` + `[RequireFeatures(AIFeatureIds.Area)]`, permission **Manage taxation** and the `INamedCatalogManager<T>` the admin pages use, whose catalog also refuses a duplicate name on save): `taxCategory`, `taxType`, `taxJurisdiction`. All three admin pages use `IDisplayManager<T>` and `CatalogEntryValidation`. Each kind has an in-use check modeled on the Tax Tables page's delete check (rules that point to the record, and child categories or jurisdictions); the Tax Categories, Types and Jurisdictions pages themselves delete without that check, so the tools are stricter than those pages. Products' `TaxationPart` category codes are not counted. Not chosen: Shipping zones (the methods view model is a list of objects, which the replay cannot post), Markets and Point of Sale departments (their controllers bind their own view models, no display drivers), tax rules (two drivers on a source catalog) and tax tables (rows are a list of objects).

**Tests** (`tests/CrestApps.OrchardCore.Tests/Agent/Records/`): every tool refuses an anonymous caller, a caller without the read permission and an unknown kind (with the list of kinds); the write tools refuse a caller who can only read; list paging and the text filter; get and not found; the projection never returns the canary secret or `Properties`; create and update through a real display driver (normalization, the secret and `Properties` kept); values keyed by section; dry run (valid and invalid); a driver error and a record rule error each return the schema; secret, unknown, fixed and wrong-shape values are refused with the schema; two saves in one scope; delete with in-use and not found; the kind enum in the schema; the registration (texts, only `deleteRecord` asks); name and projection validation of `AddAIRecordKind`; a field the editor does not change reported as `unchanged`; the Taxation kinds' registration, a tax category created through the real `TaxCategoryDisplayDriver`, a tax jurisdiction updated through the real `TaxJurisdictionDisplayDriver` (city changed; level, country and effective date kept; the name reported unchanged), and a category a tax rule uses kept.

- **Tokens.** `reverseTransactionEntry`, `applyTransactionCredit` and now `adjustTransaction` need a token from `previewTransactionAction`. It runs the same checks as the tool that acts and is bound to the transaction's state (what was owed, its status and, for a payment with credit, the customer's credit).
- **Idempotency.** `recordTransactionPayment`, `applyTransactionCredit` and `adjustTransaction` replay a key before they check what is owed. `reverseTransactionEntry` takes no key: the service refuses a second reversal and the token works once.
- **Approval.** `reverseTransactionEntry`, `applyTransactionCredit`, `adjustTransaction`, `cancelTransactionAutoCharge` and `declareShiftTips` ask. `previewTransactionAction` only reads. `setPartyCollectionSettings` does not ask: it is a switch that can be turned back at once, nothing leaves the site, no money moves, and it only stops reminders and late fees.
- **Shared helpers (AI.Core).** `AIMoneyArguments` checks free text for card and bank account numbers, for the transaction and invoicing money tools. `AILocalTimeArguments` reads a past local time (`receivedAt`), for `recordTransactionPayment`, `previewInvoiceAction` and `recordInvoicePayment`.
- **Findings (reported, not fixed).**
  - `adjustCustomerStoreCredit` (Customers) gives or takes store credit with approval, but without the preview-token flow F23 asks for.
  - `MaskingSecureCaptureTokenSink.IsValidLuhn` (ContactCenter.Core) keeps its own private Luhn check; `AIMoneyArguments.IsValidLuhn` is the shared one now. Moving the Contact Center copy would edit `ContactCenter.Core`, which does not reference `AI.Core`, so it stays.
  - A party's "reminders paused" setting stops only the scheduled sweep: **Send reminder** and **Send invoice** on the transaction page still send. The per-transaction pause behaves the same way, but the collection card's text does not say so.

### Fixed after review

A second review found these gaps in the new-from-main tools and in two Orders tools (`previewRefund`, `getOrder`). All are fixed in the code.

- **Order refund tokens.** A `previewRefund` token is bound to the order's refund state too: what is still refundable, what was refunded, the return's refunded amount and status, and the payments the refund would go to. A refund made or a payment changed after the preview makes it fail.
- **Fulfillment send race.** `TryQueueAsync` checks `checkedWithPartner` under the order's lock, on the stored state, so a request that became unclear after the tool read it is not queued without the user's check.
- **Service level titles.** `listServiceLevelRisks` and `getServiceLevelTimers` return a record's title and link only when its module lets the caller see that record; otherwise only the kind and id.
- **Ticket desk erasure.** The `ticketDesk` kind refuses a new desk that would erase protected information sooner, as it already did for a change to an existing desk.
- **Priority in use.** Before a delete, the `ticketPriority` kind checks ticket categories and the targets of tickets service level policies, besides tickets, ticket type defaults and desk priority matrices.
- **`getOrder` timeline.** It reads only the latest 20 timeline entries, with `notesTruncated` and a pointer to `getTimeline`; before, it read the whole timeline.
- **Idempotency before the balance.** `recordTransactionPayment` replays a key before it checks what is owed, so a retry after a payment went through gets the first answer, not a refusal about the balance that payment lowered.
- **Card and bank numbers.** The shared guard, `AIMoneyArguments` in AI.Core, refuses a card number only when 13 to 19 digits pass the Luhn check, an IBAN only when it is in capitals and passes its mod-97 check, and a domestic account or routing number only when bank wording is followed right away by six or more digits. Before, the invoicing tools refused any run of twelve digits.
- **Agreement balance names.** `getAgreementBalance` names an account only when the ID is an account the caller may view (**View content** on it).
- **Agreement numbers.** One lookup, `AgreementStore.FindByNumberAsync` with `NormalizeNumber` (`Agreements.Core`), finds SA-00042 in any case or as just 42, for `getAgreementBalance` and the service agreement tools.
- **Credit note `replaceDraft`.** The draft someone started is kept until the new credit passes every check; a refused replacement leaves it as it was.
- **Invoice issue.** `issueInvoice` checks whether the draft needs approval before it runs the issue command, as the page decides which button to show, so the command never refuses and discards the message's earlier work.
- **Approval added.** `pauseOrResumeRecurringPlan` asks, because resuming a plan that charges can bill a saved card. `saveServiceAgreement` asks, because saving it Active starts work orders. `adjustTransaction` needs a token from `previewTransactionAction`.

## Tool kinds instead of `.RequireApproval()` (2026-11-24)

CrestApps.Core `2.0.0-preview.389` (#327) added tool kinds, which is F3 of [01-foundation.md](01-foundation.md#f3-kind-on-the-registration-s-core). In that version an explicit `.RequireApproval()` is an approval floor: the tool asks before every call and no profile setting lowers it, and where nobody can be asked (a workflow, voice, an MCP client, background work) it never runs. A tool that asks because of its kind follows the profile's tool approval setting (`AIToolApprovalSettings`), which can let it run without asking.

All 236 tools that asked (the 11 from main, 2 that main had without approval, and 223 new ones) now declare a kind. The same 236 tools still ask by default. After the UI test, `setUserAccountState` (enable, disable or unlock other accounts) became Security too, so 237 tools ask.

| Kind | Tools | Rule used |
|---|---|---|
| Destructive (`.AsDestructive()`) | 101 | Deletes, or cannot be undone: deletes, cancels, voids, closes, final decisions, issuing an invoice, running a workflow or background task, rebuilding an index |
| External (`.AsExternal()`) | 70 | Sends an email, text, call, webhook or notice to a person; calls a paid service (model, embeddings, geocoding, carrier, lookup); moves money or value (payments, refunds, credit, gift cards, points, tips); points the site at an outside endpoint (A2A, MCP, data connection, tool instance, deployment) |
| Security (`.AsSecurity()`) | 50 | Changes access or sign-in (roles, users, account states, owners, shares, share links, account members, API keys, feed keys, secrets, Stripe keys), what the site runs (recipes, workflow types, features, site settings, tenants, an AI profile's tools) or exports personal data |
| Write (`.AsWrite()` with `.RequireApproval()`) | 16 | A change that can be undone, kept asking as decided in the batches: `saveAIDataSource`, `saveAIFileSource`, `setHomepage`, `saveB2BAccountSettings`, `respondToCalendarEvent`, `updateCalendarEvent`, `saveCoupon`, `generateCouponCodes`, `importLocalDncList`, `setLocalDncListImportState`, `pauseOrResumeRecurringPlan`, `setAppointmentStatus`, `runServiceAgreement`, `saveServiceAgreement`, `postOpenShift`, `postIntradayOffer` |

The Write row keeps the floor on purpose: Core's Write kind needs no approval, so dropping `.RequireApproval()` would stop them asking. Whether they should ask at all is for the maintainer. The other 474 tools have no kind (`Unspecified`, as before); giving them Read or Write would only add MCP tool hints. New tools declare a kind instead of calling `.RequireApproval()`, and call it only for a tool of another kind that should ask.

Not done yet: the OC profile editor has no **Tool approval** setting (the Core sample hosts show it on the Capabilities tab), so today a profile can change it only through its stored settings.

## Bugs found in main's code (reported, not fixed)

- **Tool pickers past the form limit (from the UI test).** The profile, template, post-session, workflow activity, MCP server and WebMcp tool pickers post a hidden ID and a hidden "false" for every tool, ticked or not. With about 500 tools a profile posts over 1,024 values (ASP.NET Core's default), and every save fails with HTTP 400 before the antiforgery token is read. **This pull request's tools reach that count, so it needs fixing before or with it.** A fix: post one value per ticked tool.
- **Writes not seen in the same scope (from the UI test).** `Catalog<T>` reads the cached document, which only has a change once the scope ends; so do `StaffCapabilityService` and other document services. In the chat every tool call of a message shares one scope, so a record saved earlier in the message isn't found (business hours, staff capabilities), and Report Builder's tools refuse to touch a report changed earlier in the message.
- **`DocumentCatalog` filters (from #1336).** `PageAsync` filters names, display texts and sources with `With<INameAwareIndex>` and the like, which makes YesSql join a table named after the interface ("no such table: …_INameAwareIndex_…"). Name search on the admin lists built on it fails, as `listRecords` with a query does.
- **Draft orders without a currency.** On a store without a shopper currency (Markets off, no store currency), `CartService.PriceAsync` leaves the cart's currency null, so the admin draft order editor and `saveDraftOrder` make an order whose invoice can't be issued ("Choose the currency of the invoice").
- **Recipe imports from the chat.** `ImportRecipeBaseTool` answers "Recipe was successfully imported" for an import it only queued, and runs a step no module has without a word: a workflow sent as a 'Workflow' step instead of 'WorkflowType' was reported as created.
- **Inventory after a product save.** `InventoryContentHandler` creates a product's stock item only when the scope ends, so the inventory tools say a product saved earlier in the message has none.
- **Older AI tools:**
  - `getContentItemById` reads only the published version and checks no item permission.
  - `getUserInfo` reports `IsLockedOut` from `IsLockoutEnabled`.
  - `sendNotification` answers "not sent" when the site notification was made (it only counts the other methods) and wants a user ID.
  - The content definition tools serialize with `ReferenceHandler.Preserve` (`$id`/`$values` markup).
  - `draftInvoice` bills a guest instead of the customer with that e-mail.
  - `createCalendarEvent` and `moveCalendarEvent` return the stored record, not `getCalendarEvent`'s shape.
  - Several tools answer "does not exists".
- **Agent templates.** The content, workflow, AI operations and calendar agent templates set a temperature, which reasoning deployments refuse (HTTP 400).
- **Fulfillment.** `FulfillmentAdminController.Send` and `SendAgain` do not check that the order is paid; the card only hides its button. A posted Send for an unpaid order records requests that settle as Needs attention (not paid) and notify every shipper. The engine itself never sends an unpaid order to a partner.
- **Invoicing tools shipped with main.** `InvoicingToolBase.IsAllowedAsync` (used by `findInvoices`, `summarizeReceivables`, `draftInvoice` and `sendInvoiceReminder`) reads the caller from `HttpContext` only, so those tools refuse callers on chat connections without one. `sendInvoiceReminder` e-mails the customer but is registered without `RequireApproval()`. `draftInvoice`'s line schema has no property descriptions and no `additionalProperties: false`, and `findInvoices` has no paging or `truncated` flag.
- **Statements.** `StatementsAdminController.Send` e-mails a customer statement with **View invoices** only; it should probably need **Manage invoices**, as `sendInvoiceStatement` does.
- **Ticket tools.** The six shipped ticket tools read the caller only from `HttpContext.User` (`TicketAITool.InvokeCoreAsync`), not from `IUserAccessor`, so they may refuse inside the chat hub. `TicketApiModel`, which they return, carries raw UTC times (`CreatedUtc`, `NextDueUtc`...).
- **Ticket summaries.** `TicketRecordSource.GetSummariesAsync` reads the user from `HttpContext`; without one it titles a ticket "A ticket you can't see". `listServiceLevelRisks`, `getServiceLevelTimers` and `getTimeline` then still return the kind, id, link and entries.
- **Ticket priorities.** The Priorities page's delete check (`TicketSettingsUsage`) does not count desk priority matrices, ticket category priorities or service level policy targets. A priority deleted on the page while a desk's matrix names it makes every later save of that desk fail; a category's new tickets fall back to Normal; a policy's target no longer applies. The `ticketPriority` kind checks all three itself.
- **Record sources.** `WorkOrderRecordSource` and `ContentItemRecordSource` describe a record without checking who reads it. The service-level tools therefore return a title only for a record its kind's access provider grants to the caller.
- **Content tools.** `getContentItemById` (`AI.Agent/Contents/GetContentTool.cs`) and `createOrUpdateContentItem` (`CreateOrUpdateContentTool.cs`) make no content authorization call, and `isDraft: false` publishes. With them on a profile, a caller can read a restricted knowledge article in full or publish an article.
- **Content definitions (found in the UI test).** A type made with `applyContentTypeDefinitionFromRecipe` is not visible to other tools until the message ends.
- **Work order lines added on edit (found in the UI test).** `WorkOrderService.UpdateAsync` gives no ID to a line added after the work order was created, which the admin page does too (`_LineRows.cshtml` posts the line's ID, empty for a new row). The editor keeps what was used only on lines with an ID, so parts used on such a line are probably lost on its next save. To confirm.
- **Content search (found in the UI test).** `searchForContentItems` returned unrelated items for a term that matched one menu, and not the menu.
- **Users and conversations (found in the UI test).** `getUserInfo` returns the raw user object; a model read its `IsLockoutEnabled` as "locked out" (`getUser` reports `lockedOut`). `listAIConversations` and `viewAIConversation` return raw UTC times.

## Notes for the maintainer

- `EgressNetwork.IsInternal` does not classify NAT64 (`64:ff9b::/96`) or `198.18.0.0/15`, which the Tenant Hierarchy classifier does. `importMediaFromUrl` relies on it.
- All tool calls of one chat message share one service scope, so Orchard Core's immutable document reads stay stale until the scope commits. The URL rewriting and translation tools handle it (commit 8bf806dfe); any later tool that writes through a document manager and reads it back in the same message needs the same care. The deployment plan tools read the plans with a session query, because `IDeploymentPlanService` keeps the first list it read for the scope. Still open: `checkBusinessHours` does not see a calendar `saveBusinessHoursCalendar` created earlier in the same message (both use `INamedCatalogManager<BusinessHoursSchedule>`).
- When a profile has more than 30 tools, Core's `DefaultOrchestrator` sends the model only the 20 whose words best match the message (`ScopingThreshold`, `InitialToolCount`). A profile with several large groups selected therefore loses tools from some messages.
- `AI.Agent` now references the Lucene and Elasticsearch core packages, which pulls Lucene.Net and the Elasticsearch client in for every site that installs it.
- Web crawlers fetch any address the server can reach: neither the crawler editor, the sitemap strategy nor the crawler's `HttpClient` blocks internal or loopback hosts. The crawler tools check what the editor checks and say so; an egress check belongs in the crawler's HTTP client.
- On this machine the shared compiler server produced bogus Razor errors (tag helpers not found) in batch 14; building with `-p:UseSharedCompilation=false -p:UseRazorBuildServer=false` worked.
- Scheduling registers `SchedulingResourceStaffHandler` (`ICatalogEntryHandler<SchedulingResource>`, with Staff on) to fill a staff resource's name and time zone from the staff record and give the person the Bookable capability, but nothing runs it: the Scheduling Resources page, the recipe step and the `schedulingResource` record kind all save through `SchedulingResourceStore`, a `DocumentCatalog` that runs no catalog handlers. The record kind does what the page does; the handler needs a catalog manager (or a call from the store) to take effect.
